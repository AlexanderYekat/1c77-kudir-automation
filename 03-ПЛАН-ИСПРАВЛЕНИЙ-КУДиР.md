## Не стартовать основную разработку с текущего ТЗ

Две разумные реализации сейчас дадут разный бухгалтерский результат: разрез DEBT/ADVANCE, момент закрытия аванса и граница matching → налог. Транспортный `kudir_proto` нельзя допиливать до рабочего matcher.

---

## Три окна — разные границы

| Окно | Границы | Что делает | Чего не делает |
| --- | --- | --- | --- |
| `DEBT_MATCH_WINDOW` | ИсторияНач → момент оплаты | Ищет документы задолженности, существовавшие на оплату | Не смотрит будущие реализации |
| `ADVANCE_TAX_WINDOW` | Момент оплаты → конец квартала оплаты | Хозяйственная связь, которая может заменить 5/105 фактическим НДС | Не продлевается в следующий квартал |
| `ADVANCE_EXTENDED_MATCH_WINDOW` | После квартала → `MatchHorizonEnd` | Ищет хозяйственную связь закрытия аванса | Не меняет налоговый результат уже закрытого квартала |

Источник правил: уточнения к плану. Конец квартала — налоговая граница. `MatchHorizonEnd` — предел выгрузки `documents.csv` в ТЗ №1. Не `КонецКвартала(ДатаКон)`.

## Зафиксированные факты

### НДС: аванс и реализация раздельно

Аванс, полученный до `2026-01-01`, не получает расчётный НДС 5/105.

Это не означает автоматически отсутствие НДС у реализации 2026 года. Дата денег и дата отгрузки живут на разных шкалах.

### Аналитика и закрытие

DEBT/ADVANCE — по каждой аналитике `КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID` из `ledger62`.

Немедленно закрывается только HIGH. Поля договора в `payments.csv` не authoritative. `SUCCESS` и `tax_ready` — разные признаки.

## Этап 0. Заморозка ТЗ

**Статус этапа 0:** закрыт. Формулировки внесены в `00-АРХИТЕКТУРА-КУДиР.md`, `01-ТЗ-1С-выгрузка-данных.md`, `02-ТЗ-Python-анализ-оплат.md`.

### 0.1. Хронологическая модель: немедленно закрывать ADVANCE только по однозначной HIGH-связи

- **Статус:** done
- **Файлы:** 00 §7, 02 §4 и §21.1
- **Готово, когда:** в ТЗ: HIGH закрывается сразу; неоднозначные связи идут в глобальный conflict-resolution pass.

Единый поток событий: оплаты и реализации вперемешку по дате. Оплата создаёт ADVANCE по аналитике. Пришедшая реализация сразу гасит существующий ADVANCE только если связь однозначная / HIGH (машинное основание, уникальная цепочка через счёт). Неоднозначные кандидаты не трогают remainder до conflict-resolution pass. Следующая оплата видит только уже зафиксированные HIGH-остатки. Кейс «январский аванс → A по счёту, мартовская оплата → B» проходит, потому что связь через счёт — HIGH.

### 0.2. DEBT/ADVANCE считать по аналитическим частям оплаты из ledger62, не по целому payment_id

- **Статус:** done
- **Файлы:** 00 §5, 02 §5, 01 ledger62
- **Готово, когда:** для каждой уникальной аналитики отдельно: `debt_before`, `debt_part`, `advance_part`. Неттинг между аналитиками запрещён.

Ключ аналитики: `КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID`. Одна оплата (один `payment_id`) может содержать несколько таких частей из строк `ledger62`. По каждой части: `debt_before` берётся только с этой аналитики; `debt_part = min(сумма части, debt_before)`; `advance_part = сумма части − debt_part`. Остаток Кт договора B не уменьшает долг Дт договора A. Сворачивать оплату в одно число DEBT/ADVANCE до разреза по аналитике нельзя.

### 0.3. Три окна: DEBT_MATCH_WINDOW, ADVANCE_TAX_WINDOW, ADVANCE_EXTENDED_MATCH_WINDOW + MatchHorizonEnd

- **Статус:** done
- **Файлы:** 00 §5 и §8, 01 §4 и §23, 02 окна поиска
- **Готово, когда:** конец квартала — налоговая граница. Documents выгружаются до `MatchHorizonEnd`, не до `КонецКвартала(ДатаКон)`.

`DEBT_MATCH_WINDOW`: ИсторияНач → момент оплаты. `ADVANCE_TAX_WINDOW`: момент оплаты → конец квартала этой оплаты; связь в этом окне может заменить расчётный НДС фактическим. `ADVANCE_EXTENDED_MATCH_WINDOW`: хозяйственная связь после квартала до `MatchHorizonEnd`; такая связь не меняет налоговый результат уже закрытого квартала. В ТЗ №1 нужен отдельный `MatchHorizonEnd`. Конец квартала больше не предел выгрузки документов.

### 0.4. VAT timeline раздельно для аванса и реализации; 5/105 не следует из даты отгрузки

- **Статус:** done
- **Файлы:** 00 §5.1, контракт цикла 2
- **Готово, когда:** аванс до 01.01.2026 не получает 5/105. Реализация 2026 при этом может иметь НДС.

Две независимые шкалы. Аванс: дата получения. Если аванс до 01.01.2026 — расчётный НДС 5/105 не начисляется ни на остаток, ни «задним числом». Реализация: дата отгрузки. Реализация 2026 может нести фактический НДС независимо от того, что аванс был до НДС. Нельзя писать «всё до 01.01.2026 без НДС» как общее правило для обеих сторон. Константы `VAT=5%` в цикле 1 нет.

### 0.5. DEBT_UNRESOLVED не занимает remainder; SUCCESS и tax_ready — разные признаки

- **Статус:** done
- **Файлы:** 00 §11–12, 02 run_status
- **Готово, когда:** `run_status` содержит `tax_ready`, `unresolved_debt_kopecks`, `unresolved_count`. SUCCESS при `tax_ready=0` допустим.

`available_for_advance = сумма документа − подтверждённые DEBT − подтверждённые ADVANCE`. `DEBT_UNRESOLVED` документ не занимает. Цикл 1 может быть SUCCESS, если matching отработал и инварианты сумм держатся. `tax_ready=0`, пока есть unresolved-долги. Цикл 2 не угадывает НДС для UNRESOLVED. Поля: `tax_ready=0/1`, `unresolved_debt_kopecks`, `unresolved_count`.

### 0.6. FIFO удалить полностью. Обратная хронология — только последний tie-break при порогах

- **Статус:** done
- **Файлы:** 00 §7 п.9 и §13 п.9, 02 §4
- **Готово, когда:** FIFO отсутствует. Без порогов confidence/gap — `DEBT_UNRESOLVED`, а не ближайший документ.

Обратная хронология не алгоритм выбора документа. Она допускается только когда несколько кандидатов уже прошли пороги confidence и gap, и нужно выбрать одного из равных. Если пороги не выполнены — `DEBT_UNRESOLVED`. Самый старый документ нигде не предпочитается.

### 0.7. Бухгалтерская аналитика оплаты — множество строк ledger62; поля payments.csv не authoritative

- **Статус:** done
- **Файлы:** 01 §8, 02 matcher
- **Готово, когда:** matcher не берёт договор/вид расчётов из `payments.csv` как источник истины.

`payment_id` связывает событие оплаты с его корреспонденциями. Аналитика = множество строк `ledger62` с этим `payment_id`. `ДоговорID` и `ВидРасчетовID` в `payments.csv`, если поля остаются, справочные: для отображения или диагностики. Scoring, `debt_before` и разрезы DEBT/ADVANCE читают только ledger.

### 0.8. ID задать отдельно по типам сущностей; для банка позиция + НомерПроводки()

- **Статус:** done
- **Файлы:** 00 §4, 01 идентификаторы
- **Готово, когда:** проверка уникальности и однозначности отображения ID → объект 1С. Коллизия = FAILED.

Документ: техническая позиция (`ПолучитьПозицию()`). Банковская оплата: позиции документа недостаточно — в `payment_id` входит `НомерПроводки()`, иначе две проводки одной выписки сольются. ПКО: один документ = одна оплата. Строка ledger: документ + `НомерПроводки` + порядковый номер корреспонденции. На выгрузке — проверка уникальности и однозначности отображения ID → объект 1С. Коллизия или двусмысленность = FAILED, не «взять первую». Не использовать формулировку «проверка инъекции».

### 0.9. Неплатёжный 62: всегда сальдо аналитики; remainder — только при однозначной атрибуции

- **Статус:** done
- **Файлы:** 00 §5, 01 ledger62, 02 ledger.py
- **Готово, когда:** расхождение aggregate balance и суммы document remainder → diagnostic event, не автораспределение.

Любое движение 62 меняет `signed_balance` аналитики. `document_remaining` меняется только если движение однозначно атрибутировано документу (сторно/корректировка этой реализации). Иначе remainder чужих документов не трогается. Если сумма document remainder не сходится с аналитическим сальдо — diagnostic event в `analysis.log`, без молчаливого размазывания разницы по документам.

### 0.10. Мелкие правки ТЗ: веса только в YAML, example2, analysis.log

- **Статус:** done
- **Файлы:** 00, 02, tests/golden
- **Готово, когда:** в тексте ТЗ нет числовых примеров весов. `analysis.log` обязателен.

Убрать «например +100» у `DIRECT_DOCUMENT_HINT` — в `scoring.yaml` уже +70. В golden example2 убрать сортировку по `НомерСтрокиДокумента`. `analysis.log` — обязательный выход.

## Решения, которые надо вписать в ТЗ

Вписаны в 00 §1.1 и разнесены по 01 / 02. Этап 0 закрыт. Ниже — тот же канон, не новые решения.

| Тема | Формулировка |
| --- | --- |
| Разрез DEBT/ADVANCE | По каждой аналитике `КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID` из `ledger62`. Не по целому `payment_id`. Остатки разных аналитик не неттируются. |
| Закрытие аванса | Немедленно только однозначная HIGH-связь. Неоднозначное — глобальный conflict-resolution pass. |
| Три окна | `DEBT_MATCH_WINDOW`: ИсторияНач → оплата. `ADVANCE_TAX_WINDOW`: оплата → конец квартала. `ADVANCE_EXTENDED_MATCH_WINDOW`: после квартала → `MatchHorizonEnd`, без пересчёта налога закрытого квартала. |
| Выгрузка документов | Не `КонецКвартала(ДатаКон)`. Отдельный `MatchHorizonEnd`. Конец квартала остаётся налоговой границей. |
| VAT timeline | Аванс до 01.01.2026 — без 5/105. Реализация 2026 может иметь НДС независимо от даты аванса. |
| DEBT_UNRESOLVED | Не занимает `document_remaining`. SUCCESS и `tax_ready` раздельно. Поля: `tax_ready`, `unresolved_debt_kopecks`, `unresolved_count`. |
| FIFO / хронология | FIFO удалить полностью. Обратная хронология — последний tie-break только при порогах confidence/gap; иначе `DEBT_UNRESOLVED`. |
| Аналитика оплаты | Множество строк `ledger62` данного `payment_id`. Поля договора/вида расчётов в `payments.csv` не authoritative для matcher. |
| ID | По типам сущностей. Банковская оплата: позиция + `НомерПроводки()`. Проверка уникальности и однозначности отображения ID → объект 1С. Один объект может иметь несколько PAYMENT/LEDGER ID. Коллизия ID → два объекта = FAILED. |
| Неплатёжный 62 | Всегда меняет аналитическое сальдо. `document_remaining` — только при однозначной атрибуции. Расхождение remainder и aggregate → diagnostic event, не автораспределение. |

### Переписать, не наследовать

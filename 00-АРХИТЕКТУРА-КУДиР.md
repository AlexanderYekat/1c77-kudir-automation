# Архитектура формирования КУДиР по оплатам покупателей

## 1. Статус документа

Этот документ описывает общую архитектуру и бизнес-логику проекта. Детальная реализация определяется специализированными ТЗ:

1. `01-ТЗ-1С-выгрузка-данных.md` — единственный источник требований к составу фактов, периодам, CSV-протоколу и семантике `id_map.csv` (`ссылка_1С`).
2. `02-ТЗ-Python-анализ-оплат.md` — единственный источник требований к анализу и Python-коду.
3. `04-ТЗ-1С-память-выгрузки.md` — как выгрузить те же факты, не исчерпав RAM 1С 7.7, и как после Python построить узкий словарь восстановления объектов 1С (`restore`).

При противоречии приоритет имеет соответствующее специализированное ТЗ. Здесь не фиксируются полные схемы CSV, конкретные имена новых процедур, веса scoring и внутренняя структура классов.

Документ согласован с `03-ПЛАН-ИСПРАВЛЕНИЙ-КУДиР.md` после ревизии «один цикл» и с аудитом `06-АУДИТ-ТЗ-КУДиР-2026-09-05.md` (05.09.2026): поздняя реализация не отменяет допустимый ранний счёт; источник НДС аванса выбирается по состоянию налогового окна.

**Один цикл `1С → Python → 1С`.** Второй поход в 1С за табличными частями и ставками НДС не делается. 1С за один проход выгрузки отдаёт и факты matching, и состав сумм с НДС / без НДС. Python в том же запуске делает matching и считает налоговый доход УСН. `kudir_result.csv` — готовые строки КУДиР для `СформироватьТаблицуДоходовЧистовая()`, а не заглушка matching с нулевым НДС.

Matching обязан:

- найти документы задолженности, существовавшие на момент оплаты (`DEBT_MATCH_WINDOW`);
- закрыть аванс однозначной HIGH-связью сразу, как только появилась реализация;
- найти хозяйственную связь аванса в `ADVANCE_TAX_WINDOW` (до конца квартала оплаты) и в `ADVANCE_EXTENDED_MATCH_WINDOW` (после квартала до `MatchHorizonEnd`).

Связь в `ADVANCE_TAX_WINDOW` нужна, чтобы взять фактический НДС из отгрузки / оказания услуг вместо расчётных 5/105. Связь в `ADVANCE_EXTENDED_MATCH_WINDOW` — хозяйственная: она не меняет налоговый результат уже закрытого квартала и **не отменяет** допустимый ранний счёт (`INVOICE_VAT_FALLBACK`), если в налоговом окне реализации не было.

НДС считается в том же запуске Python. Источник фактического состава — колонка `НДС` табличной части, выгруженная агрегатами в `documents.csv`. Приоритет: отгрузка / оказание услуг, затем счёт. Расчётные 5/105 — только если реализации и счёта нет. `SUCCESS` при `tax_ready=0` допустим: matching отработал, но часть строк нельзя утвердить как налоговый доход (например `DEBT_UNRESOLVED`).

## 1.1. Замороженные решения

| Тема | Формулировка |
| --- | --- |
| Разрез DEBT/ADVANCE | По каждой аналитике `КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID` из `ledger62`. Не по целому `payment_id`. Остатки разных аналитик не неттируются. |
| Закрытие аванса | Немедленно только однозначная HIGH-связь. Неоднозначное — глобальный conflict-resolution pass. |
| Три окна | `DEBT_MATCH_WINDOW`: ИсторияНач → оплата. `ADVANCE_TAX_WINDOW`: оплата → конец квартала этой оплаты. `ADVANCE_EXTENDED_MATCH_WINDOW`: после квартала → `MatchHorizonEnd`, без пересчёта налога закрытого квартала. |
| Выгрузка документов | Не `КонецКвартала(ДатаКон)`. Отдельный `MatchHorizonEnd`. Конец квартала остаётся налоговой границей. |
| Набор документов | В данной конфигурации версия 1 работает только с `Счет` → `INVOICE`, `РасходнаяНакладная` → `RECEIVABLE`, `ОказаниеУслуг` → `RECEIVABLE`. Других документов реализации/задолженности в используемой базе нет. |
| Вид расчётов документа | У `РасходнаяНакладная` и `ОказаниеУслуг` единственный реквизит — `ВидыРасчетовСПокупателями`. У `Счет` этого реквизита нет. Для проведённого `RECEIVABLE` отсутствие вида и в реквизите, и во всех проводках 62 = `FAILED`; несколько видов в проводках допустимы, поле документа остаётся пустым. |
| VAT timeline | Аванс до 01.01.2026 — без 5/105. Реализация 2026 может иметь НДС независимо от даты аванса. Две независимые шкалы. |
| Один цикл | Нет второго `1С → Python → 1С`. Состав НДС выгружается вместе с документами. Python возвращает готовые строки КУДиР. |
| Источник НДС | Колонка `НДС` табличной части. Для аванса источник выбирается **по состоянию налогового окна**: RECEIVABLE в `ADVANCE_TAX_WINDOW`, иначе счёт не позже конца квартала этой оплаты, иначе 5/105 или 0. Поздняя реализация в extended window не источник НДС и не отменяет ранний счёт. Строки ТЧ в RAM 1С не копятся. |
| Неизвестный состав | Matching сохраняется, 5/105 вместо документа запрещён, `tax_ready=0`. Технические нули НДС не являются установленным налоговым фактом (`VAT_COMPOSITION_UNKNOWN`). |
| DEBT_UNRESOLVED | Не занимает `document_remaining`. SUCCESS и `tax_ready` раздельно. Поля: `tax_ready`, `unresolved_debt_kopecks`, `unresolved_count`. |
| FIFO / хронология | FIFO отсутствует полностью. Обратная хронология не создаёт HIGH. Доказательный gap — между лучшим и вторым кандидатом; слабый третий не развязывает равную пару. Иначе `DEBT_UNRESOLVED`. |
| Аналитика оплаты | Множество строк `ledger62` данного `payment_id`. Поля договора/вида расчётов в `payments.csv` не authoritative для matcher. |
| ID | По типам сущностей. Банковская оплата: позиция + `НомерПроводки()`. `ledger_event_id` уникален для каждой строки ledger. `id_map.csv` содержит только `PAYMENT`, `DOCUMENT`, `CONTRACT`; `LEDGER` и `COUNTERPARTY` туда не входят. Коллизия одного `entity_type + id` на две системные строки = `FAILED`. Обратимая ссылка: `ЗначениеВСтрокуВнутр()`, загрузка = `ЗначениеИзСтрокиВнутр()`. |
| Неплатёжный 62 | Всегда меняет аналитическое сальдо. `document_remaining` — только при однозначной атрибуции. Расхождение remainder и aggregate → diagnostic event, не автораспределение. |

## 2. Цель

На основании оплат, проводок по счёту 62 и документов реализации определить:

- какая часть **каждой аналитики** оплаты погашает существующую задолженность этой же аналитики;
- какой документ или документы ею оплачены;
- какая часть является авансом по этой аналитике;
- какие реализации закрыли этот аванс: сразу по HIGH-связи, в `ADVANCE_TAX_WINDOW` или в `ADVANCE_EXTENDED_MATCH_WINDOW`;
- какая сумма относится к долгу, но не может быть надёжно связана с документом;
- какая часть каждой строки облагается НДС 5%, какая нет, и какой налоговый доход УСН.

Результат загружается в 1С в существующую `СформироватьТаблицуДоходовЧистовая()`. При `tax_ready=1` это готовые строки КУДиР. При `tax_ready=0` matching загружается, но книгу нельзя считать готовой к сдаче.

## 3. Общая схема и ответственность

```text
1С 7.7 → CSV → Python: взаиморасчёты, matching, НДС и доход УСН
       ← CSV ← готовые строки КУДиР и диагностика
       → СформироватьТаблицуДоходовЧистовая()
```

### 3.1. 1С 7.7

1С является источником бухгалтерских фактов и потребителем результата. Она должна:

- выгрузить все оплаты с `ИсторияНач` по `ДатаКон` с признаком `is_target`;
- для выписки считать самостоятельной оплатой одну проводку (`Опер.НомерПроводки()`), а не строку табличной части: в этой конфигурации нет `ПривязыватьСтроку`, `НомерСтрокиДокумента()` всегда 0;
- выгрузить **все** движения по счёту 62, не только 50/51/55→62 и 62→90; кредитовая оплата должна быть и в `payments.csv`, и в `ledger62.csv` с одним `payment_id`;
- выгрузить только используемые в данной конфигурации документы: `Счет`, `РасходнаяНакладная`, `ОказаниеУслуг` анализируемых клиентов **с `ИсторияНач` по `MatchHorizonEnd`**, а не по `КонецКвартала(ДатаКон)`;
- для каждого такого документа обойти табличную часть, по колонке `НДС` сложить облагаемую и необлагаемую суммы и сразу забыть строки; второй выгрузки документов нет;
- передать контрагента, договор, вид расчётов, даты и позиции документов;
- передать содержание, представление, назначение платежа, первичный документ и комментарий;
- обязательно выгрузить начальное сальдо на `ИсторияНач` в `opening_balances.csv` по ключу аналитики;
- сохранить `id_map.csv` с `ссылка_1С = ЗначениеВСтрокуВнутр(Объект)` (не `СокрЛП(Объект)`), проверить уникальность ID и однозначность отображения на одну системную строку;
- загрузить `kudir_result.csv` через `ЗначениеИзСтрокиВнутр()` и сформировать существующую таблицу доходов. Живой объект из выгрузки в RAM к загрузке не тащить.

1С не выполняет эвристический matching и не дублирует Python-алгоритм. Решение «аванс или долг» 1С не принимает.

### 3.2. Python

Python является единственным местом, где выполняются:

Бухгалтерский timeline строится только по `ledger62.csv`: каждая строка ledger создаёт/изменяет состояние взаиморасчётов. `documents.csv` сам по себе бухгалтерского движения не создаёт; он только обогащает ledger-событие метаданными документа через `source_document_id` (тип, номер, договор, комментарий, агрегаты НДС).

- восстановление взаиморасчётов по аналитике на момент каждой оплаты;
- разделение **каждой аналитической части** оплаты на погашение долга и аванс;
- разбор прямых и косвенных ссылок на документы;
- matching погашения долга в `DEBT_MATCH_WINDOW`;
- немедленное HIGH-закрытие аванса появившейся реализацией; неоднозначные связи — conflict-resolution pass в `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`;
- поиск комбинаций и scoring;
- необязательный semantic reranking;
- расчёт фактического НДС по составу найденной реализации / счёта, либо расчётных 5/105 для незакрытого аванса;
- формирование готовых строк КУДиР, `analysis.log` и `run_status.csv` (`status` отдельно от `tax_ready`).

Результат должен быть воспроизводимым и покрытым автоматическими тестами.

Один запуск = один каталог `exchange/<run_id>/`. В нём лежат входные CSV, `id_map.csv`, `kudir_result.csv`, `matches.csv`, `unresolved.csv`, `analysis.log` и `run_status.csv`. Два запуска одного периода — два каталога; чужой результат не перезаписывается. `run_id` вида `KUDIR_PROTO_ДатаНач_ДатаКон` недостаточен: нужна уникальность запуска, например `KUDIR_2026_20260904_001`.

Обратимая сериализация: `ссылка_1С = ЗначениеВСтрокуВнутр()`; Python эту колонку не читает, загрузчик делает `ЗначениеИзСтрокиВнутр()`. Представление `СокрЛП(Объект)` ссылкой не является. Контракт колонки — ТЗ №1 §23.3; жизненный цикл памяти — ТЗ №4.

### 4.1. Идентификаторы по типам сущностей

Каждая сущность имеет стабильный идентификатор, не зависящий от текстового представления (вид + номер + дата сами по себе **не** ID).

| Сущность | Из чего строится ID |
| --- | --- |
| Документ (счёт, отгрузка, оказание услуг) | Техническая позиция `ПолучитьПозицию()` |
| Банковская оплата | Позиция документа + `НомерПроводки()`. Позиции выписки недостаточно: две проводки одной выписки иначе сольются |
| ПКО | Один документ = одна оплата; ID от позиции документа |
| Строка ledger | Позиция документа + `НомерПроводки` + порядковый номер корреспонденции при обходе |

На выгрузке 1С проверяет:

- уникальность `payment_id`, `document_id`, `ledger_event_id` по их правилам;
- для сущностей, которые попадают в `id_map.csv` (`PAYMENT`, `DOCUMENT`, `CONTRACT`), однозначность `entity_type + id` → ровно одна системная строка `ЗначениеВСтрокуВнутр()`.

Коллизия одного `entity_type + id` на две разные системные строки = `FAILED`, не «взять первую ссылку». `ledger_event_id` контролируется как идентификатор строки `ledger62.csv`, но объект 1С по нему после Python не восстанавливается и в `id_map.csv` он не записывается.

### 4.2. Две проекции оплаты

Оплата — две проекции одного события: одна строка `payments.csv` и одна или несколько кредитовых корреспонденций `ledger62.csv` с тем же `payment_id`.

Ключ оплаты выписки — позиция документа + `НомерПроводки()`, не номер строки табличной части.

К взаиморасчётам, `debt_before`, scoring договора/вида расчётов и разрезу DEBT/ADVANCE применяется только ledger. `payments.csv` не второе движение денег и не authoritative-источник аналитики. Поля `ДоговорID` и `ВидРасчетовID` в `payments.csv`, если остаются в схеме, справочные: для отображения или диагностики.

Несколько корреспонденций одной проводки не означают автоматически несколько оплачиваемых документов. Порядок событий: `ДатаОперации + ПозицияДокумента + НомерПроводкиВДокументе`. `run_id` живёт в `manifest.csv` и копируется в результат. Веса matching — только `config/scoring.yaml`; в тексте ТЗ числовых примеров весов нет.

## 5. История, долг и аванс

История по умолчанию начинается 1 октября года, предшествующего отчётному. Параметр `МесяцевИстории` изменяемый. `opening_balances.csv` обязателен во всех трёх документах проекта: без него нельзя объяснить долг, возникший раньше начала выгрузки. Отсутствие файла — ошибка обработки, а не молчаливый старт с нуля.

`payments.csv` содержит все оплаты с `ИсторияНач` по `ДатаКон`, а не только платежи отчётного периода. Признак `is_target`:

- `1` — оплата попадает в `kudir_result.csv` (`ДатаНач`…`ДатаКон`);
- `0` — историческая оплата, нужна только чтобы восстановить документные остатки.

Python прогоняет matching по всем оплатам. Строки `kudir_result.csv` формируются только для `is_target=1`.

Snapshot документных остатков между запусками в версии 1 не используется. Если долг возник раньше `ИсторияНач` и конкретный документ установить невозможно, формируется `DEBT_UNRESOLVED`.

Состояние на дату оплаты рассчитывается последовательно:

```text
начальное сальдо по аналитике + движения ledger62 этой аналитики с начала периода
```

Несогласованное начальное состояние или разрыв движений отражается в диагностике, а не исправляется молча.

### 5.1. Ключ аналитики и разрез DEBT/ADVANCE

Ключ аналитики:

```text
КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID
```

Одна оплата (один `payment_id`) может содержать несколько таких частей — по строкам `ledger62` с этим `payment_id`. Сворачивать оплату в одно число DEBT/ADVANCE до разреза по аналитике нельзя. Неттинг между аналитиками запрещён: остаток Кт договора B не уменьшает долг Дт договора A.

По каждой части отдельно:

```text
debt_before  = дебетовое сальдо только этой аналитики на момент оплаты
debt_part    = min(сумма части, debt_before)
advance_part = сумма части − debt_part
```

Например, долг аналитики 7 000 и часть оплаты 10 000 дают `DEBT = 7 000` и `ADVANCE = 3 000` **по этой аналитике**. ML/LLM в этом расчёте не участвует.

Если погашение долга установлено, но документ надёжно не найден, сумма получает тип `DEBT_UNRESOLVED`, а не превращается в аванс.

Оплата **не** окончательно определяет НДС для КУДиР сама по себе. На дату поступления денег Python разделяет долг и аванс по аналитике и ищет документы. Сумму НДС он считает сразу после matching, по составу найденной реализации / счёта или по правилу 5/105. Отдельного второго цикла выгрузки нет.

### 5.2. Три окна

| Окно | Границы | Что делает | Чего не делает |
| --- | --- | --- | --- |
| `DEBT_MATCH_WINDOW` | ИсторияНач → момент оплаты | Ищет документы задолженности, существовавшие на оплату | Не смотрит будущие реализации |
| `ADVANCE_TAX_WINDOW` | Момент оплаты → конец квартала этой оплаты | Хозяйственная связь, которая может заменить 5/105 фактическим НДС | Не продлевается в следующий квартал |
| `ADVANCE_EXTENDED_MATCH_WINDOW` | После квартала оплаты → `MatchHorizonEnd` | Ищет хозяйственную связь закрытия аванса | Не меняет налоговый результат уже закрытого квартала |

Конец квартала — налоговая граница каждой конкретной оплаты. Для оплаты вычисляется `payment_tax_quarter_end = КонецКвартала(ДатаОперации)`. Поле `manifest.quarter_end = КонецКвартала(ДатаКон)` — только метаданные расчётного запуска и не заменяет правую границу `ADVANCE_TAX_WINDOW` отдельных оплат. `MatchHorizonEnd` — предел выгрузки `documents.csv`.

Документы задолженности для погашения долга ищутся в `DEBT_MATCH_WINDOW`. Реализации для закрытия аванса — в двух авансовых окнах. Поэтому `documents.csv` должен содержать документы до `MatchHorizonEnd`.

`ledger62.csv` заканчивается `ДатаКон`. Документ после `ДатаКон` (но не позже `MatchHorizonEnd`) **не** создаёт бухгалтерского события и не меняет `signed_balance`. Matcher вводит такие `RECEIVABLE` отдельным обходом доступности для хозяйственного закрытия аванса (в том числе HIGH через счёт). После `ДатаКон` в этом запуске нет будущих оплат и корректировок: доступность документа там — неполный хозяйственный контекст, не полный бухгалтерский остаток.

### 5.3. Неплатёжные движения 62

Любое движение 62 меняет `signed_balance` аналитики.

`document_remaining` меняется только если движение однозначно атрибутировано документу (сторно или корректировка этой реализации). Иначе remainder чужих документов не трогается.

Если сумма document remainder не сходится с аналитическим сальдо — diagnostic event в `analysis.log`, без молчаливого размазывания разницы по документам.

### 5.4. Один цикл: matching и НДС вместе

```text
Один цикл:
  1С → CSV → Python: долг / аванс / документы по аналитике,
                     HIGH-закрытие сразу, conflict-resolution pass,
                     фактический НДС из табличной части,
                     расчётный НДС 5/105 для незакрытого аванса
                 → CSV → 1С → СформироватьТаблицуДоходовЧистовая()
```

Второй поход `1С → Python → 1С` за строками товаров запрещён: память 1С 7.7 нельзя занимать дважды полным комплектом истории, а табличные части уже известны в момент первой выгрузки документов.

Две независимые шкалы НДС:

**Аванс — дата получения денег.** Если аванс получен до `2026-01-01`, расчётный НДС 5/105 не начисляется ни на остаток, ни «задним числом».

**Реализация — дата отгрузки.** Реализация 2026 года может нести фактический НДС независимо от того, что аванс был до НДС.

Нельзя писать «всё до 01.01.2026 без НДС» как общее правило для обеих сторон.

Источник фактического состава — колонка `НДС` табличной части документа. Она есть у отгрузки товаров, оказания услуг и счёта на оплату. Приоритет:

```text
1. найденная отгрузка / оказание услуг     (RECEIVABLE)
2. иначе счёт на оплату                    (INVOICE)
3. иначе расчётные 5/105 или 0 по шкале аванса
```

1С не выгружает каждую строку товара отдельным CSV. При обходе документа она сразу суммирует:

```text
СуммаОблагаемаяКоп     — сумма строк, где НДС > 0
СуммаНеоблагаемаяКоп   — сумма строк, где НДС = 0 / пусто
СуммаНДСКоп            — сумма колонки НДС
```

Строки табличной части после суммирования не хранятся. В `documents.csv` остаются только эти агрегаты плюс шапка.

Правила налога в том же запуске:

- погашение реализации → фактический НДС из этой реализации (по шкале отгрузки);
- аванс, закрытый отгрузкой в `ADVANCE_TAX_WINDOW` → фактический НДС из этих реализаций вместо 5/105;
- связь в `ADVANCE_EXTENDED_MATCH_WINDOW` не пересчитывает налог уже закрытого квартала аванса: поздняя отгрузка не источник НДС и **не отменяет** допустимый ранний счёт. Налог этой суммы считается так, как если бы поздней реализации не было (счёт в налоговом окне → его агрегаты; иначе 5/105 или 0 по дате получения);
- для найденного документа с неизвестным составом НДС не угадывается: технические `vat_base_kopecks = 0`, `vat_kopecks = 0`, `income_kopecks = amount_kopecks`, `reason` содержит `VAT_COMPOSITION_UNKNOWN`, `tax_ready=0`, в тексте не писать «без НДС»;
- незакрытый на конец квартала остаток аванса, полученного **с** `2026-01-01` → расчётный НДС 5/105, если до конца квартала этой оплаты нет допустимого источника состава;
- незакрытый остаток аванса, полученного **до** `2026-01-01` → без 5/105;
- если реализации нет, но есть связанный счёт, существовавший не позже конца квартала этой оплаты, → состав облагаемых и необлагаемых сумм по агрегатам счёта;
- счёт, созданный только после окончания квартала аванса, может участвовать в хозяйственном matching и цепочке к будущей реализации, но не меняет налог уже закрытого квартала и не используется как `INVOICE_VAT_FALLBACK` для него;
- для `DEBT_UNRESOLVED` НДС не угадывается: `vat_kopecks = 0`, `income_kopecks = amount_kopecks`, `tax_ready=0`.

Зачем `ADVANCE_TAX_WINDOW` нужен уже при matching:

```text
10 января  аванс 105 000, состав товаров ещё неизвестен
20 февраля отгрузка в том же I квартале:
           63 000 с НДС 5%  и  42 000 без НДС
```

Если обрезать поиск датой оплаты, февральская накладная не будет связана с январским авансом. Тогда Python увидит «неопределённый аванс» и вынужденно возьмёт 105 000 × 5/105 = 5 000 НДС и доход УСН 100 000. Если связь найдена в налоговом окне, Python возьмёт фактические 3 000 НДС и доход 102 000.

Частичное закрытие к концу квартала:

```text
аванс 105 000
до 31 марта отгружено: 42 000 без НДС + 21 000 с НДС 5%
остаток аванса 42 000
```

Цикл matching должен отдать: 63 000 на найденные реализации и 42 000 как незакрытый аванс. Налоговый слой сразу посчитает НДС 1 000 + 2 000 = 3 000 по найденным реализациям и 5/105 с остатка 42 000, если остаток получен с `2026-01-01` и счёта с составом нет.

Зачем `ADVANCE_EXTENDED_MATCH_WINDOW` и `MatchHorizonEnd`:

```text
20 декабря аванс
15 января  реализация того же счёта
```

Связь хозяйственная. `ADVANCE_TAX_WINDOW` закрылся 31 декабря. Январская реализация не даёт фактический НДС «вместо 5/105» для уже закрытого IV квартала. Но matching всё равно должен найти документ, иначе remainder и последующие оплаты увидят неверное состояние. Для декабрьского аванса налог считается по шкале аванса (5/105 или 0), не по январской отгрузке.

Правило ФНС «аванс и отгрузка в одном квартале — НДС по фактической отгрузке» мотивирует `ADVANCE_TAX_WINDOW`. НДС считается в том же запуске, как только документы найдены.

## 6. Существующий parser

Parser является внешней зависимостью и в этот репозиторий не входит. Новый parser в рамках проекта не разрабатывается и не копируется.

В `доходы-2.txt` уже используется `РазобратьНазначениеПлатежа(...)`, обращающийся к локальному сервису `http://127.0.0.1:8765/parse1c`. Механизм извлекает смысл платежа, тип, номер и дату упомянутого документа.

1С-клиент этого сервиса подключается через адаптер. Python вызывает тот же сервис. Regression-тесты: сохранённые ответы (unit) и живой сервис (integration, можно пропускать). Если сервис недоступен, разбор текста пропускается, matching продолжается, итог запуска — `SUCCESS_DEGRADED`; 1С показывает предупреждение. `SUCCESS_DEGRADED` не путать с `tax_ready`.

Parser отвечает на вопрос «что написано в тексте»; matcher — «какой документ фактически оплачивается». Эти задачи не смешиваются.

Путь к сервису, команда запуска и формат запроса/ответа указываются в ТЗ №2. Git-submodule для внешних инструментов не используется.

## 7. Порядок matching

Matcher работает по хронологической модели состояния, а не по схеме «сначала все долги, потом все авансы».

Единый поток событий: оплаты и реализации вперемешку по `ДатаОперации + ПозицияДокумента + НомерПроводкиВДокументе`.

Оплата создаёт `ADVANCE` по аналитике (после выделения `debt_part` этой аналитики). Пришедшая реализация сразу гасит существующий `ADVANCE` только если связь однозначная / HIGH (машинное основание, уникальная цепочка через счёт). Неоднозначные кандидаты не трогают remainder до conflict-resolution pass. Следующая оплата видит только уже зафиксированные HIGH-остатки.

Кейс «январский аванс → A по счёту, мартовская оплата → B» проходит, потому что связь через счёт — HIGH и закрывается до обработки мартовской оплаты.

Этапы блокировки внутри оплаты (для `DEBT` и для немедленного HIGH-аванса):

1. восстановить долг и остатки **по каждой аналитике** на момент оплаты;
2. заблокировать уникальные машинные ссылки (`Введен на основании`, ПКО);
3. зафиксировать уникальные прямые ссылки, включая допустимые частичные оплаты;
4. зафиксировать уникальные совпадения через счёт;
5. зафиксировать уникальные совпадения с остатком документа;
6. решить оставшиеся конфликты внутри одного контрагента ограниченным поиском;
7. всё ниже порога оставить `DEBT_UNRESOLVED` (для долговой части) или незакрытый `ADVANCE` (для авансовой);
8. semantic-модель в версии 1 не обязательна и подключается только после реальной статистики неоднозначностей;
9. обратная хронология — только последний tie-break, когда несколько кандидатов уже прошли пороги confidence и gap.

Глобальный conflict-resolution pass — только неоднозначные хвосты внутри `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`. Он не основной путь и не пересматривает уже зафиксированные HIGH-связи и `DEBT`.

Простой greedy запрещён как основной алгоритм. FIFO отсутствует полностью: самый старый документ нигде не предпочитается. Раннее слабое решение не должно разрушать более сильное точное соответствие.

### 7.1. Прямая ссылка

Уникальная машинная или разобранная ссылка на документ того же контрагента плюс условие `0 < сумма платежа (или его долговой части) <= остаток документа` даёт связь высокой уверенности `HIGH_PARTIAL_DIRECT` или `DIRECT_DOCUMENT_EXACT` при полном закрытии остатка.

Если платёж больше остатка указанного документа: остаток относится на этот документ, хвост идёт в дальнейший matching или в `ADVANCE`.

Точная сумма считается сильным признаком только при единственном подходящем кандидате. Два документа по 10 000 и платёж 10 000 сами по себе однозначной связи не создают.

### 7.2. Оплата по счёту

Счёт не является документом задолженности. Необходимо построить цепочку:

```text
платёж → счёт → отгрузка товаров / оказание услуг
```

Реализация по счёту может быть раньше оплаты (погашение долга в `DEBT_MATCH_WINDOW`) или позже оплаты (`ADVANCE_TAX_WINDOW` / `ADVANCE_EXTENDED_MATCH_WINDOW`). Иначе типичный сценарий «сначала деньги, потом выбор товара» не свяжется. Уникальная цепочка через счёт — HIGH и закрывает аванс сразу.

Связь счёта с реализацией определяется структурированным разбором комментария `Введен на основании`, а не посимвольным сравнением строки. Если одному счёту соответствуют несколько реализаций, проверяются суммы, остатки и комбинации; первый найденный документ автоматически не выбирается. Без порогов confidence/gap это не HIGH и не немедленное закрытие.

В налоговом слое счёт — запасной источник состава НДС: если отгрузка или оказание услуг так и не найдены, облагаемую и необлагаемую части берут из агрегатов табличной части счёта. Агрегаты выгружаются вместе с шапкой счёта в том же `documents.csv`.

### 7.3. ПКО

Для наличной оплаты сначала анализируется комментарий ПКО. Машинная ссылка на реализацию плюс `0 < сумма <= остаток` даёт связь высокой уверенности, в том числе частичную. Если сумма больше остатка, остаток идёт на указанный документ, хвост — дальше.

## 8. Кандидаты и ограничения

Другой контрагент — жёсткий запрет в любом случае.

Будущий документ — жёсткий запрет **только для погашения долга** (`DEBT`): обычный платёж не закрывает реализацию, которой ещё не было. Кандидаты `DEBT` живут в `DEBT_MATCH_WINDOW`.

Для аванса (`ADVANCE`) кандидат ищется после оплаты:

- в `ADVANCE_TAX_WINDOW` — до конца квартала этой оплаты; связь может заменить расчётный НДС фактическим;
- в `ADVANCE_EXTENDED_MATCH_WINDOW` — после квартала до `MatchHorizonEnd`; связь хозяйственная и не меняет налог закрытого квартала: не берёт НДС поздней отгрузки и не отменяет допустимый ранний счёт.

Для `DEBT` документ-кандидат должен существовать на момент оплаты и иметь непогашенный остаток. Для закрытия аванса реализация не обязана существовать на момент оплаты и не обязана иметь дебетовый остаток 62: отгрузка в счёт аванса часто уже зачтена.

Лимит реализации для аванса:

```text
available_for_advance = сумма документа − подтверждённые DEBT − подтверждённые ADVANCE
```

`DEBT_UNRESOLVED` документ не занимает: `available_for_advance` от UNRESOLVED не уменьшается.

Для документов с одной датой используется `ПозицияДокумента`, а не случайный порядок строк и не `НомерСтрокиДокумента()`.

Договор не является жёстким ограничением:

- совпадение договора даёт сильный плюс;
- несовпадение даёт штраф, но не запрещает связь;
- машинная цепочка и точная сумма могут перебить несовпадение;
- такой результат помечается `CROSS_CONTRACT_MATCH`.

Источник договора и вида расчётов для scoring — строки `ledger62` этой оплаты, не поля `payments.csv`.

В строке `DEBT` возвращается договор найденного документа задолженности. В строке `ADVANCE` с найденной реализацией — договор этой реализации. В строке `ADVANCE` без документа — договор аналитической части оплаты из ledger.

## 9. Суммы, комбинации и конфликты

Сильными считаются следующие случаи:

- оплата равна текущему остатку документа;
- оплата равна полной сумме ещё не оплаченного документа;
- несколько оплат вместе закрывают один документ;
- одна оплата закрывает несколько документов;
- очередная оплата точно закрывает остаток после частичной оплаты.

Связь является many-to-many: одна оплата может породить несколько строк результата, а один документ может закрываться несколькими оплатами.

Простой greedy запрещён как основной алгоритм. FIFO отсутствует полностью. Раннее слабое решение не должно разрушать более сильное точное соответствие. Конфликты внутри одного контрагента решаются этапами блокировки из раздела 7, а не скрытым перебором «на усмотрение реализации». Ограниченный комбинаторный поиск допускается только после уникальных блокировок, с лимитом кандидатов и детерминированным fallback, заданными в ТЗ №2.

Обратная хронология не алгоритм выбора документа. Она допускается только когда несколько кандидатов уже прошли пороги confidence и gap, и нужно выбрать одного из равных. Если пороги не выполнены — `DEBT_UNRESOLVED` (для долга) или незакрытый `ADVANCE` / conflict-resolution pass (для аванса), а не «ближайший документ». Самый старый документ нигде не предпочитается.

## 10. Scoring, уверенность и ML

Scoring учитывает, в порядке убывания значимости:

1. прямую ссылку на документ;
2. цепочку через счёт или основание;
3. совпадение с остатком и полной суммой;
4. точную комбинацию сумм;
5. договор и вид расчётов (из ledger);
6. соответствие «товар/услуга»;
7. текстовую семантику;
8. близость по времени (только как слабый признак и как tie-break при порогах).

Веса, пороги `HIGH` / `MEDIUM` / `LOW`, минимальный отрыв от второго кандидата и условие перехода в `DEBT_UNRESOLVED` находятся **только** в `config/scoring.yaml`. В тексте ТЗ числовых примеров весов нет. Каждая связь получает `match_type`, числовой `score`, `confidence` и машиночитаемый `reason`. Результат почти только по хронологии не может иметь `HIGH`.

Semantic reranker запускается только для оставшихся неоднозначных кандидатов. Он сравнивает тексты, но не рассчитывает остатки, не распределяет деньги и не отменяет жёсткие ограничения. При недоступности модели система продолжает работу; первая версия должна быть возможна без ML.

## 11. Результат: готовые строки КУДиР

Допустимые типы строки:

- `DEBT` — погашение долга с найденным документом;
- `ADVANCE` — полученный аванс; `matched_document_id` заполнен, если аванс закрыт реализацией (HIGH сразу, налоговым окном или extended match), и пуст, если реализация не найдена;
- `DEBT_UNRESOLVED` — погашение долга без надёжной привязки.

В каждой строке сумма равна конкретной части конкретной аналитики, а не полной сумме исходной оплаты.

- Для `ADVANCE`: аванс = сумма части, в оплату = 0.
- Для `DEBT` и `DEBT_UNRESOLVED`: аванс = 0, в оплату = сумма части.
- Доход УСН = сумма части − НДС этой части.
- База НДС (`vat_base_kopecks` / `СуммаСНДС`) — облагаемая часть суммы (со включённым НДС 5%), не вся оплата, если документ смешанный.
- НДС (`vat_kopecks`) — фактический из агрегатов документа / счёта, либо 5/105, либо 0.

`kudir_result.csv` содержит `run_id`, ID и скаляры (`payment_id`, `matched_document_id`, `contract_id`, суммы в копейках, `match_type`, `confidence`, `reason`, текст содержания). 1С восстанавливает `ДокументОплаты` и `Договор` по таблице соответствия.

`СодержаниеЗаписи` формируется только из подтверждённых реквизитов. Отсутствующие номер, дата или договор не выдумываются. Если НДС определён, текст это отражает (`без НДС` или `в т.ч. НДС 5%`). Для `DEBT_UNRESOLVED` фразу про НДС не писать. В `kudir_result` поле — одна физическая строка, без CR/LF внутри.

## 12. Инварианты и диагностика

Для каждой исходной оплаты обязательно:

```text
сумма DEBT + сумма ADVANCE + сумма DEBT_UNRESOLVED
= сумма исходной оплаты
```

Сумма подтверждённых привязок к документу не превышает `available_for_advance` / остаток для долга. `DEBT_UNRESOLVED` remainder документа не занимает. Остатки оплаты и документа не могут быть отрицательными. Одинаковые входные данные и настройки всегда дают одинаковый результат.

Нарушение инварианта является ошибкой обработки, а не низкой уверенностью. `matches.csv` должен объяснять каждую связь; неоднозначные случаи сохраняются отдельно для ручной проверки. `analysis.log` обязателен.

### 12.1. SUCCESS и tax_ready

`status` и `tax_ready` — разные признаки.

```text
status     = SUCCESS / SUCCESS_DEGRADED / FAILED
tax_ready  = 0 или 1
```

Цикл 1 может быть `SUCCESS`, если matching отработал и инварианты сумм держатся. `tax_ready=0`, пока есть unresolved-долги. Поля `run_status.csv`:

```text
tax_ready=0|1
unresolved_debt_kopecks
unresolved_count
```

`SUCCESS` при `tax_ready=0` допустим. По этому запуску нельзя считать книгу готовой к сдаче и нельзя угадывать НДС для `DEBT_UNRESOLVED`.

Недоступность parser даёт `SUCCESS_DEGRADED`, а не скрытый успех. Это не то же самое, что `tax_ready=0`.

### 12.2. Минимальные автоматические сценарии

- прямая ссылка с совпадающей и несовпадающей суммой;
- оплата по счёту с переходом к реализации;
- ПКО со ссылкой на основание;
- сильная связь при разных договорах;
- точная сумма сильнее хронологии;
- несколько оплат ↔ один документ и одна оплата ↔ несколько документов;
- закрытие остатка после частичной оплаты;
- январский HIGH-аванс через счёт закрывает реализацию A до мартовской оплаты, которая идёт на B;
- несколько аналитик одной оплаты: свой `debt_part` / `advance_part` по каждой, без неттинга;
- долг аналитики A и аванс аналитики B не неттируются;
- декабрьский аванс → январская реализация: extended match, налог Q4 не пересчитывается;
- аванс 2025 → реализация 2026: нет 5/105 на аванс, НДС реализации не обнуляется;
- неатрибутированное движение 62 → diagnostic event, remainder чужих документов цел;
- `SUCCESS` при `tax_ready=0`, если есть `DEBT_UNRESOLVED`;
- две равные реализации не закрывают ADVANCE немедленно; хронология только при порогах;
- несколько корреспонденций одной банковской оплаты: один `payment_id`, разные `ledger_event_id`;
- погашение долга не может ссылаться на будущий документ;
- отсутствие `opening_balances.csv` — ошибка, а не расчёт с нуля;
- исторический платёж (`is_target=0`) восстанавливает остаток, но не попадает в `kudir_result.csv`;
- недоступность parser-сервиса и semantic-модели;
- сохранение полной суммы каждой исходной оплаты.

Regression-набор parser формируется из реальных строк `доходы-2.txt` и должен оставаться зелёным при переносе или рефакторинге.

## 13. Критерии архитектурной готовности

1. 1С выгружает полные исходные факты, обязательное начальное сальдо по аналитике и не содержит второго matcher.
2. Исторические оплаты выгружаются с `is_target`; в результат версии 1 попадают только целевые.
3. Python считает `debt_before` / `debt_part` / `advance_part` по каждой аналитике `ledger62`, без неттинга между аналитиками.
4. Существующий внешний parser переиспользован и защищён regression-тестами; в репозиторий не копируется.
5. Поддержаны прямые ссылки, частичные оплаты по прямой ссылке, счета, документы-основания и ПКО.
6. Работают many-to-many связи и закрытие остатков.
7. Другой контрагент запрещён всегда. Будущий документ запрещён для `DEBT`. Для `ADVANCE` разрешены `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`.
8. Разный договор допускается как диагностируемое исключение; аналитика для scoring берётся из ledger.
9. FIFO отсутствует. Обратная хронология — только tie-break при порогах confidence/gap.
10. ML остаётся необязательным дополнительным признаком.
11. Каждая сумма сохранена, каждое решение объяснимо, CSV несёт ID по типам сущностей, а не объекты 1С. Коллизия ID = FAILED.
12. Python считает НДС и доход УСН в том же запуске. Источник фактического состава — агрегаты колонки `НДС`. Приоритет: отгрузка / оказание услуг, затем счёт, затем 5/105. Аванс и реализация живут на разных VAT-шкалах. `DEBT_UNRESOLVED` НДС не угадывает.
13. HIGH-аванс закрывается сразу. Неоднозначное — conflict-resolution pass. `DEBT_UNRESOLVED` не занимает remainder.
14. `analysis.log` обязателен. `status` и `tax_ready` разделены.
15. Документы выгружаются до `MatchHorizonEnd`, не до `КонецКвартала(ДатаКон)`.
16. Неплатёжный 62 всегда меняет сальдо аналитики; расхождение remainder и aggregate — diagnostic event.

## 14. CSV-протокол (обязательные правила)

Детали колонок — в специализированных ТЗ. Общие правила одинаковы для всех файлов:

- `run_id` и `schema_version=2` в `manifest.csv`;
- кодировка Windows-1251;
- разделитель `;`;
- даты строго `YYYY-MM-DD`;
- суммы — целые копейки;
- переносы строк внутри поля только в кавычках; в `kudir_result` переносов в `СодержаниеЗаписи` нет;
- кавычка внутри поля удваивается;
- пустое значение — пустая строка, не `NULL` и не `0`;
- точные имена и порядок колонок из ТЗ №1.

# ТЗ №4. 1С 7.7 — устойчивость выгрузки по памяти

## Статус

Документ задаёт требования к доработке `1cv77/kudir_export.txt`, чтобы выгрузка по ТЗ №1 не исчерпывала память процесса 1С 7.7 на живой базе.

Это **не замена ТЗ №1**. Состав фактов, периоды, ID, имена и порядок колонок CSV задаёт `01-ТЗ-1С-выгрузка-данных.md`. Matching Python не меняется; налоговый слой Python читает агрегаты НДС из той же выгрузки документов.

ТЗ №4 определяет:
- как не держать большие наборы в RAM;
- как писать CSV потоково;
- как заменить живые объекты в `глТаблID` на системные строковые представления;
- как затем восстановить ссылки 1С.

Уточнение к ТЗ №1: существующая колонка `ссылка_1С` в `id_map.csv` должна содержать **системное строковое представление агрегатного значения**, полученное `ЗначениеВСтрокуВнутр()`, а не `СокрЛП(Объект)`. Восстановление выполняется через `ЗначениеИзСтрокиВнутр()`.

Связанные документы:
- `00-АРХИТЕКТУРА-КУДиР.md`;
- `01-ТЗ-1С-выгрузка-данных.md`;
- `02-ТЗ-Python-анализ-оплат.md`;
- `1cv77/kudir_export.txt`.

# 1. Назначение

Текущий `КУДиР_Выполнить()` на реальном объёме завершается аварийно до окончания цикла `1С → Python → 1С`.

1С 7.7 — 32-битный процесс; практический предел зависит не только от Working Set, но и от фрагментации адресного пространства. Поэтому критерий готовности — не конкретное число мегабайт, а прохождение реального проблемного периода.

Цель:

> выгружать **тот же набор фактов**, что требует ТЗ №1, но не держать в RAM полные ledger/documents/id_map и полные тексты CSV, если данные уже можно окончательно записать на диск.

Успех:

> период, на котором текущая версия падает, доходит до полного комплекта входных CSV, запуска Python, `run_status.csv`, загрузки `kudir_result.csv` и возврата `СформироватьТаблицуДоходовЧистовая()` либо до контролируемого `FAILED` с логом, но не до аварийного исчезновения процесса.

# 2. Что нельзя менять

Запрещено устранять проблему памяти ценой изменения смысла данных.

1. Не сужать выборку относительно ТЗ №1:
   - все оплаты истории анализируемых клиентов;
   - `is_target` для целевого периода;
   - все движения 62 анализируемых клиентов без дедупа;
   - документы до `MatchHorizonEnd`, включая агрегаты НДС табличной части;
   - обязательный `opening_balances.csv`.
2. Не менять:
   - имена/порядок колонок;
   - разделитель `;`;
   - Windows-1251;
   - даты/копейки;
   - `run_id`;
   - формулы ID.
3. Не переносить matching в 1С.
4. Не сворачивать ledger.
5. Не отбрасывать «лишние» проводки 62, если ТЗ №1 требует их выгружать.
6. Не глотать ошибки и не возвращать частичный результат.
7. Не подставлять `0`, `Проведен=1` и другие фиктивные значения при ошибке чтения.
8. Оборванный CSV = `FAILED`; Python на таком каталоге не запускать.
9. Не уменьшать глубину истории/горизонт ради памяти.

# 3. Подтверждённые источники нагрузки текущего кода

## 3.1. Большие наборы одновременно живут в RAM

Сейчас до общей записи CSV одновременно существуют:

| Набор | Проблема |
| --- | --- |
| `таблОплаты` | хранится до общей записи |
| `таблLedger` | все движения 62 |
| `таблДокументы` | все документы горизонта |
| `таблСальдо` | ещё один набор |
| `глТаблID` | все ID + живые объекты 1С |
| `глЛогТекст` | весь лог одной строкой |

Пик — сумма этих структур.

## 3.2. CSV собирается одной большой строкой

Текущий паттерн:

```text
Текст = Заголовок
для каждой строки:
    Текст = Текст + CSVСтрока + CR/LF
TS.Write(Текст)
```

Для `ledger62.csv` и `id_map.csv` это создаёт ещё одну полную копию больших данных поверх таблиц и множество промежуточных строк.

## 3.3. `глТаблID` удерживает агрегатные объекты

Сейчас `КУДиР_ЗапомнитьID()` сохраняет сам объект документа/справочника.

Для `LEDGER` это особенно дорого: объект документа удерживается на каждую ledger-строку, хотя загрузчик результата использует только `PAYMENT`, `CONTRACT`, `DOCUMENT`.

## 3.4. Полные переборы таблиц

В горячих циклах выполняются линейные поиски клиента, оплаты, документа и ID. На больших объёмах это O(N×M).

## 3.5. Лог растёт в памяти

`глЛогТекст` копится до конца, а DEBUG пишется слишком часто.

## 3.6. Чужие исторические оплаты сначала копятся, потом удаляются

Нужно сначала определить клиентов с целевой оплатой, а затем собирать историю только по ним.

# 4. Основной принцип новой реализации

> **Факт, который больше не будет изменяться, сразу писать на диск. В RAM держать только компактные индексы и данные, которые ещё требуется агрегировать.**

P0/P1 ниже — уровни требований, а не две промежуточные версии. Если работа выполняется одним патчем, сразу делать конечную архитектуру P0+P1.

# 5. Ссылки 1С 7.7: запись и восстановление

Это обязательная часть ТЗ.

## 5.1. `СокрЛП(Объект)` не является технической ссылкой

Текущий код пишет в `id_map.csv` представление объекта для человека. Оно не является гарантированно обратимым.

Новая семантика колонки `ссылка_1С`:

```text
ссылка_1С = ЗначениеВСтрокуВнутр(АгрегатноеЗначение1С)
```

Состав и имя колонки не меняются.

## 5.2. Сериализация

Синтаксис 1С 7.7:

```1c
СистСсылка = ЗначениеВСтрокуВнутр(Ссылка1С);
```

Назначение: преобразовать агрегатное значение в системное строковое представление.

В `id_map.csv` записывать именно `СистСсылка`:

```1c
КУДиР_ПолеCSV(СистСсылка)
```

Обязательно:
- не применять `СокрЛП()` к `СистСсылка`;
- не менять регистр/пробелы;
- не обрезать;
- не выполнять дополнительную «нормализацию»;
- только стандартное CSV-экранирование;
- пустую обязательную ссылку не заменять фиктивным текстом.

## 5.3. Что сериализовать

| `entity_type` | Агрегатное значение |
| --- | --- |
| `PAYMENT` | документ оплаты |
| `DOCUMENT` | документ счёта/реализации/услуг |
| `CONTRACT` | элемент справочника договора |

Только эти три типа записываются в `id_map.csv`. `КонтрагентID`/`Контрагент` остаются бизнес-полями входных CSV, но `COUNTERPARTY` не сериализуется для обратной загрузки. `ledger_event_id` остаётся обязательным ID строки `ledger62.csv`, но `LEDGER` в `id_map.csv` не записывается. Несколько разных ID разрешённых типов могут ссылаться на один объект — это допустимо.

## 5.4. Восстановление

Синтаксис:

```1c
Ссылка1С = ЗначениеИзСтрокиВнутр(СистСсылка);
```

Для `PAYMENT`, `DOCUMENT`, `CONTRACT` перед чтением реквизитов обязательно проверить:
1. ID найден;
2. системная строка не пустая;
3. `ЗначениеИзСтрокиВнутр()` завершилось успешно;
4. восстановленное значение не пустое.

Только после этого разрешено:

```1c
ДокОпл.НомерДок
ДокОпл.ДатаДок
Договор.Наименование
```

Запрещён fallback по номеру, дате, наименованию, сумме и т.п.

## 5.5. Ошибка восстановления

Если обязательный ID не восстановлен:
- записать ошибку;
- не читать реквизиты объекта;
- не подставлять пустую ссылку;
- итоговая таблица должна быть полностью пустой.

Можно собрать несколько ошибок ID за один проход, но частично загруженные строки возвращать нельзя.

## 5.6. `restore`: словарь восстановления только этапа загрузки

`restore` (restore-map) — временный словарь **обратной загрузки результата Python**, а не индекс этапа экспорта. Во время выгрузки `restore` не существует. Живые объекты 1С в нём не хранятся; значение — только системная строка:

```text
ключ = entity_type + "|" + id
значение = СистСсылка
```

`restore` создаётся только после завершения экспорта, освобождения экспортных структур и выполнения Python. Собирать его во время выгрузки запрещено: это смешивает пики EXPORT и LOAD и создаёт ненужный второй набор длинных `СистСсылка`.

После завершения экспорта и Python применяется отдельная трёхпроходная загрузка:

1. первый проход по `kudir_result.csv` — проверить структуру строк и собрать только множества реально нужных ID: `PAYMENT`, непустые `CONTRACT`, непустые `DOCUMENT`;
2. один потоковый проход по `id_map.csv` — для строк, ключ которых входит в эти множества, сохранить `key → СистСсылка`; все остальные строки `id_map.csv` пропустить;
3. второй проход по `kudir_result.csv` — построчно восстановить нужные объекты через `ЗначениеИзСтрокиВнутр()` и сформировать итоговую таблицу.

Таким образом размер restore-map ограничен **результатом текущего расчётного периода**, а не всей глубиной истории и не всем `ledger62.csv`.

Для загрузчика и для самого `id_map.csv` существуют только типы:
- `PAYMENT`;
- `DOCUMENT`;
- `CONTRACT`.

`COUNTERPARTY` и `LEDGER` не являются типами `id_map.csv` вообще. Полный `id_map.csv` в `ТаблицаЗначений` также не загружается.

## 5.7. `registeredIds` и коллизия ID

`registeredIds` и `restore` — разные структуры с разным временем жизни:

```text
registeredIds — EXPORT: контроль первой регистрации PAYMENT/DOCUMENT/CONTRACT
restore       — LOAD:   только реально нужные ID из kudir_result.csv после Python
```

`registeredIds` допустимо хранить как `key → СистСсылка`, чтобы точно сравнить повторную регистрацию. После завершения экспорта он освобождается **до Python** и не переиспользуется как `restore`.

Для регистрируемых ID:

```text
если key отсутствует:
    сохранить key → СистСсылка
    записать строку id_map.csv

если key уже есть и строка совпадает:
    вторую строку id_map.csv не писать

если key уже есть и СистСсылка отличается:
    FAILED
```

Сравнивать точную системную строку, без `СокрЛП()`. Контроль относится только к `PAYMENT`, `DOCUMENT`, `CONTRACT`. Для `ledger_event_id` достаточно отдельного компактного контроля уникальности строки `ledger62.csv`; системная ссылка ledger для этого не нужна.

# 6. P0 — потоковая запись CSV

## 6.1. Запрет полного файла в переменной

Для больших CSV запрещена строка, размер которой растёт пропорционально всему файлу.

Нужно:
1. открыть `TextStream`;
2. записать заголовок;
3. писать строки через `Write`/`WriteLine`;
4. допустим фиксированный буфер 50–100 строк;
5. закрыть поток после успешного этапа.

Потоково писать:
- `payments.csv`;
- `ledger62.csv`;
- `documents.csv`;
- `opening_balances.csv`;
- `id_map.csv`.

`manifest.csv` можно оставить малой строкой.

## 6.2. CSV-протокол сохраняется

Использовать существующее `КУДиР_ПолеCSV()`/эквивалент:
- `;`;
- удвоение кавычек;
- кавычки вокруг поля с `;`, `"`, CR/LF;
- пустое поле остаётся пустым.

Особенно: `ЗначениеВСтрокуВнутр()` → сразу CSV-экранирование, без `СокрЛП()`.

## 6.3. Незавершённая выгрузка

Если сбой после создания каталога:
- `глОшибка = 1`;
- закрыть открытые потоки, насколько возможно;
- Python не запускать;
- каталог не удалять;
- записать этап, файл и число готовых строк.

Рекомендуется `export_status.csv` со статусом `IN_PROGRESS|SUCCESS|FAILED`, но это не должно менять Python-ТЗ без необходимости.

# 7. P1 — конечная архитектура RAM

## 7.1. Проход A: определить анализируемых клиентов

Диапазон:

```text
ДатаНач ... ДатаКон
```

Проводки:

```text
50/51/55 -> 62
```

Собрать только множество `КонтрагентID` целевых клиентов. Полные строки оплат здесь не нужны.

Если клиентов нет — вернуть пустую итоговую таблицу без Python. `run_id` для тяжёлой выгрузки можно не создавать.

## 7.2. После прохода A создать каталог запуска

Если клиенты есть:
1. создать `run_id`;
2. создать `exchange/<run_id>/`;
3. переключить run-specific лог;
4. записать `manifest.csv`;
5. открыть/создать `id_map.csv`;
6. продолжить тяжёлую выгрузку.

Это обязательно: ledger должен сразу иметь место назначения на диске.

## 7.3. Проход B: собрать историю оплат только выбранных клиентов

Диапазон:

```text
ИсторияНач ... ДатаКон
```

Чужие исторические оплаты вообще не добавлять.

Нужен:

```text
Dictionary payment_id → номер строки компактной таблОплаты
```

## 7.4. Оплату нельзя писать при первом появлении

Один `payment_id` может встретиться несколько раз. До конца прохода B могут измениться:
- `СуммаКоп`;
- `ДоговорID`/поля договора;
- `ВидРасчетовID`/поле вида расчётов.

Поэтому одна агрегированная строка на `payment_id` остаётся в RAM до окончания прохода B.

Затем:
1. потоково записать `payments.csv`;
2. при первой записи каждого `payment_id` зарегистрировать `PAYMENT → СистСсылка` в `id_map.csv` через экспортный `registeredIds`;
3. сохранить множество экспортированных `payment_id` для ledger;
4. после использования ненужные широкие данные очистить.

`restore` на этом этапе не создаётся.

## 7.5. Ledger не хранить целиком

Конечный алгоритм:

```text
открыть ledger62.csv
записать заголовок
для каждой подходящей проводки 62:
    сформировать поля
    сформировать ledger_event_id
    проверить уникальность ledger_event_id
    записать строку ledger62.csv
    забыть широкую строку
закрыть ledger62.csv
```

Полная `таблLedger` запрещена как постоянное хранилище.

## 7.6. `id_map.csv` писать одновременно с фактами

При первой регистрации `PAYMENT`, `DOCUMENT` или `CONTRACT` строка сразу идёт на диск. Других `entity_type` в `id_map.csv` нет.

Полную старую `глТаблID` с живой колонкой `ссылка` не строить. Ledger-строки не создают записей `id_map.csv`, поэтому объект документа операции на каждую строку ledger не хранится.

## 7.7. Документы писать потоково

При обходе `Счет`, `РасходнаяНакладная`, `ОказаниеУслуг`:
- сначала определить принадлежность выбранному клиенту;
- проверить дедуп по `document_id` через Dictionary;
- пока документ открыт, обойти табличную часть и сложить `СуммаОблагаемаяКоп` / `СуммаНеоблагаемаяКоп` / `СуммаНДСКоп` по колонке `НДС` (ТЗ №1 §15.1);
- сразу забыть строки табличной части — не копить их в `ТаблицаЗначений` и не писать `document_lines.csv`;
- сформировать строку шапки + агрегаты;
- зарегистрировать `DOCUMENT → ЗначениеВСтрокуВнутр(Док)`;
- сразу записать `documents.csv`.

Полная `таблДокументы` не нужна. Второй обход тех же документов «за НДС» запрещён: это снова подняло бы пик памяти.

## 7.8. Сальдо

`opening_balances.csv` также желательно писать по мере готовности аналитики. Смысл расчёта через `БухгалтерскиеИтоги` не менять.

# 8. Dictionary вместо переборов

Использовать `Scripting.Dictionary`.

Минимальные индексы:

| Индекс | Назначение |
| --- | --- |
| `clients` | выбранные `КонтрагентID` |
| `payments` | `payment_id → строка таблОплаты` |
| `paymentIds` | экспортированные `payment_id` |
| `documents` | дедуп `document_id` |
| `registeredIds` | EXPORT: `PAYMENT/DOCUMENT/CONTRACT key → СистСсылка` для дедупа и контроля коллизий; освобождается до Python |

`restore` в эту таблицу не входит: это структура этапа LOAD, которая создаётся только после Python на проходе L2.

Убрать из горячих циклов линейные `КУДиР_НайтиОплату`, `КУДиР_КлиентВВыборке`, `КУДиР_ЕстьИдВТаблице`, `КУДиР_НайтиСсылку` по полной таблице.

# 10. P2 — календарная нарезка, только если P0+P1 недостаточно

Если внутренний объект `Операция` всё ещё держит слишком большой диапазон, выборки резать на непересекающиеся куски:

```text
01.01–31.01
01.02–28.02
01.03–31.03
```

Правила:
1. первый кусок начинается ровно с исходной начальной даты;
2. последний заканчивается ровно конечной;
3. нет пересечений и пропусков;
4. все куски дописываются в CSV того же `run_id`;
5. заголовок пишется один раз;
6. `глПослПозиция`, `глПослПроводка`, `глНомКорр` между кусками ledger не сбрасывать.

Нарезка документов — только при реальной необходимости; предел остаётся `MatchHorizonEnd`.

# 13. Загрузчик `kudir_result.csv`

## 13.1. Старые проверки сохраняются

До данных проверить:
- `run_status.csv`;
- допустимый статус;
- `run_id`;
- все обязательные колонки;
- длину строк;
- `tax_ready=0` не блокирует допустимый matching.

## 13.2. Новый механизм восстановления без второго пика памяти

Загрузчик не использует старый `глТаблID` и не держит restore-map всей истории.

### Проход L1 — только нужные ID

Прочитать `kudir_result.csv` построчно. Полные строки результата в промежуточную `ТаблицаЗначений` не складывать. Собрать только уникальные ключи:

```text
PAYMENT|payment_id
CONTRACT|contract_id                 // если непустой
DOCUMENT|matched_document_id         // если непустой
```

Одновременно выполнить проверки формата, обязательных полей и `run_id`, которые можно выполнить без объектов 1С.

### Проход L2 — узкий restore из `id_map.csv`

Прочитать `id_map.csv` построчно. Если `entity_type + "|" + id` отсутствует в множествах L1 — строку сразу пропустить. Если присутствует — сохранить только:

```text
key → ссылка_1С (СистСсылка)
```

После конца файла проверить, что для каждого обязательного ID из L1 найдена ровно одна системная строка. Отсутствие или коллизия → `FAILED`.

### Проход L3 — формирование результата

Второй раз прочитать `kudir_result.csv` построчно. Для каждой строки:

```text
СистСсылка = restore["PAYMENT|" + payment_id]
ДокОпл = ЗначениеИзСтрокиВнутр(СистСсылка)

СистСсылка = restore["CONTRACT|" + contract_id]
Договор = ЗначениеИзСтрокиВнутр(СистСсылка)

СистСсылка = restore["DOCUMENT|" + matched_document_id]
ДокРеал = ЗначениеИзСтрокиВнутр(СистСсылка)
```

Пустой `contract_id`/`matched_document_id`, если он допустим по ТЗ №1, не восстанавливается.

После обработки строки локальные переменные `ДокОпл`, `Договор`, `ДокРеал` не кэшировать отдельно. Ссылки, которые должны присутствовать в конечной `ТаблицаЗначений`, естественно останутся в ней — это неизбежный объём итогового результата, но не объём всей истории.

## 13.3. Не читать объект после ошибки

Последовательность строго:

```text
найти СистСсылку
→ проверить
→ ЗначениеИзСтрокиВнутр()
→ проверить объект
→ только затем читать реквизиты
```

Никаких `ДокОпл.НомерДок` до успешного восстановления.

## 13.4. Частичная загрузка запрещена

Если хотя бы один обязательный ID не восстановлен, итоговая таблица возвращается полностью пустой.

# 14. `id_map.csv`: уточнённый контракт

Колонки остаются:

```text
entity_type;id;вид;номер;дата;позиция;номер_проводки;ссылка_1С
```

Меняется только техническое наполнение последней колонки.

Было в текущем коде:

```text
СокрЛП(Объект1С)
```

Должно стать:

```text
ЗначениеВСтрокуВнутр(Объект1С)
```

Это намеренное исправление, необходимое для обратимого ID → объект 1С.

Поэтому при regression:
- `payments.csv`, `ledger62.csv`, `documents.csv`, `opening_balances.csv` должны остаться семантически идентичными по бизнес-фактам;
- `id_map.csv` сохраняет те же колонки, но содержит только `PAYMENT`, `DOCUMENT`, `CONTRACT`; старые строки `COUNTERPARTY`/`LEDGER` удаляются из контракта;
- `ссылка_1С` для трёх разрешённых типов хранит `ЗначениеВСтрокуВнутр(Объект1С)`;
- golden `id_map.csv` обновить под новый набор типов;
- Python `ссылка_1С` не интерпретирует.

Старые лишние ID чужих клиентов, которые возникали до позднего удаления оплат, воспроизводить не требуется. `id_map.csv` должен соответствовать фактически экспортированному набору анализируемых клиентов.

# 15. Приёмка

## 15.1. Контрольная база: полное сравнение

Случайной выборки недостаточно.

### `payments.csv`
- одинаковое число строк;
- одинаковый набор `payment_id`;
- одинаковые бизнес-поля.

### `ledger62.csv`
- одинаковое число строк;
- одинаковый набор `ledger_event_id`;
- полное сравнение всех бизнес-полей;
- ни одной потерянной/добавленной ledger-строки.

### `documents.csv`
- одинаковое число строк;
- одинаковый набор `document_id`;
- одинаковые бизнес-поля.

### `opening_balances.csv`
- одинаковые ключи аналитики;
- одинаковые Дт/Кт остатки.

### `id_map.csv`
- нет дублей `entity_type + id`;
- обязательные ID присутствуют;
- `ссылка_1С` проходит round-trip:

```text
объект 1С
→ ЗначениеВСтрокуВнутр()
→ CSV
→ чтение CSV
→ ЗначениеИзСтрокиВнутр()
→ непустое корректное агрегатное значение
```

Сравнивать новую `ссылка_1С` со старым `СокрЛП(Объект)` не надо.

## 15.2. Живая проблемная база

1. Запустить тот же период, где текущая версия падает.
2. Проверить отсутствие полной `таблLedger`.
3. Проверить потоковый `id_map.csv`.
4. Проверить, что ledger-строки вообще не регистрируются в `id_map.csv` и не удерживают объект документа/системную ссылку на каждую строку.
5. Получить полный комплект CSV.
6. Запустить Python.
7. Получить `run_status.csv`.
8. Перед загрузкой убедиться, что структуры выгрузки освобождены и не участвуют во втором пике памяти.
9. Выполнить L1 по `kudir_result.csv`, L2 по `id_map.csv`, L3 по `kudir_result.csv`.
10. Проверить, что restore содержит только ID, реально встречающиеся в `kudir_result.csv`.
11. Проверить восстановление документа оплаты, договора и matched document через `ЗначениеИзСтрокиВнутр()`.
12. Повторный запуск создаёт новый `run_id`.
13. Искусственно повреждённая `ссылка_1С` приводит к контролируемому `FAILED` и пустому результату.

Недостаточно: «на маленькой базе не упало».

# 17. Приоритет требований

1. По составу фактов, периодам, бухгалтерской аналитике и формулам ID побеждает ТЗ №1.
2. По жизненному циклу памяти, потоковой записи, Dictionary и механизму `ссылка_1С` побеждает ТЗ №4.
3. `ЗначениеВСтрокуВнутр()` / `ЗначениеИзСтрокиВнутр()` — обязательный механизм технического ID → объект 1С.
4. Алгоритм matching задаёт ТЗ №2 и этим документом не меняется. Налоговый слой ТЗ №2 читает агрегаты НДС из `documents.csv`; сами агрегаты считаются в потоке документов по ТЗ №1 §15.1 и не должны создавать второй пик RAM.
5. После выгрузки структуры этапа выгрузки полностью освобождаются **до** запуска Python. Пик выгрузки и пик загрузки не складываются. Загрузка — три прохода L1/L2/L3 раздела 13.

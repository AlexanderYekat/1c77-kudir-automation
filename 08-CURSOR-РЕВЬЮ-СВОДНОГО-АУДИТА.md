## Замечание 1. Краткий канон §1/U4 не фиксирует, что PRE_2026 бьёт DEFAULT и состав документа

**Вывод 08.**  
§1: неизвестный состав «не запрещает определённый fallback 5/105 для целевого поступления 2026». U4: «для целевого допустимого поступления 2026 базовое правило — DEFAULT_5_105», затем «более сильный источник: валидный RECEIVABLE → INVOICE»; PRE_2026 описан отдельно как специсключение по возрасту.

**Доказательство.**  
U2 в том же 08: доказанно старый долг → `PRE_2026_DEBT`, VAT=0, income=amount, совместимо с `DEBT_UNRESOLVED` и `tax_ready=1`. Целевая оплата 2026 при чистом входящем Дт до границы (golden `success_tax_not_ready`: `ОстатокДтКоп=1000000` на `2025-10-01`, документов нет) — как раз такой случай. U4 одновременно называет валидный RECEIVABLE «более сильным», чем DEFAULT, не говоря явно, что PRE_2026 проверяется **до** состава найденного/кросс-аналитического документа.

**Почему неполно.**  
Погашение старого долга в 2026 — тоже «целевое поступление 2026». Краткая формула «2026 → 5/105 / RECEIVABLE» позволяет (а) накинуть DEFAULT на доказанно старый unresolved-долг; (б) взять фактический НДС matched RECEIVABLE 2025/2026 при возрасте долга платёжной аналитики «до 01.01.2026». Это ровно класс ошибок «default/факт перебивает правильный нулевой PRE_2026». Развёрнутые U2 и конец §5 частично спасают, но канонический порядок выбора в одном месте не зафиксирован.

**Предлагаемая формулировка.**  
«Для каждой налоговой части целевого поступления порядок такой: (1) если возраст погашаемого долга платёжной аналитики доказанно до 01.01.2026 → только `PRE_2026_DEBT` (VAT=0), даже при найденном документе/счёте с ненулевым составом и даже при платеже в 2026; (2) иначе валидный RECEIVABLE в применимом окне; (3) иначе допустимый INVOICE с остатком состава; (4) иначе при неизвестном/недопустимом составе или без источника → `DEFAULT_5_105` с диагностикой, а не «без НДС». DEFAULT и состав документа не отменяют доказанный PRE_2026. Смешанный/недоказанный возраст → OD1, не шаг (2)–(4) наугад.»

## Замечание 2. B7 / отриц. НДС ТЧ: 08 фиксирует потерю флага, но не следствие для U4 — ложный «фактический» состав

**Вывод 08.**  
D5: при отрицательном НДС строки ТЧ ставится `отрицНДС`, строка не идёт в агрегаты, «уже накопленные положительные агрегаты остаются; флаг не передаётся в `documents.csv`». После U4 неизвестный состав → fallback; отрицательное поступление отдельно (OD5).

**Доказательство.**  
`1cv77/kudir_export.txt` ~1276–1330: при `ндсСтр < 0` только `отрицНДС = 1` и лог; положительные строки по-прежнему копят `СуммаОблагаемаяКоп` / `СуммаНДСКоп`; ветка сверки агрегатов с `СуммаКоп` при `отрицНДС = 1` не выполняется; в CSV уходят ненулевые агрегаты без машинного признака. В `DOCUMENTS_FIELDS` поля флага нет. U4 в 08: валидный состав — сильный источник вместо DEFAULT.

**Почему неполно.**  
После U4 Python увидит **похожежий на достоверный** частичный состав и обязан взять его как RECEIVABLE/INVOICE-источник. Это не «неизвестный → 5/105» и не «неизвестный → VAT=0»: это **ложный фактический НДС, перебивающий DEFAULT и скрывающий неизвестность**. D5 описывает симптом экспорта, но не требует обнуления/маркировки неизвестности до налогового слоя — хотя Cursor C5 уже требовал нули при `отрицНДС=1`.

**Предлагаемая формулировка.**  
«Отрицательный НДС строки ТЧ делает состав документа неизвестным для налога: в `documents.csv` нельзя оставлять частично накопленные положительные агрегаты как налоговый факт. Либо агрегаты обнуляются и в обмен/диагностику попадает явный признак неизвестности (пока поля нет — хотя бы согласованный три-нуля при ненулевой `СуммаКоп` + лог), либо Python обязан трактовать любой документ с недоставленным признаком отриц. НДС как неизвестный состав. Под U4 такой документ не сильный источник: отбраковка → следующий источник / `DEFAULT_5_105` + `VAT_COMPOSITION_UNKNOWN` в диагностике; нельзя считать усечённые агрегаты “фактическим НДС”.»

## Замечание 4. Builder «вся сумма необлагаемая» + U4: риск принять stub-ноль за доказанный состав и не поймать unknown→DEFAULT

**Вывод 08.**  
D10/S5: builder по умолчанию создаёт необлагаемые документы и нулевой VAT; «не менять все нулевые документы на 5/105: валидный нулевой состав остаётся нулём».

**Доказательство.**  
`tests/golden/build_golden.py` `doc()`: если агрегаты не заданы, пишет `СуммаНеоблагаемаяКоп = СуммаКоп`, облагаемая/НДС = 0. Это формально **валидный нулевой** состав по U4, не тройка нулей при ненулевой сумме (неизвестный). Почти все matching-golden 2026 (например `advance_then_later_payment`) несут такой «доказанный exempt». Отдельного golden на «три нуля / расхождение → DEFAULT_5_105 + диагностика» в исполняемом CASES нет.

**Почему неполно.**  
Фраза «валидный ноль остаётся нулём» верна, но без явного запрета считать текущие matching-фикстуры налоговым эталоном после U4: (а) DEFAULT_5_105 для 2026 без сильного источника не проверяется; (б) путь «неизвестный состав ≠ без НДС / ≠ VAT=0» не регрессируется; (в) зелёный прогон с `vat=0` после появления `tax.py` будет выглядеть как успех U4, оставаясь stub-логикой matching. 08 это намекает, но не формулирует как дефект приёмки сводного плана.

**Предлагаемая формулировка.**  
«Matching-golden с автоподстановкой “вся сумма необлагаемая” после U4 доказывают только связи, не налог. Налоговая приёмка обязана иметь отдельные фикстуры: (1) явно валидный exempt; (2) валидный смешанный; (3) три нуля / расхождение / утраченный признак отриц. НДС → не сильный источник, `DEFAULT_5_105` (если применим) + диагностика, не “без НДС”; (4) новый unresolved-долг без документа → 5/105; (5) старый unresolved → PRE_2026. Пока (3)–(5) нет в runner, зелёный matching не считать закрытием U4.»

# ТЗ №2. Python

## Анализ платежей, поиск оплачиваемых документов и формирование строк КУДиР

### 1. Назначение

Python-программа является основным аналитическим модулем.

Вход:

```text
payments.csv
ledger62.csv
documents.csv
```

Выход:

```text
kudir_result.csv
matches.csv
unresolved.csv
analysis.log
```

---

# 2. Ключевое требование: не писать существующий разбор заново

В проекте уже существует работающий механизм разбора назначения платежа, используемый `доходы-2`.

Он уже умеет определять:

```text
смысл платежа
тип упомянутого документа
номер документа
дату документа
номер счета
```

и на реальных данных находит существенную часть документов.

Этот механизм необходимо переиспользовать.

Приоритет:

```text
1. использовать существующий Python-модуль напрямую;
2. если сейчас он существует только как локальный HTTP-сервис —
   подключить тот же код как библиотеку или использовать сервис;
3. если часть логики существует только в 1С —
   перенести алгоритм максимально буквально и покрыть regression-тестами;
4. только после этого добавлять новые правила.
```

Не создавать новый независимый parser с нуля.

# 4. Этапы обработки платежа

Для каждого платежа применять следующую последовательность:

```text
1. восстановить состояние взаиморасчётов;
2. определить сумму погашения долга и аванса;
3. попробовать найти прямое указание на документ;
4. попробовать цепочку через счет;
5. проверить точное совпадение суммы;
6. только если однозначного ответа нет —
   запустить стандартный эвристический matching;
7. при необходимости использовать semantic reranker.
```

---

# 5. Разделение на долг и аванс

Это чистая бухгалтерская арифметика.

Пример:

```text
долг перед платежом = 7 000
платеж = 10 000
```

Результат:

```text
debt_part = 7 000
advance_part = 3 000
```

Никакая LLM этого не определяет.

---

# 6. Первый и самый сильный путь: прямое указание документа

Сначала существующим parser'ом анализируются:

```text
СодержаниеПроводки
Содержание
ПредставлениеПроводки
НазначениеПлатежа
ПервичныйДокумент
КомментарийДокументаОплаты
```

Parser может обнаружить, например:

```text
НАКЛАДНАЯ № Н00570 от 30.06.2026
```

или:

```text
АКТ №25 от 10.08.2026
```

---

# 7. Прямой документ + совпадение суммы

Если найден конкретный документ задолженности:

```text
тип
номер
дата
контрагент
```

и:

```text
debt_part = текущий непогашенный остаток документа
```

либо:

```text
debt_part = полная сумма документа
```

при отсутствии предыдущих оплат,

такой документ принимать сразу.

Тип:

```text
DIRECT_DOCUMENT_EXACT
```

Уверенность:

```text
HIGH
```

Стандартный общий matching в этом случае не нужен.

---

# 8. Прямой документ, но сумма НЕ совпала

Если платеж указывает на конкретную накладную/акт, но сумма не совпадает:

```text
НЕ фиксировать соответствие автоматически.
```

Запустить обычный цикл matching.

При этом найденный документ получает большой бонус как кандидат:

```text
DIRECT_DOCUMENT_HINT
```

Например:

```text
+100 к score
```

но остаётся возможность установить другое распределение.

---

# 9. Второй основной путь: оплата по счету

На практике значительная доля платежей содержит именно:

```text
Оплата по счету ...
```

При этом документ задолженности — не счет, а:

```text
Отгрузка товаров
```

или:

```text
Оказание услуг
```

Поэтому необходимо построить цепочку:

```text
Платеж
→ Счет на оплату
→ документ, введенный на основании счета
→ задолженность
```

---

# 10. Поиск счета

Использовать существующий рабочий parser.

Например:

```text
Оплата по счету №00002
```

даёт:

```text
Тип = СЧЕТ
Номер = 00002
```

Если известна дата:

```text
Дата = ...
```

также использовать её.

Затем найти счет в `documents.csv` по:

```text
Контрагент
Номер
Дата — если известна
```

---

# 11. Связь Счет → Отгрузка / Оказание услуг

После нахождения счета найти документы:

```text
Отгрузка товаров
Оказание услуг
```

в комментарии которых имеется стандартизированная ссылка:

```text
Введен на основании: Счет на оплату № 00002 от 06 Января 2026 г.
```

Так как комментарий формируется программой, эта связь считается очень сильной.

Внутренний тип связи:

```text
BASE_DOCUMENT_LINK
```

---

# 12. Нормализация ссылки «Введен на основании»

Не сравнивать строку целиком посимвольно.

Разобрать её в структуру:

```text
base_type
base_number
base_date
```

Например:

```text
base_type = INVOICE
base_number = 00002
base_date = 2026-01-06
```

Поддержать лишние пробелы и различные регистры.

---

# 13. Счет → один документ → совпала сумма

Если:

```text
оплата → счет №00002
```

и найден:

```text
Оказание услуг №...
Комментарий:
Введен на основании: Счет на оплату №00002 ...
```

и:

```text
debt_part = остаток документа
```

то соответствие фиксируется сразу.

Тип:

```text
INVOICE_BASE_EXACT
```

Уверенность:

```text
HIGH
```

---

# 14. Счет → несколько документов

Один счет теоретически может стать основанием нескольких документов.

Тогда:

```text
не выбирать первый найденный.
```

Проверить:

1. точное совпадение одной суммы;
2. точное совпадение с остатком;
3. сумму нескольких связанных документов;
4. другие признаки.

Если однозначности нет — перейти к стандартному matching.

Но документы, связанные с найденным счетом, получают очень высокий score.

---

# 15. Счет найден, но сумма не совпала

Если найден счет и найден связанный документ, но:

```text
сумма платежа != сумма/остаток документа
```

не привязывать платеж насильно.

Запустить стандартный алгоритм.

Связь через счет используется как сильная подсказка, а не как абсолютное решение.

---

# 16. ПКО: отдельный быстрый путь

Для `PaymentKind=CASH` прежде всего анализировать:

```text
КомментарийДокументаОплаты
```

Частый вариант:

```text
Введен на основании:
Отгрузка товаров № Н00570 от 30 Июня 2026 г.
```

Это практически прямая машинная ссылка на документ.

---

# 17. ПКО + точная сумма

Если из комментария ПКО найден документ:

```text
Отгрузка товаров №Н00570
```

и:

```text
сумма ПКО = остаток задолженности по Н00570
```

фиксировать сразу:

```text
CASH_BASE_EXACT
HIGH
```

---

# 18. ПКО + несовпадающая сумма

Если ссылка в ПКО есть, но сумма не совпадает:

```text
не делать безусловную привязку.
```

Документ становится кандидатом с большим бонусом, после чего работает стандартный matcher.

---

# 19. Стандартный matching

Он запускается только после прямых путей.

Кандидаты должны соответствовать:

```text
тот же контрагент
документ существовал на момент оплаты
имеется непогашенный остаток
```

---

# 20. Другой контрагент — жёсткий запрет

```text
Контрагент оплаты != Контрагент документа
```

→ кандидат запрещён.

Это hard constraint.

---

# 21. Будущий документ — жёсткий запрет

Обычный платеж не может оплачивать документ, который ещё не существовал.

Использовать:

```text
Дата
ПозицияДокумента
```

Это hard constraint.

Ранее полученный аванс — отдельная ситуация и не является оплатой будущего документа на дату получения.

---

# 22. Договор НЕ является hard constraint

Это важное изменение.

Несовпадение договора:

```text
НЕ должно исключать документ.
```

Совпадающий договор:

```text
сильный плюс.
```

Разный договор:

```text
штраф,
но не запрет.
```

Например:

```text
same contract       +40
different contract  -20
unknown contract      0
```

Конкретные веса вынести в настройки.

---

# 23. Почему разный договор допускается

В реальной базе возможны:

* неверно выбранный договор в платежной строке;
* разные технические договоры;
* исторические изменения;
* ошибки пользователя;
* отличия договора оплаты от договора документа.

Поэтому если имеются сильные признаки:

```text
прямая ссылка на счет
+
ссылка "Введен на основании"
+
точная сумма
```

они имеют право перебить несовпадение договора.

При этом в `reason` необходимо отметить:

```text
CROSS_CONTRACT_MATCH
```

---

# 24. Какой договор возвращать

Если платеж сопоставлен с конкретным документом задолженности:

```text
Договор в строке DEBT
=
договор найденного документа задолженности
```

Не надо искусственно считать разные договоры одинаковыми.

Для `ADVANCE`:

```text
Договор
=
договор платежа
```

---

# 25. Приоритеты стандартного matching

Рекомендуемый порядок:

```text
1. прямой документ + точная сумма
2. счет → документ + точная сумма
3. ПКО → основание + точная сумма
4. точное совпадение остатка документа
5. точное совпадение полной суммы документа
6. несколько оплат = документ
7. одна оплата = несколько документов
8. закрытие остатка после предыдущей частичной оплаты
9. связь через счет/основание без точной суммы
10. договор
11. вид расчетов
12. товар/услуга
13. текстовая семантика
14. обратная хронология
```

---

# 26. Точные совпадения суммы

Сильными считать оба случая:

```text
платеж = первоначальная сумма документа
```

и:

```text
платеж = текущий остаток документа
```

Второй случай даже важнее для частично оплаченного документа.

---

# 27. Несколько оплат → один документ

Пример:

```text
Документ = 5 500

Оплата 1 = 4 500
Оплата 2 = 1 000
```

Получить:

```text
4 500 + 1 000 → 5 500
```

---

# 28. Одна оплата → несколько документов

Пример:

```text
Документы:
4 000
6 000

Платеж:
10 000
```

Получить две связи.

---

# 29. Очень важный случай закрытия остатка

Если:

```text
документ = 5 500
```

уже подобрана оплата:

```text
4 500
```

и имеется:

```text
1 000
```

то:

```text
1 000 = остаток документа
```

является сильным match.

---

# 30. Нельзя использовать простой FIFO

FIFO используется только как крайний fallback.

Например:

```text
документ A = 5 500
документ B = 27 200

оплаты:
4 500
27 200
1 000
```

правильно:

```text
27 200 → B
4 500 + 1 000 → A
```

а не механическое списание по хронологии.

---

# 31. Обратная хронология

При равных остальных признаках предпочтителен ближайший предшествующий документ.

Например:

```text
01.01 документ 10 000
05.01 документ 10 000
06.01 оплата 10 000
```

при отсутствии других различий:

```text
→ документ 05.01
```

---

# 32. Scoring

Пример:

```text
+200 прямая ссылка на конкретный документ
     + совпал остаток

+180 счет → документ по "Введен на основании"
     + совпала сумма

+170 ПКО → документ по "Введен на основании"
     + совпала сумма

+120 точное совпадение остатка

+100 точное совпадение полной суммы

+90  точная комбинация сумм

+70  прямая ссылка на документ, но сумма отличается

+60  связь через тот же счет

+40  тот же договор

-20  другой договор

+35  тот же вид расчетов

+30  товар ↔ товар / услуга ↔ услуга

+0..25 semantic score

+0..20 обратная хронология
```

Hard penalties:

```text
другой контрагент    → запрет
будущий документ     → запрет
```

---

# 33. Парсер и эвристический matcher — разные компоненты

Не смешивать:

```text
"извлечь из текста счет №123"
```

и:

```text
"решить, какой документ фактически оплачивается"
```

Первое выполняет parser.

Второе выполняет matcher.

Это позволит использовать уже существующий parser без переписывания всей системы.

---

# 34. Hugging Face

Используется только после обычных признаков.

Рекомендуемый порядок:

```text
точные ссылки
→ суммы
→ связи оснований
→ договор/вид расчетов
→ обычный scoring
→ только затем semantic reranker
```

Модель не нужна для:

```text
"Введен на основании: Счет №123"
```

или:

```text
платеж 27 200
документ 27 200
тот же счет
```

---

# 35. Когда использовать модель

Например осталось:

```text
три старых документа
нет номера счета
нет прямой ссылки
нет точной суммы
договоры не помогают
```

Тогда можно сравнивать тексты:

```text
payment_text
document_text
```

через multilingual reranker.

---

# 36. Восстановление взаиморасчётов

Использовать `ledger62.csv` с начала исторического периода.

По умолчанию:

```text
01.10 предыдущего года
```

Состояние рассчитывается последовательно.

---

# 37. Недостаточная историческая глубина

Если на дату начала истории:

```text
01.10 предыдущего года
```

у клиента уже существует ненулевой остаток, который невозможно объяснить выгруженными движениями, программа должна это диагностировать.

В перспективе 1С может дополнительно передавать начальное сальдо на `ИсторияНач`.

Рекомендуется добавить в экспорт:

```text
opening_balances.csv
```

либо поля начального сальдо по клиенту/аналитике.

Это позволит не выгружать всю историю базы и при этом точно восстановить состояние.

---

# 38. Рекомендуемое дополнение: opening_balances.csv

Чтобы ограничение истории октябрём было математически корректным, 1С желательно передавать начальное сальдо по 62 непосредственно перед:

```text
ИсторияНач
```

Минимально:

```text
КонтрагентID
Счет62
ДоговорID
ВидРасчетов
ОстатокДтКоп
ОстатокКтКоп
```

Тогда:

```text
начальное сальдо
+
движения с 01.10
=
точное состояние на дату каждого платежа
```

Это предпочтительнее, чем просто «отрезать» старую историю.

---

# 39. DEBT_UNRESOLVED

Если точно известно:

```text
платеж погашает долг
```

но конкретный документ надёжно определить невозможно:

```text
не превращать сумму в аванс.
```

Результат:

```text
DEBT_UNRESOLVED
```

---

# 40. Формирование строк результата

Типы:

```text
DEBT
ADVANCE
DEBT_UNRESOLVED
```

Одна исходная оплата может дать любое количество строк.

---

# 41. СуммаПлатежа

В результирующей строке:

```text
СуммаПлатежа
=
сумма конкретной части
```

Не полная сумма исходного банковского документа.

---

# 42. СуммаВАванс / СуммаВОпалату

Для `ADVANCE`:

```text
СуммаВАванс = сумма
СуммаВОпалату = 0
```

Для `DEBT` и `DEBT_UNRESOLVED`:

```text
СуммаВАванс = 0
СуммаВОпалату = сумма
```

---

# 43. СуммаВДоход

Пока:

```text
СуммаВДоход = СуммаПлатежа
```

---

# 44. НДС

Пока:

```text
СуммаСНДС = 0
СуммаНДС = 0
```

---

# 45. СодержаниеЗаписи

Если найден документ услуг:

```text
Оплата от ООО «Ромашка» за услуги по акту №25 от 10.08.2026
```

Если найдена отгрузка:

```text
Оплата от ООО «Ромашка» за товар по накладной №Н00570 от 30.06.2026
```

Если известен только долг:

```text
Оплата задолженности от ООО «Ромашка» по договору №15
```

Аванс:

```text
Получен аванс от ООО «Ромашка» по договору №15
```

Не выдумывать отсутствующие реквизиты.

---

# 46. matches.csv

Для каждой связи сохранять:

```text
payment_id
document_id

matched_amount_kopecks

match_type
score
confidence

direct_reference_score
invoice_link_score
amount_score
contract_score
calculation_type_score
semantic_score
chronology_score

reason
```

Например:

```text
INVOICE_BASE_EXACT+EXACT_REMAINDER+CROSS_CONTRACT_MATCH
```

# 47. Regression-тесты существующего parser

Обязательно сформировать тестовый набор из реальных строк `доходы-2`.

Например:

```text
Оплата по документу Счет ...
Оплата по счету ...
Оплата по сч ...
Оплата по акту ...
```

# 48. Новые тесты

### Тест: прямой акт

```text
платеж содержит акт №25
акт = 5 500
платеж = 5 500
```

→ `DIRECT_DOCUMENT_EXACT`.

### Тест: акт указан, сумма отличается

```text
акт = 5 500
платеж = 4 500
```

→ обычный matching, акт получает сильный bonus.

### Тест: через счет

```text
платеж:
Оплата по счету №00002

Оказание услуг №00005

Введен на основании: Счет на оплату №00002 ...

```

→ `INVOICE_BASE_EXACT`.

### Тест: ПКО

```text
ПКО:
Комментарий:
Введен на основании: Отгрузка товаров №Н00570 ...

сумма совпадает
```

→ `CASH_BASE_EXACT`.

### Тест: разные договоры


→ 10 000.

# 49. Критерии готовности Python

1. Не переписан без необходимости существующий parser.
2. Существующий parser покрыт regression-тестами.
3. Поддерживается прямое указание акта/накладной.
4. Поддерживается оплата по счету.
5. Поддерживается цепочка `Оплата → Счет → Реализация`.
6. Парсятся стандартизированные комментарии `Введен на основании`.
7. Поддерживается ПКО.
8. Для прямой ссылки точное совпадение суммы даёт немедленный HIGH match.
9. При несовпадении суммы запускается стандартный matcher.
10. Разный договор не является hard reject.
11. Другой контрагент является hard reject.
12. Будущий документ является hard reject.
13. Поддерживаются комбинации оплат.
14. Поддерживаются комбинации документов.
15. FIFO используется только как fallback.
16. ML является опциональным.
17. Формируется `kudir_result.csv`.
18. Формируется `matches.csv`.
19. Поддерживается `DEBT_UNRESOLVED`.
20. Контролируется сумма каждой исходной оплаты.
21. История по умолчанию начинается с 01.10 предыдущего года.
22. Поддерживается начальное сальдо на границу исторического периода.

# 4. Периоды

Параметры:

```text
ДатаНач
ДатаКон
МесяцевИстории = 3
```

Целевые платежи (`is_target=1`) выбираются:

```text
ДатаНач ... ДатаКон
```

Оплаты, движения 62, документы и начальное сальдо выгружаются начиная с `ИсторияНач`, не с `ДатаНач`. В `payments.csv` исторические оплаты имеют `is_target=0`.

Начало исторического периода задаётся только так:

```text
ИсторияНач = ДобавитьМесяц(НачалоГода(ДатаНач), -МесяцевИстории)
```

Не вычитать месяцы из произвольной `ДатаНач`. По умолчанию `МесяцевИстории = 3`, для КУДиР 2026 это `01.10.2025`. Параметр изменяемый: при `6` получится `01.07.2025`. Формулировка архитектуры «1 октября предыдущего года» — только значение по умолчанию, не вторая формула.

# 5. payments.csv

Целевые платежи КУДиР (`is_target=1`) — только:

Исторические оплаты (`is_target=0`) нужны Python, чтобы восстановить документные остатки. Без них нельзя закрыть, например, январскую доплату 1 000 после декабрьских 4 500.

В том числе:

* поступление на расчётный счёт;
* наличная оплата;
* иные используемые денежные счета.

# 6. Выписка и ПКО обрабатываются по-разному

Не смешивать разные номера:

```text
ПозицияДокумента          — момент времени документа в журнале
НомерПроводкиВДокументе   — Опер.НомерПроводки()
НомерСтрокиВДокументе     — Опер.НомерСтрокиДокумента()
```

## Ограничение этой конфигурации

При проведении документов **не включено** `ПривязыватьСтроку`. Поэтому:

```text
Опер.НомерСтрокиДокумента() = 0
```

всегда, и для выписки, и для ПКО. Это не сбой метода и не повод искать строку по сумме. Поле `НомерСтрокиВДокументе` в CSV оставляем пустым. Как идентификатор оплаты и как связь «проводка → строка выписки» его **не использовать**.

Очередь неиспользованных строк табличной части не строить. Отдельное поле `event_seq` не вводится.

Критичность: без номера строки нельзя отличить платежи внутри одной выписки по табличной части. Это **критично** для matching. Замена, которая в этой базе работает: `Опер.НомерПроводки()`.

Остаточный риск: если одна экономическая строка выписки проводится несколькими **разными** номерами проводок (не несколькими корреспонденциями одной проводки), они станут разными `payment_id`. Несколько корреспонденций **одной** проводки имеют один `НомерПроводки()` и остаются одной оплатой.

## Банковская выписка

Один документ `Выписка` может содержать несколько самостоятельных платежей. Единица оплаты — проводка:

```1c
НомерПроводкиВДокументе = Опер.НомерПроводки();
НомерСтрокиВДокументе   = "";   // всегда: ПривязыватьСтроку выключен
```

Пример из прототипа: выписка 0001, проводка 2 — МЫЛОВА 1 000, проводка 4 — РЯБОВА 1 950. Это две оплаты, два `payment_id`.

## Приходный кассовый ордер

Для ПКО весь документ является одной оплатой.

```1c
НомерСтрокиВДокументе = "";
НомерПроводкиВДокументе = Опер.НомерПроводки();
```

Не подставлять `0` вместо пустого номера строки: `0` — это число, пустое поле — отсутствие строки.

# 7. payment_id и связь с проводкой

`payment_id` — идентификатор самостоятельной оплаты, не проводки.

Для выписки:

```text
BANK|<вид>|<номер>|<дата>|<НомерПроводки>
```

например `BANK|Выписка|0001|2026-01-06|2`.

Для ПКО:

```text
CASH|<вид>|<номер>|<дата>
```

Один и тот же `payment_id` записывается:

- в **одну** строку `payments.csv`;
- во **все** кредитовые корреспонденции 62 этой же проводки в `ledger62.csv`.

Несколько корреспонденций с **одинаковым** `НомерПроводки()` внутри одного документа — одна оплата, разные `ledger_event_id`. Разные `НомерПроводки()` — разные оплаты, даже если это одна выписка. Из нескольких видов расчётов **не следует** автоматически, что оплачены разные документы: это решает matcher.

Нельзя группировать оплаты выписки по пустому `НомерСтрокиДокумента()`.

Для проводок реализации, корректировок и прочих движений 62 поле `payment_id` в `ledger62.csv` пустое.

Проводка оплаты применяется к состоянию взаиморасчётов **только** из `ledger62.csv`. Строка `payments.csv` не является вторым движением денег: это расширенное описание того же события (тексты, `is_target`, связь с выпиской). Нельзя исключать оплаты из `ledger62.csv` как дубли. Нельзя вычитать сумму ещё раз из `payments.csv`.

`СуммаКоп` в `payments.csv` равна сумме связанных проводок этой оплаты.

Уникальность строки `ledger62.csv` даёт `ledger_event_id`:

```text
source_document_id + НомерПроводки() + порядковый номер корреспонденции при обходе
```

`НомерПроводки()` не учитывает корреспонденции, поэтому для уникальности **строки ledger** его мало: нужен ещё порядковый номер корреспонденции при обходе. Для уникальности **оплаты выписки** `НомерПроводки()` достаточен.

```text
НомерПроводкиВДокументе
```

Пустое значение при сортировке меньше любого номера. `НомерСтрокиВДокументе` в сортировку не входит: в этой конфигурации он всегда пуст.

# 23. Экспортируемая история

История ограничена формулой раздела 4:

```text
ИсторияНач = ДобавитьМесяц(НачалоГода(ДатаНач), -МесяцевИстории)
```

Например:

```text
КУДиР 2026
→ история с 01.10.2025
```

Нет необходимости выгружать всю историю клиента с момента создания базы. Snapshot документных остатков между запусками в версии 1 не строится.

Если долг возник раньше `ИсторияНач` и документ в выгрузку не попал, Python сформирует `DEBT_UNRESOLVED`. При необходимости глубину увеличивают параметром `МесяцевИстории`.

# 23.1. opening_balances.csv — обязательно

Файл обязателен. Если его нет, Python завершает работу с ошибкой и не считает остатки с нуля.

Сальдо на момент непосредственно перед `ИсторияНач` по аналитике 62 для тех же клиентов, что попали в выгрузку.

Порядок колонок:

```text
КонтрагентID
Счет62
ДоговорID
ВидРасчетовID
ВидРасчетов
ДатаСальдо
ОстатокДтКоп
ОстатокКтКоп
```

`ДатаСальдо` = `ИсторияНач`. Суммы — целые копейки, **оба** остатка обязательны. Python не имеет права отбрасывать один из них по правилу «если есть кредит — вернуть кредит». Если аналитика пуста, поле пустое, не `0` и не `NULL`.

Это суммарное сальдо по клиенту/договору/виду расчётов, а не список неоплаченных документов. Конкретный старый акт вне истории не восстанавливается.

# 23.2. manifest.csv

Один файл на выгрузку. Порядок колонок:

```text
key;value
run_id;KUDIR_2026_20260903_001
schema_version;1
encoding;windows-1251
history_start;YYYY-MM-DD
date_start;YYYY-MM-DD
date_end;YYYY-MM-DD
```

`run_id` — идентификатор этого запуска выгрузки. Во все пять входных файлов его дублировать не нужно. Python копирует `run_id` в `kudir_result.csv`, чтобы не смешать файлы разных запусков и не загрузить в 1С чужой результат.

# 25. Разбиение платежа

Одна исходная оплата может породить несколько строк.

Например:

```text
10 000 поступило
7 000 погашает задолженность
3 000 является авансом
```

Результат:

```text
строка 1:
СуммаПлатежа = 7000
СуммаВОпалату = 7000

строка 2:
СуммаПлатежа = 3000
СуммаВАванс = 3000
```

---

# 26. СуммаВДоход (версия 1)

Версия 1 не формирует налоговый доход УСН. Заглушка matching:

```text
СуммаВДоход = СуммаПлатежа
income_kopecks = amount_kopecks
```

Одновременно `СуммаВАванс` и `СуммаВОпалату` ненулевыми быть не могут.

Результат нельзя считать готовой КУДиР.

# 29. Критерии готовности части 1С

1. Не перенесён как эталон запрещённый старый код FIFO, обрезки номера и поиска строки выписки по сумме.
2. Формируется `manifest.csv` с `run_id` и обязательный `opening_balances.csv`.
3. Формируется `payments.csv` со всеми оплатами истории и `is_target`.
4. Для выписки `payment_id` включает `Опер.НомерПроводки()`. `НомерСтрокиДокумента()` не используется как ключ.
5. Поддерживаются ПКО.
6. Формируется `ledger62.csv` с `ledger_event_id`, `source_document_id` и `payment_id` у оплат.
7. Формируется `documents.csv` с ролью, видом расчётов и датой договора.
8. Выгружаются все счета анализируемых клиентов.
9. Выгружаются отгрузки и оказания услуг.
10. Выгружается `Комментарий` и `ПервичныйДокумент`.
11. Аналитика берётся со стороны счета 62.
12. История начинается по умолчанию с 1 октября предыдущего года.
13. 1С не выполняет эвристический matching.
14. Загружается `kudir_result.csv` по ID через таблицу соответствия.
15. Формируется существующая `СформироватьТаблицуДоходовЧистовая()`.
16. CSV соответствует протоколу раздела 30.

# 30. CSV-протокол

Все файлы обмена:

- кодировка Windows-1251;
- разделитель `;`;
- первая строка — заголовок с точными именами колонок из этого ТЗ, в указанном порядке;
- даты строго `YYYY-MM-DD`;
- деньги — целые копейки;
- перенос строки внутри поля разрешён только если поле заключено в `"..."`;
- кавычка внутри поля удваивается (`"` → `""`);
- поле с разделителем или переносом всегда в кавычках;
- пустое значение — пустая строка между разделителями, не `"NULL"`, не `0`, не пробел как замена пустоты;
- `schema_version=1` задаётся в `manifest.csv`.

Примеры комментариев уже многострочные — протокол обязателен с первой выгрузки.

# 6. Выписка и кассовые ордера обрабатываются по-разному

Не смешивать разные номера:

```text
ПозицияДокумента          — точная позиция документа на шкале времени 1С
НомерПроводкиВДокументе   — Опер.НомерПроводки()
НомерСтрокиВДокументе     — Опер.НомерСтрокиДокумента()
```

## Ограничение этой конфигурации

При проведении документов **не включено** `ПривязыватьСтроку`. Поэтому:

```text
Опер.НомерСтрокиДокумента() = 0
```

всегда, и для выписки, и для ПКО. Это не сбой метода и не повод искать строку по сумме. Поле `НомерСтрокиВДокументе` в CSV оставляем пустым. Как идентификатор оплаты и как связь «проводка → строка выписки» его **не использовать**.

Очередь неиспользованных строк табличной части не строить. Отдельное поле `event_seq` не вводится.

Критичность: без номера строки нельзя отличить платежи внутри одной выписки по табличной части. Это **критично** для matching. Замена, которая в этой базе работает: `Опер.НомерПроводки()`.

Остаточный риск: если одна экономическая строка выписки проводится несколькими **разными** номерами проводок (не несколькими корреспонденциями одной проводки), они станут разными `payment_id`. Несколько корреспонденций **одной** проводки имеют один `НомерПроводки()` и остаются одной оплатой.

## Банковская выписка

Один документ `Выписка` может содержать несколько самостоятельных платежей. Единица оплаты — проводка:

```1c
НомерПроводкиВДокументе = Опер.НомерПроводки();
НомерСтрокиВДокументе   = "";   // всегда: ПривязыватьСтроку выключен
```

Пример из прототипа: выписка 0001, проводка 2 — МЫЛОВА 1 000, проводка 4 — РЯБОВА 1 950. Это две оплаты, два `payment_id`.

## Приходный кассовый ордер

Для ПКО весь документ является одним поступлением. Для расходного кассового ордера с Дт 62 Кт 50 весь документ является одним возвратом; фактический идентификатор вида определяется по метаданным базы, не по выдуманному имени. Он получает PaymentKind=CASH, PaymentGranularity=DOCUMENT и PAYMENT-ссылку на сам расходный документ.

Следующий прежний пример чтения относится к отдельной проводке ledger. Полученный номер не переносится в номер агрегированной CASH-оплаты и не дополняет её ID.

```1c
НомерСтрокиВДокументе = "";
НомерПроводкиВДокументе = Опер.НомерПроводки();
```

Вид оплаты определяется **точным идентификатором** вида документа этой конфигурации. Обе стороны сравнения нормализуются одинаково (`Врег(ВидДок)` сравнивается с `Врег("…")` либо проверяется равенство идентификатору метаданных). Запрещено искать смешанный регистр (`"ПриходныйОрдер"`) внутри уже преобразованной к верхнему регистру строки: такая ветка не срабатывает. Фактическое имя вида зафиксировать по метаданным базы (часто `ПКО` или `ПриходныйОрдер` / `ПриходныйКассовыйОрдер`); подстрока `ПРИХОДН` после `Врег` допустима только если не даёт ложных срабатываний на другие виды.

Не подставлять `0` вместо пустого номера строки: `0` — это число, пустое поле — отсутствие строки.

# 7. Идентификаторы по типам сущностей

ID не строится из вида + номера + даты: это не гарантирует уникальности. Основа — техническая позиция документа `ПолучитьПозицию()`.

| Сущность | Формат ID |
| --- | --- |
| Документ (счёт, отгрузка, оказание услуг) | `DOC\|{ПозицияДокумента}` |
| Банковская оплата | `BANK\|{ПозицияДокумента}\|{НомерПроводки}`. Позиции выписки недостаточно: две проводки одной выписки иначе сольются |
| ПКО / расходный кассовый документ возврата | `CASH\|{ПозицияДокумента}`. Один документ = одно денежное событие; позиции документов уникальны |
| Оплата из ручной «Операции» | `MANUAL\|{ПозицияДокумента}\|{НомерПроводки}`; номера строки банковской выписки нет |
| Строка ledger | `LED\|{ПозицияДокумента}\|{НомерПроводки}\|{N корреспонденции при обходе}` |

`payment_id` — идентификатор самостоятельной оплаты, не проводки и не строки табличной части.

Один и тот же `payment_id` связывает все подтверждённые движения одной хозяйственной оплаты в ledger. В Python формируется одна оплата с этим ID, а в `id_map.csv` сохраняется PAYMENT для восстановления документа. Отдельной строки payments.csv в новом входе нет.

ПКО получает `CASH|{ПозицияДокумента}` без номера проводки. Все его движения сохраняют собственные номера и `ledger_event_id`; отсутствующий номер проводки агрегированной оплаты не дополняется из ledger. Несколько проводок ПКО не становятся несколькими оплатами.

Банк получает `BANK|{ПозицияДокумента}|{НомерПроводки}`, ручная «Операция» — `MANUAL|{ПозицияДокумента}|{НомерПроводки}`. Вид «Операции» определяется по фактическим метаданным конфигурации. Классификация «ПКО → CASH, всё остальное → BANK» запрещена. MANUAL не имеет номера строки выписки. Разные номера банковских/ручных проводок различают события, но не отменяют проверки действующей хозяйственной принадлежности движений; совпадения суммы/даты или пустого номера строки недостаточно для объединения.

Неденежные движения не получают фиктивный payment_id. Подтверждённая связь технического сторно с оплатой не теряется из-за знака; неопределённость обозначается диагностикой. Каждое движение применяется к расчётам один раз по ledger_event_id. Формирование объекта оплаты не создаёт второго движения. Денежная сумма определяется по роли и знаку связанных движений, а не суммой всех строк с одним payment_id (§31.2).
`НомерПроводки()` не учитывает корреспонденции, поэтому для уникальности **строки ledger** его мало: нужен ещё порядковый номер корреспонденции при обходе. Для уникальности **оплаты выписки** позиция + `НомерПроводки()` достаточны.

На выгрузке проверяется уникальность всех технических ID. Для `PAYMENT`, `DOCUMENT`, `CONTRACT`, которые записываются в `id_map.csv`, дополнительно проверяется однозначность `entity_type + id` → ровно одна системная строка `ЗначениеВСтрокуВнутр()` / ровно один объект 1С. Коллизия на две разные системные строки = `FAILED`. Для `ledger_event_id` проверяется только уникальность строки `ledger62.csv`: `LEDGER` в `id_map.csv` не записывается и объект по нему после Python не восстанавливается. Один документ выписки может соответствовать нескольким `PAYMENT` ID — это допустимо. Подробности `id_map.csv` — раздел 23.3.

## 12.1. Подписанные движения, денежные возвраты и граница версии 1

Выгружать все движения 62, включая сторно и зачёты, с исходными целыми копейками со знаком. Денежные возвраты включены в нормативный объём версии 1 по новому решению владельца; старое правило «все возвраты только в диагностике» отменено.

- Положительное поступление Дт 50/51/55 → Кт 62: строки ledger, из которых формируется оплата Python, Сторона62=K.
- Возврат покупателю Дт 62 → Кт 50/51/55: также ledger и формируемое из него событие возврата Python, Сторона62=D, аналитика с дебета 62, исходная сумма положительна. Учитывать используемые субсчета. Касса — расходный кассовый документ, банк — соответствующая проводка выписки. Дата/позиция/номер/ссылки — самого возврата, а не первоначального поступления. Идентификаторы и id_map PAYMENT строятся по §6–7; возврат не искать обратно по номеру/сумме.
- Техническое отрицательное сторно корреспонденции поступления не признавать обычным положительным денежным возвратом автоматически. Сохранить исходный знак и подтверждённую связь с хозяйственной оплатой; диагностировать неподдерживаемую классификацию по 02 §36.1 без остановки расчёта остальных операций.
- Эквайринговые комиссии и прочие неподдерживаемые схемы не становятся возвратом по одному знаку суммы. Неденежные движения — ledger без фиктивной оплаты. Нулевая оплата сохраняется во входах/диагностике без доходной строки.

Python применяет каждое движение ledger ровно один раз независимо от налогового отображения. Для RETURN действует окончательный U5 (02 §36.1): явная однозначная ссылка на отгрузку/услуги в комментарии → налог из этого документа без эвристического document matching; отсутствие такой ссылки → исходная оплата, полная допустимая пара исключается, частичный/иной неполный возврат даёт отрицательную строку из состава оплаты. Исключение полной пары требует одного календарного квартала одного года. Полный возврат в другом квартале даёт новую отрицательную RETURN из состава исходной оплаты на дату возврата; исходный квартал не пересчитывается и оплата из него не удаляется. В новом формате попадание в целевой вывод определяет Python по дате операции и параметрам запуска; is_target во входе отсутствует. Возврат по явному документу не исключается как полная излишняя оплата даже при совпадении сумм.

Экспортировать полный `КомментарийДокумента` самого возврата без обрезки и без замены комментарием исходной оплаты. Это существующее поле ledger; отдельного payments.csv в новом формате нет. `source_document_id` в ledger по-прежнему означает документ, породивший проводку, а не налоговый документ U5.1. 1С не разрешает текстовую ссылку, не ищет реализацию и не решает ветвь U5; это Python. Если явно указанный документ вне выгруженных фактов, сохранить комментарий и диагностику недоступного источника без фиктивного DOCUMENT и без второго цикла выгрузки.

3. Если реквизит пуст и документ проведён — определить виды расчётов по проводкам 62 этого документа (`НайтиОперацию` + аналитика со стороны 62).
4. Если в проводках найден ровно один вид расчётов — записать его.
5. Если в проводках найдено несколько разных видов расчётов — `ВидРасчетовID` и `ВидРасчетовСПокупателем` документа оставить пустыми и записать диагностическое сообщение. Это **не `FAILED`**: точная детализация остаётся в отдельных строках `ledger62.csv`.
6. Если у проведённого `RECEIVABLE` вид расчётов не найден ни в `ВидыРасчетовСПокупателями`, ни хотя бы в одной проводке 62 — `FAILED`.

В данной конкретной конфигурации любая проведённая реализация обязана иметь вид расчётов либо в реквизите `ВидыРасчетовСПокупателями`, либо хотя бы в одной проводке 62. Отсутствие вида расчётов в обоих источниках означает повреждение / аномалию учёта и является основанием для `FAILED`.

Отдельно:

```text
несколько разных видов расчётов в проводках 62
    → допустимо, ВидРасчетовID документа пустой

ни одного вида расчётов
    → FAILED
```

Для `Счет` (`INVOICE`) реквизита `ВидыРасчетовСПокупателями` **нет вообще**. Поэтому 1С не пытается читать этот реквизит, не ищет альтернативные имена и не пытается определять вид расчётов счёта по проводкам 62. Для счёта штатно: `ВидРасчетовID = ""`, `ВидРасчетовСПокупателем = ""`; это не диагностика и не `FAILED`. Счёт используется как `INVOICE` для связи `оплата → счёт → реализация`, matching и запасного источника состава НДС. Его `ВидРасчетовID` для этих задач не обязателен.

Поля НДС обязательны для `INVOICE` и `RECEIVABLE`. Они считаются в момент обхода документа и сразу пишутся в ту же строку `documents.csv`. Как считать — раздел 15.1.

Ошибки выгрузки не глотать: нет пустого `Попытка/Исключение`, нет подстановки `СуммаКоп=0` при отсутствии реквизита суммы, нет `Проведен=1` при сбое `Проведен()`. Отсутствующий вид документа (`Счет` vs фактическое имя) — сообщение, не пустая выборка без диагностики. Исчерпание `run_id` `001…999` — `FAILED`, не коллизия на `999`.

# 15.1. Агрегаты НДС из табличной части

Колонка табличной части называется `НДС`. Она есть у:


Пока документ ещё открыт:

```text

пока Док.ПолучитьСтроку() = 1:
    сумма_строки = Док.Сумма
    ндс_строки   = Док.НДС
    если ндс_строки > 0:
        СуммаОблагаемая += сумма_строки
        СуммаНДС        += ндс_строки
    иначе если ндс_строки = 0 или пусто:
        СуммаНеоблагаемая += сумма_строки
    иначе:
        // НДС < 0: не класть в необлагаемые
        неподдерживаемый случай версии 1 — см. ниже
забыть строки
если был отрицательный НДС: обнулить все три агрегата документа; записать диагностику
записать одну строку documents.csv
```

Отрицательный `НДС` строки табличной части не является «строкой без НДС». Это может быть сторно облагаемой операции. Версия 1 такой состав не утверждает: не складывать строку в необлагаемые; записать диагностику; агрегаты документа не считать валидным источником НДС (как при расхождении инварианта). Наличие таких строк в конкретной базе не предполагается, но контракт обязан их распознать. При любом отрицательном НДС строки ТЧ перед записью обнулить все три агрегата всего документа, включая ранее накопленные положительные суммы, и записать причину неизвестности в лог. В CSV v3 три нуля при ненулевой `СуммаКоп` — согласованный признак неизвестного состава; усечённые положительные агрегаты запрещены даже при случайном совпадении сумм. При нулевой сумме положительной расходуемой ёмкости нет. Это не разрешение считать отрицательное поступление обычным доходом (OD5).

Нельзя:

- копить строки табличной части в `ТаблицаЗначений`;
- выгружать отдельный `document_lines.csv`;
- второй раз открывать те же документы «за НДС»;
- подставлять `СуммаНДСКоп = СуммаОблагаемаяКоп * 5 / 105`, если колонка `НДС` прочиталась: истина — колонка, не пересчёт.

Если реквизита `НДС` у вида документа нет — `FAILED` с именем вида. Конфигурация обещает колонку у всех трёх видов.

Если табличная часть пуста, а `СуммаКоп` (итог `Сумма`) ненулевой — состав неизвестен: три агрегата = 0, в лог сообщение. Для положительного поступления Python помечает `VAT_COMPOSITION_UNKNOWN` и выбирает следующий допустимый источник/default по 02 §21.2. Для RETURN U5 неизвестный состав выбранного источника не заменяется default: применяется диагностика 02 §36.1.

Инвариант, если строки были:

```text
СуммаОблагаемаяКоп + СуммаНеоблагаемаяКоп = СуммаКоп
```

Расхождение — сообщение в лог выгрузки, строка документа всё равно пишется. Для положительного поступления Python отвергает агрегаты как налоговый источник и применяет порядок 02 §21.2, включая определённый fallback 5/105 с диагностикой. Для RETURN выбранный источник не подменяется, неизвестный налог диагностируется по 02 §36.1; готовность зависит от определённости итогового налога.

`СуммаКоп` по-прежнему `Док.Итог("Сумма")`, не сумма только облагаемых строк.

Приоритет «отгрузка / услуги важнее счёта» 1С не применяет: она выгружает агрегаты всех трёх видов. Выбор источника — Python.

# 16. Все счета на оплату

В `documents.csv` должны попасть все счета на оплату с `ИсторияНач` по `MatchHorizonEnd` для анализируемых клиентов.

Даже если счёт:

* не формирует проводки;
* полностью оплачен;
* выписан после оплаты, в том числе после конца квартала оплаты, но не позже `MatchHorizonEnd`;
* сам по себе не является документом задолженности.

Счёт нужен как промежуточная сущность для построения связи:

```text
Оплата
↓
Счет №00002
↓
Комментарий документа реализации:
"Введен на основании: Счет на оплату №00002 ..."
↓
Отгрузка товаров / Оказание услуг
```

Реализация по этому счёту может быть и после даты оплаты. Без выгрузки таких накладных до `MatchHorizonEnd` Python не закроет аванс (налоговое окно или extended match).

Сам факт выгрузки позднего счёта до `MatchHorizonEnd` не означает, что его состав НДС можно применять задним числом.

Для `ADVANCE` источник состава НДС:

```text
1. matched RECEIVABLE,
   если связь относится к ADVANCE_TAX_WINDOW

2. иначе связанный INVOICE с валидным доступным составом,
   если сам счёт существовал не позже конца налогового квартала этой оплаты:
   invoice_date <= КонецКвартала(ДатаОплаты)

3. иначе расчётный 5/105 или 0 по шкале аванса
```

`invoice_date <= КонецКвартала(ДатаОплаты)` позволяет использовать агрегаты счёта как `INVOICE_VAT_FALLBACK`. Если счёт появился только после окончания квартала аванса, он не должен задним числом менять налог уже закрытого квартала.

Такой поздний счёт всё ещё можно использовать:

- для хозяйственного matching;
- как промежуточную связь `оплата → счёт → реализация`;
- для поиска будущей реализации до `MatchHorizonEnd`;

но не как основание пересчитать НДС аванса прошлого квартала.

Пример:

```text
15.03.2026 — аванс
31.03.2026 — конец налогового квартала этой оплаты
15.04.2026 — создан счёт
20.04.2026 — реализация
```

Апрельский счёт и апрельская реализация могут установить хозяйственную связь в `ADVANCE_EXTENDED_MATCH_WINDOW`, но не меняют налог Q1. Позднее появление счёта не отменяет правило этого раздела: все счета до `MatchHorizonEnd` всё равно выгружаются, потому что они нужны matching.

Контрпример к ошибочному чтению «extended всегда 5/105»: мартовский смешанный счёт 105 000 (НДС 3 000) + мартовский аванс + апрельская отгрузка. Налог Q1 берётся из мартовского счёта (доход 102 000), а не 5/105 со всей суммы и не НДС апрельской отгрузки. Поздняя реализация не отменяет допустимый ранний счёт.

# 21. Суммы

В CSV:

```text
СуммаКоп
```

целое число со знаком, не `float`.

```text
 5500 руб. =  550000
−100  руб. = −10000
 −0,01 руб. = −1
```

Перевод рублей с двумя десятичными знаками в копейки обязан сохранять знак. Запрещена односторонняя поправка `Цел(Сумма * 100 + 0.001)`: `Цел` отсекает дробную часть к нулю, поэтому −100,00 даёт −9999, а −0,01 даёт 0. Допустимо `Окр(Сумма * 100, 0)` языка 1С 7.7 либо симметричное правило с поправкой по знаку. Источники с большей точностью, чем 2 знака, округляются до копейки тем же `Окр(..., 0)`.

Поддержка денежных возвратов по §12.1 не разрешает менять знак исходных движений ledger или отождествлять возврат с техническим сторно. Положительное поступление, сторно поступления, возврат денег и прочее неплатёжное 62 — разные случаи: см. §12.1.

# 23. Экспортируемая история предыдущего контракта

Формулы прежнего горизонта ниже заменены для будущего формата §4 и §31.1: история с 01.01.2026 до фактического конца пакета. Увеличение глубины ради получения старого счёта не требуется.

История ограничена формулой раздела 4:

```text
ИсторияНач = ДобавитьМесяц(НачалоГода(ДатаНач), -МесяцевИстории)
```

Например:

```text
КУДиР 2026
→ история с 01.10.2025
```

Нет необходимости выгружать всю историю клиента с момента создания базы. Snapshot документных остатков между запусками в версии 1 не строится.

Документы (счета, отгрузки, оказания услуг) выгружаются до `MatchHorizonEnd` по формуле раздела 4, даже если `ДатаКон` — не последний день квартала. Конец квартала `ДатаКон` в манифест пишется как налоговая граница, не как предел выборки документов.

Если долг возник раньше `ИсторияНач` и документ в выгрузку не попал, Python сформирует `DEBT_UNRESOLVED`. При необходимости глубину увеличивают параметром `МесяцевИстории`.

# 23.1. opening_balances.csv — обязательно

Ниже — прежний детальный контракт годового opening. Для новой методики он не заменяет обязательные два разреза и все границы §31.1. Новые снимки нельзя молча дописывать в старую схему с ключом без границы.

Файл обязателен. Если его нет, Python завершает работу с ошибкой и не считает остатки с нуля.

Сальдо на момент непосредственно перед `ИсторияНач` по аналитике 62 для тех же клиентов, что попали в выгрузку.

Порядок колонок:

```text
КонтрагентID
Счет62
ДоговорID
ВидРасчетовID
ВидРасчетов
ДатаСальдо
ОстатокДтКоп
ОстатокКтКоп
```

`ДатаСальдо` = `ИсторияНач`. Суммы — целые копейки со знаком, **оба** остатка обязательны. Python не имеет права отбрасывать один из них по правилу «если есть кредит — вернуть кредит». Если аналитика пуста, поле пустое, не `0` и не `NULL`.

Это суммарное сальдо по ключу аналитики `КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID`, а не список неоплаченных документов и не свёртка по контрагенту. Остатки разных аналитик не неттируются. Конкретный старый акт вне истории не восстанавливается.

Запрос `БухгалтерскиеИтоги` обязан задать нужную детализацию, а не имитировать её циклом по отсутствующим измерениям. Для 1С 7.7:

```text
ИспользоватьСубконто(Контрагенты, этот клиент, 2)   // отбор
ИспользоватьСубконто(Договоры, , 1)                 // разворот
ИспользоватьСубконто(ВидыРасчетовСПокупателями, , 1) // разворот
ВключатьСубсчета — так, чтобы субсчета 62 входили в детализацию
ВыполнитьЗапрос(ИсторияНач, ИсторияНач, "62")
```

Режим **3** («не учитывать это субконто») для договоров и видов расчётов **запрещён**: он исключает аналитику из результата. Режим **2** для контрагента — отбор нужного клиента, это правильно. Родительский итог счёта 62 не должен дублировать сумму субсчетов в тех же строках файла. Индексы `ВыбратьСубконто` обязаны соответствовать фактическому порядку измерений запроса.

Остатки берутся непосредственно перед `ИсторияНач`. Движения первого дня истории в сальдо не входят повторно: они пойдут в `ledger62.csv`.

Приёмка: один клиент, два договора, два субсчета 62; одновременные Дт и Кт; нулевая третья аналитика в файл не попадает. Сверка с ОСВ.

Наличие date_start/date_end/quarter_end в старом файле не задаёт новый период отчёта. Версия и описание расширенного формата должны обновляться согласованно (§31.5).

```text

run_id;KUDIR_2026_20260903_001
schema_version;3
encoding;windows-1251
```

```text
quarter_end = КонецКвартала(ДатаКон) — метаданные расчётного запуска.

quarter_end НЕ является универсальной правой границей ADVANCE_TAX_WINDOW всех оплат.

payment_tax_quarter_end =

    момент оплаты ... payment_tax_quarter_end
```


Python не должен использовать `manifest.quarter_end` вместо конца квартала конкретной оплаты. `match_horizon_end` = `MatchHorizonEnd` из раздела 4 — отдельная граница хозяйственного поиска и предел `documents.csv`. Документы не режутся `quarter_end`.

Все файлы этого запуска, включая манифест и таблицу ID, лежат в `exchange/<run_id>/`. Python и загрузчик читают только этот каталог.

# 23.3. Таблица соответствия ID

Файл каталога запуска: `exchange/<run_id>/id_map.csv`. Порядок колонок:

```text
entity_type;id;вид;номер;дата;позиция;номер_проводки;ссылка_1С
```

`entity_type`: только `PAYMENT`, `DOCUMENT`, `CONTRACT`. `COUNTERPARTY` и `LEDGER` в `id_map.csv` не записываются.

Договоры регистрируются из **всех** источников, из которых Python имеет право вернуть `contract_id`:

- каждый непустой договор каждой экспортируемой корреспонденции оплаты (независимо от представления агрегированной оплаты Python);
- договор документа счёта / реализации / услуг, если не пуст.

Нельзя регистрировать CONTRACT только при обходе `documents.csv`. Иначе незакрытый `ADVANCE` с договором аналитики ledger62 законно попадёт в `kudir_result.csv`, а L2 не найдёт ссылку.

Контроль коллизий на выгрузке — `registeredIds` (время жизни EXPORT). Словарь `restore` на выгрузке не строится: он появляется только после Python на проходе L2 (ТЗ №4).

Для `PAYMENT` банковской оплаты в таблице хранятся и позиция, и `НомерПроводки`. Для документа — позиция. Вид, номер и дата — справочные поля **для человека**, не ключ и не способ найти объект при загрузке.

Python `id_map.csv` не интерпретирует: ни как matching, ни как ссылки 1С.

Как не держать этот файл и живые объекты в RAM — `04-ТЗ-1С-память-выгрузки.md`. Семантика колонок и восстановление задаются здесь.

## 23.3.1. Как объект 1С переживает поход через CSV

Текущая реализация `kudir_export.txt` кладёт в колонку `ссылка` живой объект, достаёт его через `КУДиР_НайтиСсылку()` из `глТаблID`, а в `id_map.csv` пишет `СокрЛП(глТаблID.ссылка)` — человеческое представление. Это **не** обратимая ссылка. Файл на диске для восстановления не используется.

Нормативная семантика колонки `ссылка_1С`:

```text
СистСсылка = ЗначениеВСтрокуВнутр(Объект1С)
ссылка_1С = СистСсылка
```

Имя и порядок колонок не меняются. Меняется наполнение последней колонки.

| Делать | Не делать |
| --- | --- |
| `ЗначениеВСтрокуВнутр(ДокументОплаты / Документ / Договор)` | `СокрЛП(Объект)` как техническая ссылка |
| в CSV только штатное экранирование раздела 30 | `СокрЛП()`, смена регистра, обрезка, «нормализация» системной строки |
| пустую обязательную ссылку считать ошибкой выгрузки | подставлять представление объекта, номер, дату, наименование |

Что сериализовать:

| `entity_type` | Агрегатное значение |
| --- | --- |
| `PAYMENT` | документ оплаты |
| `DOCUMENT` | документ счёта / реализации / услуг |
| `CONTRACT` | элемент справочника договора |

`КонтрагентID` / `Контрагент` остаются обязательными бизнес-полями входных CSV для аналитики, matching и формирования `СодержаниеЗаписи`, но отдельный объект справочника Контрагент после Python не восстанавливается. `ledger_event_id` остаётся обязательным идентификатором строки `ledger62.csv`, но объект 1С по нему также не восстанавливается.

Несколько разных ID могут указывать на один объект — это допустимо. Коллизия: один `entity_type + id` → две разные `СистСсылка` = `FAILED`.

Golden и живые прогоны: колонка `ссылка_1С` **намеренно** перестаёт совпадать со старым `СокрЛП(Объект)`. Остальные входные CSV семантически те же.

## 23.3.2. Восстановление при загрузке

Загрузчик не ищет живой объект в `глТаблID`. Для каждой обязательной ссылки строки `kudir_result.csv`:

```text
СистСсылка = restore[entity_type + "|" + id]
Объект = ЗначениеИзСтрокиВнутр(СистСсылка)
```

Типы, без которых нельзя заполнить `СформироватьТаблицуДоходовЧистовая()`:

- `PAYMENT` → `ДокументОплаты`;
- `CONTRACT` → `Договор`, если `contract_id` не пуст;
- `DOCUMENT` → документ реализации, если `matched_document_id` не пуст.

Пустой `contract_id` / `matched_document_id`, если он допустим разделом 24, не восстанавливается. Других типов в `id_map.csv` нет: `COUNTERPARTY` и `LEDGER` исключены из его контракта.

Пока `ЗначениеИзСтрокиВнутр()` не вернул непустое значение, **запрещено** читать `ДокОпл.НомерДок`, `ДатаДок`, `Договор.Наименование` и любые другие реквизиты. Повреждённая, пустая или невосстанавливаемая системная строка — ошибка отображения ID → объект 1С: все такие строки в лог, итог — **полностью пустая** таблица. Fallback «найдём документ по номеру и дате» / «договор по наименованию» запрещён.

Полный `id_map.csv` обратно в широкую `ТаблицаЗначений` не загружать. Достаточно компактного соответствия трёх типов на системную строку (как его держать в RAM — ТЗ №4).

# 24. Результат Python

В новом формате Python возвращает `kudir_result.csv` по целевым оплатам, определённым по дате операции и параметрам проверки (§31.1), с учётом допустимых исключений полной пары. НДС и доход УСН рассчитывает Python, 1С их не пересчитывает. Готовность всей книги определяется tax_ready; денежные возвраты дают RETURN либо доказанно исключённую полную пару, а не автоматически неготовый результат (02 §36.1).

Через CSV **нельзя** передавать объекты 1С. Порядок колонок:

```text
run_id
result_row_id
payment_id
row_type
matched_document_id
contract_id
amount_kopecks
advance_kopecks
repayment_kopecks
income_kopecks
vat_base_kopecks
vat_kopecks
match_type
confidence
reason
СодержаниеЗаписи
```

`row_type`: `DEBT`, `ADVANCE`, `DEBT_UNRESOLVED`, `RETURN`. Для RETURN payment_id указывает на PAYMENT самого возврата; contract_id — договор аналитики возврата. При U5.1 существующий matched_document_id содержит DOCUMENT явно указанной отгрузки/услуги; при U5.2 он пуст, PAYMENT исходной оплаты хранится в return_allocations.csv (§24.1). Отдельный return_document_id не нужен; PAYMENT нельзя помещать в DOCUMENT-поле.

Пустой `matched_document_id` обязателен для RETURN U5.2; для подтверждённого U5.1 документ обязателен, для невыгруженной явной ссылки — пусто с RETURN_UNRESOLVED и диагностикой. Пустое поле также допустимо для `DEBT_UNRESOLVED` и для `ADVANCE`, который не закрыт реализацией ни в налоговом окне, ни в extended match. Если аванс закрыт отгрузкой или оказанием услуг, `matched_document_id` обязателен. `DEBT_UNRESOLVED` remainder документа не занимает.

`СодержаниеЗаписи` — одна физическая строка, без CR/LF внутри поля.

`counterparty_id` в `kudir_result.csv` намеренно отсутствует. Контрагент используется во входных данных для аналитического ключа, hard constraint matching и формирования `СодержаниеЗаписи`, но отдельный объект Контрагент в `СформироватьТаблицуДоходовЧистовая()` не требуется и через `id_map.csv` не восстанавливается.

Перед загрузкой 1С читает `run_status.csv` из того же каталога. Поля:

```text
key;value
run_id;...
status;SUCCESS|SUCCESS_DEGRADED|FAILED
tax_ready;0|1
unresolved_debt_kopecks;...
unresolved_count;...
state_uncertain;0|1
historical_unresolved_count;...
historical_unresolved_kopecks;...
parser_available;0|1
schema_version;3
scoring_hash;...
vat_unknown_count;...
```

Список совпадает с ТЗ №2. Поля `state_uncertain`, `historical_unresolved_*` и `vat_unknown_count` обязательны в контракте; 1С может их только читать для диагностики. `vat_unknown_count` — число целевых строк с `VAT_COMPOSITION_UNKNOWN`.

`run_id` в `run_status.csv` и в `kudir_result.csv` должен совпасть с `manifest.csv` этого каталога. Чужой или старый результат не загружается.

Перед первой строкой данных загрузчик проверяет наличие **всех** обязательных колонок `kudir_result.csv` (не только `run_id`). Отсутствующая колонка, строка короче **или длиннее** заголовка — `FAILED`, а не пустая строка/`0`. В L1 все суммы — целые копейки; пустое числовое поле ≠ 0; нечисловая строка, дубль `result_row_id` и нарушение инвариантов §28 — `FAILED`. При любой ошибке отображения ID → объект 1С (`нет ключа`, пустая `ссылка_1С`, сбой или пустой результат `ЗначениеИзСтрокиВнутр()`, **восстановленное значение неверного типа**) загрузчик сообщает все такие строки, затем возвращает **полностью пустую** таблицу. Учитывается `глОшибка`. Частично загруженный результат в бухгалтерию не идёт. Объект по номеру, дате или наименованию не ищется.

При `FAILED` результат не загружается. При `SUCCESS` и `SUCCESS_DEGRADED` строки загружаются. `tax_ready=0` не блокирует загрузку: это сигнал, что книгу нельзя считать готовой к сдаче из-за неразрешённого итогового налога или влияющей неопределённой ёмкости. Наличие unresolved-долга само по себе не блокирует готовность. `SUCCESS` + `tax_ready=0` — валидная комбинация. Обычный поддерживаемый возврат сам по себе не снижает готовность и не создаёт SUCCESS_DEGRADED. При RETURN_TAX_UNRESOLVED или неподдерживаемом техническом сторно 1С показывает конкретную причину неполноты из диагностики и оставляет рассчитанные строки доступными. Это заранее диагностированная неполнота расчёта по 02 §36.1, а не разрешение загрузить часть повреждённого файла.

`matches.csv` 1С не загружает. Порядок колонок — как в ТЗ №2 §46: кроме общего `score` обязательны `direct_reference_score`, `invoice_link_score`, `amount_score`, `contract_score`, `calculation_type_score`, `semantic_score`, `chronology_score`.

1С по `payment_id`, `contract_id` и `matched_document_id` берёт `ссылка_1С` из `restore` — узкого словаря восстановления, который строится **только после Python** проходом L2 по `id_map.csv` согласно ТЗ №4, — и делает `ЗначениеИзСтрокиВнутр()`. Только после успешного восстановления заполняет существующую структуру:

```text
ДокументОплаты
НомерДокументаОплаты
ДатаПлатежа
СуммаПлатежа          ← amount_kopecks / 100
Договор
НомерДоговора
СодержаниеЗаписи
СуммаВАванс           ← advance_kopecks / 100
СуммаВОпалату         ← repayment_kopecks / 100
СуммаСНДС             ← vat_base_kopecks / 100
СуммаНДС              ← vat_kopecks / 100
СуммаВДоход           ← income_kopecks / 100
```

# 24.1. Обоснование контракта U5 и return_allocations.csv

Новые поля не вводятся по умолчанию. Достаточность существующего контракта проверена по назначению:

- RETURN нужен как отдельное значение существующего row_type: старые три типа обозначают положительные части DEBT/ADVANCE и требуют их split. Без отдельного типа отрицательный возврат нельзя валидировать/загрузить, не ослабив проверки обычной оплаты.
- PAYMENT самого возврата уже помещается в payment_id, а явный документ U5.1 — в существующий matched_document_id. Новый return_document_id/вид сущности id_map не нужен. contract_id и денежные колонки также существующие.
- Для U5.2 нужна ссылка на **другой PAYMENT**, исходную оплату. matched_document_id имеет тип DOCUMENT, payment_id занят возвратом, а при полной паре строки kudir_result вообще отсутствуют. Поэтому одних полей kudir_result недостаточно для однозначной машинной проверки пары, источника налога и повторных возвратов.
- Минимальное дополнение — журнал return_allocations.csv: он хранит связи/суммы истории и исключений. matches.csv имеет DOCUMENT-цель и score обычного matching, а текст СодержаниеЗаписи/analysis.log не является типизированным контрактом распределений. Новые поля основного kudir_result не требуются. Журнал — формат обмена, не требование создать отдельную внутреннюю таблицу/класс.
- Новые reason-коды помещаются в существующее reason; отдельные колонки флагов не нужны. Дополнительный tax_known убран как избыточный: неизвестные суммы однозначно отмечает allocation_type=RETURN_UNRESOLVED и reason. Новые поля run_status не вводятся; status/tax_ready/state_uncertain и журнал достаточны, имеющиеся счётчики не переопределяются как счётчики возвратов.
- CSV v3 необходима даже без новых колонок основного результата: RETURN меняет допустимые значения/знаки/инварианты, журнал становится обязательным. Изменять версию scoring.yaml из-за этого запрещено: это независимая схема настройки scoring.

`return_allocations.csv` — обязательный выход Python схемы v3, даже без возвратов (header-only). Точный порядок колонок:

```text
run_id
return_payment_id
original_payment_id
matched_document_id
amount_kopecks
vat_base_kopecks
vat_kopecks
income_kopecks
allocation_type
reason
```

Одна строка — распределённая часть реального возврата на один налоговый источник либо неизвестный хвост. return_payment_id — PAYMENT самого возврата, обязательный и существующий в payments. original_payment_id — исходный PAYMENT для U5.2; matched_document_id — существующий DOCUMENT для U5.1. В подтверждённой строке заполнен ровно один из двух источников. Для неизвестного хвоста допустим известный ID источника, расход которого нельзя подтвердить, либо оба пусты при неустановленном/невыгруженном источнике; причина и извлечённые реквизиты сохраняются в reason/analysis.log. ID не выдумываются.

allocation_type:

- CANCEL_PAIR — полное исключение излишней оплаты U5.2 в том же календарном квартале того же года; original_payment_id заполнен, matched_document_id пуст, amount равен полной сумме исходной оплаты и возврата, доступный остаток позволяет полный возврат. Налоговые колонки равны нулю, включая income: это **нулевой вклад исключённой пары**, а не налоговый состав оплаты и не утверждение, что исходная оплата была без НДС. Денежная сумма пары сохраняется в amount для контроля. Отдельный флаг известности состава пары не требуется.
- RETURN_DOCUMENT — подтверждённый U5.1, только matched_document_id; источник состава — фактический документ из комментария.
- RETURN_PAYMENT — подтверждённый частичный/иной неполный U5.2 либо полный возврат в другом календарном квартале/году, только original_payment_id; источник — признанный налоговый состав оплаты.
- RETURN_UNRESOLVED — неизвестный источник/налог, превышение ёмкости или иная неразрешённая часть; подтверждённый возвратный состав не расходует.

Для RETURN_DOCUMENT/RETURN_PAYMENT суммы — положительные величины возвращаемой части: amount>0, 0<=vat<=vat_base<=amount, income=amount−vat. Целевой результат RETURN имеет противоположные знаки. Для RETURN_UNRESOLVED технические vat_base=vat=0, income=amount, reason содержит RETURN_TAX_UNRESOLVED и причину; это не готовый налоговый факт. Для CANCEL_PAIR действует отдельное правило нулевого налогового вклада выше, а не обычное равенство income=amount−vat.

Исторические возвраты тоже отражаются в журнале и расходуют подтверждённую возвратную ёмкость своего источника, но не создают исторических строк в целевом kudir_result. Сумма amount всех частей журнала каждого возврата равна его исходной положительной сумме, включая неразрешённый хвост. Повторная запись той же части запрещена; строки одного return_payment_id+источник+allocation_type агрегируются. RETURN_UNRESOLVED не даёт права отрицательной ёмкости и не считается вторым подтверждённым расходом.

Python проверяет выбор ветви U5 и доказательство ссылки из комментария без эвристического document matching. L1 не реализует этот алгоритм повторно: проверяет типы/существование ID, контрагента, даты исходных фактов, суммы и структуру распределений. U5.1 не должен иметь PAYMENT-источник, U5.2/CANCEL_PAIR — DOCUMENT-источник. Для CANCEL_PAIR L1 обязательно проверяет совпадение календарного квартала и года исходной оплаты и возврата. Совпадение is_target не требуется: этот флаг определяет целевой вывод, а не принадлежность кварталу. Полный возврат другого квартала/года оформляется RETURN_PAYMENT, не CANCEL_PAIR; исходная книга не исправляется.

L1 сверяет полный расход каждого возврата, отсутствие повторного исключения одной оплаты, доступность подтверждённого возвратного остатка по источнику и совпадение сумм журнала с целевыми RETURN. RETURN_PAYMENT нескольких источников может проверяться агрегатно по return_payment_id; отдельный result_row_id в журнале не нужен. Для U5.1 проверяется совпадение matched_document_id журнала и результата; для неизвестных частей — RETURN_UNRESOLVED и технические суммы, без фиктивного подтверждения налога.

У полностью исключённой пары целевые строки обоих событий отсутствуют; поправка в сверке +amount для исходного поступления и −amount для возврата. Исторический участник пары не должен порождать целевую строку. Нельзя считать пропуск неисключённой оплаты/RETURN допустимым по одному факту header-only результата. Неподдерживаемое техническое сторно и нули учитываются отдельно по входам/диагностике, не как CANCEL_PAIR.

Все проверки выполняются по ID/скалярам с компактными накопителями расхода и сверки. Ради истории журнала не восстанавливать объекты 1С и не держать широкую таблицу исходных документов (04 §13). Память и жизненный цикл остаются потоковыми.

Отсутствующий файл, чужой run_id, неизвестное allocation_type, неверный тип/знак/сумма, несовместимые источники, дубль подтверждённого расхода, невозможная ссылка либо потеря неисключённой целевой операции — FAILED. Сырой возврат сверх остатка может присутствовать как диагностированный RETURN_UNRESOLVED, но подтверждённое распределение сверх остатка — нарушение инварианта. CSV-протокол — §30.

# 25. Разбиение платежа

Положительное поступление может породить несколько строк DEBT/ADVANCE по своим аналитикам ledger62. RETURN сюда не передаётся: он отдельно выбирает источник U5 и возвращаемые доли, сохраняя исходные аналитики; его advance/repayment равны нулю.

Например, одна оплата 10 000, две аналитики: долг 7 000 по договору A и нет долга по договору B на 3 000:

```text
строка 1: DEBT 7 000 по аналитике A
строка 2: ADVANCE 3 000 по аналитике B
```

Сворачивать это в одно среднее число на всю оплату нельзя. Остаток Кт другой аналитики не уменьшает долг этой.

# 26. СуммаВДоход

Налоговый доход УСН считает Python:

```text
income_kopecks = amount_kopecks − vat_kopecks
СуммаВДоход = СуммаПлатежа − СуммаНДС
```

1С эти поля не пересчитывает. Одновременно `СуммаВАванс` и `СуммаВОпалату` ненулевыми быть не могут. Для RETURN обе колонки равны 0, СуммаПлатежа отрицательна, СуммаВДоход и возвращаемые база/НДС неположительны по 02 §36.1; это отдельный тип, а не нарушение положительного DEBT/ADVANCE split.

При `tax_ready=1` результат — готовая КУДиР. При `tax_ready=0` строки всё равно загружаются, но книгу нельзя сдавать.

# 27. НДС

Приёмка загрузки по U2/U4: разрешены `DEBT_UNRESOLVED` с пустым документом и `tax_ready=1`, а также `VAT_COMPOSITION_UNKNOWN` с определённым fallback и `tax_ready=1`. `DEBT` без matched-документа по-прежнему недопустим. Числовые эталоны — 02 §48.3; 1С не пересчитывает налог и не выводит готовность из счётчиков. Приёмка экспорта отрицательного НДС ТЧ проверяет нули всех трёх агрегатов всего документа и диагностику, включая положительные строки до и после отрицательной.

Для положительных поступлений Python считает налог по порядку 02 §21.2: доказанный возраст долга, валидный доступный состав, допустимый fallback. Для RETURN этот порядок не применяется как к новой оплате: U5.1 — состав явного документа из комментария, U5.2 — исключение полной пары либо состав исходной оплаты по 02 §36.1. Во всех схемах ниже «состав документа» означает валидный доступный состав; неизвестный источник пропускается. Две независимые шкалы:

- **аванс — дата получения.** Аванс до `2026-01-01` не получает расчётный НДС 5/105 ни на остаток, ни «задним числом»;
- **реализация — дата отгрузки.** Реализация 2026 может нести фактический НДС независимо от даты аванса.

Нельзя писать «всё до 01.01.2026 без НДС» как общее правило для обеих сторон.

Константа расчётного НДС: 5%, формула `5/105`. Фактический НДС из колонки `НДС` этой формулой не подменять.

Для `DEBT` и `DEBT_UNRESOLVED` сначала проверяется возраст реально закрываемого долга исходной аналитики: доказанно до 01.01.2026 → `PRE_2026_DEBT` выше любого состава документа/счёта; неоднозначный возраст → OD1. Для остальных допустимых целевых частей 2026: валидный RECEIVABLE, затем допустимый INVOICE с остатком, иначе `DEFAULT_5_105` (02 §21.2).

Для `ADVANCE` источник состава НДС выбирается **по состоянию налогового окна**, а не по факту extended-связи:

```text
1. matched RECEIVABLE с валидным доступным составом в ADVANCE_TAX_WINDOW
2. иначе связанный INVOICE с валидным доступным составом,
   если invoice_date <= КонецКвартала(ДатаОплаты)
3. иначе расчётный 5/105 или 0 по шкале аванса
```

Это то же правило, что в разделе 16: поздний счёт после `payment_tax_quarter_end` не является `INVOICE_VAT_FALLBACK`. Поздняя реализация в `ADVANCE_EXTENDED_MATCH_WINDOW` заполняет `matched_document_id`, но не становится источником НДС и не отменяет шаг 2. Добавление апрельской отгрузки не меняет налог мартовского аванса, уже рассчитанный по мартовскому счёту.

- погашение долга → сначала доказанный `PRE_2026_DEBT`, иначе валидный состав / допустимый счёт / default по 02 §21.2;
- аванс, закрытый отгрузкой в `ADVANCE_TAX_WINDOW` → НДС из этих реализаций;
- связь в `ADVANCE_EXTENDED_MATCH_WINDOW` — хозяйственная; налог закрытого квартала как при отсутствии этой реализации;
- незакрытый остаток аванса с `2026-01-01` без реализации в налоговом окне и без допустимого счёта → 5/105;
- незакрытый остаток аванса до `2026-01-01` → без 5/105;
- нет реализации в `ADVANCE_TAX_WINDOW`, но есть связанный счёт с `invoice_date <= КонецКвартала(ДатаОплаты)` → `INVOICE_VAT_FALLBACK`, в том числе если позже появилась extended-реализация;
- связанный счёт создан только после окончания квартала оплаты → matching-связка допустима, налог закрытого квартала не пересчитывается, применяется 5/105 или 0 по шкале аванса;
- неизвестный состав найденного документа не равен доказанному VAT=0: сохранить matching и `VAT_COMPOSITION_UNKNOWN`, пропустить этот налоговый источник, проверить следующий допустимый источник, иначе применить `DEFAULT_5_105` для допустимой целевой части 2026. Доказанный `PRE_2026_DEBT` имеет приоритет; неустановленный возраст/ёмкость — OPEN_DECISION, а не fallback наугад. Диагностика неизвестного состава сама по себе не означает `tax_ready=0`;
- `DEBT_UNRESOLVED` не занимает остаток документа. Налог определяется возрастом реально закрываемой части исходной аналитики ledger: до 01.01.2026 → `PRE_2026_DEBT`, база и VAT 0, доход = сумма; с 01.01.2026 → при отсутствии более сильного допустимого источника `DEFAULT_5_105`. Неоднозначный возраст — OPEN_DECISION OD1. Счётчики unresolved сохраняются, автоматического `tax_ready=0` нет.

Смешанный документ (часть строк с НДС, часть без):

```text
vat_base_kopecks  = облагаемая доля этой части оплаты   → СуммаСНДС
vat_kopecks       = НДС этой доли                       → СуммаНДС
income_kopecks    = amount_kopecks − vat_kopecks
```

`vat_base_kopecks` может быть меньше `amount_kopecks` для положительных строк. Следующие инварианты — для DEBT/ADVANCE/DEBT_UNRESOLVED; знаки RETURN — §28:

```text
income_kopecks = amount_kopecks − vat_kopecks
vat_kopecks <= vat_base_kopecks <= amount_kopecks
```

Денежные возвраты покупателю включены по U5, отдельный путь — 02 §36.1; прежнее исключение всех возвратов из версии 1 отменено. Эквайринговые комиссии и неподдерживаемое техническое сторно остаются отдельными диагностируемыми случаями. Все подписанные движения ledger выгружаются точно по §12.1; поддерживаемый RETURN не означает автоматическую неготовность.

# 28. Обязательные контрольные проверки

Для каждой неисключённой положительной целевой оплаты сумма частей результата равна исходной сумме. Для каждого целевого возврата сумма amount строк RETURN = минус исходная положительная сумма, если возврат не исключён полной парой. Сверка исключений пары — return_allocations.csv (§24.1). Нельзя считать отсутствие обеих строк доказательством взаимной отмены без проверенной пары.

Header-only допустим для полного набора проверенных исключённых пар/нулей/диагностированного неподдерживаемого сторно. Одиночный поддерживаемый возврат обязан иметь RETURN. Исторические события в kudir_result отсутствуют, но участвуют в проверке остатка возврата. Нельзя терять положительную оплату или возврат под видом нуля/неподдерживаемой операции.

Для DEBT/ADVANCE/DEBT_UNRESOLVED:

```text
amount_kopecks > 0
advance_kopecks >= 0; repayment_kopecks >= 0
advance_kopecks + repayment_kopecks = amount_kopecks
income_kopecks = amount_kopecks - vat_kopecks
0 <= vat_kopecks <= vat_base_kopecks <= amount_kopecks
```

Для RETURN:

```text
amount_kopecks < 0
advance_kopecks = 0; repayment_kopecks = 0
income_kopecks = amount_kopecks - vat_kopecks
amount_kopecks <= vat_base_kopecks <= vat_kopecks <= 0
matched_document_id = DOCUMENT явной отгрузки/услуги для U5.1; пусто для U5.2
```

Подтверждённые и предварительные RETURN_TAX_UNRESOLVED различаются по allocation_type в return_allocations и reason, налог неизвестного целевого хвоста даёт tax_ready=0. Знак валидируется по row_type: отрицательная DEBT по-прежнему ошибка, отрицательная RETURN обязательна. 1С восстанавливает PAYMENT возврата (в том числе расходный кассовый документ) и сохраняет знаки всех колонок, без модуля суммы и без повторного пересчёта НДС. Нулевые псевдостроки вместо возвратов/исключений не разрешены.

# 29. Критерии готовности части 1С

1. Не перенесён как эталон запрещённый старый код FIFO, обрезки номера и поиска строки выписки по сумме.
2. Формируется `manifest.csv` с `run_id`, `quarter_end` и `match_horizon_end`, и обязательный `opening_balances.csv` по ключу аналитики.
3. Формируется `payments.csv` со всеми оплатами истории, `is_target` и `НомерПроводкиВДокументе`. Поля договора/вида расчётов в нём не authoritative.
4. Для выписки `payment_id` = позиция + `Опер.НомерПроводки()`. `НомерСтрокиДокумента()` не используется как ключ. Для ПКО — позиция документа. Для документа — `ПолучитьПозицию()`.
5. Поддерживаются ПКО и расходные кассовые документы возвратов, банковские поступления и возвраты по §6/§12.1.
6. Формируется `ledger62.csv` со всеми движениями 62, `ledger_event_id`, `source_document_id` и `payment_id` у оплат. Без дедупа по `document_id`.
7. Формируется `documents.csv` с ролью, видом расчётов, датой договора и агрегатами `СуммаОблагаемаяКоп` / `СуммаНеоблагаемаяКоп` / `СуммаНДСКоп`.
8. Выгружаются все счета анализируемых клиентов с `ИсторияНач` по `MatchHorizonEnd`.
9. Выгружаются отгрузки и оказания услуг за тот же интервал, включая документы после конца квартала `ДатаКон`, если они не позже `MatchHorizonEnd`.
10. Выгружается `Комментарий` и `ПервичныйДокумент`.
11. Аналитика берётся со стороны счета 62. Ключ: `КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID`.
12. История начинается по умолчанию с 1 октября предыдущего года.
13. 1С не выполняет эвристический matching, не решает DEBT/ADVANCE и не считает НДС / доход УСН.
14. Загружается `kudir_result.csv` по ID: `ссылка_1С` = `ЗначениеВСтрокуВнутр()`, восстановление = `ЗначениеИзСтрокиВнутр()`, без `СокрЛП(Объект)` и без поиска по номеру/дате. Коллизия ID = FAILED. `tax_ready=0` не блокирует загрузку.
15. Формируется существующая `СформироватьТаблицуДоходовЧистовая()` с уже посчитанными `СуммаСНДС`, `СуммаНДС`, `СуммаВДоход`.
16. CSV соответствует протоколу раздела 30. `СодержаниеЗаписи` без CR/LF.
17. Табличная часть документов обходится только чтобы сложить агрегаты НДС; строки товаров в RAM и в отдельный CSV не складываются. Второго прохода выгрузки нет.
18. `opening_balances.csv`: разворот договоров и видов расчётов режимом 1, субсчета 62, без неттинга аналитик; сверка с ОСВ.
19. Копейки со знаком: сторно не сдвигается к нулю.
20. Приходный/расходный кассовый вид распознаётся по нормализованному идентификатору метаданных; один документ = одно CASH-событие, направление определяется корреспонденцией.
21. В `id_map` есть CONTRACT всех договоров экспортируемых корреспонденций оплаты, не только документов.
22. Загрузчик: логическая CSV-запись для `id_map`; ошибка числа/полей/типа объекта → полностью пустая таблица; `глОшибка` учитывается. Проверяются подписанный RETURN и return_allocations, исключённые пары не маскируют пропуски. Приёмка возвратов — 02 §48.3 п.15–30.

# 30. CSV-протокол

Все файлы обмена:

- кодировка Windows-1251;
- разделитель `;`;
- первая строка — заголовок с точными именами колонок из этого ТЗ, в указанном порядке;
- даты строго `YYYY-MM-DD`;
- деньги — целые копейки;
- переносы строк внутри поля разрешены только если поле заключено в `"..."`; в `kudir_result.csv` поле `СодержаниеЗаписи` — одна физическая строка, без CR/LF;
- кавычка внутри поля удваивается (`"` → `""`);
- поле с разделителем или переносом всегда в кавычках;
- число полей строки равно заголовку: меньше **и больше** — `FAILED`;
- незакрытая кавычка / EOF внутри кавычек — `FAILED`;
- читатель `id_map.csv` обязан собирать **логическую** CSV-запись (переносы внутри кавычек). Указание «не писать parser логических записей» из плана №3 относится только к однострочному `kudir_result.csv`;
- пустое значение — пустая строка между разделителями, не `"NULL"`, не `0`, не пробел как замена пустоты;
- колонка `ссылка_1С` в `id_map.csv` — сырая строка `ЗначениеВСтрокуВнутр()`, без `СокрЛП()`; экранирование только по правилам этого раздела;
- `schema_version=3` задаётся в `manifest.csv`. Схема v3 расширяет v2: поддерживаемые возвраты в payments, тип RETURN с подписанными суммами/условными инвариантами и двумя ветвями U5, обязательный журнал return_allocations.csv. Минимальность полей/файла обоснована в §24.1. Имена существующих колонок сохранены, но семантика и состав файлов изменены несовместимо. До чтения данных потребители требуют v3, v1/v2 отвергают с объяснением; молчаливой автоконвертации нет. Это требование будущей реализации: текущий код и тесты этой актуализацией не изменяются.

## 31.1. Охват, период Python и снимки

Общий охват — с 01.01.2026 до фактической конечной даты, включая следующие годы; выбранный отчётный квартал не ограничивает ledger и документы. Манифест должен описывать этот охват и полноту набора независимо от периода запуска Python. Максимальная дата имеющейся строки не заменяет фактическую границу: в последний день может не быть движений.

Параметры начала/конца проверки передаются в Python и выбираются в интерфейсе; принадлежность оплаты периоду определяется по дате учётной операции. Ни в одной новой входной CSV-схеме is_target нет. Повторный расчёт другого квартала использует тот же полный пакет в пределах его охвата.

Обязательны снимки из 1С на начало всех кварталов охвата, обязательные годовые и непосредственно перед документами оплат. Два разреза: покупатель и покупатель+договор; 62.1/62.2 объединены, отсутствие вида расчётов у 62.2 допустимо. Для каждого снимка передаются граница (начало дня либо перед позицией документа на шкале времени 1С), разрез, идентификаторы аналитики, остатки и достоверность получения. Пустой договор не обозначает автоматически итог по всем договорам. Ключ снимка различает границу и разрез; нулевой полученный остаток отличается от отсутствующего снимка. Старый opening с уникальностью только по аналитике нельзя расширить новыми границами без нового контракта.

Начало квартала исключает движения первого дня; преддокументный снимок исключает все проводки документа. Совпадающие годовой/квартальный снимки обозначают один ресурс. Для контроля повторной выгрузки нужны отдельно Дт и Кт на начале и конце кварталов (§31.4); одно нетто-сальдо для этого недостаточно. Для двух методических разрезов сальдо = Дт − Кт. Последующие годовые снимки не меняют границу общего старого долга 01.01.2026. Конкретное размещение снимков в файлах и порядок колонок подлежат согласованному техническому оформлению при реализации.

## 31.2. Сопоставление прежних схем и сохранение фактов оплаты

Проверены перечни PAYMENTS_FIELDS и LEDGER_FIELDS в `src/kudir_proto/csv_io.py`, а также чтение и валидация в `src/kudir/loaders.py`. Сейчас загрузчик отдельно читает payments.csv и проверяет is_target. Это факт текущего кода, не признак готовности нового формата. Различия схем нельзя считать уже устранёнными:

- `payment_id`, дата/позиция учётной операции, номера проводки/строки, суммы, счета, покупатель, договор/вид и их реквизиты, содержание/представление проводки, `ПервичныйДокумент` уже есть в обеих схемах. В ledger сохраняется каждая исходная строка, её знак, аналитика и связь с оплатой; совпадение названия поля не доказывает одинаковую роль суммы.
- `PaymentKind` и `PaymentGranularity` есть в payments и отсутствуют в ledger. Сохранить их смысл в расширенном ledger для связанных оплат: BANK/CASH/MANUAL и POSTING/DOCUMENT соответственно. MANUAL — самостоятельный вид, не BANK или безликий OTHER. Классификация должна опираться на фактический вид документа конфигурации.
- `ВидДокументаОплаты`, `НомерДокументаОплаты`, `ДатаДокументаОплаты` не равны автоматически `ВидДокумента`, `НомерДокумента`, `ДатаДокумента` ledger. Последние описывают документ, породивший проводку. Отдельные факты платёжного документа должны сохраниться в ledger; для банка номер и дату даёт функция владельца (§31.3).
- `НазначениеПлатежа` отсутствует как отдельное поле прежнего ledger. Сохранить доступное исходное назначение конкретного платежа, если оно отличается от содержания проводки. Не считать копирование общего текста выписки восстановлением назначения банковской строки.
- `КомментарийДокументаОплаты` прежнего payments и `КомментарийДокумента` ledger сопоставляются по подтверждённому источнику. Комментарий самого возврата обязателен для ТЗ №2 §36.1 и не заменяется назначением исходной оплаты. При разных источниках оба текста и происхождение сохраняются, а не выбирается первый удобный.
- `is_target` не переносится: это вычисление Python по параметрам проверки и дате.

Расширить описание ledger ровно недостающими сведениями и закрепить их источник/допустимую пустоту в будущей схеме. Связь движений с одной хозяйственной оплатой должна быть достаточной для группировки; оплата не восстанавливается эвристически по сумме, номеру и дате.

Денежная сумма хозяйственной оплаты учитывает роль движения и исходный знак. Например, два денежных поступления одной оплаты на 62.1 = 60 000 и 62.2 = 40 000 дают 100 000; внутренний перенос 40 000 между 62.1/62.2 не увеличивает эту сумму до 140 000. Корреспонденции одного движения не дублируют поступление. Возврат и техническое сторно сохраняют свою природу. Аналитические изменения сальдо выполняются по исходным ledger-строкам один раз; собранная Python оплата не проводится повторно. Если роль/принадлежность не установлена, нужны диагностика и открытая часть, а не фиктивная сумма.

## 31.3. CASH, MANUAL, BANK, точная позиция и функция владельца

Окончательные форматы: `CASH|{ПозицияДокумента}` для ПКО; `MANUAL|{ПозицияДокумента}|{НомерПроводки}` для оплаты ручной «Операцией»; `BANK|{ПозицияДокумента}|{НомерПроводки}` для банковской оплаты. Промежуточный MANUAL без номера проводки запрещён. Несколько движений ПКО — одна CASH-оплата; номера отдельных проводок в ledger и их числовой порядок сохраняются. Отсутствующий номер агрегированной CASH-оплаты из ledger не дополняется. Для MANUAL номер проводки обязателен, номера строки выписки нет; BANK сохраняет предусмотренные проверки принадлежности движений.

`ПозицияДокумента` — позиция документа на шкале времени 1С, а не произвольный индекс или номер строки. Название уже однозначно и не меняется ради косметики. Исходные значения, включая пробелы, сохраняются точно:

```text
"#20260601 679630000    464838   "
"#20260601 680830000    465538   "
```

Для неоднозначного поля `позиция` прежнего id_map семантика та же: позиция документа на шкале времени 1С. Если при оформлении нового формата требуется техническое переименование, одновременно обновляются описание всех схем, экспорт/чтение/валидация/ID/сортировка и сценарии; одностороннее переименование недопустимо. Нормализация пробелов технической позиции недопустима.

**Контракт подключения функции владельца для банковских реквизитов:** точка использования — подготовка платёжных реквизитов для конкретной проводки банковской выписки перед формированием соответствующих фактов ledger. Вход: достоверная ссылка на документ выписки, его точная позиция на шкале времени 1С и числовой номер проводки, позволяющие владельцу обратиться к конкретной операции. Номер строки табличной части не обязателен и не выдумывается; сумма/текст не служат единственным ключом связи.

Результат функции: номер и дата **первичного платёжного документа этой проводки**, с явным отсутствием каждого недоступного значения и диагностикой причины отсутствия/ошибки/неоднозначности. Для CSV даты приводятся к согласованному формату, номер остаётся реквизитом документа, а не числом для вычислений. Если функция не подключена, отсутствующие значения остаются пустыми с диагностикой; запрещён fallback на номер/дату выписки или другого документа-источника. `ДатаОперации` и `ПозицияДокумента` сохраняют учётный смысл независимо от результата функции.

Функцию реализует владелец. Здесь описан только её вход и результат; конфигурационно-зависимый алгоритм и программная точка подключения в текущем запуске не создаются.

## 31.4. Повторная выгрузка ledger по контрольным остаткам

Перед повторным экспортом сравниваются полученные из 1С остатки Дт и Кт на начало и конец каждого квартала с контрольными остатками предыдущей успешной выгрузки: одинаковые границы и разрезы, отдельно оба остатка. Начало квартала — до первого движения квартала, конец — после последнего движения квартала, до первого движения следующего. Два остатка нельзя заменить одной их разностью. Полный сохранённый квартал должен покрывать требуемые движения и область аналитики; незавершённый квартал/обрезанный набор не считается полным календарным кварталом.

Если все эти остатки совпадают и полный сохранённый ledger квартала имеется, его повторно не выгружать, использовать сохранённые строки. Если остатки различаются либо полного квартала нет — выгрузить квартал заново. Обновление заменяет прежние строки квартала, не дописывает их второй раз. Объединённый пакет включает сохранённые и обновлённые кварталы без пробелов и дублей. Детали надёжного сохранения — ТЗ №4 §19.

Решение владельца: **совпадения контрольных остатков достаточно**. Совпадение оборотов, хеш проводок, журнал изменений и другие доказательства неизменности не требуются. Изменения реквизитов/текстов и иные изменения, не затронувшие эти остатки, этим способом не обнаруживаются. Нужна возможность принудительной полной выгрузки.

Пропуск относится только к ledger. Он не разрешает не получать остальные обязательные данные и снимки; контрольные остатки из 1С всё равно читаются. Проверенные решения приложения не заменяют ledger и не дают второго ресурса.

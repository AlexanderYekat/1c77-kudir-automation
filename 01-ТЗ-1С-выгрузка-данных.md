# ТЗ №1. Выгрузка учётных фактов из 1С 7.7 для Python

Актуальная техническая редакция от 14.09.2026. Контракт `schema_version=4` для последующей реализации. Это спецификация, а не подтверждение готовности выгрузчика. Редакция заменяет прежнее описание обмена целиком.

## 1. Назначение и приоритет

1С передаёт учётные факты. Python выполняет анализ, сопоставление, проверку бухгалтером, сохранение решений и формирование готового отчёта. Контракт ниже — единый источник требований к входу последующего ТЗ Python.

Основания: документы `10-МЕТОДИЧЕСКОЕ-ТЗ-СОПОСТАВЛЕНИЕ-ОПЛАТ.md` (включая §3.1), `11-МЕТОДИЧЕСКОЕ-ТЗ-ФУНКЦИИ-СОПОСТАВЛЕНИЯ.md` и последующие явные решения владельца, внесённые в действующие разделы. Последние имеют приоритет. MATCHING-TEST-CASES — материалы проверки, а не автоматическое утверждение их предложений. Исторические документы 03–09 не задают новый контракт.

Оставшиеся предложения документа 11 §14.2 не утверждаются этим ТЗ: единая позиция сложной группы и частные механизмы предварительной защиты. Рекомендация между исполнениями с окончательным выбором бухгалтером и принцип B/Q уже приняты; обязательная очередь актов не задаётся. Принятые неопределённости §14.3 и остатка старого счёта остаются для бухгалтера.

В данном этапе меняется только документация. Код 1С/Python, конфигурация, исполняемые тесты и реальные CSV не изменяются; выгрузки и миграции не запускаются. План №12 и ТЗ Python согласуются в этом документальном этапе; реализация — отдельное поручение.

## 3. Ответственность

1С получает исходные реквизиты, тексты, проводки, документы, остатки, доступные связи и сведения о полноте. Не выбирает оплаченный документ, не вычисляет методическую доступность кандидата, пять сумм или проверенность. Смысловой разбор текста и внешний parser относятся к Python, не являются обязательным этапом нового экспорта.

Сохранённые распределения, версии решений, конфликты и занятость, установленная программой, — собственные данные Python, не выдуманные реквизиты 1С. Налоговые правила этим ТЗ не меняются.

Обратная загрузка в 1С сейчас не требуется и не является условием приёмки. ID, позиции и id_map сохраняют прослеживаемость для возможного будущего развития. Сам загрузчик, его интерфейс и выходной формат отчёта здесь не проектируются.

## 6. Документ, проводка и строка

ПозицияДокумента — точное исходное значение позиции документа на шкале времени 1С. НомерПроводкиВДокументе — числовой `Опер.НомерПроводки()`. НомерСтрокиВДокументе — только фактическая строка табличной части.

По существующему ТЗ в конфигурации ПривязыватьСтроку выключен, номер строки возвращает 0. В CSV поле строки пустое. Не подставлять 0, номер проводки и не искать строку очередью по сумме/тексту. У MANUAL строки выписки нет по смыслу.

ПКО — одно поступление на документ. Расходный кассовый документ возврата — самостоятельное событие своего документа вида РасходныйОрдер; природа спорного движения устанавливается вручную по §12. Выписка и ручная «Операция» различают самостоятельные оплаты по проводкам; корреспонденции одной проводки не создают несколько оплат.

## 7. Идентификаторы

Документ имеет устойчивый ключ 1С: изменение даты, времени, номера, содержимого или состава проводок не меняет его идентичность. ПозицияДокумента — изменяемый реквизит хронологии, а не ключ. У строки выписки устойчивого ключа нет; номер проводки может измениться после добавления или удаления строк.

K — устойчивый ключ документа в области source_id, в однозначном кодировании: символ `%` заменяется на `%25`, затем `|` на `%7C`; остальные символы сохраняются без обрезки и нормализации. Обратное декодирование выполняется один раз. Это кодирование компонента ID, не изменение исходного ключа. Источник ключа подтверждён: в цикле операций точный результат ЗначениеВСтрокуВнутр(Опер.Документ), в цикле документов — ЗначениеВСтрокуВнутр от текущего документа. Внутренние числа не извлекаются, пробелы не обрезаются. K — кодирование всей этой строки указанными заменами, а не позиции. ЗначениеИзСтрокиВнутр восстанавливает объект и не является функцией получения ключа. Механизм применим к справочникам и ручной операции через её документ; существующие бизнес-ключи справочников ниже не меняются.

Примеры исходных ключей владельца:

    {"O","0","0","0","0","0","       238    464838   "}
    {"O","0","0","0","0","0","       276    464818   "}

Здесь нет %/|, поэтому K совпадает с исходной строкой посимвольно. Кавычки экранируются только внешним CSV-слоем (§30). Одинаковость двух обходов и устойчивость при изменениях проверяет разработчик в будущей приёмке §29.

Формулы:

- документ: `DOC|{K}`;
- касса: `CASH|{K}`;
- банк: `BANK|{K}|{НомерПроводки}`;
- ручная операция: `MANUAL|{K}|{НомерПроводки}`;
- строка ledger: `LED|{K}|{НомерПроводки}|{N}`.

N — последовательный положительный номер экспортируемой стороны корреспонденции в пределах документа и номера проводки данной версии источника. Две стороны 62→62 имеют разные N. Обход всех корреспонденций/сторон должен быть устойчивым при неизменном источнике; это проверяется на базе. N различает строки, но не задаёт хозяйственную очерёдность одновременных сторон и не является постоянным ключом строки между выгрузками.

Имя колонки payment_id в CSV сохраняется, но это исходный ID оплаты для группировки в конкретном пакете. Для BANK/MANUAL он является локатором, а не постоянным ID хозяйственной оплаты. Постоянный ID такой оплаты назначает и хранит Python отдельно; в его хранилище исходное поле называется source_payment_id, постоянное — persistent_payment_id. Эти внутренние имена не добавляют колонок в CSV 1С. Для CASH постоянная идентичность опирается на (source_id, CASH|K).

Версия локатора хранится в Python вместе с source_id и ledger_source_run_id квартала исходного денежного события (§23.4). Новый run_id сборки не меняет версию REUSED-источника. Ссылки связанных переносов/сторно разрешаются к исходному событию; его версию нельзя подменять версией квартала переноса. ledger_event_id также идентифицирует строку этой версии, а не вечную проводку. В одном собранном пакете противоречивые версии одного локатора не объединяются по совпадению ID: это конфликт входа с диагностикой.

После фактического обновления документа Python сопоставляет его прежние и новые оплаты только внутри того же устойчивого документа по контрагенту, сумме, номеру/дате первичного платежа и назначению. Только доказанное однозначное соответствие сохраняет постоянный ID; номер проводки, порядок строк, дата/сумма сами по себе этого не доказывают. При неоднозначности либо исчезновении прежней оплаты сохраняются её история и проверенное решение, фиксируется конфликт для бухгалтера; перенос решения на другую строку и автоматическое подтверждение новой оплаты запрещены. Доказанно новая оплата получает новый постоянный ID. Разделение/объединение оплат автоматически не выполняется; исторические версии не добавляют деньги повторно. Смена реквизитов может потребовать пересмотра распределения даже при сохранённом ID. Для REUSED новое сопоставление версий не производится: необнаруженные изменения остаются принятым ограничением кеша.

Сохраняются бизнес-ключи текущего кода: `C|{код покупателя}`, `D|{КонтрагентID}|{код договора}`, `VR|{идентификатор вида расчётов}`. Проверяются уникальность/устойчивость внутри области учёта. Коллизия не исправляется произвольным суффиксом. run_id не входит в бизнес-ID.

Коды получают из Контр.Код/Дог.Код, идентификатор вида — ВидР.Идентификатор(). Переименование отображаемого объекта не меняет ключ; изменение исходного кода требует выявления изменения и пересмотра связей, не обещания вечной стабильности такого ID.

У агрегированной CASH-оплаты номер проводки отсутствует и не дополняется из ledger, даже если проводка одна. У BANK/MANUAL номер обязателен; MANUAL без номера запрещён. Несколько PAYMENT могут ссылаться на одну выписку.

Позиции `"#20260601 679630000    464838   "` и `"#20260601 680830000    465538   "` сохраняются посимвольно, включая завершающие пробелы. Запрещены СокрЛП, .strip(), замена пробелов/регистра позиции. P/B/M далее — условные устойчивые ключи документов, не позиции и не реальные значения.

Изменение позиции/номера документа не меняет DOC|K и CASH|K. Перенумерация проводок может изменить BANK/MANUAL и ledger-локаторы, но сама по себе не создаёт новую хозяйственную оплату. Системная ссылка обеспечивает прослеживаемость объекта, не устойчивость строки выписки. Один ID не гарантирует неизменность содержания документа.

## 9. Тексты и происхождение

СодержаниеПроводки ← Опер.СодержаниеПроводки; Содержание ledger ← Опер.Содержание; ПредставлениеПроводки ← Опер.ПредставлениеПроводки(); ПервичныйДокумент ← доступное исходное представление Опер.ПервичныйДокумент. Последнее не объявляется структурированной ссылкой без проверки типа.

Тексты раздельные, сохраняются полностью, без извлечения только цифр номера или выбора первого непустого поля. Python разбирает основания с привязкой к строке/полю. Текст не доказывает связь с конкретным объектом.

ИсточникНазначения: POSTING_CONTENT — содержание проводки; PRIMARY_DOCUMENT — подтверждённый реквизит первичного документа; UNAVAILABLE — источник недоступен, назначение пусто, причина в diagnostics. Перечисление не утверждает наличие конкретного реквизита.

## 10. Комментарии

КомментарийДокумента ledger относится к источнику движения, Комментарий documents — к своему документу, КомментарийДокументаОплаты — к подтверждённому платёжному документу. Доступный Док.Комментарий читается с проверкой наличия реквизита. Исходные строки «Введен на основании: …» сохраняются. Текущий base_document_links.py читает Комментарий documents; новый потребитель должен учитывать остальные переданные источники.

Прочитанная пустая строка допустима. Отсутствующий реквизит/ошибка чтения отличаются от неё диагностикой. Для связанного движения комментарий оплаты повторяется только при доказанной принадлежности.

## 11. Аналитика

У каждой стороны ledger свои покупатель, договор и вид расчётов. Не копировать аналитику другой стороны переноса. Наименование — для показа, ID — для связи.

Разрезы методики: CUSTOMER и CUSTOMER_CONTRACT по объединению 62.1/62.2. Вид расчётов — признак проверки кандидата, не третья пара долг/аванс. У 62.2 и INVOICE его отсутствие штатно; фиктивный вид «пусто» не создаётся.

Пустой договор не означает все договоры. В снимках различаются EMPTY (подтверждённо пустой) и UNKNOWN (недоступен); в ledger/documents неизвестность фиксируется diagnostics. Несколько договоров ПКО сохраняются в движениях, единый договор всей оплаты Python не выдумывает. При достоверном покупателе общий вариант остаётся доступен.

## 12. ledger62.csv

Канонический заголовок, порядок фиксирован:

```text
ledger_event_id;source_document_id;payment_id;ДатаОперации;ПозицияДокумента;НомерСтрокиВДокументе;НомерПроводкиВДокументе;ВидДокумента;НомерДокумента;ДатаДокумента;СуммаКоп;СчетДебета;СчетКредита;Счет62;Сторона62;КонтрагентID;Контрагент;ДоговорID;Договор;НомерДоговора;ДатаДоговора;ВидРасчетовID;ВидРасчетовСПокупателем;СодержаниеПроводки;Содержание;ПредставлениеПроводки;КомментарийДокумента;ПервичныйДокумент;MovementRole;PaymentKind;PaymentGranularity;ВидДокументаОплаты;НомерДокументаОплаты;ДатаДокументаОплаты;НазначениеПлатежа;ИсточникНазначения;КомментарийДокументаОплаты
```

Одна строка — одна сторона 62 корреспонденции. Все строки сохраняются, включая отрицательные/нулевые, возвраты, зачёты, переносы и неизвестные виды источника. Для 62→62 две строки; равенство сумм не разрешает удалить одну.

Обязательны ID строки, дата операции, точная позиция, положительный целый номер проводки, оба счёта, Счет62, Сторона62 (D/K), подписанная СуммаКоп, MovementRole. Отсутствие обязательной позиции/номера или неоднозначный ID — ошибка полного пакета; факт остаётся в незавершённом диагностическом наборе, успешный пакет не публикуется, фиктивная позиция не создаётся. Если исходные идентификаторы сохранены, но их временное сравнение или граница группы не подтверждены, это отдельная неизвестность порядка по §§22, 27, а не утрата исходной строки.

source_document_id всегда означает породивший движение DOC, не PAYMENT и не изменяемое исполнение. При доступном объекте обязателен и разрешается через DOCUMENT id_map; объект не обязан быть кандидатом documents. Недоступность объекта не оправдывает потерю движения, но нарушает приёмку прослеживаемости.

payment_id заполнен только при доказанной принадлежности денежному событию. Для самостоятельного неденежного движения пуст; для связанного переноса/сторно допустима ссылка на установленную оплату без денежного вклада. Неизвестная принадлежность диагностируется, не определяется равенством даты/суммы.

payment_id не дублирует source_document_id по смыслу: source_document_id отвечает на вопрос «какой документ породил движение», payment_id — «к какому исходному денежному событию относится движение в данном пакете». Отдельной колонки document_id в ledger нет, она есть в documents.csv. У двух оплат одной выписки source_document_id одинаков (`DOC|B`), а payment_id различается (`BANK|B|2`, `BANK|B|10`). У ПКО оба ID связаны с одним объектом, но обозначают разные сущности (`DOC|P` и `CASH|P`). В действующем выгрузчике для части денежных строк используется присваивание srcId=payId; это фактическое дублирование старой реализации, которое не является правилом контракта v4. Код в данном документальном этапе не изменяется.

MovementRole: CASH_IN — фактическое поступление; CASH_OUT — фактический возврат; REVERSAL — техническое сторно; NONCASH — отгрузка/зачёт/перенос/иное неденежное изменение; UNKNOWN — неустановленная природа. Основание — счета, знак и доказанный механизм проведения; одного слова в тексте/отрицательного знака недостаточно. UNKNOWN влияет на сальдо, но до ручного решения не создаёт подтверждённую оплату. Для спорных возвратов/сторно экспортёр сохраняет UNKNOWN и MOVEMENT_ROLE_UNKNOWN; обязательная автоматическая классификация не требуется. Исходные локаторы/снимки сохраняются. Если денежная принадлежность ещё не установлена, payment_id пуст; событие доступно в Python по source_document_id и ledger_event_id версии. После решения Python хранит производную роль/группу и постоянную идентичность отдельно, без новых колонок и переписывания входа.

PaymentKind/Granularity обязательны при payment_id, иначе пусты. CASH→DOCUMENT, BANK/MANUAL→POSTING. Первичные реквизиты одной группы совпадают либо явно неизвестны; конфликт нельзя разрешать первой строкой. Тексты движений могут различаться и сохраняются все. Аналитика читается со стороны 62; неизвестный покупатель диагностируется, движение остаётся, оценка разреза неподтверждённая.

СуммаКоп — сумма корреспонденции со знаком, не модуль. Изменение сальдо: D→+СуммаКоп, K→−СуммаКоп, независимо от роли. Внутренний перенос даёт ноль по покупателю при двух договорных изменениях.

### 12.1. Денежная сумма без двойного учёта

Внутри принятого пакета Python группирует подтверждённые строки по исходному payment_id; между версиями источника действует сопоставление §7, а не равенство этой строки. Вклад CASH_IN — сумма K62 против Дт 50/51/55; CASH_OUT — минус сумма D62 против Кт 50/51/55. Каждая денежная корреспонденция учитывается один раз по ledger_event_id. У внутренних движений/REVERSAL денежного вклада нет. Их влияние на сальдо/действительность источника сохраняется отдельно.

Противоречие роли, знака и счетов означает неподтверждённую оплату с диагностикой, не применение модуля. Исходная оплата и поздний денежный возврат имеют разные payment_id; техническое сторно не становится денежной парой.

ПКО: денежные K-строки 6000000 и 4000000 копеек, внутренний перенос 4000000 двумя сторонами. Одна CASH-оплата =10000000, не 14000000/18000000. Изменение общего сальдо =−10000000. Объект оплаты повторно сальдо не меняет.

В данной базе одно банковское поступление не бывает на разных номерах проводок: вопрос закрыт. Несколько корреспонденций одной проводки учитываются один раз; самостоятельные оплаты выписки сохраняются раздельно. Обязательная склейка разных номеров не проектируется, совпадение суммы/текста не является основанием склейки. Предложение единой границы сложной группы не становится обязательным случаем банка.

Обязательны document_id, роль/тип, вид, дата, позиция, фактическая сумма и флаги Проведен/ПомеченНаУдаление (`0`/`1`). Номер — строковый реквизит, отсутствие диагностируется; номер не является ID. Сейчас Содержание documents записывается пустым, иного источника в коде не подтверждено.

Не путать итог и текущую строку. В обоих файлах НомерДоговора сейчас получается из Дог.Наименование, ДатаДоговора — из Дог.ДатаВозникновенияОбязательства. Это сохраняемая семантика существующих вспомогательных функций, а не утверждение о наличии реквизитов Дог.Номер/Дог.Дата. Наименования покупателя/договора/вида — представления соответствующих объектов для показа. Эти поля используются Python при проверке оснований и объяснении аналитики.

У RECEIVABLE точное имя реквизита — ВидыРасчетовСПокупателями, не похожие имена CSV. Заполненное значение используется; при пустом и проведённом документе допустим текущий поиск вида по проводкам 62. Одно найденное значение записывается; несколько значений оставляют поле пустым с диагностикой, детализация остаётся в ledger. Прежнее ТЗ подтверждает ограничение базы: у проведённой реализации вид должен быть хотя бы в одном из этих источников; полное отсутствие/недоступный обещанный реквизит — ошибка экспорта. Непроведённый документ может иметь пустой вид. У INVOICE реквизит отсутствует штатно, его не читать и не искать альтернативные имена.

### 15.1. Агрегаты НДС

Сохраняются три агрегата прежнего ТЗ, рассчитываемые в одном обходе табличной части Сумма/НДС всех трёх видов. НДС — сумма в рублях, не ставка. Положительный НДС: сумма строки входит в облагаемую, НДС суммируется отдельно. Прочитанный нулевой или штатно пустой НДС означает необлагаемую строку по подтверждённой семантике базы. Расчёт 5/105 не заменяет исходный НДС.

VATCompositionStatus=KNOWN только при достоверно прочитанных согласованных агрегатах. Инвариант: СуммаОблагаемаяКоп+СуммаНеоблагаемаяКоп=СуммаКоп; НДС входит в облагаемую сумму, повторно к итогу не добавляется.

Отрицательный НДС строки, пустая табличная часть при ненулевом итоге или расхождение инварианта: VATCompositionStatus=UNKNOWN, все три агрегата пусты, причина в diagnostics. Это замена старого кодирования неизвестности тремя нулями. Отрицательные исходные суммы документов/движений сохраняются. Достоверный нулевой итог с нулевыми агрегатами допускает KNOWN. Отсутствующий обещанный реквизит НДС/ошибка чтения — ошибка экспорта, не нулевой налог.

Не выгружать/не накапливать товарные строки, не выполнять второй обход ради НДС. Выбор налогового источника и правила возврата остаются в Python; новые налоговые нормы здесь не устанавливаются.

## 16. Счета и основания

Все счета доступной истории выгружаются независимо от проводок и найденных оплат. Ссылки исполнения на счёт сохраняются в исходных комментариях/содержании; Python разбирает номер, дату, вид основания с учётом других документов и назначений оплат.

Старые счета до 01.01.2026 не получать, не выгружать и не проверять. Их реквизиты из назначения — ключ поиска исполнений в доступной истории с 2026 года. Текст ссылки сохраняется без строки старого документа/требования восстановить его объект. Год счёта не превращает найденное исполнение в старый долг.

При отсутствии исполнения Python применяет принятое правило старого долга с контролем ресурса. При частичном/неоднозначном исполнении остаток остаётся бухгалтеру. Экспорт эти решения не принимает. Сбой parser не доказывает отсутствия ссылок.

## 17. Изменения и доступные связи

Сохраняются все влияющие движения: денежные возвраты, сторно поступлений/исполнений, зачёты, переносы между субсчетами/договорами/покупателями. Завершение подбора оплаты не останавливает выгрузку истории. Для возврата нужны собственный комментарий и доступное основание исходной оплаты. Условия исключения полной пары одного календарного квартала остаются в ТЗ №2 §8.5, не выполняются экспортёром.

По уточнению владельца один акт в данной конфигурации всегда закрывает ровно один счёт. Сценарий распределения одного исполнения между несколькими счетами не является допустимым хозяйственным случаем конфигурации; модель неизвестных долей между счетами не требуется. Это не устанавливает обратное ограничение «один счёт — только один акт» и не отменяет контроль сумм и частичных оплат.

Ссылка на счёт в комментарии документа формируется программой в стабильном формате и надёжно разбирается парсером Python. Комментарий передаётся полностью, но не остаётся только архивным текстом: parser извлекает вид, номер и дату основания, а Python использует их для связи исполнения со счётом. В коде это чтение выполняют parse_base_link/document_is_based_on_invoice в src/kudir/base_document_links.py. Для штатной связи акт→счёт не требуется ожидать отдельного структурированного реквизита или объявлять связь неизвестной лишь потому, что она передана комментарием.

Если вопреки штатному формату в одном комментарии обнаружено несколько разных счетов, это аномалия для ручного разбирательства: записать WARNING с кодом MULTIPLE_INVOICE_REFERENCES в diagnostics проверки Python, привязать его к document_id и полю Комментарий, сохранить исходный текст и найденные альтернативы. Не завершать обработку пакета ошибкой, не выбирать первый счёт молча и не распределять сумму по предполагаемым долям. Связь этого документа остаётся неразрешённой до решения бухгалтера; остальные документы обрабатываются. Это требование обработки аномалии, а не утверждение о реализованной проверке множественных ссылок: текущий parse_base_link использует поиск первого совпадения. Форма диагностики — §27; диагностика проверки Python не переписывает исходный квартальный кеш.

Надёжной отдельной связи «изменение/возврат → исполнение → сумма» практически нет, что подтверждено владельцем. Природу возврата/сторно, связи и суммы устанавливает бухгалтер в данных Python; универсальное автоматическое правило OD7 не требуется. Текст проводки — материал разбора, не гарантированная атрибуция. Решение имеет основание, историю, статус проверки и пересмотр при изменении фактов. До решения неопределённое влияние видно отдельно. CSV и проводки не изменяются, signed-влияние не дублируется; произвольный акт/счёт по знаку/названию/тексту не освобождается. После установления данных действуют U2/U4, OD2/OD3 и U5, общий контроль суммы. Новые CSV/выдуманные реквизиты не требуются. Штатная ссылка акт→счёт остаётся отдельным установленным фактом.

«Тихое» редактирование шапки/условий счёта без сохранённой истории остаётся только теоретическим ограничением: текущая сумма сама по себе не позволяет восстановить прежнюю редакцию. По подтверждению владельца в закрытом периоде такое редактирование исключено, в открытом практически не встречается и на логику сопоставления не влияет. Оно не вводит дополнительной блокировки сопоставления или обязательной неизвестности доступности штатного счёта. История версий не предполагается; изменения, отражённые отдельными операциями, по-прежнему передаются ledger. Принятое ограничение кеширования кварталов по четырём общим остаткам сохраняется.

## 18. Функция владельца для банковской первички

Точка подключения — получение реквизитов конкретного банковского поступления/возврата перед записью его ledger. Функцию владелец сам вручную допишет; её предоставление сейчас не требуется и начало Python не блокирует; конфигурационный алгоритм/программный вызов в этом этапе не создаются.

Вход: достоверная ссылка на выписку, её устойчивый ключ, точная позиция и положительный целый номер проводки текущей согласованно читаемой версии. Номер строки не нужен. Сумма/текст не заменяют адрес проводки этой версии; этот адрес не является постоянным ключом оплаты.

Результат: номер первичного платёжного документа (строка), дата (дата или отсутствие), состояние FOUND, PARTIAL, NOT_FOUND, AMBIGUOUS, NOT_CONNECTED либо ERROR и причина. Это логический контракт, не утверждение о готовой сигнатуре 1С. Номер/дата отсутствуют независимо; FOUND требует оба, PARTIAL сохраняет только достоверную часть. При неоднозначности не выбирать первый вариант; ERROR не подменять отсутствием.

Реквизиты идут в НомерДокументаОплаты/ДатаДокументаОплаты; все состояния кроме FOUND фиксируются diagnostics с payment_id и затронутым полем. Пока функция не подключена, оба поля пусты и диагностированы. Достоверные учётные факты могут анализироваться с видимой неполнотой, но получение первички не считается принятым.

Пример: проводка 7 выписки №100 от 01.06.2026, функция вернула №55 от 31.05.2026. ДатаОперации остаётся 01.06; реквизиты источника — 100/01.06; первичные — 55/31.05. При отсутствии результата 100/01.06 в первичку не подставляются.

Реализация (11.10.2026, kudir_export `2026.10.11-03`, по данным BANKDIAG_20261011_001 и проверке владельца): источник — строка табличной части выписки, ссылка ПервичныйДокумент (номер и дата — НомерДок/ДатаДок документа-платёжки, не её представление), без ссылки — список РеквизитыПлатДокументов. Строка находится по проводке сопоставлением всей выписки: проводки идут в порядке строк, денежная проводка берёт следующую свободную строку с тем же направлением, суммой, корр. счётом, субконто 1–3 и началом назначения платежа; строка без проводки пропускается. Проводке без строки или пропущенной строке с ключом сопоставленной — AMBIGUOUS на всю выписку. Несколько платёжек одной строки — номера через «; » и общая дата (FOUND); разные даты — PARTIAL без даты; список, обрезанный длиной поля, — PARTIAL с прочитанными номерами и диагностикой по номеру.

## 19. Получение фактов

1. Установить область, доступную конечную дату и согласованное чтение; новый каталог запуска имеет статус WRITING.
2. Получить четыре общих квартальных контроля, проверить наличие полных сохранённых квартальных пакетов и определить повторное использование всего пакета квартала (§23.4).
3. Для REUSED взять из последнего успешного сохранения весь квартальный комплект: ledger, documents, snapshots и id_map вместе с относящейся диагностикой. Эти данные из 1С повторно не получать.
4. Для REFRESHED получить заново весь комплект квартала: ledger с принадлежностью, ролями и текстами, документы с агрегатами, обязательные снимки и id_map. Потоково собрать сохранённые и обновлённые кварталы без пропусков и дублей.
5. Проверить комплект, закрыть потоки; опубликовать manifest, контроли и COMPLETE только после успеха всего пакета. При сбое сохранить последний успешный пакет.

Это этапы получения данных, не план изменения программных модулей. Жизненный цикл памяти/публикация — ТЗ №4.

## 20. Согласованность и ограничение сохранённого квартального пакета

Свежие контрольные остатки и данные обновляемых кварталов читаются на живой базе в принятых владельцем условиях: пользователей мало, мешающих изменений они не внесут. source_read_mode=QUIET_WINDOW отражает эти условия без отдельного согласования окна, блокировок или автоматического создания копии. CONSISTENT_COPY допустим только при фактическом чтении копии, которую пользователь при необходимости создаёт вручную. Новых средств согласованности не требуется. Контроль структуры, ошибок и полноты сохраняется; заявление владельца не является выполненным испытанием. Кешированные кварталы сохраняют состояние своего успешного получения.

По принятому решению владельца совпадение четырёх общих остатков с последним успешным сохранением разрешает пропустить ВЕСЬ пакет полного квартала: ledger, documents, snapshots и id_map. Снимки и ссылки такого квартала не освежаются отдельными запросами. COMPLETE означает завершённость по правилам v4, а не актуальность каждого сохранённого факта на момент нового запуска. Происхождение в ledger_quarters относится ко всему квартальному комплекту.

Изменения, не влияющие на четыре общих остатка, не обнаруживаются: это принятое ограничение для проводок, документов, снимков и id_map, включая тексты, аналитику, реквизиты, состав документов и доступность объектов. Новая диагностика этих изменений не обещается, поскольку данные пропущенного квартала не читаются. Проверки уже собранных файлов сохраняются; обнаруженное в них расхождение, в том числе между кварталами разных сохранений, показывается как неподтверждённая оценка и не становится дополнительным условием перечитывания. Для актуализации всего комплекта всех кварталов есть FULL.

## 21. Типы и пустота

На транспорте поля текстовые; ID, позиции, номера и тексты — строки. Даты YYYY-MM-DD в календаре учёта, без перевода ДатаОперации в UTC. Номера документов/коды сохраняют ведущие нули. Номера проводок/N — положительные десятичные целые, сравниваются численно. Флаги только 0/1, перечисления только из данного контракта.

Суммы Коп/kopecks — целые копейки регламентированного учёта RUB: 100 рублей→10000; −0,01→-1. Без разделителей тысяч, десятичных частей и экспоненты. Перевод рублей симметричен по знаку; Python считает целыми без float. Иная учётная валюта требует уточнения, валютные и рублёвые суммы не смешиваются.

Пустое поле — отсутствие, никогда не ноль/false/все договоры/полная свободная сумма. Известный ноль — 0. Существенная неизвестность объясняется diagnostics. Штатно неприменимые поля (строка MANUAL, вид 62.2/INVOICE) не требуют сообщений на каждую строку.

## 22. Хронология

Документы упорядочены шкалой времени 1С, внутри — числовым номером проводки. Ledger/documents записываются в порядке учёта. Стороны одной корреспонденции не являются отдельными последовательными денежными событиями. 2 перед 10, независимо от строки ID.

Позиция хранится исходной строкой; разбор/сравнение в Python допускается после подтверждения соответствия порядку 1С. Номер/дата документа, лексикографический ID или случайная очередь CSV порядок не заменяют. При сохранённых исходных позициях неустановленный междокументный порядок отмечается ORDER_UNKNOWN: затронутая временная классификация/пара долг–аванс неподтверждённая, технический порядок строк файла не выдаётся за хозяйственный. Полная приёмка хронологии требует проверки на базе; event_seq не вводится.

Перед оплатой Python берёт преддокументный снимок и только предшествующие независимые движения документа данного разреза. Собственные/последующие движения оплаты исключены. Для сложной группы с неустановленной границей сохраняются факты и неопределённость, правило «перед первым движением» §14.2.1 не утверждается.

## 23. Снимки и метаданные

### 23.1. balance_snapshots.csv

```text
BoundaryKind;BoundaryDate;BeforeDocumentID;ПозицияДокумента;Slice;КонтрагентID;ДоговорID;ContractState;ОстатокДтКоп;ОстатокКтКоп;Status
```

BoundaryKind=DAY_START либо BEFORE_DOCUMENT; BoundaryDate обязательна. DAY_START исключает все движения указанного дня, ID/позиция пусты. BEFORE_DOCUMENT: ID/позиция обязательны, состояние после всех предшествующих документов и до всех проводок данного документа; BoundaryDate — его дата операции. Это не конец дня/остаток после выписки.

Slice=CUSTOMER или CUSTOMER_CONTRACT; КонтрагентID обязателен. CUSTOMER: договор пуст, ContractState=ALL (итог этого покупателя). CUSTOMER_CONTRACT: VALUE с обязательным ID, EMPTY с подтверждённо пустым договором или UNKNOWN при недоступности. EMPTY не является итогом всех договоров. Status=KNOWN или UNKNOWN; у KNOWN обе суммы обязательны, включая нули; у UNKNOWN обе пусты и причина в diagnostics. Для неизвестного договора статус UNKNOWN.

Ключ: (BoundaryKind, BoundaryDate, BeforeDocumentID, Slice, КонтрагентID, ContractState, ДоговорID). Одна строка на ключ; позиция соответствует ID. Годовая/квартальная граница при совпадении — один DAY_START для двух целей.

Обязательные прямые снимки 1С: начало 01.01.2026; начало каждого следующего года охвата; начало всех кварталов охвата, включая текущий неполный; непосредственно перед каждым документом поступления/возврата, включая ещё не разобранную группу денежных движений.

«Прямые» обозначает источник снимков при получении квартала. При REUSED обязательные снимки входят в сохранённый пакет квартала и повторно из 1С не запрашиваются; для REFRESHED получаются заново вместе с остальным комплектом. DAY_START принадлежит начинающемуся на этой границе кварталу, годовой снимок — его I кварталу; BEFORE_DOCUMENT — кварталу документа по дате операции. Расширение охвата само по себе не дополняет снимки REUSED-кварталов новой аналитикой. Если для нового контекста в сохранённых снимках нет ключа, это неизвестность, не ноль и не скрытый повод перечитать квартал; актуализация выполняется через FULL.

Годовые/квартальные снимки получают в двух разрезах по всем покупателям/договорам, присутствующим во входящих остатках, ledger или documents всей области, включая нулевой остаток на данной границе. Этот набор определяется по полной истории, не по выбранным оплатам. Преддокументные снимки — для покупателей/договоров затронутых движений документа. Несколько оплат выписки одного ключа используют один снимок. Отсутствие необходимого ключа — отсутствие данных, не ноль.

В обоих разрезах объединены 62.1/62.2, без повторного родительского итога. S=Дт−Кт: положительное — долг, отрицательное — аванс. Исходные знаки учётных компонентов при сторно не превращаются в модуль. Два разреза — один ресурс. Сальдо CUSTOMER сверяется с суммой договорных сальдо, включая EMPTY; при UNKNOWN сверка не считается успешной. Отдельные Дт/Кт разных разрезов после свёртки могут различаться, сверяется подписанный результат.

Сверка: S начала квартала + подписанные движения от включённого начала квартала до исключённой позиции документа = S перед документом. Затем только предшествующие независимые движения этого документа доводят состояние до оплаты. К готовому преддокументному снимку история повторно не прибавляется. Аналогично сверяются годовые/квартальные границы между собой. Допуск 0 копеек; расхождение не скрывать произвольным допуском.

Новый квартал/год не добавляет старого ресурса и не освобождает документы. Старый долг начинается 01.01.2026; квартальный долг может содержать документы 2026 года.

### 23.2. manifest.csv / export_status.csv

Оба файла key;value, ключи уникальны. Порядок manifest:

```text
run_id
schema_version
identity_scheme
encoding
source_id
account_scope
currency
history_start
match_horizon_end
source_read_mode
export_mode
coverage_status
```

run_id — уникальный непустой ID запуска; schema_version=4; identity_scheme=STABLE_DOCUMENT_V1; encoding=windows-1251; source_id — стабильное заданное обозначение базы/области учёта; account_scope=62.1+62.2:ALL_CUSTOMERS; currency=RUB. Даты по §4. source_read_mode=QUIET_WINDOW для живой базы; CONSISTENT_COPY — только для фактически выбранной ручной копии (§20). export_mode=INCREMENTAL либо FULL. coverage_status=COMPLETE либо INCOMPLETE. Старые date_start/date_end/quarter_end удалены, это не границы входа.

export_status: ключи run_id, schema_version, status в таком порядке. status=WRITING/COMPLETE/FAILED. COMPLETE записывается последним после закрытия всех файлов и проверок. Только COMPLETE при совпадении run_id/версии и coverage_status=COMPLETE допускает вход Python. Нет маркера/незаконченная запись/несовпадение — отказ от пакета. Неполнота необязательного реквизита допускает COMPLETE с diagnostics, потеря обязательных фактов/охвата — нет.

### 23.3. id_map.csv

DOCUMENT.id совпадает с устойчивым DOC|K в source_document_id/documents.document_id/BeforeDocumentID. Позиция, номер и дата — реквизиты полученной версии объекта; смена этих реквизитов не создаёт новый DOCUMENT. PAYMENT.id содержит исходный payment_id пакета по §7, не persistent_payment_id Python. У BANK/MANUAL ссылка указывает на документ выписки/операции, а номер проводки — только на место в данной версии: открытие той же проводки после редактирования не доказывает прежнюю оплату. Сериализованная ссылка и устойчивый ключ имеют разные назначения; равенство/неравенство сериализации не заменяет сопоставление оплат в Python.

```text
entity_type;id;вид;номер;дата;позиция;номер_проводки;ссылка_1С
```

Сохраняется прежний заголовок; позиция означает точную позицию документа на шкале времени 1С. Типы: PAYMENT — документ денежного события; DOCUMENT — кандидат или источник движения; CONTRACT — договор. LEDGER/COUNTERPARTY не добавляются. Ключ (entity_type,id), одна строка/один объект; несколько ID могут ссылаться на один объект.

PAYMENT/DOCUMENT: вид/позиция обязательны, номер/дата — доступные реквизиты именно объекта. У банковского PAYMENT это выписка, не первичка ledger. Номер проводки обязателен для BANK/MANUAL, пуст для CASH/DOCUMENT. У CONTRACT позиция/номер проводки пусты. Все непустые договорные ID ledger/documents/snapshots, source_document_id, document_id и подтверждённые payment_id разрешаются в id_map.

ссылка_1С — точный результат ЗначениеВСтрокуВнутр(Объект1С), без СокрЛП/нормализации. Python хранит непрозрачную строку, не исполняет/не интерпретирует. Проверка обратимости ЗначениеИзСтрокиВнутр на базе при получении квартала подтверждает прослеживаемость, не требует загрузчика отчёта. При REUSED сохраняется id_map того же квартального комплекта: объекты не открываются повторно ради обновления ссылок или проверки их текущей доступности. Один ключ на разные системные строки в собираемом наборе — ошибка, не выбор первой. Представление объекта не заменяет системную ссылку.

### 23.4. ledger_quarters.csv

Имя файла и имена колонок сохраняются; решение о кешировании и происхождение описывают теперь ВЕСЬ пакет квартала, а не один ledger. Число ledger-строк остаётся отдельной характеристикой внутри полного комплекта.

```text
quarter_start;quarter_end;covered_through;full_quarter;opening_debit_kopecks;opening_credit_kopecks;closing_debit_kopecks;closing_credit_kopecks;control_status;ledger_action;ledger_source_run_id;ledger_row_count
```

Ключ quarter_start, одна строка на квартал охвата. quarter_end — последний день календарного квартала; covered_through — последняя полностью покрытая дата квартального комплекта. full_quarter=1 только при всех днях/полной области и полном составе ledger, documents, snapshots и id_map, иначе 0. ledger_row_count — неотрицательное целое, включая обе стороны; ноль допустим для доказанно пустого ledger и не доказывает отсутствие документов или снимков.

Четыре значения — прямые ОБЩИЕ Дт/Кт объединённых 62.1/62.2 на начало/конец календарного квартала, БЕЗ разрезов покупателей/договоров/видов расчётов. Компоненты двух субсчетов суммируются в одинаковой настройке общих итогов, без повторного родительского итога. Не заменять их max(нетто,0) и сравнением клиентов. Начало — до первого движения первого дня, конец — после всех движений последнего дня до следующего квартала. Настройки/границы повторного запроса те же.

control_status=KNOWN при четырёх достоверных суммах, иначе UNKNOWN с пустыми недоступными значениями и причиной diagnostics. Для текущего неполного квартала closing-поля пусты, UNKNOWN, full_quarter=0; остаток на covered_through не выдаётся за календарный конец.

ledger_action=REUSED/REFRESHED применяется ко всему квартальному комплекту. ledger_source_run_id — успешный запуск, фактически получивший этот комплект (старый для REUSED, текущий для REFRESHED). Кеш также связан с source_id, областью, версией и границами: чужая база, старая версия, обрезанная выборка или прежний кеш только ledger не являются полным квартальным пакетом. Полнота фиксирует успешное получение всего комплекта, а не повторную проверку его актуальности в базе.

Достаточное правило: полный сохранённый пакет квартала нужной области v4 есть, все четыре свежих общих остатка KNOWN совпали с контролями последнего успешного сохранения — REUSED для ledger, documents, snapshots и id_map целиком, без их повторного получения из 1С. Сравнения оборотов, хешей, журнала изменений, отдельных клиентов/договоров, документов, снимков или ссылок с текущей базой не требуются. Одного нетто недостаточно. Любое отличие/неизвестное контрольное значение или отсутствие полного квартального комплекта — получить ВЕСЬ квартал заново и заменить все четыре его набора вместе; отсутствие одного набора нельзя исправлять частичным освежением остальных из разных запусков.

Текущий неполный квартал всегда обновляется всем комплектом от начала до фактической конечной даты. При расширении до конца квартала получить полный комплект заново; новые кварталы получить целиком в доступном охвате. Старые полные кварталы следуют тому же правилу четырёх значений. FULL перечитывает ledger, documents, snapshots и id_map всех кварталов. В REFRESHED удалённые/изменённые строки исчезают за счёт замены квартальной части каждого набора, не добавления поверх старых. Перенос даты между кварталами при сохранённых общих остатках может не обнаружиться; FULL получает действующий набор.

Общие контроли определяют пропуск всего квартального пакета, но не заменяют методические снимки: в итог входят сохранённые снимки REUSED-кварталов и заново полученные снимки REFRESHED-кварталов. Изменения, не влияющие на общие остатки, не обнаруживаются во всех четырёх наборах — принятое ограничение, не повод вводить дополнительные доказательства неизменности.

Квартальная часть ledger определяется ДатаОперации, documents — ДатаДокумента; снимки распределены по §23.1. Квартальный id_map содержит ссылки, необходимые его ledger/documents/snapshots, в том числе общие с другими кварталами договоры. Вместе с комплектом сохраняется относящаяся к нему диагностика, чтобы при REUSED не потерять известную неполноту. Итоговые manifest/export_status/ledger_quarters формируются для нового запуска; запись новой служебной оболочки не означает перечитывания квартальных фактов.

Сборка объединяет квартальные части каждого файла. Общие ключи id_map выводятся один раз: совпадающая системная ссылка означает тот же объект; при различии только описательных реквизитов используется строка из более позднего календарного квартала среди включённых частей, без запроса 1С и без изменения исходных кешей. Разные системные ссылки одного ключа — ошибка коллизии. Совпадающие годовой/квартальный снимки также выводятся один раз по их ключу. При замене квартала общая ссылка остаётся, если её требует другая включённая часть; старые строки удаляются по принадлежности заменяемому комплекту, а не безусловным удалением всех общих ID.

## 24. Источник → назначение → потребитель Python

Имена модулей обозначают существующие точки работы, не готовую поддержку v4:

- Версия, источник, охват, завершённость из метаданных экспорта → полнота/совместимость → loaders.py/csv_io.py и выбор периода engine.py/интерфейса.
- Проводки и доказанная принадлежность первичному поступлению → денежная сумма и единица оплаты → будущая сборка оплат вместо чтения payments. Вид/гранулярность берутся из проверенного вида документа, первичка банка — из функции владельца.
- Содержание/назначение/комментарии из конкретных объектов и проводок → прямые основания и просмотр → parser, поиск кандидатов и интерфейс. Исходные поля не заменяются результатом разбора.
- Сторона, сумма, аналитика из обеих сторон операции → подписанное состояние → ledger.py и два варианта документа 11 §4. Текущий четырёхкомпонентный analytics_key не является реализацией двух новых разрезов.
- Прямые бухгалтерские итоги на заданных границах → старый ресурс, состояние до документа, сверка кварталов → будущий потребитель снимков по документу 11 §3; готового читателя нового файла нет.
- Сумма, статусы и основания документов → цепочки счёт/исполнение, действительность и доступность → base_document_links.py и сопоставление §§6–8 документа 11. Два сальдо не восстанавливают документную доступность.
- НДС из табличной части с достоверностью → исходный состав → налоговый слой Python; 1С не выбирает налоговое основание оплаты.
- Четыре общих квартальных остатка → повторное использование всего квартального комплекта ledger/documents/snapshots/id_map → экспортёр; Python проверяет заявленный охват/состав и показывает происхождение, не выполняет запрос итогов 1С.
- ID/позиции/системные ссылки → соединение фактов с решениями и прослеживаемость → приложение Python. Сохранённые проверенные распределения и конфликты приходят из его хранилища, не из 1С.

## 27. diagnostics.csv

Неоднозначность соответствия оплат между прежней и новой версиями — WARNING в отдельной диагностике Python с постоянным ID (если был), исходными локаторами, source_id и версиями получения; прежние решения сохраняются до ручного разбора. Это не ошибка чтения 1С и не основание переписывать входной diagnostics.csv. Коллизия обязательных ID внутри самого пакета по-прежнему является ошибкой структуры, а не такой неоднозначностью сопоставления.

```text
severity;file;record_key;field;code;message
```

Поля обязательны, кроме field при сообщении обо всей записи. severity=WARNING/ERROR; file — затронутый файл; record_key — ID либо JSON-массив компонентов составного ключа в его порядке (с CSV-экранированием), PACKAGE для пакета. code — стабильный непустой машинный код, message — конкретная причина. Диагностика не заменяет исходный факт.

Минимальные коды: PRIMARY_NOT_CONNECTED, PRIMARY_PARTIAL, PRIMARY_NOT_FOUND, PRIMARY_AMBIGUOUS, PRIMARY_ERROR, SOURCE_FIELD_UNAVAILABLE, PAYMENT_MEMBERSHIP_UNKNOWN, MOVEMENT_ROLE_UNKNOWN, DOCUMENT_LINK_UNKNOWN, ANALYTICS_UNKNOWN, ORDER_UNKNOWN, SNAPSHOT_UNKNOWN, SNAPSHOT_MISMATCH, VAT_COMPOSITION_UNKNOWN, COVERAGE_INCOMPLETE, ID_COLLISION, READ_ERROR, CSV_INVALID.

Для проверки комментариев в Python дополнительно применяется MULTIPLE_INVOICE_REFERENCES уровня WARNING по §17. Это ручное разбирательство по конкретному документу, не ERROR всего пакета. Исходный экспортный diagnostics и сохранённый кеш при проверке не переписываются; предупреждение сохраняется в diagnostics проверки Python с той же привязкой file/record_key/field.

WARNING — факты сохранены, конкретный реквизит/вывод неизвестен: первичка не подключена, связь возврата неизвестна, состав НДС неизвестен, сверка фактов собранных квартальных комплектов дала расхождение или временной порядок не подтверждён при сохранённых позициях. Python показывает неподтверждённую оценку, не ноль. ERROR — потеря обязательных фактов, ошибка чтения обещанного реквизита, неоднозначный ID, отсутствие обязательной позиции/номера, неполный охват, повреждение структуры: пакет FAILED. Неизвестный обязательный снимок сохраняется как UNKNOWN для разбора причины, но приёмку полноты снимков не проходит. Неполный календарный квартал при достоверном covered_through сам по себе не ошибка. Диагностика из REUSED-комплекта сохраняется; она не объявляется результатом повторной проверки текущего состояния базы.

Неизвестный результат самого обязательного запроса снимка — SNAPSHOT_UNKNOWN уровня ERROR; известный результат запроса с неизвестной аналитикой — ANALYTICS_UNKNOWN, затронутый разрез неподтверждён. Последний не стирает достоверный общий разрез покупателя. UNKNOWN конечного контроля текущего неполного квартала — ожидаемая причина для REFRESHED, а не ошибка методического снимка. Различие статусов не разрешает подменять отсутствующие числа нулями.

## 28. Проверки на файлах

1. Восемь файлов, версия 4 и identity_scheme=STABLE_DOCUMENT_V1, точные заголовки, кодировка, логические CSV-записи, число полей, типы, завершённость и совпадение run_id. Проверка профиля обязательна также для происхождения кешированных кварталов. Старый пакет не становится совместимым удалением payments или заменой метки версии.
2. Уникальность document_id, ledger_event_id, ключей снимков, кварталов и id_map; формы CASH/BANK/MANUAL, точность позиций, числовые номера, обязательные ссылки. Повтор payment_id допустим, повтор ledger_event_id — нет.

Обязательные снимки/аналитические ключи проверяются по контексту получения комплекта; недостающий для расширенного контекста ключ REUSED-снимка явно неизвестен по §23.1, не считается нулём и не вызывает скрытого освежения квартала.
4. Подписанные изменения D/K, согласованные денежные роли/счета/суммы; внутренние движения не увеличивают деньги, собранная оплата не меняет сальдо второй раз. Все тексты частей сохранены, влияние UNKNOWN не пропущено.
5. Сверки снимков §23.1 с учётом известности; совпадающие границы не создают ресурсов. Общие контроли не заменяются нетто или методическими разрезами.
6. Статусы документов, агрегаты KNOWN/UNKNOWN, пустые поля и diagnostics согласованы. Источник движения не автоматически считается изменяемым исполнением.
7. Сравнение сохранённых пакетов/контролей: REUSED соответствует четырём числам и полному кешу ledger/documents/snapshots/id_map, все четыре части имеют общее происхождение квартального комплекта. REFRESHED заменяет весь комплект, FULL не переиспользует его части. Проверить сборку общих ключей и сохранение диагностики. На файлах проверяется заявленное происхождение, но не доказывается свежий запрос контролей в 1С.

Текущие loaders требуют payments/is_target и равенство суммы всех связанных ledger-строк; их успешный запуск не проверяет новый контракт.

## 29. Проверки на базе и приёмка

Дополнительная приёмка идентичности: изменение времени/номера/содержимого документа сохраняет DOC|K, а для CASH также CASH|K; позиция и снимок BEFORE_DOCUMENT отражают фактически прочитанную версию. После добавления/удаления строки выписки прежняя оплата с проводки 5 может перейти на 4: локатор BANK|K|5 меняется на BANK|K|4, но при доказанном соответствии Python сохраняет persistent_payment_id. Новая оплата на проводке 5 не наследует прежнее решение. Две неразличимые оплаты дают конфликт для бухгалтера, без выбора по порядку, падения сопоставления или потери истории. Удаление оплаты и разделение/объединение также не разрешаются молча. Эти сценарии выполняются после REFRESHED/FULL; REUSED не выявляет такие изменения. Если перенос документа между кварталами дал противоречивые версии одного устойчивого ID в собранных файлах, фиксируется конфликт входа, а не новый ID или суммирование дублей; это не добавляет условия автоматического перечитывания кеша.

На живой базе в принятых условиях разработчик при получении квартального комплекта проверяет полноту покупателей/движений/документов, границы, метаданные, принадлежность денег и сохранение UNKNOWN спорной роли для ручного решения, позиции/корреспонденции, первичку владельца и системные ссылки. Сверить каждый вид прямых снимков с итогами на одинаковых границах, включая переносы, сторно, нули и 62.2 без вида. При проверке REUSED убедиться, что после сравнения четырёх общих остатков ни ledger, ни документы, ни снимки, ни id_map этого квартала не запрашиваются заново. Проверка их актуальности в текущей базе не является дополнительным условием REUSED. CSV сам по себе не доказывает отсутствия пропущенного объекта.

Приёмка: полный пакет большого охвата без аварии памяти; смена квартала в покрытой истории; четыре совпавших контроля; отличие компонентов при равном нетто; отсутствие/неполнота кеша; текущий квартал; расширение на новый год; FULL; обрыв получения/публикации без утраты последнего успешного пакета. Обратимость системной ссылки возвращает тот же объект нужного типа, не требует разработки обратного загрузчика отчёта.

Ошибки для текстовых сценариев: дубли ID, обрезанная позиция, MANUAL без номера, слитые банковские оплаты, ноль вместо неизвестного снимка, потерянная сторона переноса, первичка заменена выпиской, частичный квартал объявлен полным, незакрытая кавычка/поток, сбой реквизита, смешение старого ledger с отдельно освежёнными documents/snapshots/id_map того же квартала, отсутствие одной части кеша при объявленном REUSED. Ожидаются диагностика и отказ от неподтверждённого вывода/пакета согласно §27, не исправление факта догадкой.

## 30. CSV и совместимость

Уточнённый контракт v4 имеет обязательный manifest.identity_scheme=STABLE_DOCUMENT_V1. Тот же признак хранится в метаданных квартального кеша; профиль без него либо с прежними ID через позицию несовместим. Его нельзя объявить пригодным REUSED-кварталом, переименовать старые ID без получения ключей или автоматически перенести решения Python. Это проверка совместимости формата, не дополнительный контроль неизменности: при наличии полного совместимого комплекта четыре совпавших общих остатка по-прежнему означают REUSED всех четырёх наборов. Заголовки ledger/id_map сохранены; при реализации потребители должны явно проверить профиль и различать исходный и постоянный ID оплаты (§7).

Windows-1251/cp1251 без BOM, разделитель `;`, окончания записей CRLF. Заголовки обязательны, регистр/порядок точные. Поля с разделителем, кавычкой, CR/LF заключаются в двойные кавычки, внутренняя кавычка удваивается. Допустимо кавычить все строки; позиции с конечными пробелами рекомендуется всегда. Чтение логическими CSV-записями, не физическими строками. Исходные переносы сохраняются. Непредставимые символы нельзя молча заменять вопросительными знаками: ошибка и диагностика.

Позиции, устойчивые ключи, ID и системные ссылки не обрезаются после чтения. Остальные исходные значения также не меняются ради CSV; поисковая нормализация — отдельное производное действие Python.

Версия 4 отделена от фактической 2 и прежнего документального варианта 3 с НДС. Старые payments/opening/выходные CSV и обязательная обратная загрузка не являются требованиями v4. Угадывание версии и частичная совместимость запрещены. Будущие экспортёр/схемы/загрузка/валидация/сборка оплат меняются согласованно; новый заголовок сам по себе не означает готовность.

# ТЗ №2. Python

## Анализ платежей, поиск оплачиваемых документов и формирование строк КУДиР

### 1. Назначение

Документ согласован с `03-ПЛАН-ИСПРАВЛЕНИЙ-КУДиР.md` после ревизии «один цикл» и с `00-АРХИТЕКТУРА-КУДиР.md`. Matcher уже есть в `src/kudir/`; налоговый слой `tax.py` — следующая доработка по этому ТЗ.

Python-программа является аналитическим модулем: matching оплат **и** расчёт готовых строк КУДиР.

Оплата не определяет сумму НДС сама по себе. Python раскладывает поступление на погашение долга и аванс **по каждой аналитике `ledger62`**, ищет документы и сразу считает НДС / доход УСН:

- задолженность — в `DEBT_MATCH_WINDOW` (ИсторияНач → момент оплаты);
- закрытие аванса HIGH — сразу при появлении реализации;
- остальные связи аванса — в `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`;
- фактический НДС — из агрегатов колонки `НДС` найденной отгрузки / оказания услуг, иначе из счёта, иначе 5/105 по шкале аванса.

Отдельного второго цикла `1С → Python → 1С` нет. Константа расчётного НДС: 5%, формула `5/105`. `SUCCESS` и `tax_ready` — разные признаки. `tax_ready=1` означает, что строки можно считать готовой КУДиР.

Вход — файлы каталога `exchange/<run_id>/`:

```text
manifest.csv
payments.csv
ledger62.csv
documents.csv
opening_balances.csv
```

`opening_balances.csv` обязателен. Отсутствие файла — ошибка, расчёт с нуля запрещён. Python читает только каталог текущего `run_id`; два запуска одного периода не делят файлы.

Выход — в тот же каталог:

```text
kudir_result.csv
matches.csv
unresolved.csv
analysis.log
run_status.csv
```

В `kudir_result.csv` попадают только оплаты с `is_target=1`. Исторические оплаты участвуют в matching и восстанавливают остатки документов. Если историческая оплата не сопоставилась, это фиксируется: `historical_unresolved_*`, `state_uncertain=1`. Если неоднозначность касается аналитики, нужной целевому периоду, `tax_ready=0`. `analysis.log` обязателен.

Через CSV передаются ID и скаляры, не объекты 1С. Аналитика оплаты — множество строк `ledger62` с данным `payment_id`. Поля договора/вида расчётов в `payments.csv` matcher не читает.

# 2. Ключевое требование: не писать существующий разбор заново

Parser является внешней зависимостью и в этот репозиторий не входит. Новый parser не разрабатывается и не копируется.

Он уже умеет определять:

```text
смысл платежа
тип упомянутого документа
номер документа
дату документа
номер счета
```

Приоритет:

```text
1. вызывать существующий HTTP-сервис http://127.0.0.1:8765/parse1c;
2. инкапсулировать вызов в legacy_parser_adapter.py;
3. покрыть regression-тестами реальные строки;
4. только после этого добавлять новые правила matcher.
```

Если parser недоступен: для этой оплаты текстовый разбор пропускается, matching продолжается по суммам и основаниям. Система не падает целиком. Итог запуска:

```text
SUCCESS           — parser был доступен
SUCCESS_DEGRADED  — parser недоступен или часть строк не разобрана
FAILED            — ошибка данных, схемы или инварианта
```

`SUCCESS` и `SUCCESS_DEGRADED` — код завершения 0. `FAILED` — ненулевой код, `kudir_result.csv` не создаётся. Статус пишется в `run_status.csv`. 1С при `SUCCESS_DEGRADED` показывает предупреждение; строки `HIGH`, полученные без parser, загружать можно.

`SUCCESS` / `SUCCESS_DEGRADED` не означают `tax_ready=1`. Matching может успешно закончиться при неразрешённых долгах: тогда `status=SUCCESS` (или `SUCCESS_DEGRADED`) и `tax_ready=0`.

Перед разбором проверять `GET /health` (если сервис его отдаёт). Одинаковые строки кэшировать на время запуска. Regression: unit-тесты на сохранённых ответах parser; отдельный integration-тест живого сервиса, который можно пропускать, если сервис не запущен.

Формат запроса/ответа — как у текущего клиента в `доходы-2.txt`. Адрес задаётся конфигурацией, по умолчанию `http://127.0.0.1:8765/parse1c`.

Не создавать новый независимый parser с нуля.

# 4. Хронологическая модель состояния

Оплаты и реализации обрабатываются в едином потоке событий, вперемешку, в порядке:

```text
ДатаОперации
ПозицияДокумента
НомерПроводкиВДокументе
```

Ключ одинаков для `payments.csv` и `ledger62.csv`. `НомерСтрокиВДокументе` пуст и в порядок не входит. Исторические оплаты обрабатываются вместе с целевыми; в результат попадают только `is_target=1`.

Бухгалтерский timeline создаётся **только строками `ledger62.csv`**. `documents.csv` само по себе не добавляет второе движение и не меняет `signed_balance`. Для реализации её ledger-событие связывается с записью `documents.csv` по `source_document_id`; документ даёт метаданные для matching и налога (роль, номер, договор, комментарий, агрегаты НДС), а изменение взаиморасчётов остаётся единственным ledger-событием.

Модель «сначала все долги по всем оплатам, потом все авансы этапом 10» запрещена. Оплата создаёт `ADVANCE` по аналитике. Пришедшая реализация сразу гасит существующий `ADVANCE` только если связь однозначная / HIGH (машинное основание, уникальная цепочка через счёт). Неоднозначные кандидаты не трогают remainder до conflict-resolution pass. Следующая оплата видит только уже зафиксированные HIGH-остатки.

Кейс «январский аванс → A по счёту, мартовская оплата → B» проходит, потому что связь через счёт — HIGH и закрывается до мартовской оплаты.

Для каждой оплаты matcher идёт этапами блокировки, а не одним greedy-проходом:

```text
1. восстановить состояние взаиморасчётов по каждой аналитике
   на момент оплаты;
2. по каждой части ledger62 этой оплаты отдельно:
   debt_before, debt_part, advance_part;
3. заблокировать уникальные машинные ссылки
   (ПКО / «Введен на основании»);
4. зафиксировать уникальные прямые ссылки и допустимые частичные оплаты;
5. зафиксировать уникальные совпадения через счёт;
6. зафиксировать уникальные совпадения остатка;
7. решить оставшиеся конфликты ограниченным поиском
   внутри одного контрагента;
8. всё ниже порога — DEBT_UNRESOLVED (долг) или незакрытый ADVANCE;
9. semantic reranker в версии 1 не обязателен;
10. обратная хронология — только tie-break при уже пройденных
    порогах confidence и gap.
```

Глобальный conflict-resolution pass — только неоднозначные хвосты внутри `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`. Он не основной путь, не пересматривает HIGH и `DEBT` и не превращает аванс в долг.

Простой greedy как основной алгоритм запрещён. FIFO отсутствует полностью.

HIGH-закрытие аванса выполняется в потоке событий, а не «после всех оплат».

# 5. Разделение на долг и аванс

Это чистая бухгалтерская арифметика **по каждой аналитике**, не по целому `payment_id`.

Ключ аналитики:

```text
КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID
```

Источник — строки `ledger62` с данным `payment_id`. Поля `ДоговорID` / `ВидРасчетовID` в `payments.csv` matcher не читает.

По каждой части отдельно:

```text
debt_before  = дебетовое сальдо только этой аналитики на момент оплаты
debt_part    = min(сумма части, debt_before)
advance_part = сумма части − debt_part
```

Неттинг между аналитиками запрещён. Остаток Кт договора B не уменьшает долг Дт договора A. Сворачивать оплату в одно число DEBT/ADVANCE до разреза по аналитике нельзя.

Пример одной аналитики:

```text
долг перед платежом по этой аналитике = 7 000
часть оплаты по этой аналитике = 10 000
debt_part = 7 000
advance_part = 3 000
```

Пример двух аналитик одного `payment_id`:

```text
аналитика A: долг 10 000, часть оплаты 10 000 → DEBT 10 000
аналитика B: долга нет, часть оплаты 5 000  → ADVANCE 5 000
```

не «свернуть контрагента и получить ADVANCE 5 000 на всю оплату».

Никакая LLM этого не определяет. После разделения долга/аванса и matching Python сразу считает НДС. `debt_part` ищет прошлую реализацию в `DEBT_MATCH_WINDOW`. `advance_part` закрывается HIGH сразу при появлении однозначной реализации; иначе — conflict-resolution pass в авансовых окнах.

# 7. Прямой документ + сумма в пределах остатка

Если найдена уникальная ссылка на конкретный документ задолженности того же контрагента и документ существовал на момент оплаты:

```text
0 < сумма_к_распределению <= текущий непогашенный остаток документа
```

связь фиксируется сразу.

- полное закрытие остатка: `DIRECT_DOCUMENT_EXACT`, `HIGH`;
- частичная оплата: `HIGH_PARTIAL_DIRECT`, `HIGH`.

Стандартный общий matching в этом случае не нужен.

Частичная оплата — нормальный случай, а не ошибка суммы.

---

# 8. Прямой документ, платёж больше остатка

Если ссылка уникальна, но сумма больше остатка указанного документа:

```text
остаток → этот документ (DIRECT_DOCUMENT_EXACT / HIGH_PARTIAL_DIRECT)
хвост  → дальнейший matching или ADVANCE
```

Если ссылка неоднозначна (несколько документов) или сумма не помогает выбрать кандидата — не фиксировать автоматически. Документ получает бонус `DIRECT_DOCUMENT_HINT` (вес — только `scoring.yaml`, ключ `direct_hint`) и идёт в общий цикл.

Точная сумма сама по себе сильна только при единственном кандидате. Два документа по 10 000 и платёж 10 000 однозначной связи не создают.

# 9. Второй основной путь: оплата по счету

На практике значительная доля платежей содержит именно:

```text
Оплата по счету ...
```

При этом документ задолженности — не счет, а:

```text
Отгрузка товаров
```

или:

```text
Оказание услуг
```

Поэтому необходимо построить цепочку:

```text
Платеж
→ Счет на оплату
→ документ, введенный на основании счета
→ задолженность или закрытие аванса
```

Реализация по счёту может быть раньше оплаты (погашение долга в `DEBT_MATCH_WINDOW`) или позже оплаты (закрытие аванса в `ADVANCE_TAX_WINDOW` или `ADVANCE_EXTENDED_MATCH_WINDOW`). Оба случая обязательны. Уникальная цепочка через счёт — HIGH и закрывает аванс сразу, не дожидаясь глобального pass.

Счёт — связка matching и запасной источник состава НДС. Если отгрузка или оказание услуг не найдены, облагаемую и необлагаемую части берут из агрегатов счёта (`СуммаОблагаемаяКоп` / `СуммаНеоблагаемаяКоп` / `СуммаНДСКоп`). Отгрузка и оказание услуг приоритетнее счёта.

# 12. Нормализация ссылки «Введен на основании»

Не сравнивать строку целиком посимвольно.

Разобрать её в структуру:

```text
base_type
base_number
base_date
```

Например:

```text
base_type = INVOICE
base_number = 00002
base_date = 2026-01-06
```

Поддержать лишние пробелы и различные регистры.

---

# 13. Счет → один документ → сумма в пределах остатка

Если:

```text
оплата → счет №00002
```

и найден ровно один связанный документ задолженности, и:

```text
0 < сумма_к_распределению <= остаток документа
```

то соответствие фиксируется сразу (`INVOICE_BASE_EXACT` или частичный аналог, `HIGH`).

---

# 14. Счет → несколько документов

Один счет теоретически может стать основанием нескольких документов.

Тогда:

```text
не выбирать первый найденный.
```

Проверить:

1. точное совпадение одной суммы;
2. точное совпадение с остатком;
3. сумму нескольких связанных документов;
4. другие признаки.

Если однозначности нет — перейти к стандартному matching.

Но документы, связанные с найденным счетом, получают очень высокий score.

---

# 15. Счет найден, платёж больше остатка связанного документа

Остаток относится на связанный документ, хвост идёт в matching или аванс.

Если связанных документов несколько и однозначности нет — не привязывать насильно. Связь через счет остаётся сильной подсказкой.

---

# 16. ПКО: отдельный быстрый путь

Для `PaymentKind=CASH` прежде всего анализировать:

```text
КомментарийДокументаОплаты
```

Частый вариант:

```text
Введен на основании:
Отгрузка товаров № Н00570 от 30 Июня 2026 г.
```

Это практически прямая машинная ссылка на документ.

---

# 17. ПКО + сумма в пределах остатка

Если из комментария ПКО найден уникальный документ и:

```text
0 < сумма ПКО (или её долговой части) <= остаток документа
```

фиксировать сразу:

```text
CASH_BASE_EXACT или HIGH_PARTIAL_DIRECT
HIGH
```

---

# 18. ПКО + сумма больше остатка

Остаток — на указанный документ, хвост — дальше. Если ссылка неоднозначна — бонус кандидата и общий matcher.

---

# 19. Стандартный matching

Он запускается только после прямых путей.

Кандидаты погашения долга должны соответствовать:

```text
тот же контрагент
документ существовал на момент оплаты   (DEBT_MATCH_WINDOW)
имеется непогашенный остаток
```

Кандидаты закрытия аванса задаются разделом 21.1, а не этим списком.

---

# 20. Другой контрагент — жёсткий запрет

```text
Контрагент оплаты != Контрагент документа
```

→ кандидат запрещён.

Это hard constraint.

---

# 21. Будущий документ — запрет только для долга

Для `DEBT` обычный платеж не может оплачивать документ, который ещё не существовал.

Использовать:

```text
Дата
ПозицияДокумента
```

Это hard constraint для погашения задолженности. Кандидаты `DEBT` живут только в `DEBT_MATCH_WINDOW`.

Ранее полученный аванс — отдельная ситуация: его связывают с реализацией после оплаты по правилам раздела 21.1.

---

# 21.1. Закрытие аванса

Не основной путь «после всех оплат». HIGH закрывается в хронологическом потоке. Глобальный pass — только неоднозначные хвосты.

Три окна (имена обязательны):

| Окно | Границы | Назначение |
| --- | --- | --- |
| `DEBT_MATCH_WINDOW` | ИсторияНач → момент оплаты | Только долг. Сюда аванс не ищет будущие реализации |
| `ADVANCE_TAX_WINDOW` | Момент оплаты → конец квартала этой оплаты | Связь может заменить 5/105 фактическим НДС. Не продлевается в следующий квартал |
| `ADVANCE_EXTENDED_MATCH_WINDOW` | После квартала оплаты → `MatchHorizonEnd` | Хозяйственная связь. Не меняет налоговый результат уже закрытого квартала |

Квартал берётся **от даты этой оплаты**, не от `ДатаКон`. `MatchHorizonEnd` приходит из `manifest.csv` (`match_horizon_end`), не вычисляется как `КонецКвартала(ДатаКон)`.

Немедленное закрытие. Если у аналитики есть `ADVANCE` и появилась реализация с однозначной HIGH-связью (машинное основание, уникальная цепочка оплата → счёт → реализация), аванс закрывается сразу. Remainder документа уменьшается. Следующая оплата видит уже зафиксированный остаток.

Conflict-resolution pass. Неоднозначные кандидаты remainder не трогают, пока pass не выберет связь выше порогов confidence/gap. Без порогов — незакрытый `ADVANCE` или запись в `unresolved.csv`, не «ближайший документ». Обратная хронология только как последний tie-break среди уже прошедших пороги.

Кандидаты pass — документы `RECEIVABLE` того же контрагента:

```text
документ позже оплаты (Дата / ПозицияДокумента)
дата документа <= конец соответствующего окна
документ проведён и не помечен на удаление
ещё не исчерпан available_for_advance
```

Остаток взаиморасчётов по реализации **не** является условием закрытия аванса. Отгрузка в счёт аванса часто сразу закрывается зачётом 62, и дебетовый остаток по ней уже нулевой.

```text
available_for_advance = сумма документа
                      − подтверждённые DEBT
                      − подтверждённые ADVANCE
```

`DEBT_UNRESOLVED` документ не занимает: `available_for_advance` от него не уменьшается.

Приоритет связи, тот же дух scoring, что и для долга:

```text
1. цепочка оплата → счёт → реализация «Введен на основании»   (HIGH, сразу)
2. уникальная прямая ссылка в назначении на эту будущую реализацию
3. точный остаток / полная сумма / комбинация сумм
4. договор, вид расчётов (из ledger), товар/услуга
5. обратная хронология — только tie-break при порогах
```

Типы связи:

```text
ADVANCE_INVOICE_BASE        — через счёт (HIGH, как правило сразу)
ADVANCE_TAX_WINDOW_DIRECT   — прямая ссылка в налоговом окне
ADVANCE_TAX_WINDOW_AMOUNT   — по сумме в налоговом окне
ADVANCE_EXTENDED_MATCH      — хозяйственная связь после квартала
```

`row_type` остаётся `ADVANCE`. `matched_document_id` заполняется найденной реализацией. `confidence` и пороги — те же правила `scoring.yaml`. Для extended match в `reason` явно: налог закрытого квартала не пересчитывается.

Частичное закрытие:

```text
аванс 105 000
до конца квартала отгружено 63 000
```

даёт две строки:

```text
ADVANCE 63 000  — с matched_document_id реализации
ADVANCE 42 000  — без документа (незакрытый остаток)
```

Несколько реализаций в счёт одного аванса — несколько строк `ADVANCE` с разными документами. Сумма частей равна исходному авансу этой аналитики.

Pass не пересматривает уже зафиксированные `DEBT` / HIGH-`ADVANCE` и не превращает аванс в долг. Бухгалтерское разделение на дату оплаты не меняется: закрытая отгрузкой сумма всё равно `ADVANCE`, просто с документом. Документ в налоговом окне нужен, чтобы взять фактический НДС из реализации. Документ в extended match нужен состоянию remainder и последующим оплатам, не налогу закрытого квартала.

Если одному авансу подходят несколько реализаций и однозначности нет — не выбирать первую попавшуюся и не брать ближайшую по дате без порогов.

# 21.2. НДС и доход УСН — тот же запуск

Закрытие аванса само по себе НДС не считает: сначала matching, затем налоговый слой `tax.py` по уже зафиксированным строкам. Налог закрытого квартала по связи из `ADVANCE_EXTENDED_MATCH_WINDOW` не пересчитывается. НДС для `DEBT_UNRESOLVED` не угадывается.

Две независимые шкалы:

```text
Аванс — дата получения денег.
  до 2026-01-01: расчётный НДС 5/105 не начисляется
                ни на остаток, ни «задним числом»
  с 2026-01-01: незакрытый на конец квартала остаток
                без реализации и без счёта → 5/105

Реализация — дата отгрузки.
  реализация 2026 может нести фактический НДС
  независимо от даты аванса
```

Нельзя писать «всё до 01.01.2026 без НДС» как общее правило для обеих сторон.

Источник фактического состава — агрегаты `documents.csv`:

```text
СуммаОблагаемаяКоп
СуммаНеоблагаемаяКоп
СуммаНДСКоп
```

Приоритет:

```text
1. matched RECEIVABLE в ADVANCE_TAX_WINDOW (отгрузка / оказание услуг)
2. иначе INVOICE, связанный с этой оплатой / авансом,
   только если invoice_date <= КонецКвартала(ДатаОперации оплаты)
3. иначе 5/105 или 0 по шкале аванса
```

Отгрузка и оказание услуг всегда важнее счёта, даже если у счёта другой состав.

```text
DEBT с реализацией
  → НДС из агрегатов этой реализации (шкала отгрузки)

ADVANCE с реализацией в ADVANCE_TAX_WINDOW
  → НДС из этой реализации вместо 5/105

ADVANCE с реализацией в ADVANCE_EXTENDED_MATCH_WINDOW
  → хозяйственная связь; налог квартала аванса
    по шкале аванса (5/105 или 0), не фактический НДС
    поздней отгрузки

ADVANCE без реализации, но есть связанный счёт, существовавший не позже конца квартала оплаты
  → состав по агрегатам счёта
    (`INVOICE_VAT_FALLBACK`; для аванса с 2026-01-01; до 2026-01-01 — без 5/105)

ADVANCE: связанный счёт создан только после окончания квартала оплаты
  → счёт можно использовать для хозяйственного matching / цепочки к реализации,
    но его агрегаты не пересчитывают налог закрытого квартала;
    применяется 5/105 или 0 по шкале аванса

ADVANCE без документа и без счёта
  → с 2026-01-01: 5/105; до 2026-01-01: 0

DEBT_UNRESOLVED
  → НДС не угадывается;
    vat_base_kopecks = 0
    vat_kopecks = 0
    income_kopecks = amount_kopecks
    tax_ready = 0
```

Matcher должен помнить `invoice_id`, если оплата/аванс связан со счётом, даже когда RECEIVABLE не найден. В `kudir_result.csv` поле `invoice_id` не обязательно: налоговый слой берёт его из состояния matcher. `INVOICE_VAT_FALLBACK` допустим только для счёта, существовавшего не позже `payment_tax_quarter_end`. Поздний счёт после этой даты может оставаться matching-связкой, но не источником НДС закрытого квартала.

### Смешанный документ и частичная оплата

На remainder документа дополнительно ведутся:

```text
remaining_taxable
remaining_exempt
remaining_vat
```

При полном закрытии остатка берётся весь оставшийся состав, без пропорционального округления.

При частичной сумме `P`, `total = remaining_taxable + remaining_exempt`:

```text
taxable = округлить(P * remaining_taxable / total)
exempt  = P − taxable
vat     = если remaining_taxable > 0:
              округлить(remaining_vat * taxable / remaining_taxable)
          иначе 0
```

Тогда:

```text
vat_base_kopecks = taxable
vat_kopecks      = vat
income_kopecks   = P − vat
```

Если документ целиком без НДС: `vat_base = 0`, `vat = 0`, `income = P`.
Если целиком с НДС: `vat_base = P`, `vat` из доли `remaining_vat`.

Расчётные 5/105, когда нет валидного состава:

```text
vat_kopecks = как Окр(сумма_руб * 5 / 105, 2) в 1С 7.7,
              результат в копейки
vat_base_kopecks = amount_kopecks
income_kopecks = amount_kopecks − vat_kopecks
```

Колонку `НДС` документа формулой 5/105 не подменять. Если агрегаты документа расходятся (`СуммаОблагаемаяКоп + СуммаНеоблагаемаяКоп ≠ СуммаКоп`) или все три нули при ненулевой `СуммаКоп` — состав неизвестен: 5/105 вместо документа не брать, для затронутых целевых строк `tax_ready=0`.

`tax_ready=1` только если у всех целевых частей НДС определён (документ, счёт или законные 5/105 / 0).

# 22. Договор НЕ является hard constraint

Это важное изменение.

Несовпадение договора:

```text
НЕ должно исключать документ.
```

Совпадающий договор:

```text
сильный плюс.
```

Разный договор:

```text
штраф,
но не запрет.
```

Источник договора и вида расчётов для scoring — строки `ledger62` этой оплаты, не поля `payments.csv`.

Совпадение и штраф задаются ключами `same_contract`, `different_contract`, `unknown_contract` в `config/scoring.yaml`. Числовых примеров весов в ТЗ нет.

# 23. Почему разный договор допускается

В реальной базе возможны:

* неверно выбранный договор в платежной строке;
* разные технические договоры;
* исторические изменения;
* ошибки пользователя;
* отличия договора оплаты от договора документа.

Поэтому если имеются сильные признаки:

```text
прямая ссылка на счет
+
ссылка "Введен на основании"
+
точная сумма
```

они имеют право перебить несовпадение договора.

При этом в `reason` необходимо отметить:

```text
CROSS_CONTRACT_MATCH
```

# 24. Какой договор возвращать

Если платеж сопоставлен с конкретным документом задолженности:

```text
Договор в строке DEBT
=
договор найденного документа задолженности
```

Не надо искусственно считать разные договоры одинаковыми.

Для `ADVANCE` с найденной реализацией:

```text
Договор
=
договор этой реализации
```

Для `ADVANCE` без документа:

```text
Договор
=
договор аналитической части оплаты из ledger62
```

Не договор из `payments.csv`.

# 25. Приоритеты стандартного matching

Рекомендуемый порядок для погашения долга:

```text
1. прямой документ + точная сумма
2. счет → документ + точная сумма
3. ПКО → основание + точная сумма
4. точное совпадение остатка документа
5. точное совпадение полной суммы документа
6. несколько оплат = документ
7. одна оплата = несколько документов
8. закрытие остатка после предыдущей частичной оплаты
9. связь через счет/основание без точной суммы
10. договор
11. вид расчетов
12. товар/услуга
13. текстовая семантика
14. обратная хронология — только tie-break при порогах
```

Закрытие аванса выполняется по разделу 21.1 (HIGH сразу, pass для неоднозначного) и не вставляет будущую реализацию в погашение долга.

# 26. Точные совпадения суммы

Сильными считать оба случая:

```text
платеж = первоначальная сумма документа
```

и:

```text
платеж = текущий остаток документа
```

Второй случай даже важнее для частично оплаченного документа.

---

# 27. Несколько оплат → один документ

Пример:

```text
Документ = 5 500

Оплата 1 = 4 500
Оплата 2 = 1 000
```

Получить:

```text
4 500 + 1 000 → 5 500
```

---

# 28. Одна оплата → несколько документов

Пример:

```text
Документы:
4 000
6 000

Платеж:
10 000
```

Получить две связи.

---

# 29. Очень важный случай закрытия остатка

Если:

```text
документ = 5 500
```

уже подобрана оплата:

```text
4 500
```

и имеется:

```text
1 000
```

то:

```text
1 000 = остаток документа
```

является сильным match.

---

# 30. FIFO отсутствует

FIFO запрещён полностью: и как основной алгоритм, и как fallback. Самый старый документ нигде не предпочитается.

Например:

```text
документ A = 5 500
документ B = 27 200

оплаты:
4 500
27 200
1 000
```

правильно:

```text
27 200 → B
4 500 + 1 000 → A
```

а не механическое списание «сначала самый старый». Если пороги confidence/gap не выполнены — `DEBT_UNRESOLVED`, а не ближайший и не самый старый документ.

---

# 31. Обратная хронология — только последний tie-break

Обратная хронология не алгоритм выбора документа. Пороги `high_min_score` / `high_min_gap` считаются по score **без** chronology. Хронология допускается только когда несколько кандидатов уже прошли эти пороги относительно остальных и между собой равны. Тогда из равных берётся ближайший к оплате. `chronology_score` пишется в `matches.csv` как объяснение tie-break и HIGH не создаёт.

Пример допустимого tie-break:

```text
кандидат A = 180, кандидат B = 180, кандидат C = 100
отрыв пары A/B от C проходит high_min_gap
A и B равны между собой
```

тогда из A и B берётся ближайший предшествующий. Самый старый документ при этом не предпочитается.

Если пороги не выполнены (нет отрыва, низкий score) — `DEBT_UNRESOLVED` для долга или незакрытый `ADVANCE` / conflict-resolution pass для аванса, а не ближайший документ.

```text
01.01 документ 10 000
05.01 документ 10 000
06.01 оплата 10 000
нет ссылки, нет отрыва
```

→ `DEBT_UNRESOLVED`, не документ 05.01 «потому что ближе».

Результат почти только по хронологии не может иметь `HIGH`.

# 32. Scoring

Веса, пороги и лимиты поиска живут **только** в `config/scoring.yaml`. Файл обязателен: отсутствие — ошибка запуска (`FAILED`). В коде matcher второго набора весов нет. В тексте ТЗ числовых примеров весов нет. Хеш содержимого `scoring.yaml` пишется в `run_status.csv` и `analysis.log`.

Ключи весов (имена, не значения):

```text
direct_exact
invoice_base_exact
cash_base_exact
exact_remainder
exact_full_amount
exact_combination
direct_hint
same_invoice
same_contract
different_contract
unknown_contract
same_calculation_type
goods_or_service_match
semantic_max
chronology_max
```

Договор и вид расчётов для этих ключей берутся из `ledger62`, не из `payments.csv`.

Hard penalties:

```text
другой контрагент                              → запрет всегда
будущий документ для DEBT                      → запрет
реализация вне ADVANCE_TAX_WINDOW
  и вне ADVANCE_EXTENDED_MATCH_WINDOW          → не кандидат закрытия аванса
```

---

# 32.1. Пороги уверенности и неоднозначность

Правила живут только в `config/scoring.yaml` (секции `confidence` и `search`), не хардкодом в matcher:

```text
HIGH / MEDIUM / LOW — по ключам high_min_score, high_min_gap,
                      medium_min_score, medium_min_gap,
                      low_min_score, low_min_gap
иначе: DEBT_UNRESOLVED (для долга) или незакрытый ADVANCE
```

Дополнительно:

- результат почти только по хронологии не может быть `HIGH`;
- точная сумма даёт автоматическую блокировку только при единственном кандидате;
- лимит кандидатов и времени — ключи `max_candidates`, `timeout_seconds_per_counterparty`;
- при превышении лимита — детерминированный fallback: уже заблокированное HIGH, остаток `DEBT_UNRESOLVED`, запись в `analysis.log`;
- пересмотр уже заблокированной связи `HIGH` запрещён; `LOW` можно пересмотреть, пока обрабатывается тот же контрагент и не начат следующий;
- без порогов confidence/gap обратная хронология документ не выбирает.

# 33. Парсер и эвристический matcher — разные компоненты

Не смешивать:

```text
"извлечь из текста счет №123"
```

и:

```text
"решить, какой документ фактически оплачивается"
```

Первое выполняет parser.

Второе выполняет matcher.

Это позволит использовать уже существующий parser без переписывания всей системы.

# 34. Hugging Face

Используется только после обычных признаков.

Рекомендуемый порядок:

```text
точные ссылки
→ суммы
→ связи оснований
→ договор/вид расчетов

→ только затем semantic reranker
```

Модель не нужна для:


# 36. Восстановление взаиморасчётов

Использовать `opening_balances.csv` и `ledger62.csv` с начала исторического периода.

По умолчанию:

```text
01.10 предыдущего года
```

Состояние ведётся по ключу аналитики `КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID`:

```text
начальное сальдо аналитики
+ движения ledger62 этой аналитики с ИсторияНач
= signed_balance аналитики на момент события
```

Оба поля `ОстатокДтКоп` и `ОстатокКтКоп` используются. Нельзя схлопывать их правилом «если есть кредит — вернуть кредит». Неттинг между аналитиками запрещён.

Проводка оплаты применяется к взаиморасчётам **только** из `ledger62.csv`. Строка `payments.csv` — расширенное описание того же события, не второе движение денег. Несколько строк ledger с одним `payment_id` — части одной оплаты; каждая проводится один раз по своему `ledger_event_id`. Оплаты из `ledger62.csv` не отбрасывать. `payments.csv` деньги второй раз не двигает.

Проводки реализации связываются с документами по `source_document_id`. Уникальность строки ledger — `ledger_event_id`. Именно ledger-строка является событием бухгалтерского timeline; строка `documents.csv` не проводится второй раз и не создаёт отдельного изменения `signed_balance`.

Неплатёжное движение 62 (зачёт, корректировка, сторно, прочее) всегда меняет `signed_balance` аналитики. `document_remaining` меняется только если движение однозначно атрибутировано документу (сторно/корректировка этой реализации). Иначе remainder чужих документов не трогается. Если сумма document remainder не сходится с аналитическим сальдо — diagnostic event в `analysis.log`, без молчаливого размазывания разницы по документам.

`DocumentRole=INVOICE` не создаёт задолженность. Кандидаты погашения долга — `RECEIVABLE` в `DEBT_MATCH_WINDOW`. Кандидаты закрытия аванса — `RECEIVABLE` в `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`. Счета остаются связкой в обоих авансовых окнах.

Перед matching Python читает `run_id` и `match_horizon_end` из `manifest.csv` и копирует `run_id` в `kudir_result.csv` и `run_status.csv`.

В `documents.csv` допустимы счета и реализации с датой после `ДатаКон`, но не позже `MatchHorizonEnd`. Для восстановления долга на момент оплаты будущие документы не используются.

Поля `run_status.csv`:

```text
key;value
run_id;...
status;SUCCESS|SUCCESS_DEGRADED|FAILED
tax_ready;0|1
unresolved_debt_kopecks;...
unresolved_count;...
state_uncertain;0|1
historical_unresolved_count;...
historical_unresolved_kopecks;...
parser_available;0|1
schema_version;2
scoring_hash;...
```

`SUCCESS` при `tax_ready=0` — валидная комбинация: matching отработал, инварианты сумм держатся, но есть `DEBT_UNRESOLVED`, неизвестный состав НДС найденного документа или историческая неоднозначность на аналитике целевого периода. Книгу по этому запуску нельзя считать готовой к сдаче. `analysis.log` обязателен.

Историческая оплата (`is_target=0`) в `kudir_result.csv` не пишется. Если она не сопоставилась, matcher не имеет права молча изменить `signed_balance` и оставить `document_remaining` и `tax_ready` как будто история однозначна: пишутся `HISTORICAL_UNRESOLVED` в `analysis.log`, счётчики `historical_unresolved_*` и `state_uncertain=1`.

# 39. DEBT_UNRESOLVED

Если точно известно:

```text
платеж погашает долг
```

но конкретный документ надёжно определить невозможно:

```text
не превращать сумму в аванс.
```

Результат:

```text
DEBT_UNRESOLVED
```

`DEBT_UNRESOLVED` не занимает `document_remaining` и не уменьшает `available_for_advance`. Matching при этом может быть `SUCCESS`. `tax_ready=0`, пока `unresolved_count > 0` или `unresolved_debt_kopecks > 0`. НДС для UNRESOLVED не угадывается.

# 40. Формирование строк результата

Типы:

```text
DEBT
ADVANCE
DEBT_UNRESOLVED
```

Одна исходная оплата может дать любое количество строк — в том числе по нескольким аналитикам одного `payment_id`. В `kudir_result.csv` пишутся только части оплат с `is_target=1`. `СодержаниеЗаписи` — одна физическая строка, без CR/LF.

Порядок колонок `kudir_result.csv` — как в ТЗ №1:

```text
run_id
result_row_id
payment_id
row_type
matched_document_id
contract_id
amount_kopecks
advance_kopecks
repayment_kopecks
income_kopecks
vat_base_kopecks
vat_kopecks
match_type
confidence
reason
СодержаниеЗаписи
```

`contract_id` для `DEBT` — договор найденного документа, для `ADVANCE` с реализацией — договор этой реализации, для `ADVANCE` без документа — договор аналитической части из `ledger62`. Не договор из `payments.csv`. Объекты 1С в файл не записываются.

`counterparty_id` в `kudir_result.csv` намеренно отсутствует. Контрагент остаётся обязательным во входных CSV: это часть `AnalyticsKey`, hard constraint при matching и источник текста для `СодержаниеЗаписи`. Отдельный объект Контрагент обратно в 1С не требуется.

# 44. НДС

Правила — раздел 21.2. Кратко:

```text
vat_base_kopecks  — облагаемая доля части (со включённым НДС)
vat_kopecks       — НДС этой доли
income_kopecks    = amount_kopecks − vat_kopecks
```

Не вычитать 5/105 из банковского поступления, если есть валидный состав отгрузки / оказания услуг / счёта. Не брать фактический НДС поздней отгрузки для `ADVANCE_EXTENDED_MATCH`. Аванс до `2026-01-01` не получает 5/105. Реализация 2026 может иметь фактический НДС независимо от даты аванса. НДС для `DEBT_UNRESOLVED` не угадывается.

# 45. СодержаниеЗаписи

Только подтверждённые реквизиты. Нет номера, даты или договора — этот фрагмент не подставляется. Если НДС определён, текст это отражает. Для `DEBT_UNRESOLVED` фразу про НДС не писать.

Шаблоны:

```text
DEBT + оказание услуг, без НДС:
Оплата от {Контрагент} за услуги по акту №{Номер} от {Дата}, без НДС

DEBT + оказание услуг, есть НДС:
Оплата от {Контрагент} за услуги по акту №{Номер} от {Дата}; сумма {Сумма} руб., в т.ч. НДС 5% — {НДС} руб.

DEBT + отгрузка, без НДС:
Оплата от {Контрагент} за товар по накладной №{Номер} от {Дата}, без НДС

DEBT + отгрузка, есть НДС:
Оплата от {Контрагент} за товар по накладной №{Номер} от {Дата}; сумма {Сумма} руб., в т.ч. НДС 5% — {НДС} руб.

DEBT_UNRESOLVED + договор:
Оплата задолженности от {Контрагент} по договору {Договор}

DEBT_UNRESOLVED без договора:
Оплата задолженности от {Контрагент}

ADVANCE + документ + отгрузка / услуги:
те же шаблоны, что для DEBT, но начало «Получен аванс от {Контрагент} в счёт …»

ADVANCE + договор без документа, есть НДС 5/105:
Получен аванс от {Контрагент} по договору {Договор}; сумма {Сумма} руб., в т.ч. НДС 5% — {НДС} руб.

ADVANCE + договор без документа, без НДС:
Получен аванс от {Контрагент} по договору {Договор}, без НДС

ADVANCE без договора и без документа:
Получен аванс от {Контрагент}
  + суффикс НДС, если он определён; без суффикса, если не определён
```

Не выдумывать отсутствующие реквизиты. Не писать «без НДС», если состав на самом деле неизвестен.

→ один `payment_id`, два `ledger_event_id`. Не фиксировать автоматически два разных документа только из-за двух видов расчётов.

### Тест: две оплаты в одной выписке без номера строки

```text
Выписка 0001, НомерПроводки=2, МЫЛОВА, 1 000
```

```text

```

### Тест: две одинаковые суммы без прочих признаков

```text
два документа по 10 000
платёж 10 000
нет ссылки и нет отрыва
```

### Тест: нет opening_balances.csv

→ ошибка обработки, не расчёт с нуля.

### Тест: аванс и отгрузка в том же квартале через счёт

```text
10 января оплата 105 000, долга нет
назначение: оплата по счету №00002
20 февраля отгрузка 105 000
комментарий: Введен на основании: Счет на оплату №00002 ...
```

→ `ADVANCE` с `matched_document_id` февральской отгрузки, `ADVANCE_INVOICE_BASE`, закрытие HIGH сразу (не «после всех оплат»).
Не оставлять аванс без документа только потому, что накладная позже оплаты.

### Тест: 2.1 старый ADVANCE → A, поздняя оплата → B

```text
10 янв аванс по счёту №1
10 фев реализация A на основании счёта
15 фев реализация B
1 мар оплата без назначения
```

→ январский ADVANCE закрывает A сразу (HIGH через счёт). Мартовский платёж → B, не `DEBT_UNRESOLVED`.

### Тест: 2.2 несколько аналитик одной оплаты

Один `payment_id`, две аналитики. На A есть долг, на B нет.

→ DEBT по A и ADVANCE по B. Суммы по `payment_id` не неттятся.

### Тест: 2.3 долг A + аванс B без неттинга

Оплата по A не уменьшается авансом B. DEBT по A = `min(оплата_A, долг_A)`.

### Тест: 2.4 декабрьский аванс → январская реализация

Связь в `ADVANCE_EXTENDED_MATCH_WINDOW`. Налог Q4 не пересчитывается. Нужен `MatchHorizonEnd` позже конца Q4.

### Тест: 2.5 аванс 2025 → реализация 2026

На аванс 2025 расчётный НДС не начисляется. Реализация 2026 может нести фактический НДС. Нельзя вывести «без НДС» для отгрузки 2026 из даты денег. Если январская реализация в `ADVANCE_EXTENDED_MATCH_WINDOW`, налог декабрьского/2025 аванса всё равно без 5/105.

### Тест: смешанная накладная, приоритет над счётом

```text
отгрузка: 63 000 с НДС 5% (НДС 3 000) + 42 000 без НДС
счёт того же платежа: вся сумма с НДС
оплата закрывает отгрузку
```

→ НДС 3 000 и доход 102 000 из отгрузки, не 5/105 со всей суммы и не состав счёта.

### Тест: нет реализации, есть счёт в том же налоговом квартале

```text
аванс 2026, реализация не найдена
счёт существует не позже конца квартала оплаты
счёт: 42 000 без НДС + 21 000 с НДС 5%
```

→ состав со счёта, `INVOICE_VAT_FALLBACK`. Не 5/105 на всю сумму.

### Тест: счёт появился после окончания квартала аванса

```text
15.03.2026 — аванс
31.03.2026 — payment_tax_quarter_end
15.04.2026 — счёт с известным составом НДС
20.04.2026 — реализация по этому счёту
```

→ апрельский счёт и реализация допустимы для хозяйственной связи / `ADVANCE_EXTENDED_MATCH_WINDOW`, но состав апрельского счёта не применяется задним числом к Q1. Налог Q1 остаётся по шкале аванса (5/105 или 0).

### Тест: 2.6 неатрибутированное движение 62

Зачёт/прочее без однозначной ссылки на документ. Сальдо аналитики изменилось. `document_remaining` чужих документов нет. Есть diagnostic event в `analysis.log`.

### Тест: 2.7 SUCCESS при tax_ready=0

Есть `DEBT_UNRESOLVED`. `status=SUCCESS`, `tax_ready=0`, `unresolved_count>0`, `unresolved_debt_kopecks>0`. Remainder документов не занят UNRESOLVED.

### Тест: 2.8 неоднозначные одинаковые реализации

Две равные реализации не закрывают ADVANCE немедленно. Без отрыва по score — `DEBT_UNRESOLVED` или отложенный pass, не «ближайший документ потому что FIFO/хронология».

### Тест: 2.9 несколько корреспонденций банка

Один `НомерПроводки()` → один `payment_id`. Каждая корреспонденция — свой `ledger_event_id` и своя аналитика. ID оплаты = позиция + `НомерПроводки`.

### Тест: отгрузка в следующем квартале

```text
10 января аванс 105 000
05 апреля отгрузка 105 000, тот же счёт
```

→ хозяйственная связь `ADVANCE_EXTENDED_MATCH` при выгруженном `MatchHorizonEnd`. Налог I квартала не пересчитывается (не подменять 5/105 фактическим НДС апрельской отгрузки). Если уникальная цепочка через счёт — HIGH, закрытие сразу.

### Тест: частичное закрытие аванса до конца квартала

```text
аванс 105 000
до 31 марта: реализация 42 000 без привязки НДС
             и реализация 21 000
остаток 42 000
```

→ две (или три) строки `ADVANCE` на найденные реализации и строка `ADVANCE` 42 000 без документа.
Сумма частей = 105 000. НДС по найденным реализациям — из агрегатов этих документов; по остатку — 5/105 или состав счёта, не «ноль потому что matching».

### Тест: долг не может ссылаться на будущий документ

```text
на момент оплаты есть долг
единственная «подходящая» накладная датирована после оплаты
```

→ `DEBT` / `DEBT_UNRESOLVED`, не привязка к будущей накладной как к долгу.
Закрытие аванса не перекладывает эту сумму в аванс.

### Тест: порядок внутри одной даты

`Пример2`: 15 800 → Отгрузка товаров Н00001, 5 500 → Оказание услуг 00001, порядок по `ДатаОперации + ПозицияДокумента + НомерПроводкиВДокументе`. `НомерСтрокиДокумента` в сортировку не входит.

# 48.1. CSV-протокол

Чтение и запись — строго по разделу 30 ТЗ №1: Windows-1251, разделитель `;`, даты `YYYY-MM-DD`, целые копейки, quoting с удвоением кавычек, пустое поле ≠ `0` и ≠ `NULL`.

При отсутствии `manifest.csv`, неизвестной или несовпадающей `schema_version` (ожидается `2`) Python **немедленно** прекращает обработку до загрузки остальных файлов, не создаёт `kudir_result.csv` и возвращает ненулевой код (`FAILED`). Автоконвертация схемы не выполняется.

# 49. Критерии готовности Python

1. Существующий parser вызывается как внешний сервис и покрыт regression-тестами; код сервиса не копируется.
2. Поддерживается прямое указание акта/накладной, включая `HIGH_PARTIAL_DIRECT`.
3. Поддерживается оплата по счету и цепочка `Оплата → Счет → Реализация`. HIGH через счёт закрывает аванс сразу.
4. Парсятся стандартизированные комментарии `Введен на основании`.
5. Поддерживается ПКО.
6. При неединственной ссылке или равных суммах нескольких кандидатов автоматический HIGH не ставится.
7. Разный договор не является hard reject. Договор/вид расчётов для scoring — из `ledger62`.
8. Другой контрагент является hard reject.
9. Будущий документ является hard reject для `DEBT`. Для `ADVANCE` — `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`.
10. Поддерживаются комбинации оплат и документов. Разрез DEBT/ADVANCE — по каждой аналитике, без неттинга.
11. Matcher идёт хронологическим потоком событий и этапами блокировки. FIFO отсутствует. Обратная хронология — только tie-break при порогах.
12. Пороги HIGH/MEDIUM/LOW и отрыв заданы только `scoring.yaml`. В ТЗ нет числовых примеров весов.
13. ML является опциональным и в версии 1 не обязателен.
14. Формируется `kudir_result.csv` по схеме ТЗ №1 только для `is_target=1`, с тем же `run_id`. `СодержаниеЗаписи` без CR/LF.
15. Формируется `matches.csv` с разложением score. `analysis.log` обязателен.
16. Поддерживается `DEBT_UNRESOLVED`; он не занимает remainder. `status` и `tax_ready` разделены; поля `unresolved_debt_kopecks`, `unresolved_count`, `state_uncertain`, `historical_unresolved_*`.
17. Контролируется сумма каждой исходной целевой оплаты.
18. `opening_balances.csv` обязателен; оба остатка Дт и Кт используются; ключ — аналитика.
19. CSV читается по протоколу ТЗ №1 (Windows-1251, `;`, даты ISO, quoting).
20. Оплата склеивается с проводками 62 по `payment_id` и проводится только через ledger.
21. `config/scoring.yaml` обязателен и является единственным источником весов.
22. Недоступность parser даёт `SUCCESS_DEGRADED`, а не скрытый успех. Это не то же самое, что `tax_ready=0`.
23. Python считает НДС и доход УСН в том же запуске. Приоритет: реализация в налоговом окне, затем счёт, существовавший не позже конца квартала конкретной оплаты, затем 5/105/0. Счёт после конца квартала не пересчитывает налог закрытого квартала. Аванс и реализация живут на разных VAT-шкалах.
24. HIGH-аванс закрывается сразу. Неоднозначное — conflict-resolution pass. Extended match не пересчитывает налог закрытого квартала.
25. Агрегаты колонки `НДС` из `documents.csv` обязательны. Строки товаров Python не требует отдельным файлом. Отгрузка / услуги приоритетнее счёта.
26. Неплатёжный 62 всегда меняет сальдо аналитики; расхождение remainder и aggregate — diagnostic event.
27. `tax_ready=1` только когда НДС всех целевых строк определён. `DEBT_UNRESOLVED` и неизвестный состав документа держат `tax_ready=0`.
28. `income_kopecks = amount_kopecks − vat_kopecks`. Колонку `НДС` документа не подменять формулой 5/105.

### 1. Назначение

Актуализация по решениям владельца U1–U4 и окончательному U5 текущей сессии; основания — `08-СВОДНЫЙ-АУДИТ-И-РЕШЕНИЯ-КУДиР.md` и его Cursor-ревью. Приоритет: U1–U5 (окончательный U5 заменяет ранние варианты возвратов) → специализированные ТЗ 01/02/04 в своей области → архитектура 00. Новые правила этих ТЗ явно перекрывают противоречащие им положения планов 03/05; 03, 05, 06, оба 07 и оба 08 сохраняются как история работ и аудитов, не как источник отменённых требований. Нормативный порядок налога и приёмка — 02 §21.2 и §48.3; оставшиеся OPEN_DECISION — 02 §50. Это изменение требований, не утверждение о готовности текущего кода.

Python-программа является аналитическим модулем: matching оплат **и** расчёт готовых строк КУДиР.

Оплата не определяет сумму НДС сама по себе. Python раскладывает поступление на погашение долга и аванс **по каждой аналитике `ledger62`**, ищет документы и сразу считает НДС / доход УСН:

- задолженность — в `DEBT_MATCH_WINDOW` (ИсторияНач → момент оплаты);
- закрытие аванса HIGH — сразу при появлении реализации;
- остальные связи аванса — в `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`;
- налог — сначала доказанный PRE_2026_DEBT, иначе валидный доступный состав реализации / допустимого счёта, иначе default 5/105 для целевой части 2026; неустановленный возраст долга — OD1 (§21.2).

Отдельного второго цикла `1С → Python → 1С` нет. Константа расчётного НДС: 5%, формула `5/105`. `SUCCESS` и `tax_ready` — разные признаки. `tax_ready=1` означает, что строки можно считать готовой КУДиР.

Вход — файлы каталога `exchange/<run_id>/`:

```text

```

`opening_balances.csv` обязателен. Отсутствие файла — ошибка, расчёт с нуля запрещён. Python читает только каталог текущего `run_id`; два запуска одного периода не делят файлы.

Выход — в тот же каталог:

```text

```

В `kudir_result.csv` попадают только оплаты с `is_target=1`. Исторические поступления участвуют в matching и восстанавливают остатки документов; исторические RETURN проходят только отдельный путь §36.1. Если историческая оплата не сопоставилась, это фиксируется: `historical_unresolved_*`, `state_uncertain=1`. Историческая неоднозначность даёт `tax_ready=0` только если не позволяет определить налог или доступную ёмкость целевой части. При доказанном возрасте и определённом налоге `state_uncertain=1` совместим с `tax_ready=1`. `analysis.log` обязателен.

Через CSV передаются ID и скаляры, не объекты 1С. Аналитика оплаты — множество строк `ledger62` с данным `payment_id`. Поля договора/вида расчётов в `payments.csv` matcher не читает.

# 2. Ключевое требование: не писать существующий разбор заново

Parser является внешней зависимостью и в этот репозиторий не входит. Новый parser не разрабатывается и не копируется.

Он уже умеет определять:

```text
смысл платежа
тип упомянутого документа
номер документа
дату документа
номер счета
```

Приоритет:

```text
1. вызывать существующий HTTP-сервис http://127.0.0.1:8765/parse1c;
2. инкапсулировать вызов в legacy_parser_adapter.py;
3. покрыть regression-тестами реальные строки;
4. только после этого добавлять новые правила matcher.
```

Если parser недоступен: для этой оплаты текстовый разбор пропускается, matching продолжается по суммам и основаниям. Система не падает целиком. Итог запуска:

```text
SUCCESS           — parser был доступен
SUCCESS_DEGRADED  — parser недоступен или часть строк не разобрана
FAILED            — ошибка данных, схемы или инварианта
```

`SUCCESS` и `SUCCESS_DEGRADED` — код завершения 0. `FAILED` — ненулевой код, `kudir_result.csv` не создаётся. Статус пишется в `run_status.csv`. 1С при `SUCCESS_DEGRADED` показывает предупреждение; строки `HIGH`, полученные без parser, загружать можно. Этот статус применяется также при неподдерживаемых возвратах/сторно: рассчитанные строки доступны для проверки по §36.1.

`SUCCESS` / `SUCCESS_DEGRADED` не означают `tax_ready=1`. Matching может успешно закончиться при неразрешённых связях: `status=SUCCESS` (или `SUCCESS_DEGRADED`), а `tax_ready` определяется отдельно по §21.2 и может быть 1 при доказанном налоге unresolved-долга.

Перед разбором проверять `GET /health` (если сервис его отдаёт). Одинаковые строки кэшировать на время запуска. Regression: unit-тесты на сохранённых ответах parser; отдельный integration-тест живого сервиса, который можно пропускать, если сервис не запущен.

Формат запроса/ответа — как у текущего клиента в `доходы-2.txt`. Адрес задаётся конфигурацией, по умолчанию `http://127.0.0.1:8765/parse1c`.

Не создавать новый независимый parser с нуля.

# 4. Хронологическая модель состояния

Оплаты и реализации обрабатываются в едином потоке событий, вперемешку, в порядке:

```text
ДатаОперации
ПозицияДокумента
НомерПроводкиВДокументе
```

Ключ одинаков для `payments.csv` и `ledger62.csv`. `НомерСтрокиВДокументе` пуст и в порядок не входит. Исторические оплаты обрабатываются вместе с целевыми; в результат попадают только `is_target=1`.

Бухгалтерский timeline создаётся **только строками `ledger62.csv`**.

```text
documents.csv сам по себе не создаёт бухгалтерское событие в timeline.

Хронологическое событие движения взаиморасчётов создаётся строкой ledger62.csv.

Для реализации ledger-строка связывается с documents.csv через source_document_id.

documents.csv предоставляет метаданные документа:
тип, номер, договор, комментарий, состав НДС и т.п.

Изменение signed_balance происходит только по ledger62.csv.
```

Python не создаёт второе бухгалтерское движение из строки `documents.csv`. Для реализации её ledger-событие связывается с записью `documents.csv` по `source_document_id`; документ даёт метаданные для matching и налога, а изменение взаиморасчётов остаётся единственным ledger-событием.

`ledger62.csv` заканчивается `ДатаКон`. Документ `RECEIVABLE` с датой после `ДатаКон`, но не позже `MatchHorizonEnd`, есть только в `documents.csv`. Matcher вводит его **отдельным обходом доступности** для закрытия аванса (HIGH через счёт, conflict-resolution pass окон), **без** создания бухгалтерского события и без изменения `signed_balance`. После `ДатаКон` в этом запуске нет будущих оплат и корректировок: доступность такого документа — неполный хозяйственный контекст. Глобальный pass «только для неоднозначного» сам по себе этот случай не описывает.

Модель «сначала все долги по всем оплатам, потом все авансы этапом 10» запрещена. Оплата создаёт `ADVANCE` по аналитике. Пришедшая реализация сразу гасит существующий `ADVANCE` только если связь однозначная / HIGH (машинное основание, уникальная цепочка через счёт). Неоднозначные кандидаты не трогают remainder до conflict-resolution pass. Следующая оплата видит только уже зафиксированные HIGH-остатки.

Кейс «январский аванс → A по счёту, мартовская оплата → B» проходит, потому что связь через счёт — HIGH и закрывается до мартовской оплаты.

Перед вызовом matcher определить направление денежного события из ledger. Положительное поступление идёт по следующим этапам; возврат Дт 62 → Кт денег — только по §36.1; техническое сторно — по отдельной диагностике. Наличие положительной СуммаКоп у возврата не делает его обычной оплатой. Все три пути сохраняют одно применение ledger.

Для каждого положительного поступления matcher идёт этапами блокировки, а не одним greedy-проходом:

```text
1. восстановить состояние взаиморасчётов по каждой аналитике
   на момент оплаты;
2. по каждой части ledger62 этой оплаты отдельно:
   debt_before, debt_part, advance_part;
3. заблокировать уникальные машинные ссылки
   (ПКО / «Введен на основании»);
4. зафиксировать уникальные прямые ссылки и допустимые частичные оплаты;
5. зафиксировать уникальные совпадения через счёт;
6. зафиксировать уникальные совпадения остатка;
7. решить оставшиеся конфликты ограниченным поиском
   внутри одного контрагента, включая отложенные долговые
   части нескольких оплат (раздел 27.1);
8. всё ниже порога — DEBT_UNRESOLVED (долг) или незакрытый ADVANCE;
9. semantic reranker в версии 1 не обязателен;
10. обратная хронология — только tie-break при уже пройденных
    порогах confidence и gap.
```

Глобальный conflict-resolution pass — только неоднозначные хвосты внутри `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`. Он не основной путь, не пересматривает HIGH и `DEBT` и не превращает аванс в долг.

Простой greedy как основной алгоритм запрещён. FIFO отсутствует полностью.

HIGH-закрытие аванса выполняется в потоке событий, а не «после всех оплат».

# 5. Разделение на долг и аванс

Это чистая бухгалтерская арифметика **по каждой аналитике**, не по целому `payment_id`.

Ключ аналитики:

```text
КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID
```

Источник — строки `ledger62` с данным `payment_id`. Поля `ДоговорID` / `ВидРасчетовID` в `payments.csv` matcher не читает.

Для каждой положительной аналитической части поступления отдельно (RETURN исключён из этого split):

```text
debt_before  = дебетовое сальдо только этой аналитики на момент оплаты
debt_part    = min(сумма части, debt_before)
advance_part = сумма части − debt_part
```

Неттинг между аналитиками запрещён. Остаток Кт договора B не уменьшает долг Дт договора A. Сворачивать оплату в одно число DEBT/ADVANCE до разреза по аналитике нельзя.

Пример одной аналитики:

```text
долг перед платежом по этой аналитике = 7 000
часть оплаты по этой аналитике = 10 000
debt_part = 7 000
advance_part = 3 000
```

Пример двух аналитик одного `payment_id`:

```text
аналитика A: долг 10 000, часть оплаты 10 000 → DEBT 10 000
аналитика B: долга нет, часть оплаты 5 000  → ADVANCE 5 000
```

не «свернуть контрагента и получить ADVANCE 5 000 на всю оплату».

Никакая LLM этого не определяет. После разделения долга/аванса и matching Python сразу считает НДС. `debt_part` ищет прошлую реализацию в `DEBT_MATCH_WINDOW`. `advance_part` закрывается HIGH сразу при появлении однозначной реализации; иначе — conflict-resolution pass в авансовых окнах.

---

# 6. Первый и самый сильный путь: прямое указание документа

Сначала существующим parser'ом анализируются:

```text
СодержаниеПроводки
Содержание
ПредставлениеПроводки
НазначениеПлатежа
ПервичныйДокумент
КомментарийДокументаОплаты
```

Parser может обнаружить, например:

```text
НАКЛАДНАЯ № Н00570 от 30.06.2026
```

или:

```text
АКТ №25 от 10.08.2026
```

---

# 7. Прямой документ + сумма в пределах остатка

Если найдена уникальная ссылка на конкретный документ задолженности того же контрагента и документ существовал на момент оплаты:

```text
0 < сумма_к_распределению <= текущий непогашенный остаток документа
```

связь фиксируется сразу.

- полное закрытие остатка: `DIRECT_DOCUMENT_EXACT`, `HIGH`;
- частичная оплата: `HIGH_PARTIAL_DIRECT`, `HIGH`.

Стандартный общий matching в этом случае не нужен.

Частичная оплата — нормальный случай, а не ошибка суммы.

---

# 8. Прямой документ, платёж больше остатка

Если ссылка уникальна, но сумма больше остатка указанного документа:

```text
остаток → этот документ (DIRECT_DOCUMENT_EXACT / HIGH_PARTIAL_DIRECT)
хвост  → дальнейший matching или ADVANCE
```

Если ссылка неоднозначна (несколько документов) или сумма не помогает выбрать кандидата — не фиксировать автоматически. Документ получает бонус `DIRECT_DOCUMENT_HINT` (вес — только `scoring.yaml`, ключ `direct_hint`) и идёт в общий цикл.

Точная сумма сама по себе сильна только при единственном кандидате. Два документа по 10 000 и платёж 10 000 однозначной связи не создают.

---

# 9. Второй основной путь: оплата по счету

На практике значительная доля платежей содержит именно:

```text
Оплата по счету ...
```

При этом документ задолженности — не счет, а:

```text
Отгрузка товаров
```

или:

```text
Оказание услуг
```

Поэтому необходимо построить цепочку:

```text
Платеж
→ Счет на оплату
→ документ, введенный на основании счета
→ задолженность или закрытие аванса
```

Реализация по счёту может быть раньше оплаты (погашение долга в `DEBT_MATCH_WINDOW`) или позже оплаты (закрытие аванса в `ADVANCE_TAX_WINDOW` или `ADVANCE_EXTENDED_MATCH_WINDOW`). Оба случая обязательны. Уникальная цепочка через счёт — HIGH и закрывает аванс сразу, не дожидаясь глобального pass.

Счёт — связка matching и запасной источник состава НДС. Если отгрузка или оказание услуг не найдены, облагаемую и необлагаемую части берут из агрегатов счёта (`СуммаОблагаемаяКоп` / `СуммаНеоблагаемаяКоп` / `СуммаНДСКоп`). Валидный доступный состав отгрузки и услуги в применимом налоговом окне приоритетнее счёта; доказанный PRE_2026_DEBT выше обоих источников (02 §21.2).

---

# 10. Поиск счета

Использовать существующий рабочий parser.

Например:

```text
Оплата по счету №00002
```

даёт:

```text
Тип = СЧЕТ
Номер = 00002
```

Если известна дата:

```text
Дата = ...
```

также использовать её.

Затем найти счет в `documents.csv` по:

```text
Контрагент
Номер
Дата — если известна
```

---

# 11. Связь Счет → Отгрузка / Оказание услуг

После нахождения счета найти документы:

```text
Отгрузка товаров
Оказание услуг
```

в комментарии которых имеется стандартизированная ссылка:

```text
Введен на основании: Счет на оплату № 00002 от 06 Января 2026 г.
```

Так как комментарий формируется программой, эта связь считается очень сильной.

Внутренний тип связи:

```text
BASE_DOCUMENT_LINK
```

Для погашения долга связанная реализация должна существовать на момент оплаты (`DEBT_MATCH_WINDOW`). Для закрытия аванса та же цепочка через счёт ищется среди реализаций после оплаты: HIGH закрывается сразу; неоднозначное идёт в conflict-resolution pass окон `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`.

---

# 12. Нормализация ссылки «Введен на основании»

Не сравнивать строку целиком посимвольно.

Разобрать её в структуру:

```text
base_type
base_number
base_date
```

Например:

```text
base_type = INVOICE
base_number = 00002
base_date = 2026-01-06
```

Поддержать лишние пробелы и различные регистры.

---

# 13. Счет → один документ → сумма в пределах остатка

Если:

```text
оплата → счет №00002
```

и найден ровно один связанный документ задолженности, и:

```text
0 < сумма_к_распределению <= остаток документа
```

то соответствие фиксируется сразу (`INVOICE_BASE_EXACT` или частичный аналог, `HIGH`).

---

# 14. Счет → несколько документов

Один счет теоретически может стать основанием нескольких документов.

Тогда:

```text
не выбирать первый найденный.
```

Проверить:

1. точное совпадение одной суммы;
2. точное совпадение с остатком;
3. сумму нескольких связанных документов;
4. другие признаки.

Если однозначности нет — перейти к стандартному matching.

Но документы, связанные с найденным счетом, получают очень высокий score.

---

# 15. Счет найден, платёж больше остатка связанного документа

Остаток относится на связанный документ, хвост идёт в matching или аванс.

Если связанных документов несколько и однозначности нет — не привязывать насильно. Связь через счет остаётся сильной подсказкой.

---

# 16. ПКО: отдельный быстрый путь

Для `PaymentKind=CASH` прежде всего анализировать:

```text
КомментарийДокументаОплаты
```

Частый вариант:

```text
Введен на основании:
Отгрузка товаров № Н00570 от 30 Июня 2026 г.
```

Это практически прямая машинная ссылка на документ.

---

# 17. ПКО + сумма в пределах остатка

Если из комментария ПКО найден уникальный документ и:

```text
0 < сумма ПКО (или её долговой части) <= остаток документа
```

фиксировать сразу:

```text
CASH_BASE_EXACT или HIGH_PARTIAL_DIRECT
HIGH
```

---

# 18. ПКО + сумма больше остатка

Остаток — на указанный документ, хвост — дальше. Если ссылка неоднозначна — бонус кандидата и общий matcher.

---

# 19. Стандартный matching

Он запускается только после прямых путей.

Кандидаты погашения долга должны соответствовать:

```text
тот же контрагент
документ существовал на момент оплаты   (DEBT_MATCH_WINDOW)
имеется непогашенный остаток
```

Кандидаты закрытия аванса задаются разделом 21.1, а не этим списком.

---

# 20. Другой контрагент — жёсткий запрет

```text
Контрагент оплаты != Контрагент документа
```

→ кандидат запрещён.

Это hard constraint.

---

# 21. Будущий документ — запрет только для долга

Для `DEBT` обычный платеж не может оплачивать документ, который ещё не существовал.

Использовать:

```text
Дата
ПозицияДокумента
```

Это условие допустимого временного окна операции погашения задолженности. Кандидаты `DEBT` живут только в `DEBT_MATCH_WINDOW`.

Ранее полученный аванс — отдельная ситуация: его связывают с реализацией после оплаты по правилам раздела 21.1.

---

# 21.1. Закрытие аванса

Не основной путь «после всех оплат». HIGH закрывается в хронологическом потоке. Глобальный pass — только неоднозначные хвосты.

Три окна (имена обязательны):

| Окно | Границы | Назначение |
| --- | --- | --- |
| `DEBT_MATCH_WINDOW` | ИсторияНач → момент оплаты | Только долг. Сюда аванс не ищет будущие реализации |
| `ADVANCE_TAX_WINDOW` | Момент оплаты → конец квартала этой оплаты | Связь может заменить 5/105 фактическим НДС. Не продлевается в следующий квартал |
| `ADVANCE_EXTENDED_MATCH_WINDOW` | После квартала оплаты → `MatchHorizonEnd` | Хозяйственная связь. Не меняет налоговый результат уже закрытого квартала |

Квартал берётся **от даты этой оплаты**, не от `ДатаКон` и не от `manifest.quarter_end`. Python не должен использовать `manifest.quarter_end` вместо конца квартала конкретной оплаты. `MatchHorizonEnd` приходит из `manifest.csv` (`match_horizon_end`) и остаётся отдельной границей хозяйственного поиска; он не вычисляется как `КонецКвартала(ДатаКон)`.

Немедленное закрытие. Если у аналитики есть `ADVANCE` и появилась реализация с однозначной HIGH-связью (машинное основание, уникальная цепочка оплата → счёт → реализация), аванс закрывается сразу. Remainder документа уменьшается. Следующая оплата видит уже зафиксированный остаток.

Conflict-resolution pass. Неоднозначные кандидаты remainder не трогают, пока pass не выберет связь выше порогов confidence/gap. Без порогов — незакрытый `ADVANCE` или запись в `unresolved.csv`, не «ближайший документ». Обратная хронология только как последний tie-break среди уже прошедших пороги.

Кандидаты pass — документы `RECEIVABLE` того же контрагента:

```text
документ позже оплаты (Дата / ПозицияДокумента)
дата документа <= конец соответствующего окна
документ проведён и не помечен на удаление
ещё не исчерпан available_for_advance
```

Остаток взаиморасчётов по реализации **не** является условием закрытия аванса. Отгрузка в счёт аванса часто сразу закрывается зачётом 62, и дебетовый остаток по ней уже нулевой.

```text
available_for_advance = единый remaining RECEIVABLE
                      после подтверждённых исторических и целевых DEBT/ADVANCE
                      и доказанных корректировок ёмкости
```

`DEBT_UNRESOLVED` документ не занимает: `available_for_advance` от него не уменьшается.

Приоритет связи, тот же дух scoring, что и для долга:

```text
1. цепочка оплата → счёт → реализация «Введен на основании»   (HIGH, сразу)
2. уникальная прямая ссылка в назначении на эту будущую реализацию
3. точный остаток / полная сумма / комбинация сумм
4. договор, вид расчётов (из ledger), товар/услуга
5. обратная хронология — только tie-break при порогах
```

Типы связи:

```text
ADVANCE_INVOICE_BASE        — через счёт (HIGH, как правило сразу)
ADVANCE_TAX_WINDOW_DIRECT   — прямая ссылка в налоговом окне
ADVANCE_TAX_WINDOW_AMOUNT   — по сумме в налоговом окне
ADVANCE_EXTENDED_MATCH      — хозяйственная связь после квартала
```

`row_type` остаётся `ADVANCE`. `matched_document_id` заполняется найденной реализацией. `confidence` и пороги — те же правила `scoring.yaml`. Для extended match в `reason` явно: налог закрытого квартала не пересчитывается.

Частичное закрытие:

```text
аванс 105 000
до конца квартала отгружено 63 000
```

даёт две строки:

```text
ADVANCE 63 000  — с matched_document_id реализации
ADVANCE 42 000  — без документа (незакрытый остаток)
```

Несколько реализаций в счёт одного аванса — несколько строк `ADVANCE` с разными документами. Сумма частей равна исходному авансу этой аналитики.

Pass не пересматривает уже зафиксированные `DEBT` / HIGH-`ADVANCE` и не превращает аванс в долг. Бухгалтерское разделение на дату оплаты не меняется: закрытая отгрузкой сумма всё равно `ADVANCE`, просто с документом. Документ в налоговом окне нужен, чтобы взять фактический НДС из реализации. Документ в extended match нужен состоянию remainder и последующим оплатам, не налогу закрытого квартала.

Если одному авансу подходят несколько реализаций и однозначности нет — не выбирать первую попавшуюся и не брать ближайшую по дате без порогов.

---

# 21.2. НДС и доход УСН — тот же запуск

Закрытие аванса само по себе НДС не считает: сначала matching, затем налоговый слой `tax.py` по уже зафиксированным строкам. Налог закрытого квартала по связи из `ADVANCE_EXTENDED_MATCH_WINDOW` не пересчитывается: поздняя реализация не источник НДС и не отменяет допустимый ранний счёт. Налог unresolved и неизвестного состава определяется следующим каноном, независимо от уверенности matching.

### Канонический порядок U2/U4 для каждой налоговой части положительного поступления

RETURN обрабатывается отдельно по U5 (§36.1): явный документ → его фактический состав, иначе излишняя оплата → состав исходной оплаты. Следующий порядок не применяется к RETURN как к новому поступлению.

1. Для погашаемого долга (`DEBT` и `DEBT_UNRESOLVED`) установить возраст **реально закрываемой части исходной аналитики ledger**. Доказанно до 01.01.2026 → только `PRE_2026_DEBT`: `vat_base_kopecks=0`, `vat_kopecks=0`, `income_kopecks=amount_kopecks`. Это правило выше DEFAULT и любого фактического состава, в том числе документа другой аналитики с ненулевым VAT. Дата поступления 2026 его не отменяет.
2. Если возраст закрываемой долговой части неоднозначен — `OPEN_DECISION OD1`; нельзя переходить к составу/default наугад. Если старые и новые части доказанно определены, рассчитать их раздельно. Для доказанно нового долга (с 01.01.2026) и допустимого целевого аванса 2026 далее действует порядок источников.
3. Валидный фактический доступный состав найденной отгрузки / услуги (`RECEIVABLE`) в применимом налоговом окне имеет приоритет над счётом и default.
4. Иначе — валидный состав допустимого связанного `INVOICE` в пределах его оставшейся денежной ёмкости и состава. Для аванса счёт должен существовать не позже конца квартала оплаты; налоговый состав нельзя расходовать сверх суммы счёта.
5. Иначе — `DEFAULT_5_105` для допустимой целевой части поступления 2026, в том числе нового `DEBT_UNRESOLVED`. `vat_base=amount`, `vat=Окр(amount * 5 / 105, 0)` в копейках по правилу округления ниже, `income=amount−vat`. Для исторического аванса до 2026 расчётные 5/105 не начисляются. Extended-связь не пересчитывает закрытый квартал.

Валидный фактический VAT=0 означает «без НДС»; валидный смешанный состав даёт фактическую долю. Неизвестный состав не равен доказанному VAT=0: три нуля при ненулевой сумме, расхождение агрегатов или отрицательный НДС ТЧ не являются сильным источником. Сохранить `VAT_COMPOSITION_UNKNOWN`, перейти к следующему допустимому источнику / default. Частично накопленные положительные агрегаты при отрицательном НДС ТЧ нельзя принимать за факт (01 §15.1). Matching-документ и налоговый источник могут различаться.

`tax_ready=1` означает определённый налог всех целевых частей. `unresolved_count`, `unresolved_debt_kopecks`, `historical_unresolved_*`, `state_uncertain` и `vat_unknown_count` сохраняют диагностику, но ни один не является автоматическим запретом готовности. `vat_unknown_count` считает целевые строки с `VAT_COMPOSITION_UNKNOWN`, а не документы и не незавершённые расчёты. Если открытый OD1 или неопределённость исходных данных влияет на целевой налог/ёмкость, `tax_ready=0` с объяснением причины. Технические нули в такой незавершённой строке не являются налоговым фактом и не разрешают текст «без НДС». Fallback не исправляет повреждённый CSV, неизвестную сумму, двойной расход или неатрибутированную корректировку ёмкости.

Возраст не выводится из одной даты снимка `ДатаСальдо` после последующих движений. Чистый входящий долг на 01.10.2025 доказывает существование до границы, но после движений 2026 необходимо доказательство возраста именно закрываемого остатка. Cross-analytics документ сам по себе не переносит дату возникновения долга в платёжной аналитике. FIFO/LIFO/пропорция возрастов не вводятся; смешанное частичное закрытие без доказательства — OD1.

Следующие схемы источников применяются после этой проверки возраста и только к валидному доступному составу.

Две независимые шкалы:

```text
Аванс — дата получения денег.
  до 2026-01-01: расчётный НДС 5/105 не начисляется
                ни на остаток, ни «задним числом»
  с 2026-01-01: незакрытый на конец квартала остаток
                без реализации и без счёта → 5/105

Реализация — дата отгрузки.
  реализация 2026 может нести фактический НДС
  независимо от даты аванса
```

Нельзя писать «всё до 01.01.2026 без НДС» как общее правило для обеих сторон.

Источник фактического состава — агрегаты `documents.csv`:

```text
СуммаОблагаемаяКоп
СуммаНеоблагаемаяКоп
СуммаНДСКоп
```

Приоритет источника НДС аванса считается **по состоянию налогового окна**. Extended-связь на этот приоритет не влияет:

```text
1. matched RECEIVABLE с валидным доступным составом в ADVANCE_TAX_WINDOW (отгрузка / оказание услуг)
2. иначе INVOICE с валидным доступным составом, связанный с этой оплатой / авансом,
   только если invoice_date <= КонецКвартала(ДатаОперации оплаты)
3. иначе 5/105 или 0 по шкале аванса
```

Валидный доступный состав отгрузки и услуги в налоговом окне важнее счёта после проверки PRE_2026_DEBT, даже если у счёта другой состав. Поздняя отгрузка **не** важнее раннего счёта.

```text
DEBT с реализацией
  → сначала PRE_2026_DEBT / проверка возраста; иначе валидный состав,
    допустимый счёт или DEFAULT_5_105 по канону выше

ADVANCE с реализацией в ADVANCE_TAX_WINDOW
  → НДС из этой реализации вместо 5/105

ADVANCE с реализацией в ADVANCE_EXTENDED_MATCH_WINDOW
  → хозяйственная связь (matched_document_id заполняется);
    налог закрытого квартала — как если бы этой реализации не было:
    шаг 2 (допустимый ранний счёт) или шаг 3 (5/105 или 0).
    Фактический НДС поздней отгрузки не берётся и не отменяет ранний счёт.

ADVANCE без реализации в налоговом окне, но есть связанный счёт,
существовавший не позже конца квартала оплаты
  → состав по агрегатам счёта
    (`INVOICE_VAT_FALLBACK`; для аванса с 2026-01-01; до 2026-01-01 — без 5/105)
    даже если позже есть extended-реализация

ADVANCE: связанный счёт создан только после окончания квартала оплаты
  → счёт можно использовать для хозяйственного matching / цепочки к реализации,
    но его агрегаты не пересчитывают налог закрытого квартала;
    применяется 5/105 или 0 по шкале аванса

ADVANCE без документа в налоговом окне и без допустимого счёта
  → с 2026-01-01: 5/105; до 2026-01-01: 0

Найденный документ / счёт, состав неизвестен
  → VAT_COMPOSITION_UNKNOWN; следующий допустимый источник / DEFAULT_5_105
    по канону выше. Неизвестный источник не равен «без НДС».

DEBT_UNRESOLVED
  → доказанно старый закрываемый долг: PRE_2026_DEBT, VAT 0;
    доказанно новый: допустимый источник / DEFAULT_5_105;
    неоднозначный возраст: OPEN_DECISION OD1, tax_ready=0.
    При определённом налоге unresolved совместим с tax_ready=1.
```

Пример B1 (ранний смешанный счёт + поздняя отгрузка):

```text
10.03 — счёт 105 000: 63 000 с НДС 3 000 + 42 000 без НДС
15.03 — аванс 105 000
20.04 — реализация по этому счёту
```

Налог Q1: НДС 3 000, доход 102 000 (счёт). Не 5 000 / доход 100 000. Апрельская отгрузка не меняет налог закрытого квартала.

Matcher должен помнить `invoice_id`, если оплата/аванс связан со счётом, даже когда RECEIVABLE не найден или найден только в extended window. В `kudir_result.csv` поле `invoice_id` не обязательно: налоговый слой берёт его из состояния matcher. `INVOICE_VAT_FALLBACK` допустим только для счёта, существовавшего не позже `payment_tax_quarter_end`. Поздний счёт после этой даты может оставаться matching-связкой и звеном цепочки `оплата → счёт → реализация` до `MatchHorizonEnd`, но не источником НДС закрытого квартала.

Пример:

```text
15.03.2026 — аванс
31.03.2026 — конец налогового квартала этой оплаты
15.04.2026 — создан счёт
20.04.2026 — реализация
```

Апрельский счёт и апрельская реализация могут установить хозяйственную связь в `ADVANCE_EXTENDED_MATCH_WINDOW`, но не меняют налог Q1.

### Смешанный документ, частичная оплата и расход состава

У каждого `RECEIVABLE` (товары и услуги) и каждого `INVOICE` есть расходуемая денежная ёмкость. Для валидного состава дополнительно ведётся остаток состава. У неизвестного состава денежная ёмкость сохраняется, но налоговые остатки не инициализируются выдуманными exempt-суммами.

Единый денежный remaining документа учитывает подтверждённые исторические и целевые распределения и доказанные корректировки. Все аналитики одного контрагента и пути direct/chain/combination/conflict используют один остаток. DEBT и ADVANCE расходуют одну хозяйственную ёмкость RECEIVABLE; `available_for_advance` не может обходить уже использованную или скорректированную ёмкость. При `remaining=0` документ исключается **до** score, проверки уникальности, cap и комбинаций: никакая идеальная ссылка не разрешает повторную оплату. Неподтверждённый provisional и unresolved остаток не занимают.

Исторические подтверждения, в том числе `is_target=0`, уменьшают remaining до целевых распределений, ровно один раз. Полная сумма документа не доказывает его свободный остаток при неполной истории; нужна доказательная начальная ёмкость. Связанный расход INVOICE и его реализаций и резерв состава extended определены ниже (решённые OD2/OD3). Они применяются ко всем подтверждённым историческим и целевым частям, независимо от выбранного выходного налогового источника.

Для каждого валидного налогового источника:

```text
remaining_amount    = remaining_taxable + remaining_exempt   // ёмкость
remaining_taxable
remaining_exempt
remaining_vat
```

Инициализация состава — валидные агрегаты `documents.csv` с учётом подтверждённого предыдущего расхода. Отрицательные `remaining_*` запрещены; состав нельзя использовать на сумму больше денежного remaining источника. Здесь remaining — свободный остаток для нового распределения. Для уже подтверждённой части хранится её собственный денежный резерв и зарезервированный состав; налог этой части берётся из своего резерва, даже если свободный remaining после её распределения стал нулевым. Это не повторный расход и не разрешение другой оплате использовать исчерпанный источник. Формулы частичного расхода ниже применяются к свободным остаткам непосредственно перед новым резервом; выдача налога из существующего резерва повторно их не применяет.

Расходуют состав **исторические и целевые** распределения в том же детерминированном порядке, что и matching-timeline. Иначе НДС целевого периода зависит от `ДатаНач` отчёта, и копейки «прыгают».

Что расходует состав источника:

1. Каждый подтверждённый расход денежной ёмкости RECEIVABLE резервирует пропорциональную долю его собственного валидного состава: DEBT (включая PRE_2026), ADVANCE в налоговом окне и ADVANCE_EXTENDED_MATCH. Зарезервированная доля больше недоступна другой оплате.
2. Каждый подтверждённый расход денежной ёмкости INVOICE резервирует долю собственного состава счёта: как непосредственно по оплате счёта, так и через его оплаченную реализацию. Если счёт выбран налоговым источником, использовать уже зарезервированную для этой части долю, не списывать её повторно.
3. Выходной НДС части определяется каноном U2/U4. Резерв состава и налог строки — разные операции: резерв RECEIVABLE при PRE_2026 или extended не начисляет его НДС старому платежу.

### Связанный расход счёта и реализаций — решение OD2

Владелец поручил выбрать правило. Принято: подтверждённая оплата реализации одновременно занимает ёмкость однозначно связанного счёта, но одна экономическая часть оплаты расходует каждый документ не более одного раза.

- Само создание реализации по счёту и текстовая ссылка как признак matching ёмкость счёта не расходуют. Расход появляется при подтверждённом распределении оплаты. Связь с INVOICE должна быть доказана: уникальное основание либо явно заданные суммы частей по нескольким основаниям. При нескольких равноправных счетах без распределения не выбирать первый и не списывать всю сумму с каждого; пометить возможные затронутые остатки как неопределённые. Если это влияет на ёмкость/налог целевой части, ready=0 с диагностикой недостаточных данных, а не новое бизнес-правило.
- Подтверждённая часть P по реализации занимает P в RECEIVABLE и `min(P, remaining счёта)` в связанном INVOICE. Для нескольких доказанных оснований правило применяется отдельно к заданным частям P_i; сумма P_i не превышает P. Превышение остатка счёта не отменяет допустимую оплату реализации и её фактический состав: хвост не занимает счёт, не получает его состав и диагностируется как превышение покрытия счётом. Запрет cross-analytics netting сохраняется.
- Учитывать идентичность экономической части оплаты при разбиении/объединении строк результата. Если ранее эта часть уже занимала счёт как оплата без реализации / INVOICE_VAT_FALLBACK, нахождение реализации не занимает счёт повторно. Предел применяется к ещё не занятой этой частью сумме. Повторный проход и смена налогового источника сами по себе не меняют remaining.
- Если одна оплата сначала использовала счёт, затем допустимая реализация в том же налоговом окне стала более сильным источником, выходной налог заменить составом реализации. Денежный резерв и резерв состава счёта оставить занятыми этой оплатой; реализация резервирует собственный состав один раз. Если впоследствии изменилось само подтверждённое распределение оплаты (а не только налоговый источник), прежние затронутые резервы отменить и пересчитать зависимые остатки в детерминированном порядке; нельзя освобождать счёт просто из-за выбора RECEIVABLE для налога.
- Резерв каждого документа пропорционален **его собственному** оставшемуся составу по формулам ниже. НДС реализации не вычитается из VAT счёта: различие составов допустимо и не создаёт отрицательных остатков. Выходная строка никогда не суммирует НДС двух источников.
- История, прямые ссылки, цепочки и комбинации используют те же правила и одну ёмкость. Связанные распределения учитываются в установленном порядке timeline; при позднем установлении связи пересчитать затронутые резервы в этом порядке с устранением повторного расхода. Уже подтверждённые связи не пересматриваются лишь ради свободной ёмкости счёта. Неподтверждённую часть не считать расходом, но влияющую неопределённость истории не скрывать.
- При remaining счёта = 0 он не является доступным документом для другой оплаты и не даёт налоговый состав. Уже доказанное отношение «реализация основана на этом счёте» может сохраняться как метаданные RECEIVABLE: это не новое распределение на исчерпанный INVOICE и не отдельный кандидат, влияющий на уникальность доступных документов.

### Резерв состава extended — решение OD3

Владелец поручил выбрать правило. Принято: подтверждённый старый extended-аванс резервирует в реализации ту же пропорциональную долю taxable/exempt/vat, что обычная частичная оплата. Использовать оставшийся состав на момент распределения, формулы округления ниже и правило последней части. Резерв расходуется ровно один раз вместе с денежной ёмкостью.

Эта доля исключается из доступного состава для последующих доплат, но не переносится в налог старого аванса: PRE_2026/налог закрытого квартала и допустимый ранний счёт сохраняются. Доплата получает только оставшуюся долю реализации. При неизвестном составе резервировать деньги, не выдумывать taxable/exempt/vat; выходной налог определяется очередью источников U2/U4. Если валидный состав позднее восстановлен в текущем расчёте, сначала восстановить расход всех подтверждённых частей в том же порядке, затем вычислять доступный остаток; закрытый квартал не пересчитывать.

Превышение ёмкости счёта. Счёт 105 000, аванс 150 000, отгрузки нет:

- часть ≤ `remaining_amount` счёта → пропорция по составу счёта;
- хвост → отдельная часть аванса со своим правилом источника (5/105 или 0), а не пропорция на все 150 000 как на «частичную оплату» 105 000.

Несколько оплат по одному счёту расходуют одну и ту же ёмкость последовательно.

Противоречие состава счёта и частичных реализаций: не допускать отрицательных остатков состава. Если сумма хвоста и применимость default определены, недостоверный состав даёт `VAT_COMPOSITION_UNKNOWN` и следующий источник / `DEFAULT_5_105`. Если исходные факты не позволяют установить само распределение или доступную ёмкость по принятым правилам, `tax_ready=0` для влияющей на целевой налог неопределённости с диагностикой; fallback недостаток этих фактов не устраняет.

Округление до целых копеек — `Окр(…, 0)` языка 1С 7.7. Две пропорции:

```text
при частичной сумме P, total = remaining_taxable + remaining_exempt > 0:
    taxable = Окр(P * remaining_taxable / total, 0)
    exempt  = P − taxable
    vat     = если remaining_taxable > 0:
                  Окр(remaining_vat * taxable / remaining_taxable, 0)
              иначе 0
```

Последняя часть, исчерпывающая остаток источника, забирает **весь** оставшийся состав без повторного пропорционирования (как полное закрытие остатка).

При полном закрытии остатка берётся весь оставшийся состав, без пропорционального округления.

Тогда:

```text
vat_base_kopecks = taxable
vat_kopecks      = vat
income_kopecks   = P − vat
```

Если документ целиком без НДС: `vat_base = 0`, `vat = 0`, `income = P`.
Если целиком с НДС: `vat_base = P`, `vat` из доли `remaining_vat`.

Расчётные 5/105 для допустимой целевой части 2026, когда нет валидного доступного состава и исключения PRE_2026_DEBT:

```text
vat_kopecks = как Окр(сумма_руб * 5 / 105, 2) в 1С 7.7,
              результат в копейки
vat_base_kopecks = amount_kopecks
income_kopecks = amount_kopecks − vat_kopecks
```

Колонку `НДС` документа формулой 5/105 не подменять. Если агрегаты расходятся или все три нули при ненулевой `СуммаКоп`, или в ТЧ был отрицательный НДС — состав неизвестен: формат строки как в таблице выше (`VAT_COMPOSITION_UNKNOWN`). Счётчик `vat_unknown_count` в `run_status.csv` и перечень в `analysis.log`.

`tax_ready=1` только если у всех целевых частей НДС определён (валидный документ, допустимый счёт или законные 5/105 / 0) по канону U2/U4; `VAT_COMPOSITION_UNKNOWN` совместим с определённым fallback и `tax_ready=1`.

Приёмка расхода состава: одинаковый НДС целевых платежей при расчёте квартала и всего года на одном полном наборе фактов; историческая частичная оплата; старый extended-аванс и новая доплата — пропорциональный резерв и числовой пример §48.3; превышение суммы счёта; три частичных оплаты с округлением до копейки.

# 22. Договор, вид расчётов и счёт 62 — признаки scoring, не запреты

Document matching разрешён между аналитиками одного `КонтрагентID`. Только другой контрагент — абсолютный hard reject. Различие договора, вида расчётов и счёта 62 — scoring evidence / penalty / diagnostic, а не запрет, во всех путях поиска, включая прямую ссылку. Пустота и множественность — unknown/multiple, а не выдуманное совпадение. Окно, роль, действительность документа и положительная ёмкость остаются условиями допустимости конкретной операции: будущая реализация не является DEBT, INVOICE не является отгрузкой.

DEBT/ADVANCE рассчитывается исключительно по исходному ключу `КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID` из ledger. Cross-analytics matching не меняет split и signed_balance, cross-analytics netting запрещён. Источник счёта 62 документа — однозначная подтверждённая связь с ledger; при отсутствии/множественности — unknown/multiple и OD4, не произвольный первый счёт.

Несовпадение договора:

```text
НЕ должно исключать документ.
```

Совпадающий договор:

```text
сильный плюс.
```

Разный договор:

```text
штраф,
но не запрет.
```

Источник договора и вида расчётов для scoring — строки `ledger62` этой оплаты, не поля `payments.csv`.

Совпадение и штраф задаются ключами `same_contract`, `different_contract`, `unknown_contract` в `config/scoring.yaml`. Числовых примеров весов в ТЗ нет.

# 23. Почему разный договор допускается

В реальной базе возможны:

* неверно выбранный договор в платежной строке;
* разные технические договоры;
* исторические изменения;
* ошибки пользователя;
* отличия договора оплаты от договора документа.

Поэтому если имеются сильные признаки:

```text
прямая ссылка на счет
+
ссылка "Введен на основании"
+
точная сумма
```

они имеют право перебить несовпадение договора.

При этом в `reason` необходимо отметить:

```text
CROSS_CONTRACT_MATCH
```

# 24. Какой договор возвращать

Если платеж сопоставлен с конкретным документом задолженности:

```text
Договор в строке DEBT
=
договор найденного документа задолженности
```

Не надо искусственно считать разные договоры одинаковыми.

Для `ADVANCE` с найденной реализацией:

```text
Договор
=
договор этой реализации
```

Для `ADVANCE` без документа:

```text
Договор
=
договор аналитической части оплаты из ledger62
```

Не договор из `payments.csv`.

# 25. Приоритеты стандартного matching

Рекомендуемый порядок для погашения долга:

```text
1. прямой документ + точная сумма
2. счет → документ + точная сумма
3. ПКО → основание + точная сумма
4. точное совпадение остатка документа
5. точное совпадение полной суммы документа
6. несколько оплат = документ
7. одна оплата = несколько документов
8. закрытие остатка после предыдущей частичной оплаты
9. связь через счет/основание без точной суммы
10. договор
11. вид расчетов
12. товар/услуга
13. текстовая семантика
14. обратная хронология — только tie-break при порогах
```

Закрытие аванса выполняется по разделу 21.1 (HIGH сразу, pass для неоднозначного) и не вставляет будущую реализацию в погашение долга.

# 27. Несколько оплат → один документ

Пример:

```text
Документ = 5 500

Оплата 1 = 4 500
Оплата 2 = 1 000
```

Получить:

```text
4 500 + 1 000 → 5 500
```

## 27.1. Отложенные долговые части внутри контрагента

Хронологический проход обрабатывает одну оплату. Комбинация нескольких долговых оплат на один документ не является ни немедленным HIGH первой оплаты, ни глобальным pass, который описан только для авансов.

Контрольный случай раздела 30:

```text
документы 5 500 и 27 200
оплаты 4 500, затем 27 200, затем 1 000
```

Первая 4 500 может быть неоднозначной. Если она **окончательно** стала `DEBT_UNRESOLVED` и вышла из поиска, последняя 1 000 не увидит остатка 1 000 у документа 5 500.

Правило:

1. Бухгалтерское разделение DEBT/ADVANCE на дату оплаты не пересматривается.
2. Уже подтверждённые HIGH не пересматриваются.
3. Неоднозначная долговая часть внутри одного контрагента может оставаться **provisional** (не занимает remainder окончательно, не пишет `DEBT_UNRESOLVED` в результат), пока обрабатывается этот контрагент и не исчерпан `timeout_seconds_per_counterparty`.
4. Поиск комбинаций (раздел 28, bounded combination search) объединяет provisional-части с последующими оплатами того же контрагента.
5. `DEBT_UNRESOLVED` фиксируется, когда контрагент завершён либо сработал cap/timeout: тогда remainder документов provisional не занимает.
6. `LOW` можно пересмотреть, пока не начат следующий контрагент (как в §32.1); HIGH нельзя.

# 30. FIFO отсутствует

FIFO запрещён полностью: и как основной алгоритм, и как fallback. Самый старый документ нигде не предпочитается.

Например:

```text
документ A = 5 500
документ B = 27 200

оплаты:
4 500
27 200
1 000
```

правильно:

```text
27 200 → B
4 500 + 1 000 → A
```

а не механическое списание «сначала самый старый». Если пороги confidence/gap не выполнены — `DEBT_UNRESOLVED`, а не ближайший и не самый старый документ.

---

# 31. Обратная хронология — только последний tie-break

Обратная хронология не алгоритм выбора документа. Пороги `high_min_score` / `high_min_gap` считаются по score **без** chronology.

Доказательный `gap` — отрыв **лучшего** допустимого кандидата от **второго** допустимого. Если лучший и второй равны (gap = 0 между ними), HIGH **не** фиксируется, даже если оба далеко от слабого третьего.

Запрещённый пример (так делать нельзя):

```text
A = 180, B = 180, C = 100
отрыв пары A/B от C проходит high_min_gap
```

Добавление слабого C не даёт новых доказательств выбора между A и B. Без C пара остаётся неоднозначной; с C она тоже остаётся неоднозначной. Хронология не превращает эту пару в HIGH. Если хронология нужна для порядка показа вариантов в диагностике, этот порядок отделён от автоматической бухгалтерской привязки.

`chronology_score` пишется в `matches.csv` как объяснение порядка среди уже равных **после** того, как HIGH уже законно получен по другим признакам, либо как tie-break только когда gap между первым и вторым уже выполнен **до** учёта хронологии — чего при равенстве A и B нет.

Если пороги не выполнены (нет отрыва лучшего от второго, низкий score) — `DEBT_UNRESOLVED` для долга или незакрытый `ADVANCE` / conflict-resolution pass для аванса, а не ближайший документ.

```text
01.01 документ 10 000
05.01 документ 10 000
06.01 оплата 10 000
нет ссылки, нет отрыва
```

→ `DEBT_UNRESOLVED`, не документ 05.01 «потому что ближе».

Результат почти только по хронологии не может иметь `HIGH`.

# 32. Scoring

Веса, пороги и лимиты поиска живут **только** в `config/scoring.yaml`. Файл обязателен: отсутствие — ошибка запуска (`FAILED`). В коде matcher второго набора весов нет. В тексте ТЗ числовых примеров весов нет. Хеш содержимого `scoring.yaml` пишется в `run_status.csv` и `analysis.log`.

Ключи весов (имена, не значения):

```text
direct_exact
invoice_base_exact
cash_base_exact
exact_remainder
exact_full_amount
exact_combination
direct_hint
same_invoice
same_contract
different_contract
unknown_contract
same_calculation_type
goods_or_service_match
semantic_max
chronology_max
```

Договор и вид расчётов для этих ключей берутся из `ledger62`, не из `payments.csv`.

Hard penalties:

```text
другой контрагент                              → запрет всегда
будущий документ для DEBT                      → запрет
реализация вне ADVANCE_TAX_WINDOW
  и вне ADVANCE_EXTENDED_MATCH_WINDOW          → не кандидат закрытия аванса
```

# 32.1. Пороги уверенности и неоднозначность

Правила живут только в `config/scoring.yaml` (секции `confidence` и `search`), не хардкодом в matcher:

```text
HIGH / MEDIUM / LOW — по ключам high_min_score, high_min_gap,
                      medium_min_score, medium_min_gap,
                      low_min_score, low_min_gap
иначе: DEBT_UNRESOLVED (для долга) или незакрытый ADVANCE
```

Дополнительно:

- результат почти только по хронологии не может быть `HIGH`;
- точная сумма даёт автоматическую блокировку только при единственном кандидате;
- лимит кандидатов и времени — ключи `max_candidates`, `timeout_seconds_per_counterparty`;
- при превышении лимита — детерминированный fallback: уже заблокированное HIGH, остаток `DEBT_UNRESOLVED`, запись в `analysis.log`;
- пересмотр уже заблокированной связи `HIGH` запрещён; `LOW` можно пересмотреть, пока обрабатывается тот же контрагент и не начат следующий;
- без порогов confidence/gap обратная хронология документ не выбирает.

# 36. Восстановление взаиморасчётов

Использовать `opening_balances.csv` и `ledger62.csv` с начала исторического периода.

По умолчанию:

```text
01.10 предыдущего года
```

Состояние ведётся по ключу аналитики `КонтрагентID + Счет62 + ДоговорID + ВидРасчетовID`:

```text
начальное сальдо аналитики
+ движения ledger62 этой аналитики с ИсторияНач
= signed_balance аналитики на момент события
```

Оба поля `ОстатокДтКоп` и `ОстатокКтКоп` используются. Нельзя схлопывать их правилом «если есть кредит — вернуть кредит». Неттинг между аналитиками запрещён.

Проводка оплаты применяется к взаиморасчётам **только** из `ledger62.csv`. Строка `payments.csv` — расширенное описание того же события, не второе движение денег. Несколько строк ledger с одним `payment_id` — части одной оплаты; каждая проводится один раз по своему `ledger_event_id`. Оплаты из `ledger62.csv` не отбрасывать. `payments.csv` деньги второй раз не двигает.

Проводки реализации связываются с документами по `source_document_id`. Уникальность строки ledger — `ledger_event_id`. Именно ledger-строка является событием бухгалтерского timeline; строка `documents.csv` не проводится второй раз и не создаёт отдельного изменения `signed_balance`.

Неплатёжное движение 62 (зачёт, корректировка, сторно, прочее) всегда меняет `signed_balance` аналитики. `document_remaining` меняется только если движение однозначно атрибутировано документу (сторно/корректировка этой реализации). Иначе remainder чужих документов не трогается. Если сумма document remainder не сходится с аналитическим сальдо — diagnostic event в `analysis.log`, без молчаливого размазывания разницы по документам.

`DocumentRole=INVOICE` не создаёт задолженность. Кандидаты погашения долга — `RECEIVABLE` в `DEBT_MATCH_WINDOW`. Кандидаты закрытия аванса — `RECEIVABLE` в `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`. Счета остаются связкой в обоих авансовых окнах.

Перед matching Python читает `run_id` и `match_horizon_end` из `manifest.csv` и копирует `run_id` в `kudir_result.csv` и `run_status.csv`. Поле `quarter_end` манифеста — метаданные запуска; правая граница `ADVANCE_TAX_WINDOW` каждой оплаты считается от `ДатаОперации` этой оплаты, а не подставляется из `manifest.quarter_end`.

В `documents.csv` допустимы счета и реализации с датой после `ДатаКон`, но не позже `MatchHorizonEnd`. Для восстановления долга на момент оплаты будущие документы не используются.

Поля `run_status.csv`:

```text
key;value
run_id;...
status;SUCCESS|SUCCESS_DEGRADED|FAILED
tax_ready;0|1
unresolved_debt_kopecks;...
unresolved_count;...
state_uncertain;0|1
historical_unresolved_count;...
historical_unresolved_kopecks;...
parser_available;0|1
schema_version;3
scoring_hash;...
vat_unknown_count;...
```

`SUCCESS` при `tax_ready=0` — валидная комбинация: matching отработал, инварианты сумм держатся, но не определён итоговый налог целевой части, например возраст реально закрываемого смешанного долга (OD1) либо влияющая ёмкость, неустановленная из-за неполных исходных фактов. Unresolved или неизвестный состав источника сами по себе не достаточны для неготовности. Книгу по этому запуску нельзя считать готовой к сдаче. `analysis.log` обязателен.

Историческая оплата (`is_target=0`) в `kudir_result.csv` не пишется. Если она не сопоставилась, matcher не имеет права молча изменить `signed_balance` и оставить `document_remaining` и `tax_ready` как будто история однозначна: пишутся `HISTORICAL_UNRESOLVED` в `analysis.log`, счётчики `historical_unresolved_*` и `state_uncertain=1`.

# 36.1. RETURN — отдельный путь по окончательному решению U5

U5 заменяет все предыдущие правила этой сессии о природе и налоге возвратов. Уточнение от 12.09.2026: этот путь выполняется перед итоговой КУДиР независимо от завершения подбора исполнения исходной оплаты; остановка подбора по документу 11 §8.4 не прекращает обработку возвратов и сторно. Сначала прочитать комментарий **самого возврата**, затем выбрать ровно одну ветвь: явный однозначный документ отгрузки/услуг → U5.1; отсутствие такой ссылки → возврат излишне уплаченного по U5.2. RETURN не является отрицательной оплатой для DEBT/ADVANCE matcher. Все фактические движения ledger сохраняются и применяются ровно один раз в своих аналитиках и датах, даже если пара исключена из КУДиР.

### Входные факты и отделение от технического сторно

Возврат денег покупателю — Дт 62 → Кт 50/51/55 с используемыми субсчетами: банковская проводка или расходный кассовый документ. В ledger остаются исходная положительная сумма, реальные счета, дата/позиция и PAYMENT-ссылка на сам возврат; в новом формате Python формирует хозяйственное событие возврата из ledger (§51). Налоговая сумма RETURN отрицательна. Контрагент/договор/вид расчётов берутся со стороны 62. Отрицательное техническое сторно Дт денег → Кт 62 не переклассифицируется автоматически в такой возврат; неподдерживаемое сторно сохраняется со знаком в фактах/диагностике, не останавливая расчёт других операций.

Для определения ветви используется комментарий самого возврата: назначение/комментарий исходной оплаты и отдельный ПервичныйДокумент не подменяют отсутствующую ссылку в нём. Комментарий возврата передаётся полностью в существующем `КомментарийДокумента`; отдельное поле с «угаданным» ID реализации экспортёр не создаёт. Извлечение явной ссылки и проверка её однозначности — отдельная операция Python, не подбор кандидата по score. Если разбор недоступен, отсутствие результата parser не доказывает отсутствие ссылки: до достоверного чтения комментария природа возврата не установлена, RETURN_UNRESOLVED, ready=0 для влияющей целевой части. Parser-статус отражается отдельно.

### U5.1. Явный документ отгрузки / оказания услуг

1. В комментарии явно и однозначно указан конкретный RECEIVABLE: документ отгрузки или услуг. Использовать именно его. Допустимы извлечение точного ID либо точной ссылки вида/номера/даты из текста и однозначное разрешение этих реквизитов в исходных документах. Номер, дата и вид здесь — написанные пользователем реквизиты ссылки, а не признаки эвристического подбора. Нельзя выбирать документ по сумме, договору, близости даты, хронологии, score, сходству текста или через цепочку счёта.
2. Только другой КонтрагентID — абсолютный запрет связи. Разные договор/вид/счёт62 одного контрагента не запрещают явный документ; фиксируется диагностика, ledger не переносится. Проверяются роль и действительность указанного документа; обычные окна DEBT/ADVANCE и их scoring не применяются к этому пути возврата.
3. При однозначно указанном документе, отсутствующем в выгруженных фактах, либо недостоверном составе не заменять его другой реализацией/счётом/исходной оплатой/default. Сохранить извлечённую ссылку и причину недоступности в диагностике, выдать предварительную RETURN_UNRESOLVED. Не выдумывать DOCUMENT ID. Это недостаток фактов, а не разрешение перейти к U5.2.
4. Налоговый источник — фактический валидный состав **именно указанного документа**. Предыдущий налог исходной оплаты, PRE_2026_DEBT этой оплаты и default текущего года не заменяют состав документа U5.1. Достоверный VAT=0 → возврат без НДС. Смешанный состав → соответствующая доля taxable/exempt/vat по формулам частичного расхода §21.2. Последняя доступная возвращаемая часть забирает остаток состава, без накопленной ошибки округления.
5. Полная сумма документа не доказывает свободную возвратную ёмкость при неполной истории: нужны достаточная история возвратов/корректировок или подтверждённый начальный остаток. Недостающий факт нельзя заменить полной суммой при регистрации документа. Указанный документ имеет возвратную ёмкость и возвратный состав: доказанная сумма/фактический состав документа минус уже подтверждённые возвраты по нему и однозначно атрибутированные изменения доступной для возврата суммы. Это отдельный **смысл остатка**, не требование создать новый класс/таблицу. Оплаченный документ с обычным payment remaining=0 может иметь положительную возвратную ёмкость. Нельзя использовать уже израсходованный на обычные оплаты remaining как возвратный остаток и нельзя возвращать по документу сверх доступного возвратного остатка.
6. Подтверждённый расход возвратного состава производится один раз в истории и цели. Превышение доступной суммы не подтверждается и не расходует состав: допустимую часть можно распределить до остатка, превышение отдельно диагностируется как RETURN_CAPACITY_EXCEEDED, tax_ready=0; налог превышения не утверждается. Не скрывать лишнюю сумму и не переводить её автоматически в возврат излишней оплаты.
7. Эта ветвь всегда отражает возврат по реализации/услуге, даже когда сумма равна всей первоначальной оплате и даты близки. Правило взаимного исключения пары U5.2 здесь **не действует**. Исходная оплата остаётся обычной строкой, если она входит в целевой период; возврат — отдельной отрицательной строкой.

### U5.2. Нет явной однозначной ссылки на реализацию: возврат излишней оплаты

Прочитанный комментарий без явной однозначной ссылки на отгрузку/услуги означает эту ветвь, в том числе пустой комментарий, ссылка только на INVOICE либо несколько неоднозначных упоминаний реализаций. Не запускать эвристический поиск реализации и не превращать ссылку на счёт в цепочку к реализации. Неоднозначные упоминания сохранить в диагностике; не назначать один из документов по score.

Определить исходную оплату отдельно, среди более ранних поступлений того же КонтрагентID, с учётом позиции/проводки внутри дня. Использовать прямую ссылку на оплату и другие непротиворечивые доказательства связи; одно равенство суммы при нескольких допустимых оплатах не обеспечивает однозначности. Нельзя выбирать ближайшую/первую оплату или распределять по FIFO. Договор, вид расчётов и счёт62 остаются доказательствами/диагностикой, не запретами. Не переиспользовать DEBT/ADVANCE matcher для RETURN и не искать документ, чтобы определить исходную оплату.

**Полный возврат с исключением пары:** оплата и возврат относятся к одному календарному кварталу одного года, исходная оплата однозначно установлена, возврат равен **полной исходной сумме** оплаты, явного документа реализации/услуг в комментарии нет, доступный остаток возврата позволяет вернуть всю эту сумму. Исходная оплата и возврат взаимно исключаются из готовой КУДиР; две строки +доход/−доход не формируются. Несколько частичных возвратов, в сумме равных оплате, не превращаются задним числом в одну полную пару. После прежнего частичного/полного возврата новый возврат на полную исходную сумму превышает остаток и не является допустимой полной парой.

**Возврат в другом квартале:** по окончательному уточнению владельца исходный квартал не пересчитывается и исходная оплата не удаляется. Даже полный возврат всей оплаты отражается только новой отрицательной строкой на дату возврата, с ранее признанным налоговым составом исходной оплаты. В годовом расчёте, включающем обе даты, сохраняются обе строки в своих кварталах; в расчёте квартала возврата выводится только возврат. Это правило действует и при переходе года. Для исключения пары сравниваются календарные квартал и год, а не границы выбранного периода проверки или принадлежность операции целевому выводу. Историческая оплата того же квартала может участвовать в допустимой паре, но не дублируется в целевом выводе. Возврат по явному документу U5.1 всегда остаётся отдельной отрицательной строкой с составом документа. OD6 закрыт; межквартальные исправления не формируются.

**Частичный / иной неполный возврат, а также полный возврат другого квартала:** исходная оплата остаётся в расчёте КУДиР, возврат даёт отдельную отрицательную строку на свою дату. Исторические операции не дублируются в целевом CSV. Источник — **ранее определённый налоговый результат исходной оплаты**, в том числе фактический VAT=0, смешанный состав, PRE_2026 либо применённый тогда default. Не выполнять новый поиск документов и не пересчитывать возврат как независимое поступление. Возврат 21 000 из исходных 105 000 с доходом 100 000/VAT 5 000 → уменьшение дохода 20 000 и VAT 1 000.

Для исходной оплаты требуется сохраняемый денежный остаток возврата и её признанный налоговый состав, уменьшенный на уже распределённые возвраты. Использовать имеющееся состояние/журнал распределений, если оно обеспечивает этот контракт; конкретная структура данных не задаётся. Исторические возвраты учитываются до целевых, исходная полная сумма не восстанавливается при новом запуске или смене ДатаНач. Частичный возврат пропорционально расходует ещё не возвращённый состав по §21.2; доказанное отнесение к конкретной части исходной оплаты важнее общей пропорции. Последняя часть забирает остаток. Подтверждённый расход не может превышать доступную сумму/состав оплаты; превышение остаётся диагностированным, без второго расхода и без фиктивной пары.

Если исходная оплата или её ранее признанный состав не установлены, возврат остаётся в своей ветви U5.2, виден для проверки как RETURN_UNRESOLVED/ready=0. Ни поиск реализации, ни новый default не устраняют этот недостаток фактов.

### Подписанные поля RETURN и диагностика

Для известной части R>0, возвращаемой базы B и VAT V:

```text
row_type = RETURN
payment_id = PAYMENT самого возврата
matched_document_id = DOCUMENT указанной реализации для U5.1; пусто для U5.2
amount_kopecks = -R
advance_kopecks = 0
repayment_kopecks = 0
vat_base_kopecks = -B
vat_kopecks = -V
income_kopecks = -(R - V) = amount_kopecks - vat_kopecks
amount_kopecks <= vat_base_kopecks <= vat_kopecks <= 0
```

Нули advance/repayment отличают возврат от положительного split; у DEBT/ADVANCE/DEBT_UNRESOLVED прежние инварианты сохраняются. Договор — подтверждённая аналитика самого возврата. PAYMENT исходной оплаты нельзя записать в matched_document_id: связь PAYMENT→PAYMENT хранит журнал §24.1 ТЗ 01. Для U5.1 существующий matched_document_id достаточен, новое return_document_id не требуется. Если ссылка извлечена, но объекта нет во входе, поле пусто, реквизиты/ошибка в reason/логе; не выдумывать ID.

match_type: RETURN_DOCUMENT / RETURN_PAYMENT_FULL / RETURN_PAYMENT_PARTIAL / RETURN_UNRESOLVED. Для подтверждённой прямой ссылки confidence=HIGH означает однозначность реквизитов, не результат score. reason различает RETURN_DOCUMENT_EXPLICIT, RETURN_PAYMENT_COMPOSITION, RETURN_PAIR_EXCLUDED, RETURN_PAYMENT_UNRESOLVED, RETURN_SOURCE_UNAVAILABLE, RETURN_TAX_UNRESOLVED, RETURN_CAPACITY_EXCEEDED и неоднозначные ссылки; коды помещаются в существующее reason. Не создавать новые колонки для каждого признака.

Неустановленный налог/превышение: технические amount=-R, income=-R, база/VAT=0, RETURN_UNRESOLVED, reason=RETURN_TAX_UNRESOLVED вместе с причиной. Это предварительное отображение движения, не утверждённое уменьшение дохода и не доказанный VAT=0. Состав сверх ёмкости не списывается. Текст сообщает «налоговый состав не определён»; готовность влияющей целевой части = 0, остальные рассчитанные строки доступны. При известном составе текст отражает уменьшение дохода/VAT и только подтверждённые реквизиты источника.

### Состояние, обычные распределения и периоды

Нужны два различимых назначения учёта: возвраты по исходной оплате U5.2 и возвраты по явному документу U5.1, со своими доказанными доступными суммами и составом. Уже израсходованный на обычную оплату состав документа не исчезает как факт и не становится заново свободным для другой оплаты: хранится/восстанавливается исходный фактический состав, обычный расход и возвратный расход. Один возврат относится к одной ветви, не списывается одновременно с оплаты и документа «на всякий случай». Условия U1/U3 обычных оплат не отменяются.

Денежный возврат не является сам по себе сторно реализации и не разрешает произвольно пересматривать HIGH обычной оплаты. Прежнее автоматическое освобождение всех её резервов по одному факту возврата отменено. Бухгалтерский signed_balance меняется по ledger; отдельная доказанная корректировка документа учитывается по существующему правилу и ровно один раз. Если нужно решить, как возврат U5.1/U5.2 меняет ранее занятые **обычные** ёмкости RECEIVABLE/INVOICE или общий экономический остаток при возвратах разных ветвей, а факты не задают единственного результата, это OPEN_DECISION OD7, не выдуманный перенос/восстановление. На чистые сценарии возвратного расхода без такого влияния OD7 не распространяется.

### Журнал, полнота и готовность

`return_allocations.csv` — минимальный машинно проверяемый журнал: 01 §24.1. Он нужен для отсутствующих в kudir_result пар, PAYMENT→PAYMENT связи и исторических возвратов, не имеющих целевых строк; одно СодержаниеЗаписи/analysis.log не обеспечивает проверку ID и повторного расхода. Не задаётся отдельная обязательная внутренняя таблица/класс. Для документной ветви журнал использует тот же matched_document_id, что результат. Новые поля run_status не требуются: status, tax_ready, state_uncertain, имеющиеся счётчики, журнал и reason покрывают требования. Возвратную неоднозначность не считать unresolved-долгом в unresolved_debt_kopecks.

Для неисключённого целевого поступления сумма результата = входной сумме; для RETURN = минус исходной положительной сумме возврата. Для исключённой полной пары журнал обосновывает отсутствие целевых строк: поправка +R для исходной оплаты, −R для возврата. Каждая неисключённая целевая операция и каждый неизвестный хвост должны оставаться видимыми; нельзя скрыть пропуск положительной оплаты или RETURN фиктивной парой. Оба ledger-события сохраняются независимо от вывода.

При определённых налогах/остатках возврат или полная пара сами по себе не снижают готовность: SUCCESS/ready=1 допустим. Неизвестный налог, влияющая неопределённость ёмкости, OD7 в применимой части → tax_ready=0 с конкретной причиной и доступным результатом. Недоступный parser либо неподдерживаемое техническое сторно могут дать SUCCESS_DEGRADED (код 0); обычный RETURN не означает degraded. Полностью исключённая допустимая пара имеет нулевой налоговый вклад, даже если её состав не был установлен; влияние на иные части проверяется отдельно.

Нулевая оплата сохраняется во входах/ZERO_PAYMENT в логе без доходной строки и без автоматической неготовности. Header-only возможен при проверенных полных парах/нулях/неподдерживаемом сторно, но не при пропущенном неисключённом возврате. Повреждённый CSV, невозможный ID, двойной подтверждённый расход и несогласованные суммы по-прежнему FAILED; отрицательное сторно отдельно сохраняет диагностический режим, а не становится RETURN по одному знаку.

Версия **CSV exchange schema=3** обоснована расширением row_type, подписанными суммами/новыми инвариантами RETURN и обязательным журналом. Новые колонки основного kudir_result не нужны. Имеющаяся версия scoring.yaml — другая сущность, её не менять. Код/тесты пока не приводятся к новой схеме; текущий v2 не считается совместимым.

# 39. DEBT_UNRESOLVED

Если точно известно:

```text
платеж погашает долг
```

но конкретный документ надёжно определить невозможно:

```text
не превращать сумму в аванс.
```

Результат:

```text
DEBT_UNRESOLVED
```

`DEBT_UNRESOLVED` не занимает `document_remaining` и не уменьшает `available_for_advance`. Matching при этом может быть `SUCCESS`. Налог и `tax_ready` определяются по §21.2: старый закрываемый долг → VAT 0, новый без сильного источника → 5/105, неустановленный возраст → OD1. Счётчики unresolved не обнулять и не использовать как автоматический блокер.

# 44. НДС

Правила — раздел 21.2. Кратко:

```text
vat_base_kopecks  — облагаемая доля части (со включённым НДС)
vat_kopecks       — НДС этой доли
income_kopecks    = amount_kopecks − vat_kopecks
```

Не вычитать 5/105 из банковского поступления, если есть валидный доступный состав допустимой отгрузки / услуги / счёта в применимом налоговом окне, с учётом приоритета PRE_2026_DEBT (§21.2). Не брать фактический НДС поздней отгрузки для `ADVANCE_EXTENDED_MATCH`. Аванс до `2026-01-01` не получает 5/105. Реализация 2026 может иметь фактический НДС независимо от даты аванса. Для `DEBT_UNRESOLVED` применять возраст реально закрываемой части по 02 §21.2; неопределённый возраст — OPEN_DECISION OD1.

---

Для RETURN источник по §36.1: явный документ отгрузки/услуг имеет собственный фактический состав U5.1; только без такой ссылки используется исходная оплата U5.2. Новый default не подменяет ни один установленный источник.

# 45. СодержаниеЗаписи

Только подтверждённые реквизиты. Нет номера, даты или договора — этот фрагмент не подставляется. Если НДС определён, текст это отражает. Для `DEBT_UNRESOLVED` отражать доказанный налог по U2: «без НДС» при `PRE_2026_DEBT` либо рассчитанный НДС при `DEFAULT_5_105`; при нерешённом возрасте налоговую фразу не писать. Реквизиты ненайденного документа не выдумывать.

В шаблонах `{ПодтверждённаяНалоговаяФраза}` = «, без НДС» для PRE_2026 либо «; сумма {Сумма} руб., в т.ч. НДС 5% — {НДС} руб.» для определённого DEFAULT; при OD1 фрагмент пустой.

Шаблоны:

```text

Оплата от {Контрагент} за услуги по акту №{Номер} от {Дата}, без НДС

DEBT + оказание услуг, есть НДС:
Оплата от {Контрагент} за услуги по акту №{Номер} от {Дата}; сумма {Сумма} руб., в т.ч. НДС 5% — {НДС} руб.

Оплата от {Контрагент} за товар по накладной №{Номер} от {Дата}, без НДС

DEBT + отгрузка, есть НДС:
Оплата от {Контрагент} за товар по накладной №{Номер} от {Дата}; сумма {Сумма} руб., в т.ч. НДС 5% — {НДС} руб.

те же шаблоны, что для DEBT, но начало «Получен аванс от {Контрагент} в счёт …»

ADVANCE + договор без документа, есть НДС 5/105:

ADVANCE без договора и без документа:

  + суффикс НДС, если он определён; без суффикса, если не определён
```

Не выдумывать отсутствующие реквизиты. Не писать «без НДС», если состав на самом деле неизвестен.

# 48.3. Обязательная приёмка U1–U5 после актуализации

Это требования к будущей реализации и ожидаемым результатам, не заявление о прохождении текущих тестов. Старые expected не являются источником налоговых правил. Для всех налоговых примеров суммы ниже в рублях; целевое поступление — 2026, история и начальная ёмкость полны, иных неопределённостей нет.

1. U1: у оплаты и документа одного контрагента различаются договор, вид расчётов и счёт 62. Сильная доказательная связь при допустимом окне/роли и положительном remaining разрешена, различия объяснены. Split DEBT/ADVANCE и signed_balance каждой исходной аналитики не меняются. При другом контрагенте связь запрещена независимо от score. Unknown/multiple счёта 62 не превращается в совпадение или запрет.
2. U2: unresolved закрывает доказанно старые 105 000 → `PRE_2026_DEBT`, база/VAT 0, доход 105 000, ready=1. Ненулевой VAT matched-документа, в том числе другой аналитики, доказанный старый возраст не отменяет. Доказанно новый unresolved 105 000 без сильного источника → `DEFAULT_5_105`, база 105 000, VAT 5 000, доход 100 000, ready=1.
3. Возраст: полностью закрываются доказанные 42 000 старого + 63 000 нового долга без налогового документа → отдельные части: старые VAT 0 / доход 42 000; новые VAT 3 000 / доход 60 000. Частично закрывается смесь без доказательства распределения → OD1, ready=0, без FIFO/LIFO/пропорции. Дата cross-analytics документа не заменяет доказательство возраста платёжного остатка.
4. U4 для аванса 105 000 или доказанно нового долга: валидный RECEIVABLE с облагаемой суммой 63 000 / необлагаемой 42 000 / VAT 3 000 → база 63 000, VAT 3 000, доход 102 000; приоритет над счётом и default. Явно валидный exempt 105 000 → база/VAT 0, доход 105 000. Неизвестный состав (пустая ТЧ, три нуля, расхождение, отрицательный НДС ТЧ) без другого допустимого источника → база 105 000, VAT 5 000, доход 100 000, `VAT_COMPOSITION_UNKNOWN` + `DEFAULT_5_105`, ready=1. При валидном допустимом раннем счёте использовать его состав вместо default. Matching найденного документа сохраняется; неизвестность не подписывать «без НДС».
5. U3: RECEIVABLE 100 000, исторически подтверждено 40 000, новый запрос 80 000 → на документ не больше 60 000, оставшиеся 20 000 идут по собственному split и правилам поиска/налога. Повторить для товара/услуги, DEBT/ADVANCE, другой аналитики, direct/chain/combination/conflict. После remaining=0 идеальная ссылка не возвращает документ кандидатом и исчерпанный peer не мешает уникальности другого доступного документа. Однозначная корректировка уменьшает общую ёмкость, не только один путь расхода.
6. INVOICE 105 000 со смешанным составом 63 000 / 42 000 / VAT 3 000: исторический fallback на 42 000 расходует taxable 25 200, exempt 16 800, VAT 1 200; remaining денег 63 000, taxable 37 800, exempt 25 200, VAT 1 800. Следующий аванс 84 000 без реализации расходует не более 63 000 со счёта (VAT 1 800), хвост 21 000 → default VAT 1 000. Итого VAT 2 800, доход 81 200. Третья оплата не использует этот счёт при remaining=0. Отдельно проверить три частичных расхода с копеечным хвостом и полным исчерпанием состава. Состав суммарно не расходуется сверх суммы счёта. Дополнительные эталоны совместного расхода и extended приведены ниже; OD2/OD3 закрыты.
7. Полный налоговый runner сравнивает amount/advance/repayment/income/vat_base/vat, источник и reason, unresolved и все поля run_status, включая `vat_unknown_count`. Matching-golden с автозаполнением builder «вся сумма необлагаемая» подтверждают связи, но не являются налоговыми эталонами U4 без явно заданных фактов состава. Валидные нулевые составы не заменять массово на 5/105.
8. Устаревшие ожидания: `success_tax_not_ready` / `test_2_7_success_with_tax_ready_zero` при чистом старом долге должны требовать PRE_2026/ready=1 по §48 тест 2.7; `historical_unresolved_blocks_tax` / `test_4_6_historical_unresolved_*` при определённом старом целевом долге не должны блокировать tax_ready лишь из-за истории (`state_uncertain=1` допустим). Название старого каталога не задаёт ожидаемый статус.
9. Два ожидания tied HIGH 180/180/100 (`test_tied_group_separated_from_rest_uses_nearest`, `test_chronology_picks_nearest_in_tied_high_group`) не соответствуют §31: gap лучшего со вторым равен нулю, третий не разрешает HIGH. Зелёные тесты с таким ожиданием не подтверждают готовность. Схема без `vat_unknown_count` и runner без income/vat_base не подтверждают налоговый контракт.
10. Расчёт квартала и года на одном полном наборе фактов даёт одинаковый налог целевых частей; смена ДатаНач не возвращает израсходованную ёмкость. Extended не пересчитывает закрытый квартал; ранний допустимый счёт сохраняется. Открытый OD1 и недостаточные исходные факты ёмкости должны выявляться, а не скрываться default или зелёными matching-тестами. По OD2/OD3 обязательны числовые эталоны ниже.


Дополнительные эталоны принятых OD2/OD3 (все суммы в рублях):

11. OD2: INVOICE 105 000, состав taxable 63 000 / exempt 42 000 / VAT 3 000. Реализация по этому счёту на 42 000 имеет собственный состав taxable 42 000 / VAT 2 000; её подтверждённая оплата 2026 закрывает доказанно новый долг. Выходной VAT = 2 000, доход = 40 000. В счёте эта оплата резервирует 42 000 денег, taxable 25 200 / exempt 16 800 / VAT 1 200, а не VAT реализации 2 000. Remaining счёта: деньги 63 000, taxable 37 800 / exempt 25 200 / VAT 1 800. Следующий аванс 84 000 только по этому счёту: 63 000 используют остаток счёта (VAT 1 800), хвост 21 000 — default (VAT 1 000), итог VAT 2 800 / доход 81 200. Счёт исчерпан.
12. OD2, замена источника: счёт и состав как в п.11, аванс 42 000 сначала использует счёт (VAT 1 200). Затем в том же налоговом окне подтверждена полностью облагаемая реализация на 42 000 / VAT 2 000. Итоговый налог аванса заменяется на VAT 2 000 / доход 40 000. Remaining счёта остаётся 63 000 и VAT 1 800; повторного списания 42 000 или освобождения резерва нет. Remaining реализации = 0. Повторный проход даёт те же остатки. При реализации в extended налог старого квартала остаётся VAT 1 200, денежные остатки те же.
13. OD2, границы: реализация 126 000 основана на единственном счёте 105 000 без прежнего расхода. Подтверждённая оплата реализации 126 000 расходует в RECEIVABLE 126 000, в INVOICE 105 000; 21 000 сверх покрытия не дают отрицательного remaining счёта, но остаются оплатой реализации с её собственным составом. Два разных подтверждённых платежа по реализациям одного счёта суммируются до его ёмкости, одна и та же часть оплаты через два пути не суммируется повторно. # 49. Критерии готовности Python

1. Существующий parser вызывается как внешний сервис и покрыт regression-тестами; код сервиса не копируется.
2. Поддерживается прямое указание акта/накладной, включая `HIGH_PARTIAL_DIRECT`.
3. Поддерживается оплата по счету и цепочка `Оплата → Счет → Реализация`. HIGH через счёт закрывает аванс сразу.
4. Парсятся стандартизированные комментарии `Введен на основании`.
5. Поддерживается ПКО.
6. При неединственной ссылке или равных суммах нескольких кандидатов автоматический HIGH не ставится.
7. Договор, вид расчётов и счёт 62 — scoring evidence / penalty / diagnostic, не hard reject; matching внутри контрагента разрешён между аналитиками, split ledger неизменен (§22).
8. Другой контрагент является hard reject.
9. Будущий документ вне допустимого окна операции `DEBT`. Для `ADVANCE` — `ADVANCE_TAX_WINDOW` и `ADVANCE_EXTENDED_MATCH_WINDOW`.
10. Поддерживаются комбинации оплат и документов. Разрез DEBT/ADVANCE — по каждой аналитике, без неттинга.
11. Matcher идёт хронологическим потоком событий и этапами блокировки. FIFO отсутствует. Обратная хронология — только tie-break при порогах.
12. Пороги HIGH/MEDIUM/LOW и отрыв заданы только `scoring.yaml`. В ТЗ нет числовых примеров весов.
13. ML является опциональным и в версии 1 не обязателен.
14. Формируется `kudir_result.csv` по схеме ТЗ №1 только для `is_target=1`, с тем же `run_id`. `СодержаниеЗаписи` без CR/LF.
15. Формируется `matches.csv` с разложением score. `analysis.log` обязателен.
16. Поддерживается `DEBT_UNRESOLVED`; он не занимает remainder. `status` и `tax_ready` разделены; поля `unresolved_debt_kopecks`, `unresolved_count`, `state_uncertain`, `historical_unresolved_*`.
17. Контролируется сумма каждой исходной целевой оплаты по §36.1: полный результат поддерживаемых положительных частей и доказательные исключения полных пар/неподдерживаемого сторно/нулевых частей. Возврат отражается отрицательной строкой или подтверждённой полной парой, не останавливая расчёт других оплат.
18. `opening_balances.csv` обязателен; оба остатка Дт и Кт используются; ключ — аналитика.
19. CSV читается по протоколу ТЗ №1 (Windows-1251, `;`, даты ISO, quoting).
20. Оплата склеивается с проводками 62 по `payment_id` и проводится только через ledger. `documents.csv` не создаёт отдельного бухгалтерского события: timeline и `signed_balance` меняет только `ledger62.csv`.
21. `config/scoring.yaml` обязателен и является единственным источником весов.
22. Недоступность parser даёт `SUCCESS_DEGRADED`, а не скрытый успех. Это не то же самое, что `tax_ready=0`.
23. Python считает НДС и доход УСН в том же запуске. Источник аванса — состояние налогового окна: валидный доступный состав реализации в окне, иначе допустимого счёта с остатком, иначе 5/105/0. Поздняя реализация не источник НДС и не отменяет ранний счёт. Счёт после конца квартала не пересчитывает налог закрытого квартала. Аванс и реализация живут на разных VAT-шкалах.
24. HIGH-аванс закрывается сразу. Неоднозначное — conflict-resolution pass. Документ после `ДатаКон` входит в matching обходом доступности без `signed_balance`.
25. Агрегаты колонки `НДС` из `documents.csv` обязательны. Строки товаров Python не требует отдельным файлом. Валидный доступный состав отгрузки / услуги в налоговом окне приоритетнее счёта; поздняя отгрузка счёт не отменяет.
26. Неплатёжный 62 всегда меняет сальдо аналитики; расхождение remainder и aggregate — diagnostic event.
27. `tax_ready=1` только когда НДС всех целевых строк определён. `DEBT_UNRESOLVED` и `VAT_COMPOSITION_UNKNOWN` не блокируют готовность автоматически; применять порядок PRE_2026 → валидный RECEIVABLE → допустимый INVOICE → DEFAULT_5_105, при неустановленном возрасте — OD1. Технические нули НДС при неизвестном составе не есть «без НДС».

29. Gap HIGH — между лучшим и вторым кандидатом. Слабый третий не создаёт HIGH у равной пары. Хронология HIGH не создаёт.

OD2: реализация и связанный счёт резервируются без повторного расхода одной части оплаты, смена налогового источника не освобождает счёт. OD3: extended резервирует пропорциональный состав без пересчёта старого квартала (§48.3 п.11–14).
32. Поле vat_unknown_count в run_status.csv сохраняет смысл; дополнительные счётчики U5 не нужны.
33. U5 реализуется отдельным путём: явный документ только из комментария без document matching и с собственным возвратным составом; без такой ссылки — исходная оплата, исключение допустимой полной пары или частичный возврат из признанного состава оплаты. Подписанные RETURN, журнал, два назначения возвратного остатка и пределы расхода — §36.1 / 01 §24.1. Приёмка — §48.3 п.15–30; применимые случаи OD7 не маскируются готовностью.

# 50. Оставшиеся OPEN_DECISION и граница реализации

Вопросы перенесены из 08 в действующий нормативный ТЗ. После отдельного поручения владельца выбрать решения OD2 и OD3 закрыты правилами §21.2; OD1 и OD4 остаются открытыми; OD5 закрыт окончательным U5 (§36.1); OD6 закрыт уточнением владельца: другой квартал — только новая запись, без исправления исходного квартала; влияние на обычные ёмкости выделено в OD7. Доказанный PRE_2026 имеет приоритет по §21.2; конфликт означает OD1 лишь когда само доказательство возраста/отнесения закрываемой части неоднозначно.

### OD1. Погашение смешанного по возрасту unresolved-долга

Нужен доказательный источник распределения либо отдельное решение владельца для частичного погашения смеси до/после 01.01.2026. Входной scalar ledger и даты не дают единственного ответа. Не вводить FIFO, LIFO, пропорцию, «старый сначала» или «весь новый» по умолчанию. Аналогично требуется правило доказательства при cross-analytics документе, противоречащем возрасту долга платёжной аналитики. До решения — matching допустим, налог затронутой части не объявляется однозначным. Чисто старые/новые доказанные случаи не блокировать.

Обсуждаемое предложение владельца «сначала старую» пока не утверждено окончательно. Возможная формулировка: при известных остатках старого и нового долга одной аналитики и отсутствии более сильного доказательства погашения сначала расходовать старый возрастной остаток, затем новый. Это порядок возрастного учёта, не FIFO поиска документов. Он не восстанавливает неизвестную величину старого остатка и не отменяет доказанную привязку закрываемой части. До окончательного решения примеры неоднозначного частичного погашения остаются OPEN_DECISION.

### OD2 — RESOLVED. Связанный расход счёта и реализаций

Закрыто по поручению владельца «сам реши»: связанный расход и один резерв на экономическую часть оплаты в каждом документе, собственная пропорция состава каждого документа, сохранение резерва при замене налогового источника. Нормативные правила — §21.2; числовая приёмка — §48.3 п.11–13.

### OD3 — RESOLVED. Состав, резервируемый старым extended-авансом

Закрыто по поручению владельца «сам реши»: пропорциональный резерв остаточного состава реализации без изменения налога старого квартала. Нормативные правила — §21.2; числовая приёмка — §48.3 п.14.

### OD4. Источник счёта62 документа

DOCUMENTS_FIELDS этого поля не содержит; счета и будущие документы могут не иметь ledger-событий. Требуется подтвердить источник аналитики в 1С/схеме и трактовку документа с несколькими счетами62. До этого признак unknown, без hard reject и без выдуманного совпадения. Формат нового поля/набора и веса — технические решения после подтверждения источника, а не повод заново согласовывать U1.

### OD5 — RESOLVED. Окончательный U5 заменяет прежние варианты возвратов

U5.1: только явный однозначный документ отгрузки/услуг из комментария, фактический состав этого документа, отдельная возвратная ёмкость, без document matching/default/подмены оплатой. U5.2: при отсутствии такой ссылки определить исходную оплату; допустимый полный возврат всей оплаты в том же календарном квартале того же года исключает обе операции, частичный/иной неполный возврат сохраняет обе с отрицательным налогом из признанного состава оплаты. RETURN не проходит DEBT/ADVANCE matcher. Правила — §36.1, обмен — 01 §24.1, приёмка — §48.3 п.15–30. Уточнение владельца по OD6 ограничивает исключение пары одним календарным кварталом одного года; полный возврат в другом квартале сохраняет исходную оплату и создаёт новую отрицательную строку из её состава. Требование двух target-событий не вводится. Единый источник «исходная оплата для всех возвратов» отменён: U5.1 использует явный документ.

### OD6 — RESOLVED. Возврат в другом квартале — только новая запись

Владелец запретил исправление одного квартала из другого. Если возврат произошёл в другом календарном квартале/году, исходная оплата и книга её квартала остаются без изменений; на дату возврата формируется отдельная отрицательная RETURN, даже при возврате всей суммы. Для U5.2 налог наследуется из признанного состава исходной оплаты; для U5.1 — из явно указанного документа. Исключение полной пары U5.2 допускается только в одном календарном квартале одного года. Пересчёт/повторный выпуск исходной книги не требуется. Отдельный статус, reason-код или поле CSV для этого правила не нужны: даты источников, RETURN_PAYMENT_FULL и RETURN_PAYMENT уже обеспечивают проверку. Поддерживаемый межквартальный возврат сам по себе не снижает tax_ready.

### OD7 — OPEN_DECISION. Возвратные и обычные ёмкости при связанных документах/оплатах

U5 задаёт расход возвратной ёмкости оплаты/документа, но не общее правило освобождения ранее занятых обычных ёмкостей RECEIVABLE/INVOICE и распределения влияния между ними при возврате по документу, нескольких исходных оплатах или возвратах обеих ветвей одного хозяйственного основания. Не переносить налоговый состав между источниками, не восстанавливать обычные резервы автоматически и не уменьшать обе возвратные ёмкости одним возвратом без доказанного основания. Нужны подтверждённая связь/корректировка либо решение для такого смешанного сценария. До этого ledger применяется как факт, возвратный расход ведётся по выбранному источнику U5, влияющая на последующие целевые распределения неопределённость диагностируется. Чистые возвраты по одному источнику и их частичные пропорции определены U5 и не требуют нового согласования.

Эти OD не разрешают откладывать уже определённые исправления gap, CSV/L1/L3, расход обычного документа и чистые U2/U4-сценарии. Недостающие веса, названия reason и реализация журнала сами по себе не требуют новых бизнес-правил.


Открыты OD1 и применимые случаи OD7; OD2/OD3/OD5/OD6 закрыты, но не разрешают выдумывать недостающие исходные факты. OD4 — незакрытое подтверждение источника факта; отсутствие признака остаётся unknown/multiple и не запрещает matching.

В рамках актуализации изменяются только нормативные документы. До разрешения влияющих бизнес-вопросов и отдельной команды владельца к реализации кода и изменению тестов не переходить.

## 51.1. Методика и границы этапа

Применять документ 11, редакция 4: одна хозяйственная оплата, два разреза и пять сумм, сильные основания и старейший доступный долг, общий доступный горизонт. Рабочие предложения §14.2 остаются предложениями; этот раздел не утверждает их. Старые scoring и окна настоящего ТЗ не возвращаются в новую функцию. Исполняемые изменения, миграции, реальные выгрузки и тесты реализации выполняются позднее по отдельному запросу.

По счёту 2025 года использовать номер и дату из назначения как ключ поиска ссылок в актах, накладных и других исполнениях доступной истории с 01.01.2026 до фактического конца, включая следующие годы. Не требовать объект старого счёта и его собственный остаток. Найденное исполнение проверять по доступности и суммам; долг/аванс определять относительно оплаты. Если связанного исполнения нет, по принятому правилу считать назначенную сумму погашением старого долга без доказательства старого исполнения, сохраняя контроль старого ресурса и расхождений. По последующему принятому решению при частичном исполнении связывать подтверждённую доступную часть, а остаток оставлять неопределённым для бухгалтера, без автоматического старого долга, аванса или другого документа (документ 11 §6.2). При неоднозначных исполнениях сохранять альтернативы без произвольного выбора.

Слабые результаты сравнивать по документу 11 §9: общие части учитывать один раз, договорному разрезу автоматический приоритет не давать, последовательные варианты механически не смешивать. При равносильных несовместимых результатах сохранять альтернативы. Сценарии 15 и 25 MATCHING-TEST-CASES.md проверяют именно это, не утверждая прочие предложения отчётов.

После полного распределения оплаты прекратить подбор её исполнения. Общая обработка истории продолжается, самостоятельные последующие операции рассматриваются отдельно. До готовой КУДиР применять §36.1 со всеми условиями полной пары в одном календарном квартале одного года; в другом квартале сохранять исходную запись и формировать отрицательную строку возврата. Исключение из результата не удаляет движения из расчётов. Денежный возврат не равен сторно; конкретное сторно/корректировка исполнения меняет проверку его действительности и допустимой суммы, но сам возврат не освобождает произвольный документ. Открытые вопросы влияния на ёмкости не закрываются автоматически.

Принятое последующее решение по документу 11 §14.3: сохранять неопределённости для бухгалтера. По счёту с 2026 года сохранить назначение и доказанные части, а неопределённый остаток не направлять автоматически на другой долг и не выбирать его окончательную классификацию. При превышении старого назначения над доступным долгом сохранить назначение, ресурс и расхождение, не увеличивать ресурс и не превращать превышение в аванс. При равносильных конкурирующих прямых оплатах сохранить конфликт, альтернативы и общий лимит, не выбирать победителя по очереди, дате или пропорции. Это согласованное поведение алгоритма; результат конкретного случая остаётся открытым до решения бухгалтера. Прочие предложения §14.2, в том числе механизмы предварительной защиты, этим не утверждены. Ранее принятое правило неопределённого остатка старого счёта сохраняется. Текстовая приёмка — сценарии 13, 17, 24 и 30 MATCHING-TEST-CASES.md.

## 51.2. Вход, период и оплата из ledger

Источник нового входного контракта — ТЗ №1 §31. Отдельный payments.csv и входной is_target удаляются. Хозяйственные оплаты остаются внутренними сущностями Python и формируются из ledger по подтверждённой принадлежности движений. Сумма определяется по денежной роли и знаку, а не суммой всех связанных строк. Исходные движения применяются к состоянию один раз, объект оплаты не создаёт повторного списания. Полнота и уникальность проверяются по ledger_event_id, связям payment_id и восстановимым PAYMENT ID, а не существованию строк payments.csv.

Недостающие прежнему ledger PaymentKind/PaymentGranularity, сведения первичного платёжного документа, назначение и происхождение комментариев сохраняются по сопоставлению полей ТЗ №1 §31.2. Загрузчик и валидатор должны согласованно читать будущую версию; старые пакеты и текущие структуры не считаются уже идентичными новому формату.

Параметры начала/конца проверки — вход запуска Python и выбор интерфейса. Целевые оплаты определяются по ДатаОперации учётного события, а не дате первичного платёжного документа. Пакет содержит всю доступную историю с 01.01.2026 до фактической конечной даты, в том числе вне цели; вычисленный отбор не вырезает конкурирующие оплаты, возвраты, изменения исполнений и занятые суммы. Смена квартала в покрытом пакете не требует экспорта. Получать все квартальные, обязательные годовые и преддокументные снимки в двух разрезах; совпавшие границы не складывать. Отсутствие снимка не равно нулю.

Повторный экспорт может переиспользовать ledger квартала по совпадению контрольных Дт/Кт на начале и конце при наличии полного сохранённого квартала. Python получает итоговую полную историю из сохранённых и заменённых кварталов без дублей. Не требовать обороты, хеши или журнал изменений как дополнительные доказательства; правило и ограничение обнаружения изменений — ТЗ №1 §31.4, №4 §19. Снимки и другие обязательные данные не пропускаются по одному факту переиспользования ledger.

## 51.3. Идентификаторы, порядок и реквизиты

ПКО — одна `CASH|{ПозицияДокумента}`. У агрегированной CASH-оплаты отсутствующий номер проводки не дополняется из ledger; номера отдельных проводок и порядок внутри документа сохраняются в движениях. Единая граница сложной группы по-прежнему имеет статус предложения документа 11 §14.2.1.

Ручная «Операция» — `MANUAL|{ПозицияДокумента}|{НомерПроводки}`: номер проводки обязателен, номера строки выписки нет. Банк — `BANK|{ПозицияДокумента}|{НомерПроводки}` с действующими проверками принадлежности. Нельзя классифицировать всё кроме ПКО как BANK или принимать MANUAL без номера проводки. Несколько корреспонденций одной оплаты не создают несколько поступлений.

Позиция — точное исходное значение позиции документа на шкале времени 1С, с сохранением пробелов; числовой номер проводки задаёт порядок внутри документа. Технические идентификаторы и позиции нельзя обрезать общей нормализацией строк. Номер и дата первичного банковского платёжного документа поступают по контракту функции владельца (ТЗ №1 §31.3); неизвестные значения пусты с диагностикой, без подстановки реквизитов выписки. Дата/позиция учётной операции сохраняются отдельно и задают период/хронологию независимо от первичных реквизитов.

# ТЗ №2. Python

## Анализ платежей, поиск оплачиваемых документов и формирование строк КУДиР

### 1. Назначение

Python-программа является основным аналитическим модулем версии 1: matching оплат, а не готовая налоговая КУДиР.

Вход:

```text
manifest.csv
payments.csv
ledger62.csv
documents.csv
opening_balances.csv
```

`opening_balances.csv` обязателен. Отсутствие файла — ошибка, расчёт с нуля запрещён.

Выход:

```text
kudir_result.csv
matches.csv
unresolved.csv
analysis.log
```

В `kudir_result.csv` попадают только оплаты с `is_target=1`. Исторические оплаты участвуют в matching и восстанавливают остатки документов.

Через CSV передаются ID и скаляры, не объекты 1С.

---

# 2. Ключевое требование: не писать существующий разбор заново

Parser является внешней зависимостью и в этот репозиторий не входит. Новый parser не разрабатывается и не копируется.

Он уже умеет определять:

```text
смысл платежа
тип упомянутого документа
номер документа
дату документа
номер счета
```

Приоритет:

```text
1. вызывать существующий HTTP-сервис http://127.0.0.1:8765/parse1c;
2. инкапсулировать вызов в legacy_parser_adapter.py;
3. покрыть regression-тестами реальные строки;
4. только после этого добавлять новые правила matcher.
```

Если сервис недоступен: для этой оплаты текстовый разбор пропускается, matching продолжается по суммам и основаниям, в `analysis.log` пишется ошибка. Система не падает целиком.

Формат запроса/ответа — как у текущего клиента в `доходы-2.txt`. Адрес задаётся конфигурацией, по умолчанию `http://127.0.0.1:8765/parse1c`.

Не создавать новый независимый parser с нуля.

# 4. Этапы обработки платежа

Оплаты обрабатываются в хронологическом порядке (`ДатаОперации`, `ПозицияДокумента`, `НомерСтрокиВДокументе` / `НомерПроводкиВДокументе`), сначала исторические, затем целевые.

Для всей области одного контрагента matcher идёт этапами блокировки, а не одним greedy-проходом:

```text
1. восстановить состояние взаиморасчётов на момент оплаты;
2. определить сумму погашения долга и аванса;
3. заблокировать уникальные машинные ссылки
   (ПКО / «Введен на основании»);
4. зафиксировать уникальные прямые ссылки и допустимые частичные оплаты;
5. зафиксировать уникальные совпадения через счёт;
6. зафиксировать уникальные совпадения остатка;
7. решить оставшиеся конфликты ограниченным поиском
   внутри одного контрагента;
8. всё ниже порога — DEBT_UNRESOLVED;
9. semantic reranker в версии 1 не обязателен.
```

FIFO и скрытый greedy как основной алгоритм запрещены.

---

# 5. Разделение на долг и аванс

Это чистая бухгалтерская арифметика.

Пример:

```text
долг перед платежом = 7 000
платеж = 10 000
```

Результат:

```text
debt_part = 7 000
advance_part = 3 000
```

Никакая LLM этого не определяет.

---

# 6. Первый и самый сильный путь: прямое указание документа

Сначала существующим parser'ом анализируются:

```text
СодержаниеПроводки
Содержание
ПредставлениеПроводки
НазначениеПлатежа
ПервичныйДокумент
КомментарийДокументаОплаты
```

Parser может обнаружить, например:

```text
НАКЛАДНАЯ № Н00570 от 30.06.2026
```

или:

```text
АКТ №25 от 10.08.2026
```

---

# 7. Прямой документ + сумма в пределах остатка

Если найдена уникальная ссылка на конкретный документ задолженности того же контрагента и документ существовал на момент оплаты:

```text
0 < сумма_к_распределению <= текущий непогашенный остаток документа
```

связь фиксируется сразу.

- полное закрытие остатка: `DIRECT_DOCUMENT_EXACT`, `HIGH`;
- частичная оплата: `HIGH_PARTIAL_DIRECT`, `HIGH`.

Стандартный общий matching в этом случае не нужен.

Частичная оплата — нормальный случай, а не ошибка суммы.

---

# 8. Прямой документ, платёж больше остатка

Если ссылка уникальна, но сумма больше остатка указанного документа:

```text
остаток → этот документ (DIRECT_DOCUMENT_EXACT / HIGH_PARTIAL_DIRECT)
хвост  → дальнейший matching или ADVANCE
```

Если ссылка неоднозначна (несколько документов) или сумма не помогает выбрать кандидата — не фиксировать автоматически. Документ получает бонус `DIRECT_DOCUMENT_HINT` (например `+100`) и идёт в общий цикл.

Точная сумма сама по себе сильна только при единственном кандидате. Два документа по 10 000 и платёж 10 000 однозначной связи не создают.

---

# 9. Второй основной путь: оплата по счету

На практике значительная доля платежей содержит именно:

```text
Оплата по счету ...
```

При этом документ задолженности — не счет, а:

```text
Отгрузка товаров
```

или:

```text
Оказание услуг
```

Поэтому необходимо построить цепочку:

```text
Платеж
→ Счет на оплату
→ документ, введенный на основании счета
→ задолженность
```

---

# 10. Поиск счета

Использовать существующий рабочий parser.

Например:

```text
Оплата по счету №00002
```

даёт:

```text
Тип = СЧЕТ
Номер = 00002
```

Если известна дата:

```text
Дата = ...
```

также использовать её.

Затем найти счет в `documents.csv` по:

```text
Контрагент
Номер
Дата — если известна
```

---

# 11. Связь Счет → Отгрузка / Оказание услуг

После нахождения счета найти документы:

```text
Отгрузка товаров
Оказание услуг
```

в комментарии которых имеется стандартизированная ссылка:

```text
Введен на основании: Счет на оплату № 00002 от 06 Января 2026 г.
```

Так как комментарий формируется программой, эта связь считается очень сильной.

Внутренний тип связи:

```text
BASE_DOCUMENT_LINK
```

---

# 12. Нормализация ссылки «Введен на основании»

Не сравнивать строку целиком посимвольно.

Разобрать её в структуру:

```text
base_type
base_number
base_date
```

Например:

```text
base_type = INVOICE
base_number = 00002
base_date = 2026-01-06
```

Поддержать лишние пробелы и различные регистры.

---

# 13. Счет → один документ → сумма в пределах остатка

Если:

```text
оплата → счет №00002
```

и найден ровно один связанный документ задолженности, и:

```text
0 < сумма_к_распределению <= остаток документа
```

то соответствие фиксируется сразу (`INVOICE_BASE_EXACT` или частичный аналог, `HIGH`).

---

# 14. Счет → несколько документов

Один счет теоретически может стать основанием нескольких документов.

Тогда:

```text
не выбирать первый найденный.
```

Проверить:

1. точное совпадение одной суммы;
2. точное совпадение с остатком;
3. сумму нескольких связанных документов;
4. другие признаки.

Если однозначности нет — перейти к стандартному matching.

Но документы, связанные с найденным счетом, получают очень высокий score.

---

# 15. Счет найден, платёж больше остатка связанного документа

Остаток относится на связанный документ, хвост идёт в matching или аванс.

Если связанных документов несколько и однозначности нет — не привязывать насильно. Связь через счет остаётся сильной подсказкой.

---

# 16. ПКО: отдельный быстрый путь

Для `PaymentKind=CASH` прежде всего анализировать:

```text
КомментарийДокументаОплаты
```

Частый вариант:

```text
Введен на основании:
Отгрузка товаров № Н00570 от 30 Июня 2026 г.
```

Это практически прямая машинная ссылка на документ.

---

# 17. ПКО + сумма в пределах остатка

Если из комментария ПКО найден уникальный документ и:

```text
0 < сумма ПКО (или её долговой части) <= остаток документа
```

фиксировать сразу:

```text
CASH_BASE_EXACT или HIGH_PARTIAL_DIRECT
HIGH
```

---

# 18. ПКО + сумма больше остатка

Остаток — на указанный документ, хвост — дальше. Если ссылка неоднозначна — бонус кандидата и общий matcher.

---

# 19. Стандартный matching

Он запускается только после прямых путей.

Кандидаты должны соответствовать:

```text
тот же контрагент
документ существовал на момент оплаты
имеется непогашенный остаток
```

---

# 20. Другой контрагент — жёсткий запрет

```text
Контрагент оплаты != Контрагент документа
```

→ кандидат запрещён.

Это hard constraint.

---

# 21. Будущий документ — жёсткий запрет

Обычный платеж не может оплачивать документ, который ещё не существовал.

Использовать:

```text
Дата
ПозицияДокумента
```

Это hard constraint.

Ранее полученный аванс — отдельная ситуация и не является оплатой будущего документа на дату получения.

---

# 22. Договор НЕ является hard constraint

Это важное изменение.

Несовпадение договора:

```text
НЕ должно исключать документ.
```

Совпадающий договор:

```text
сильный плюс.
```

Разный договор:

```text
штраф,
но не запрет.
```

Например:

```text
same contract       +40
different contract  -20
unknown contract      0
```

Конкретные веса вынести в настройки.

---

# 23. Почему разный договор допускается

В реальной базе возможны:

* неверно выбранный договор в платежной строке;
* разные технические договоры;
* исторические изменения;
* ошибки пользователя;
* отличия договора оплаты от договора документа.

Поэтому если имеются сильные признаки:

```text
прямая ссылка на счет
+
ссылка "Введен на основании"
+
точная сумма
```

они имеют право перебить несовпадение договора.

При этом в `reason` необходимо отметить:

```text
CROSS_CONTRACT_MATCH
```

---

# 24. Какой договор возвращать

Если платеж сопоставлен с конкретным документом задолженности:

```text
Договор в строке DEBT
=
договор найденного документа задолженности
```

Не надо искусственно считать разные договоры одинаковыми.

Для `ADVANCE`:

```text
Договор
=
договор платежа
```

---

# 25. Приоритеты стандартного matching

Рекомендуемый порядок:

```text
1. прямой документ + точная сумма
2. счет → документ + точная сумма
3. ПКО → основание + точная сумма
4. точное совпадение остатка документа
5. точное совпадение полной суммы документа
6. несколько оплат = документ
7. одна оплата = несколько документов
8. закрытие остатка после предыдущей частичной оплаты
9. связь через счет/основание без точной суммы
10. договор
11. вид расчетов
12. товар/услуга
13. текстовая семантика
14. обратная хронология
```

---

# 26. Точные совпадения суммы

Сильными считать оба случая:

```text
платеж = первоначальная сумма документа
```

и:

```text
платеж = текущий остаток документа
```

Второй случай даже важнее для частично оплаченного документа.

---

# 27. Несколько оплат → один документ

Пример:

```text
Документ = 5 500

Оплата 1 = 4 500
Оплата 2 = 1 000
```

Получить:

```text
4 500 + 1 000 → 5 500
```

---

# 28. Одна оплата → несколько документов

Пример:

```text
Документы:
4 000
6 000

Платеж:
10 000
```

Получить две связи.

---

# 29. Очень важный случай закрытия остатка

Если:

```text
документ = 5 500
```

уже подобрана оплата:

```text
4 500
```

и имеется:

```text
1 000
```

то:

```text
1 000 = остаток документа
```

является сильным match.

---

# 30. Нельзя использовать простой FIFO

FIFO используется только как крайний fallback.

Например:

```text
документ A = 5 500
документ B = 27 200

оплаты:
4 500
27 200
1 000
```

правильно:

```text
27 200 → B
4 500 + 1 000 → A
```

а не механическое списание по хронологии.

---

# 31. Обратная хронология

При равных остальных признаках предпочтителен ближайший предшествующий документ.

Например:

```text
01.01 документ 10 000
05.01 документ 10 000
06.01 оплата 10 000
```

при отсутствии других различий:

```text
→ документ 05.01
```

---

# 32. Scoring

Пример:

```text
+200 прямая ссылка на конкретный документ
     + совпал остаток

+180 счет → документ по "Введен на основании"
     + совпала сумма

+170 ПКО → документ по "Введен на основании"
     + совпала сумма

+120 точное совпадение остатка

+100 точное совпадение полной суммы

+90  точная комбинация сумм

+70  прямая ссылка на документ, но сумма отличается

+60  связь через тот же счет

+40  тот же договор

-20  другой договор

+35  тот же вид расчетов

+30  товар ↔ товар / услуга ↔ услуга

+0..25 semantic score

+0..20 обратная хронология
```

Hard penalties:

```text
другой контрагент    → запрет
будущий документ     → запрет
```

Веса выносятся в конфигурацию (например `config/scoring.yaml`). Значения выше — стартовые.

---

# 32.1. Пороги уверенности и неоднозначность

Стартовые правила, меняются только конфигурацией, не хардкодом в matcher:

```text
HIGH:   score >= 150 И (нет второго кандидата ИЛИ отрыв >= 40)
MEDIUM: score >= 80  И отрыв >= 20
LOW:    score >= 50  И отрыв >= 10
иначе:  DEBT_UNRESOLVED
```

Дополнительно:

- результат почти только по хронологии не может быть `HIGH`;
- точная сумма даёт автоматическую блокировку только при единственном кандидате;
- в комбинаторный поиск не более 8 кандидатов на одну оплату;
- лимит времени поиска задаётся в конфигурации (старт: 2 секунды на контрагента);
- при превышении лимита — детерминированный fallback: этапы 3–6 уже заблокированного, остаток `DEBT_UNRESOLVED`, запись в `analysis.log`;
- пересмотр уже заблокированной связи `HIGH` запрещён; `LOW` можно пересмотреть, пока обрабатывается тот же контрагент и не начат следующий.

# 33. Парсер и эвристический matcher — разные компоненты

Не смешивать:

```text
"извлечь из текста счет №123"
```

и:

```text
"решить, какой документ фактически оплачивается"
```

Первое выполняет parser.

Второе выполняет matcher.

Это позволит использовать уже существующий parser без переписывания всей системы.

---

# 34. Hugging Face

Используется только после обычных признаков.

Рекомендуемый порядок:

```text
точные ссылки
→ суммы
→ связи оснований
→ договор/вид расчетов
→ обычный scoring
→ только затем semantic reranker
```

Модель не нужна для:

```text
"Введен на основании: Счет №123"
```

или:

```text
платеж 27 200
документ 27 200
тот же счет
```

---

# 35. Когда использовать модель

Например осталось:

```text
три старых документа
нет номера счета
нет прямой ссылки
нет точной суммы
договоры не помогают
```

Тогда можно сравнивать тексты:

```text
payment_text
document_text
```

через multilingual reranker.

---

# 36. Восстановление взаиморасчётов

Использовать `opening_balances.csv` и `ledger62.csv` с начала исторического периода.

По умолчанию:

```text
01.10 предыдущего года
```

Состояние = обязательное начальное сальдо + движения с `ИсторияНач`, последовательно по всем оплатам файла, включая `is_target=0`.

Проводки связываются с документами по `source_document_id`, а не повторным поиском по виду/номеру/дате.

`DocumentRole=INVOICE` не создаёт задолженность. Кандидаты погашения — `RECEIVABLE`.

---

# 37. Недостаточная историческая глубина

Если на `ИсторияНач` есть ненулевой остаток, который нельзя разложить на выгруженные документы, это не ошибка файла: конкретный старый акт вне истории не обязан быть найден.

Погашение такого остатка целевым платежом без однозначного документа:

```text
DEBT_UNRESOLVED
```

Отсутствие самого `opening_balances.csv` — ошибка обработки.

Snapshot документных остатков между запусками в версии 1 не используется.

---

# 38. opening_balances.csv

Обязательный вход. Минимальные поля — как в ТЗ №1:

```text
КонтрагентID
Счет62
ДоговорID
ВидРасчетовID
ВидРасчетов
ДатаСальдо
ОстатокДтКоп
ОстатокКтКоп
```

Тогда:

```text
начальное сальдо
+
движения с ИсторияНач
=
состояние на дату каждого платежа
```

Это восстанавливает размер долга, но не имя документа, созданного до `ИсторияНач`.

---

# 39. DEBT_UNRESOLVED

Если точно известно:

```text
платеж погашает долг
```

но конкретный документ надёжно определить невозможно:

```text
не превращать сумму в аванс.
```

Результат:

```text

```

Типы:

`contract_id` для `DEBT` — договор найденного документа, для `ADVANCE` — договор оплаты. Объекты 1С в файл не записываются.

# 48. Новые тесты

### Тест: прямой акт

```text
платеж содержит акт №25
акт = 5 500
платеж = 5 500
```

→ `DIRECT_DOCUMENT_EXACT`.

### Тест: акт указан, частичная оплата

```text
акт = 5 500
платеж = 4 500
уникальная ссылка на акт
```

→ `HIGH_PARTIAL_DIRECT`, связь фиксируется.

### Тест: через счет

```text
платеж:
Оплата по счету №00002

документ:
Оказание услуг №00005
Комментарий:
Введен на основании: Счет на оплату №00002 ...

суммы совпадают
```

→ `INVOICE_BASE_EXACT`.

### Тест: ПКО

```text
ПКО:
Комментарий:
Введен на основании: Отгрузка товаров №Н00570 ...

сумма совпадает
```

→ `CASH_BASE_EXACT`.

### Тест: разные договоры

```text
платеж — договор A
документ — договор B

но:
счет совпадает
основание совпадает
сумма совпадает
```

→ документ разрешено выбрать.

В `reason`:

```text
CROSS_CONTRACT_MATCH
```

### Тест: сумма важнее хронологии

```text
10 000 старый документ
12 000 новый документ
платеж 10 000
```

→ 10 000.

### Тест: несколько оплат

```text
4 500 + 1 000 → 5 500
```

Ключевой golden-кейс `пример1`: январские 1 000 закрывают остаток акта услуг 5 500 после исторических 4 500. Исторические оплаты имеют `is_target=0` и в `kudir_result.csv` не попадают.

### Тест: две одинаковые суммы без прочих признаков

```text
два документа по 10 000
платёж 10 000
нет ссылки и нет отрыва
```

→ не автоматический HIGH; при недостаточном отрыве `DEBT_UNRESOLVED`.

### Тест: нет opening_balances.csv

→ ошибка обработки, не расчёт с нуля.

### Тест: порядок внутри одной даты

`Пример2`: 15 800 → Отгрузка товаров Н00001, 5 500 → Оказание услуг 00001, с учётом `ПозицияДокумента`.

# 49. Критерии готовности Python

1. Существующий parser вызывается как внешний сервис и покрыт regression-тестами; код сервиса не копируется.
2. Поддерживается прямое указание акта/накладной, включая `HIGH_PARTIAL_DIRECT`.
3. Поддерживается оплата по счету и цепочка `Оплата → Счет → Реализация`.
4. Парсятся стандартизированные комментарии `Введен на основании`.
5. Поддерживается ПКО.
6. При неединственной ссылке или равных суммах нескольких кандидатов автоматический HIGH не ставится.
7. Разный договор не является hard reject.
8. Другой контрагент является hard reject.
9. Будущий документ является hard reject.
10. Поддерживаются комбинации оплат и документов.
11. Matcher идёт этапами блокировки; FIFO только как последний fallback.
12. Пороги HIGH/MEDIUM/LOW и отрыв заданы конфигурацией.
13. ML является опциональным и в версии 1 не обязателен.
14. Формируется `kudir_result.csv` по схеме ТЗ №1 только для `is_target=1`.
15. Формируется `matches.csv`.
16. Поддерживается `DEBT_UNRESOLVED`, в том числе для долга до начала истории.
17. Контролируется сумма каждой исходной целевой оплаты.
18. `opening_balances.csv` обязателен.
19. CSV читается по протоколу ТЗ №1 (Windows-1251, `;`, даты ISO, quoting).
20. Версия 1 не претендует на готовый налоговый доход КУДиР.

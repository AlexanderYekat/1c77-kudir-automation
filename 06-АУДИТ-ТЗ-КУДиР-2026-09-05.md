## 2. Ошибки кода, которые нужно включить в план №5

### A1. Начальное сальдо теряет обязательную аналитику — высокий приоритет

**Место:** код, `КУДиР_СобратьСальдоКлиента`, строка 1188; №5, вводное ограничение и §6.7.1; №4, §7.8.

Сейчас написано:

```1c
БухИт.ИспользоватьСубконто(ВидыСубконто.Контрагенты, Контр, 2);
БухИт.ИспользоватьСубконто(ВидыСубконто.Договоры, , 3);
БухИт.ИспользоватьСубконто(ВидыСубконто.ВидыРасчетовСПокупателями, , 3);
БухИт.ВыполнитьЗапрос(историяНач, историяНач, "62");
```

У `ИспользоватьСубконто` режим 3 исключает соответствующую аналитику из детализации; для разворота нужен режим 1. Кроме того, здесь не вызывается `ВключатьСубсчета`: по умолчанию запрос не разворачивает итоги по субсчетам. Это подтверждается описанием обоих методов в [руководстве по встроенному языку 1С 7.7, глава 20 — онлайн-копия документации](https://anatoly4xs.narod.ru/manual/lang/lang0201.htm).

Затем код пытается обходить договоры и виды расчётов, которые сам исключил из результата запроса. Как именно это проявится в конкретной базе — пустыми выборками либо укрупнённым результатом — требуется проверить в 1С. Но нужная детализация этим запросом не задаётся.

**Последствие:** ключи opening_balances не соответствуют ключам ledger62. Например, долг 10 000 по договору A и аванс 10 000 по B должны остаться двумя аналитическими остатками. Укрупнение или отсутствие этих строк может превратить оплату долга A в аванс.

**Поправка:** сохранить механизм `БухгалтерскиеИтоги`, но исправить настройки запроса: отбор нужного клиента, разворот по договорам и видам расчётов, детализация по используемым субсчетам 62 без одновременного включения родительского итога. Затем проверить соответствие индексов обхода субконто фактическому результату запроса. Запрет №5 «не переписывать сальдо» должен явно разрешать это исправление.

**Приёмка:** сверка с ОСВ по одному клиенту, двум договорам и двум субсчетам, включая одновременные Дт/Кт остатки и нулевое сальдо другой аналитики. Проверять остатки непосредственно перед ИсторияНач, без повторного включения движения первого дня.

### A2. Перевод отрицательных сумм в копейки искажает сторно — высокий приоритет

**Место:** код, `КУДиР_Копейки`, строка 443; №1, §7 и §12 требуют выгружать сторно.

```1c
Возврат Цел(Число(Сумма) * 100 + 0.001);
```

`Цел` отсекает дробную часть. Добавление положительной поправки к отрицательному числу сдвигает результат к нулю. Семантика функции подтверждена в [руководстве по языку 1С 7.7, математические функции](https://anatoly4xs.narod.ru/manual/lang/lang0071.htm).

| Сумма | Текущая формула, коп. | Требуется, коп. |
| --- | ---: | ---: |
| 100,00 | 10000 | 10000 |
| −100,00 | −9999 | −10000 |
| −0,01 | 0 | −1 |
| −123,45 | −12344 | −12345 |

Это арифметически воспроизведено с Decimal по семантике отсечения дробной части; запуском 1С проверка не является.

**Поправка:** убрать одностороннюю добавку 0.001, зафиксировать точное преобразование сумм с двумя десятичными знаками и отдельное правило для источников с большей точностью. Контролировать знак и целочисленный формат CSV. Исключение возвратов из версии 1 не разрешает портить отрицательные движения ledger.

**Приёмка:** положительная проводка и равное ей сторно дают ровно нулевую сумму; −0,01 сохраняется как −1 копейка.

### A3. Ветка распознавания приходного ордера не срабатывает — высокий приоритет

**Место:** код, `КУДиР_ВидОплаты`, строка 807; №5, §6.4.2.

```1c
Найти(Врег(ВидДок), "ПриходныйОрдер")
```

В верхнем регистре ищется строка смешанного регистра. Для имени `ПриходныйОрдер` результат — BANK. Имя `ПриходныйКассовыйОрдер` эта проверка также не распознаёт. Если фактический идентификатор вида буквально `ПКО`, первая ветка работает; фактические метаданные кассового документа в приложениях отсутствуют.

**Последствие при затронутом имени:** один ПКО с несколькими номерами проводок может стать несколькими банковскими оплатами; `PaymentGranularity` и путь `CASH_BASE_EXACT` также окажутся неверными.

**Поправка:** использовать точный идентификатор ПКО этой конфигурации с одинаковой нормализацией обеих сторон. Это исправление выбора типа оплаты, а не изменение согласованных формул ID.

**Приёмка:** фактический ПКО с несколькими проводками 50→62 даёт одну CASH-оплату от позиции документа; разные банковские проводки одной выписки остаются разными оплатами.

### A4. План не обеспечивает регистрацию всех договоров оплаты — высокий приоритет

**Место:** №5, §6.4.2, §6.4.3, §6.5 и §6.6.4; №2, §24 и §40.

В плане регистрация CONTRACT явно закреплена за обходом документов. В проходе оплат явно предусмотрен PAYMENT, а договоры агрегированной оплаты при расхождении очищаются. При этом для незакрытого ADVANCE Python возвращает договор аналитической части из ledger62.

Пример: одна оплата имеет части по A и B; реализации и счёта по B нет. В payments договор может быть пустым, в documents договора B тоже нет. В результате Python законно вернёт `contract_id=B`, но L2 может не найти его в id_map.

В старом коде договор каждой корреспонденции оплаты регистрируется до агрегации — строка 864. При перестройке это свойство нужно сохранить явно.

**Поправка:** регистрировать каждый непустой договор каждой экспортируемой корреспонденции оплаты до очистки справочных полей. Можно делать это в проходе B либо в потоковом ledger, пока ссылка доступна. Договоры документов также регистрировать. Перед запуском Python обеспечить полноту CONTRACT для всех источников, из которых разрешено формировать `contract_id`.

**Приёмка:** один payment_id, два разных договора, незакрытый аванс без документов — оба CONTRACT присутствуют; L1/L2/L3 загружают обе части.

### A5. Ошибка числового поля не отбрасывает результат — высокий приоритет

**Место:** код, `КУДиР_КопейкиВРубли`, строка 1508; `КУДиР_ЗагрузитьИВосстановить`, строка 1665; №5, §6.9.

При пустом числовом поле helper вызывает `КУДиР_Сбой`, устанавливает `глОшибка=1` и возвращает 0. Загрузчик проверяет в конце только локальный счётчик `Ошибок`, который числовой helper не увеличивает. Он может вернуть непустую таблицу с подставленным нулём и сообщить о восстановленных строках.

Для нечисловой строки вызов `Число(С)` не защищён обработкой с контролируемым завершением загрузки.

**Поправка:** в L1 валидировать все числовые поля как целые копейки. Любая ошибка формата, суммы, ID, типа строки или восстановления должна приводить к единому отказу от всей итоговой таблицы. Наличие `глОшибка=1` обязательно учитывать перед возвратом результата.

В чекпоинте закрепить и проверки №1 §28: `advance + repayment = amount`, `income = amount − vat`, `0 <= vat <= vat_base <= amount` для поддерживаемых положительных результирующих частей, сохранение суммы по каждой целевой оплате. Для сверки с payments после освобождения EXPORT можно отдельно прочитать компактный набор ID/сумм с диска; хранить широкую таблицу до Python не требуется.

**Приёмка:** валидная строка, затем строка с пустым НДС, буквой вместо копеек, неверным разложением суммы или дублирующим `result_row_id` — полностью пустой результат и контролируемая ошибка.

### A6. Новый L2 требует более строгого CSV-чтения и проверки восстановленного значения

**Место:** №1, §30; №4, §13.2; №5, §6.9.2–6.9.4; код, `КУДиР_РазобратьCSVСтроку`, строка 1446.

Существующий parser принимает одну физическую строку и в конце не проверяет, закрыты ли кавычки. Загрузчик проверяет только «полей меньше заголовка», но допускает лишние поля. В L2 впервые нужно читать id_map с исходной системной строкой, без её нормализации. Общий протокол допускает CR/LF внутри процитированного поля; для id_map исключения не задано.

**Поправка:** определить чтение логической CSV-записи из потока, включая переносы внутри кавычек, удвоенные кавычки, точное количество полей и ошибку EOF внутри кавычек. Либо отдельно и явно сузить допустимый формат id_map, доказав совместимость с реальной сериализацией и всеми справочными полями. Молчаливое применение старого ReadLine-parser не соответствует нынешнему контракту. Старое указание №3 §5.3 «не писать parser логических записей» относится к однострочному kudir_result и не должно запрещать корректный L2.

Round-trip в №5 §6.10.1 должен проверять восстановление именно исходного значения. Непустой результат десериализации сам по себе недостаточен: системная строка может оказаться корректной, но содержать число, другой тип или другой документ.

**Приёмка:** перенос и кавычки внутри допустимого поля id_map; незакрытая кавычка; лишнее поле; корректная сериализация неверного типа; две разные ссылки с разными ID. Во всех ошибочных случаях процесс жив, итоговая таблица пуста.

### A7. Сравнение со старой выгрузкой не может быть единственным эталоном

**Место:** №5, §6.10.1; №4, §14 и §15.1.

Требование одинаковых бизнес-полей полезно для проверки сохранности при оптимизации памяти. Но A1–A3 должны намеренно изменить ошибочные остатки, отрицательные суммы и, при затронутом виде ПКО, ID/группировку оплат. Исправление вида расчётов также может заполнить ранее пустое поле.

**Поправка:** сравнивать весь комплект, заранее перечислив допустимые изменения с независимыми ожидаемыми значениями. Для остальных фактов требовать полного совпадения. Добавить сверку с бухгалтерскими данными контрольной базы, а не только old/new CSV.

Успешный поиск строк в исходнике не доказывает правильность API 1С. Закомментированный вызов или неверный параметр метода может удовлетворять такому тесту.

## 3. Противоречия и недоопределённые правила остальных ТЗ

### B1. Поздняя реализация может ошибочно отменить состав НДС раннего счёта — высокий приоритет

**Место:** №2, §21.2, таблица приоритета против ветки ADVANCE_EXTENDED_MATCH_WINDOW; №1, §27; №0, §5.4.

Приоритет требует: нет реализации в налоговом окне → использовать допустимый счёт, существовавший до конца квартала аванса. Другая ветка требует для аванса с поздней реализацией 5/105 либо 0. Эти указания дают разные результаты, когда ранний счёт смешанный.

Пример:

- 10 марта — счёт 105 000: 63 000 с НДС 3 000, 42 000 без НДС;
- 15 марта — аванс 105 000;
- 20 апреля — реализация по этому счёту.

По приоритету источников НДС аванса — 3 000, доход — 102 000. По безусловной ветке extended — НДС 5 000, доход — 100 000. Разница дохода — 2 000 рублей.

**Поправка:** поздняя реализация не становится источником НДС и не отменяет допустимый ранний счёт. При любом состоянии extended-связи сначала выбрать источник по состоянию налогового окна: подходящая реализация в окне, иначе допустимый счёт, иначе расчётные 5/105 или 0. Синхронно исправить №0, №1 и №2.

**Приёмка:** добавление апрельской отгрузки в выгрузку не меняет налог мартовского аванса, уже рассчитанный по мартовскому счёту.

### B2. Налоговый остаток документа и счёта описан не полностью — высокий приоритет

**Место:** №2, §21.2, подраздел «Смешанный документ и частичная оплата»; §1 и §40 о целевых строках.

Заданы `remaining_taxable`, `remaining_exempt`, `remaining_vat`, но не определены все события их расходования и порядок расчёта:

1. Нужно ли расходовать состав историческими оплатами `is_target=0`? Да, иначе результат зависит от того, с какого дня сформирован отчёт, и теряется корректное распределение копеек.
2. Как расходовать состав реализации, частично закрытой старым авансом из другого квартала? Денежная ёмкость реализации занята, хотя НДС аванса берётся из другого источника и не пересчитывается. Резервирование состава реализации и НДС выходной строки — разные операции.
3. Как ограничить использование состава счёта его суммой и как учесть несколько оплат по одному счёту?
4. Что делать при частичной реализации с составом, отличным от счёта, и при остатке аванса, для которого снова нужен счёт?
5. Какой конкретно режим округления используется в двух пропорциях? Слова «округлить» недостаточно для общего контракта 1С/Python.

Пример недостаточного ограничения: счёт на 105 000, аванс 150 000, отгрузки нет. Формулу пропорции нельзя применять ко всем 150 000 как к частичной оплате остатка 105 000: она выходит за ёмкость счёта.

**Поправка:** описать отдельный расходуемый состав каждого источника, обрабатывать исторические и целевые распределения в едином детерминированном порядке, явно ограничить распределение доступной суммой. Превышение счёта выделять в отдельную часть аванса с собственным правилом источника. При противоречии состава счёта и частичных реализаций не допускать отрицательных остатков состава; неопределённый хвост помечать для проверки. Зафиксировать округление и отдачу оставшихся копеек последней части.

**Приёмка:** одинаковый НДС целевых платежей при расчёте квартала и всего года на одном полном наборе фактов; историческая частичная оплата; старый аванс и новая доплата; превышение суммы счёта; три частичных оплаты с округлением до копейки.

### B3. Не определён формат строки с найденным документом, но неизвестным НДС

**Место:** №1, §15.1 и §24; №2, §21.2 и §40; №5, §6.6.2 и §6.9.

При плохих агрегатах предписано сохранить matching, запретить подстановку 5/105 и выставить `tax_ready=0`. Но значения `vat_base_kopecks`, `vat_kopecks`, `income_kopecks` для такой строки не заданы. Для DEBT_UNRESOLVED числовые заглушки прямо определены; для DEBT/ADVANCE с найденным документом и неизвестным составом — нет.

Возможные реализации — пустые суммы, нули или отказ всего запуска — поведут себя по-разному. Пустые суммы дополнительно конфликтуют с обязательными числовыми полями загрузчика.

**Поправка:** закрепить один формат. Совместимый с текущими колонками вариант: сохранить тип строки и matched_document_id, `vat_base_kopecks=0`, `vat_kopecks=0`, `income_kopecks=amount_kopecks` использовать как технические значения, обязательно записать `VAT_COMPOSITION_UNKNOWN` в reason и `tax_ready=0`, не писать «без НДС». Явно пояснить, что нулевой НДС в такой строке не является установленным налоговым фактом. Для неизвестного состава добавить диагностический счётчик/перечень затронутых строк.

Схема run_status в №1 также должна перечислить уже обязательные в №2 `state_uncertain` и `historical_unresolved_*`; иначе единый контракт описан двумя разными списками.

### B4. Не описан запуск matching для реализаций после ДатаКон

**Место:** №1, §4; №2, §4, §21.1 и тест «отгрузка в следующем квартале»; №5 сохраняет эти периоды.

Ledger заканчивается ДатаКон. Документы идут дальше — до MatchHorizonEnd. При этом бухгалтерский timeline допускается только из ledger, а HIGH-закрытие предписано делать при появлении реализации. Для документа после ДатаКон соответствующего ledger-события во входах нет.

Само разделение бухгалтерских событий и справочных документов правильно. Пробел — отсутствие явно описанного механизма, который вводит будущий документ в хозяйственный matching, не меняя signed_balance.

**Поправка:** определить отдельный обход доступности будущих RECEIVABLE для matching, включая уникальные HIGH-связи, без создания бухгалтерского движения. Глобальный pass «только для неоднозначного» сам по себе этот случай не описывает. Отдельно обозначить, что после ДатаКон отсутствуют будущие оплаты и корректировки: доступность документов там определяется неполным хозяйственным контекстом, а не полным бухгалтерским остатком.

**Приёмка:** ДатаКон=31.03; аванс в марте; реализация в апреле присутствует только в documents. Хозяйственная связь находится, но signed_balance до 31.03 и налог закрытого квартала не меняются.

### B5. Для комбинации нескольких долговых оплат нет однозначно описанного этапа

**Место:** №2, §4, §27, §30 и §32.1; №0, §7 и §9.

Требуется связывать несколько оплат с одним документом. Одновременно описан хронологический проход по одной оплате, а общий pass ограничен авансами. Есть запрет пересмотра DEBT, но разрешение пересмотра LOW. Не определено, где хранятся отложенные долговые части и когда они объединяются.

Контрольный случай из самого ТЗ: документы 5 500 и 27 200; оплаты 4 500, затем 27 200, затем 1 000. Первая оплата ещё может быть неоднозначной. Если она окончательно стала DEBT_UNRESOLVED и больше не участвует в поиске, последняя 1 000 не увидит остатка 1 000 у документа 5 500.

**Поправка:** описать обработку отложенных долговых частей внутри контрагента: какие provisional-связи допустимы, какой поиск объединяет несколько оплат, когда фиксируется окончательный DEBT_UNRESOLVED. Уже подтверждённые HIGH и бухгалтерское разделение DEBT/ADVANCE сохранять. Проверить это по реализации matcher после получения Python-файлов.

Это пробел требований, а не доказательство ошибки отсутствующего в комплекте Python-кода.

### B6. Правило gap позволяет постороннему слабому кандидату создать HIGH

**Место:** №2, §31 и §49 п.6; №3, §4.6.4.

Пример §31 разрешает выбирать по близости между A=180 и B=180, если есть C=100 и отрыв пары от C достаточен. Но A и B всё ещё равноправны. Без C две равные реализации должны остаться неоднозначными. Добавление слабого C не даёт никаких новых доказательств выбора между A и B.

Это также расходится с критерием №2 §49: равные суммы нескольких кандидатов не создают автоматический HIGH.

**Поправка:** считать доказательный gap между лучшим и вторым допустимыми решениями. При нулевом отрыве не фиксировать HIGH только по хронологии. Если хронология нужна для порядка показа вариантов, отделить этот порядок от автоматической бухгалтерской привязки.

**Приёмка:** добавление или удаление заведомо слабого третьего кандидата не превращает неоднозначную пару в HIGH.

### B7. Все движения 62 и ограничения версии 1 требуют явной границы

**Место:** №1, §7, §12, §27; №2, §5 и §21.2; №5, «Вне скоупа».

Требуется сохранить сторно, зачёты и остальные движения ledger. При этом алгоритм оплаты предполагает положительную сумму, а возвраты исключены из версии 1. Не определено поведение отрицательной проводки 50/51/55→62: текущий код включает её в payments наравне с поступлением.

Также отрицательный НДС строки документа попадает в ветку «иначе необлагаемая», хотя это может быть сторнирующая строка облагаемой операции. Наличие таких строк в конкретной базе не подтверждено; контракт должен либо поддержать их, либо явно распознать неподдерживаемый случай.

**Поправка:** отдельно определить положительное поступление, сторно поступления, возврат денег и прочее неплатёжное движение. Подписанные суммы ledger сохранять точно. Для неподдерживаемого сценария выдавать явную диагностику и не объявлять затронутый результат готовой полной КУДиР. Это не требует сейчас реализовывать весь учёт возвратов или эквайринга.

## 4. Что в плане и ТЗ сделано правильно

- Один цикл выгрузки с агрегатами НДС согласован между №0–№5. Второй запрос табличных частей не нужен.
- Списки и порядок основных колонок №1 и №2 совпадают: payments — 28, ledger62 — 28, documents v2 — 23, kudir_result — 16. Это проверено автоматическим сравнением списков из Markdown.
- Для реализаций закреплён единственный реквизит `ВидыРасчетовСПокупателями`. Альтернативных имён добавлять не нужно. Для `Счет` реквизит не читается.
- Несколько видов расчётов в проводках проведённой реализации допустимы; отсутствие любого вида в обоих источниках по условиям этой конфигурации — ошибка. При реализации helper должен различать «ничего не найдено» и «найдено несколько»: сейчас оба случая возвращают пустую строку. План уже требует правильное поведение; это нужно реализовать явным статусом/выходным признаком.
- `registeredIds` и `restore` разделены. PAYMENT/DOCUMENT/CONTRACT остаются тремя восстанавливаемыми типами; удаление COUNTERPARTY/LEDGER из id_map обосновано назначением загрузчика.
- Оплаты не нужно исключать из ledger как дубли payments: только ledger изменяет бухгалтерское сальдо.
- Конец квартала каждой оплаты правильно отделён от общего quarter_end манифеста.
- P2/P3 разумно отложены до подтверждённой необходимости.

Обоснование квартальной границы не является найденной ошибкой: ФНС в п.13 методических рекомендаций для УСН на 2026 год допускает исчисление НДС при отгрузке, если аванс и отгрузка приходятся на один квартал; для частичной отгрузки отдельно рассматривает оставшийся аванс. Это правило про исчисление НДС; само по себе оно не закрывает все технические вопросы распределения сумм КУДиР. [Методические рекомендации ФНС, п.13](https://data.nalog.ru/html/sites/www.new.nalog.ru/doc/metod_usn_nds_2026.pdf).

## 5. Уточнения к приёмке и статусам

В №3 одновременно присутствуют «блокеры P0/P1 = 0», статусы done, предупреждение «не стартовать разработку» и исторические формулировки о цикле 2. №5 использует №3 как источник утверждения о закрытых этапах. Но часть заявлений не соответствует приложенному коду: чтение вида из проводок закомментировано, `Комментарий` читается напрямую, ledger/counterparty остаются в id_map.

**Исправить статусы:** архивные этапы отделить от актуальных обязательных требований; для каждого текущего чекпоинта указывать «реализовано в такой-то версии / проверено тестом / проверено в 1С». Снять утверждение об отсутствии блокеров для текущего комплекта до закрытия A1–A6.

В №5 §6.6.5 проверка существования `Комментарий` должна охватывать все места вызова helper: банковские документы, ПКО и документы прочих операций ledger, а не только три вида из documents.csv. Функция по таблице «известных трёх видов» не должна терять существующие комментарии других видов.

Контроль коллизии ID нужно делать до окончательного пропуска дубликата. Иначе ранний `documents.Exists(document_id) → пропустить` может не дать `registeredIds` сравнить две системные ссылки. После этого допустим обычный дедуп того же объекта.

Сценарий «дойти до контролируемого FAILED» доказывает обработку ошибки, но не успешную выгрузку. Завершение в FAILED из-за незавершённого Python v2 не должно закрывать весь этап 6. Для готовности нужна хотя бы одна полная успешная цепочка 1С v2 → Python → L1/L2/L3 на валидных данных и отдельные отрицательные проверки.

## 7. Минимальный набор проверок перед принятием

1. Долг A и аванс B на начало истории сохраняются раздельно; разные субсчета 62 не сливаются.
2. Проводка + сторно дают 0; −0,01 рубля выгружается как −1 копейка.
3. Реальный ПКО с несколькими проводками остаётся одной CASH-оплатой.
4. Один payment_id с договорами A/B и без реализации восстанавливает оба договора.
5. Плохое число в любой строке после корректных строк отбрасывает весь результат.
6. Повреждённые CSV-кавычки, ссылка неверного типа и коллизия ссылки завершаются контролируемо.
7. Ранний смешанный счёт + поздняя отгрузка не меняют НДС закрытого квартала.
8. Невалидный состав matched-документа возвращается в заранее согласованном формате с tax_ready=0.
9. Исторические оплаты расходуют состав и копейки; целевой налог воспроизводим при другом начале отчётного периода на тех же фактах.
10. Оплата больше суммы счёта не расходует его состав сверх доступной суммы.
11. Реализация после ДатаКон находится без бухгалтерского движения из documents.csv.
12. Неоднозначные 4 500, затем точные 27 200, затем 1 000 поддерживают требуемую комбинацию из ТЗ.
13. Слабый третий кандидат не создаёт HIGH у двух равных сильных.
14. Валидный проблемный период проходит полный обмен; искусственные ошибки дают FAILED и пустую итоговую таблицу.
